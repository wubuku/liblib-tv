# batch 715：导演台里有三个互不联动的横向滚动位置，底部条没有任何位置能点全 15 枚控件

日期：2026-10-03　验收器：`scripts/verify-liblib-batch715.py`（6 条判据，零 store 写入，不改 `src/`）

## 起点

713 测出时间轴默认缩放装不下 8 秒全程（标尺 1779px / 可见 958px），只能横向滚动。
714 测出 zoom 划块低端 24 档是空行程，而且划块**能点也能用键盘**（推翻了 712）。

这两批都只谈**时间轴那一个**滚动容器。本批问一个更基础、也更容易被默认掉的问题：
**整个导演台到底有几个横向滚动容器？它们联动吗？各自装得下自己的内容吗？**

## 决定性读数（视口 1280×1150）

| 读数 | 值 |
|---|---|
| 横向滚动容器普查（`overflow-x: auto/scroll`） | 一共 9 个，其中 **1280 下 2 个**真能滚、**1024 下 3 个** |
| 时间轴轨道容器 | 958 / 1779（`max 821`） |
| **底部浮动条** | 可见 **694** / 内容 **944**（`max 250`） |
| 工具条 `timeline-controls-scroll` | 1280 下不溢出；**1024 下溢出 20px**（裁掉「删除关键帧」） |
| **容器之间的联动** | **零** —— 任何一个滚到底，别的 `scrollLeft` 一个都不动 |
| 真实滚轮 | 三个容器**全部**有效（底部条在 5 个横向采样点上都到 250） |
| 底部条控件总数 | **15 枚** |
| **1280 全程最优位置** | **同时点到 13/15**，最少 2 枚打不到 |
| **1024 全程最优位置** | **同时点到 10/15**，最少 5 枚打不到 |
| 带 `tiny-scrollbar`（有可见滚动条样式）的容器 | **只有时间轴那一个** |

**⟹ 底部条不存在「全部可见」的滚动位置。**
944px 的内容塞进 694px（1024 下是 438px）的框里，**任何**滚动位置都有控件落在框外。

## 滚动不是解药，是换一批死控件

跨全程扫 5 个滚动位置（1280，框 694 / 内容 944）：

| `scrollLeft` | 0 | 62 | 125 | 187 | 250 |
|---|---|---|---|---|---|
| 打不到的控件数 | **3** | **2** | **2** | **3** | **3** |
| 具体是谁 | 上传图片 / 发送 / 描述 | 发送 / 描述 | 发送 / 描述 | 发送 / 移动 / 旋转 | 移动 / 旋转 / 缩放 |

1024 下（框 438）同一张表是 **8 / 5 / 7 / 8 / 9** 枚。

⟹ **两端打到的集合不相交**（1280 下 `dead@0` 与 `dead@max` 交集为空）：
滚到最右，右端那三枚（上传图片 / 描述想搭建的场景 / 发送）确实活了，
但**左端最基础的三枚视口工具（移动 / 旋转 / 缩放）被推出框外变成死的**。

**不是「不可达」，是「没有全都可达的位置」。** 这两件事必须分开说 ——
按 703 立的纪律，逐位置扫了全程而不是只看两个极端
（顺带修正了一个我自己差点写错的推论：「两端都死」不等于「哪都死」，
1024 下九宫格/虚拟相机正是只在中间才活）。

## 而你甚至不知道它能滚

三个容器里**只有时间轴那一个**写了 `tiny-scrollbar`（可见滚动条样式）；
底部条与工具条都是裸 `overflow-x-auto` ⟹ macOS 覆盖式滚动条，**不滚就不显示**。

⟹ **默认状态下，底部条右侧 250px 的控件（其中包括 prompt 输入框与它的发送按钮）
既看不见、也点不动、也没有任何提示说右边还有东西。**
这与 batch 618 修掉的 `pr-260` 覆盖问题是同一类（内容画到不透明块底下、
命中测试打不到、无滚动条提示），只是那次在头部、这次在底部条。

## 判据

| 判据 | 断言 |
|---|---|
| `the-bottom-bar-never-shows-all-of-its-controls` | 两个视口下 `scrollW > clientW`、控件恒为 **15 枚**；跨全程 5 个位置**每一个**都有死控件；1280 两端各 3 枚且**不相交**；全程最优分别只到 **13/15** 与 **10/15** |
| `the-wheel-scrolls-the-bottom-bar-everywhere` | 底部条上 5 个横向采样点，真实滚轮**每一处**都到 `max` |
| `scrolling-the-bottom-bar-trades-one-set-of-dead-controls-for-another` | 两端死亡集合**互不相交**；`dead@max` 恰为 {移动, 旋转, 缩放}；`dead@0` 含 {发送, 描述想搭建的场景}；滚到最右后这三枚 `inBox` 且 `hitSelf` |
| `the-desk-has-two-independent-horizontal-scrollers-at-1280` | 1280 下恰好 2 个可滚容器（底部条 / 时间轴）；程序置底与真实滚轮都到 `max`；**谁的 `moved` 都是空** |
| `a-third-scroller-appears-at-1024-and-nothing-cross-links` | 1024 下恰好 3 个；工具条溢出 **20px** 且裁掉「删除关键帧」；**依然零联动**；1280 下该容器不溢出 |
| `only-the-timeline-scroller-has-a-styled-scrollbar` | 两个视口下带 `tiny-scrollbar` 的容器都**只有** `data-director-timeline` |

两轮连跑 **6/6**，读数逐条一致。

## 探针自己踩的两个坑（都记在这里，因为它们伪装成了读数）

**① 「滚轮无效」是探针假象。** 第一版联动探针里，
底部条的 `scrollLeft` 读出来一直是 0，看起来像「滚轮被吞」。
换 5 个横向采样点逐点测，**每一处都到 250**。
差别在于那一版把「读值」和「归零」写在了同一个脚本里 ——
读之前先把 `scrollLeft` 设成了 0。
⟹ **读滚动位置要用一个只读的脚本。** 复现不出来的读数不记。

**② 索引跨状态不稳定，直接毁掉了因果读数。** 第二版联动探针用列表下标驱动容器，
结果 1280 返回 `None`、1024 把时间轴的 `max 1077` 当成了底部条的结果 ——
因为「普查列表」（含不可滚的）和「驱动列表」（只含可滚的）下标根本不对齐。
⟹ **「谁带动了谁」这种因果结论必须按稳定标识（最近的 `data-*` 属性）定位，
不能用下标。** 这条本来就在方法论里，这次是自己又犯了一次。

## 方法论收获（可复用）

**① 「可达集」要扫全程，不能只看两端。**
「默认点不到」和「滚过去能点到」都是**位置**的函数，
而 713 已经立过一条同源的纪律：**可达 ≠ 有入口**。
本批把它推进一步：**「可达集」本身可能是空的** ——
不是某个控件不可达，而是**没有任何单一时刻能让全部控件都可达**。
⟹ 判这类问题必须**在自变量上采样**（这里是滚动位置），
**只看端点会同时产生两种错读**：把「只在中间活」说成「哪都死」，
把「两端各活一半」说成「有解」。

**② 普查要一次列全，别按需分批查。**
「导演台有几个滚动容器」这个问题一开始我是按「时间轴有没有第二个滚动容器」
去查的，查出来才顺手撞见底部条。
⟹ **「我以为只有一处」和「只有一处」之间没有逻辑关系** ——
像 707 的快捷键普查那样，先把全集列出来，再问关系。

**③ 零联动要写成断言，不能写成观察。**
三个容器各自能滚（各自都有效）很容易读成「它们配合得很好」；
**「谁的 `moved` 都是空」才是可断言的事实**，
而且它的用户含义很具体：**三个独立的滚动位置，界面一个都不告诉你现在在哪。**

## 待拍板（不阻塞）

- **底部条在 694px 的框里塞 944px 的 15 枚控件** ——
  全程没有任何位置能点全，最好也只能同时点 13 枚（1024 下 10 枚）。
  要不要收控件集、换行、还是给一个可见的溢出提示
- **底部条与工具条都没有滚动条样式**（只有时间轴有）——
  要不要给这两个也挂 `tiny-scrollbar`
- **底部条默认就把 prompt 输入框和发送按钮推到框外**（滚到底才活）——
  要不要把这两枚提到左边，或给底部条一个与视口同宽的容器
- 1024 下工具条溢出 20px、裁掉「删除关键帧」—— 小问题，一并记
