# Batch 632 —— <360 那个更极端的角：顶栏条目互相叠压，以及普查只打中心点这个盲区

## 零源站断言

本批**没有一条源站读数**。源站窄屏顶栏上那枚 170px 居中组与左右两簇如何共处、
**源站是否也有这个重叠**，都**未取证**（待授权第 10 项）。所以本批**不修布局**，
只把缺陷量化、把解释结构化、并把问题具体化。

## 一、扫法

623/627/628/629 四批的最小值**全是 360**，两个方向都没低过。631 刚证明 ≤898 确实是
另一套布局族，所以 sub-360 很可能又是一族。

宽度 **25 档**（200..430，**在两条阈值附近加密**：中心点阈值 338、矩形相交阈值 377，
外加 336/338/376/377/378/406 这些边界值）× 高度 **3 档**（320/568/896）= **75 格**，
另加 4 次**全新加载**交叉校验。零尺寸检查沿用 623 的 `BLIND_JS`。

## 二、挖到的东西：定宽 170px 的居中视角组压住顶栏两簇

`DirectorDesk.tsx:1029-1031` 的视角切换组是：

```
div[role=group][aria-label=导演台视角]
  .pointer-events-auto.absolute.left-1/2.top-2.z-10.-translate-x-1/2
    div.flex.h-9.w-[170px] items-center justify-center gap-0.5 overflow-hidden …
```

**绝对定位、居中、定宽 170px，既不参与顶栏的 flex 流也不收缩**（605 在源站
1920×1150 实测过这个形状：`170x36 @(875,8)`）。窗口一变窄它就压在左右两簇上：

| 窗口 | 居中组横跨 | 盒与组相交的顶栏控件 |
| --- | --- | --- |
| 200 | 15..185 | `关闭` / `收起` / `导出导演台项目` / `导入导演台项目` **四枚全中** |
| 280 | 55..225 | `收起` / `导出导演台项目` / `导入导演台项目` |
| 320 | 75..245 | `收起`(64..104 压 29px) / `导出导演台项目`(202..234 压 43px) |
| 360 | 95..265 | `收起`（压 9px） |
| 378 起 | 104..274 | 无（正好相切） |

75 格中 **54 格**存在叠压；**自推导上界 377**，高于它一律不再触发（不许被无声放宽）。

## 三、本批最重要的产出：普查的这个盲区，和它的**可测量宽度**

普查的命中测试只打每个控件的**中心点**（`AUDIT_JS` 的 `elementFromPoint(cx, cy)`），
所以**部分被盖的控件 `own=True` 直接通过**。这与 623 的零尺寸盲区同形：

> **普查报零不等于没有被盖住，只等于中心点没被盖住。**

两个阈值都量出来了：

| 判据 | `收起` | `导出导演台项目` | `关闭` | `导入导演台项目` |
| --- | --- | --- | --- | --- |
| 普查（中心点） | **338** | 280 | 220 | 220 |
| 矩形相交（结构） | **377** | 320 | 260 | 240 |
| **盲区带宽** | **39px** | **40px** | **40px** | **20px** |

**最扎人的一条**：**359 与 360 落在盲区带内** —— 而那正是 623/627/628/629
**四批的采样下界**。四批全部踩在这条盲区上，**全部报干净**。已写成断言
（`the-prior-batches-sampling-floor-sits-inside-the-blind-band`），日后谁把普查的
采样点「改多几个」想蒙混过去，这条会先红。

## 四、严重性：叠压最狠的那枚，恰好是 631 证明「点了什么也不发生」的那枚

631 已证明 ≤898 时 `收起` 是一个**只让自己消失的空控件**。而 632 发现它在 <339 宽
时**连点都点不到**。两条合起来：**这枚控件在窄屏既无功能又不可点**。真正付出代价的
是 `导出/导入导演台项目`（中心被盖 ≤280 / ≤220，盒相交 ≤320 / ≤240）。

**本批不修布局**，理由与 628 对第一族的处置同源：源站窄屏顶栏未取证；而且怎么处置是
**设计决定**——把这枚绝对居中的组改成参与流、或让它在窄屏换位，都会改动一个 605
已在源站实测过的形状。所以只把解释结构化（两个半边都必须成立：受害者是顶栏控件
**且**结构探针独立确认它的盒与该组相交），把边界从扫描自身推导，并把问题具体化。

## 六、本批判据自己踩的三个坑

1. **按盖住者的「文本」归因，漏掉了容器。** 第一版写 `hit not in ("导演视角",
   "机位视角")`，在 336/338 两格红了——那里的 `hitLabel` 是
   **`'导演视角机位视角'`**，即那个 group **容器**把自己两枚按钮的文字拼在一起。
   **盖住者常常是容器而不是某个叶子控件，按名字匹配成员就会漏。**
   改法不是把字符串匹配写宽，而是**换成两个独立测量互相印证**：普查的中心点判定说
   「这枚被盖了」，结构探针独立说「这枚的盒与居中组相交」，两者一致才算归因。
2. **自推导边界的检查里用了个任意标签。** 「前四批的下界是否落在盲区带内」那条，
   我写了 `w > centre_bound.get(next(iter(rect_bound)), -1)` —— `next(iter(...))`
   取的是字典里**随便一个**标签的阈值。**用任意一个成员去代表整组，是把集合当标量用。**
3. **探针把 group 自己的按钮也算成「被盖」。** 第一版探针的 `own` 判定写得不严谨，
   于是 `导演视角` / `机位视角`（group 的亲儿子）被列进「中心点被盖」。普查自己的读数
   才是可信的那份。**探针自己的缺陷会伪装成被测物的缺陷——先分清是谁的错。**
