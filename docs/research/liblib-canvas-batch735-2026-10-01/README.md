# batch 735 — 46 写点的运行时实例普查（收官）：把「写点数 / 身份数 / 名义峰值 / 可见峰值 / 累计枚次」五个口径分开记账

## 起点

729–734 花了六批把 46 个 `data-inert` 写点收口成「**42 已逐处打开 + 4 条件门控**」。
每一批都只报「这一族渲染出几枚」，从来没有回答过一个整体问题：

> **这 46 个写点在浏览器里，一共是几枚按钮？**

本批做收官普查：一个会话里把画布驱动到 16 个状态，逐状态数实例。
写着写着发现前一版普查脚本报的三个数分属三个不同的问题，混着报会**高估用户能遇到的控件量**——
于是本批的主要工作不是「数出个数」，而是**先把口径拆开**。

## 决定性读数

### ① 五个数，各回答五个不同的问题

| 口径 | 问的是 | 读数 |
|---|---|---|
| 静态写点 | 源码里写了几个 `data-inert` | **46** 处 / 16 文件 |
| 去重可及名 | 有几种**不同**的按钮 | **83** 种 |
| 名义峰值 | 单个最富的状态里同时有几枚 | **25** 枚（特效库，**可见仅 1**） |
| 可见可点峰值 | 同一时刻**看得见也点得到**最多几枚 | **22** 枚 |
| 驱动一遍累计 | 16 个状态加起来渲染多少枚次 | **114** 枚次 |

前一版普查脚本报的是「峰值并存 25 / 去重身份 78 / 累计实例 87」。
其中 **87 是个混合量**（把每个身份在多个状态的最大并存数相加），既不是能同时遇到的，也不是不同控件数；
**25 那个「峰值」是特效库面板：25 枚里 24 枚 `opacity: 0` + `pointer-events: none`，可见的只有 1 枚筛选按钮。**

真峰值是 **22**：视频卡标记选择 12 枚 + 底部坞生成历史 10 枚，**22/22 全部可见**。

> **不要把下表的「实例数」一列相加。** 不同族的富状态彼此互斥 —— 风格库 16 枚收藏与特效库 24 枚收藏
> 是**同一个写点**（`LibraryShowcasePanel:130`）在两个 tab 里的两种渲染，同一时刻只能有一个；
> 图片卡的编辑分支与全景分支也互斥。唯一例外是 `TopNavBar` 两枚，它在**每个**状态里都在。

### ② 普查脚本自己踩了坑：「视频卡·片段重拍」那一步是假读数

普查状态表里，「视频卡·片段重拍」与「视频卡·标记选择」**两行 12 枚逐字相同**——
面板压根没打开，那 12 枚是上一状态的残留。归因：

```tsx
// VideoProcessingToolbar.tsx:256-257
function ToolbarButton({ label, title, ... }) {
  return <button type="button" title={title} …>{children}<span>{label}</span></button>;
}
```

`片段重拍` 只传了 `label`，**`title` 是 `undefined`**（`:131`）⟹
`button[title="片段重拍"]` **恒 0 命中**，而 734 批就是按 `title` 找到它的（当时那个按钮处于另一状态，才没暴露）。
改按可见文本点开：

| | 读数 |
|---|---|
| `button[title="片段重拍"]` 命中 | **0** |
| 按可见文本命中 | 1，`clicked` |
| 点开前后自身枚数 | **6 → 9** |

9 枚 = `VideoNode:498` 播放视频 1 + `SegmentReshootPanel` **6**（`:138` 的 `.map` 撑成 参考/标记/角色库 3 枚 + `:230` 积分 + `:236` 生成参数 + `:257` 翻译）
+ `VideoProcessingToolbar:244-245` 撤销/重做 2 —— 生成面板自己那 3 枚被换掉了。

**一个状态表的相邻两行逐字相同，就是探针没点着的信号。**

### ③ 底部坞三面板互斥，不是叠加

| 动作 | 自身枚数 |
|---|---|
| 开「生成历史」 | 10 |
| 再开「教程」 | **4**（不是 14） |
| 再开「工具箱」 | **4**（不是 18） |

而底部坞面板**能**和卡片面板叠加：标记选择 12 + 生成历史 10 = **22，全可见**。
所以「峰值」有两个答案，取决于问的是「哪个面板最富」还是「用户最多能同时碰到几枚」。

### ④ 40 枚不可见 = 40 个**互不相同**的可及名，Tab 260 步停靠 77 次

| | 读数 |
|---|---|
| 不可见实例 | 风格库 **16** + 特效库 **24** = **40** 枚 |
| 全部 | `opacity: 0` **40/40**、`pointer-events: none` **40/40** |
| 可及名互不相同 | **40/40**（`收藏 Seedream 5.0 pro`、`收藏 小蜜蜂运镜`……） |
| 自然 Tab 260 步 | 停在 `button[data-inert]` 上 **77 次**、**27 种**名（25 自身 + 2 顶栏） |

**27 = 25 + 2 对上了账**：特效库 25 枚里 24 枚带各自的收藏名，加顶栏两枚。
键盘用户 Tab 进素材库，会依次落进 **24 个看不见、点不着的按钮**；屏幕阅读器会依次播报 24 个不同的「收藏 XXX」。

### ⑤ 静态扫描范围必须与前批**逐字**一致

普查第一版写的是 `src/**/*.tsx` ⟹ 扫出 **47 处 / 17 文件**，C1 直接挂掉。
多出来的那一处是 `src/components/frameos/FrameosGroupToolbar.tsx:257`
—— **FrameOS 的文件**，不在 LibTV 画布范围内。729/730 的扫描显式排除
`src/app/frameos`、`src/components/frameos`、`src/components/jimeng`，本批第一版把这张排除表丢了。

顺带一条观察：那枚 FrameOS 按钮带的是**同一套契约**（`cursor: default` + `title` 说明 + `data-inert`），
说明「未接线控件自证惰性」这套写法是跨 App 复用的 —— 但本批只记不评判。

**「46 变 47」差点被读成「有人新加了写点」；先查范围，再查代码。**

① **普查口径要不要固定成一份常驻检查** —— 这五个数混着报（或把互斥状态相加）会高估控件量，

② **40 枚不可见但可聚焦的收藏按钮**（承 732，待拍板第 ① 条）——

## 方法论

① **一个状态表的相邻两行逐字相同，就是探针没点着的信号** —— 本批「片段重拍 12 枚」与「标记选择 12 枚」逐字段相等，
差一个字符都不差。数字对得上不代表事情发生了。

② **口径要按「回答什么问题」来分** —— 写点数、实例数、身份数、峰值各回答一件事；
把它们揉成一个「累计实例数」（前一版的 87）就同时污染了三件事。**报数之前先说清数的是哪一个。**

③ **峰值要分「名义」和「可见」** —— 25 枚里 24 枚 `opacity: 0` 时，25 不是用户体验到的 25，是 DOM 里有 25。
`opacity: 0` 的东西不该计入「用户能碰到几枚」。

④ **静态扫描范围要和前批逐字一致** —— 丢了排除表就扫出 47，差一个数会先被怀疑成「别人改了代码」。

⑤ **`title` 不等于可及名** —— `ToolbarButton` 只传 `label`，可及名来自子节点 `<span>`；
按 `title` 找入口在**同一个组件**上时灵时不灵（取决于别处有没有恰好传了 `title`）。

⑥ **对不上的数字自己就是线索** —— 本批 C1 第一次挂掉（47 ≠ 46）、Tab 停靠次数在 30/31 间浮动，
两个「不一致」各自都带出一条真结论。

⑦ **两张长得像的表，性质可能不同** —— 台账的 `| Batch N |` 是**批次登记**，本 README 的「与前几批的关系」是**交叉引用**；
本地 pre-commit 钩子用一条正则区分二者，靠的只是首格有没有 `Batch` 字样。
写表格时先问一句「这张表会被谁读」——**一个只认形状不认语义的检查器，会把引用读成声明。**

## 探针返工三处

① **普查脚本的入口选择器踩了 `title`**（`button[title="片段重拍"]` 恒 0 命中）⟹
状态表里「片段重拍」一行是「标记选择」的复制品，**累计枚次（114）跟着偏了 3**；
改按可见文本点开后 6→9，才对上 734 记的「`SegmentReshootPanel` 4 写点 → 6 枚」。

② **静态扫描第一版丢了范围排除表**（`src/**/*.tsx`）⟹ 47 处 / 17 文件，
多出的是 FrameOS 的 `FrameosGroupToolbar.tsx:257`；补回 729/730 的三个排除前缀后回到 46/16。

③ **本文档自己被 pre-commit 钩子拦下一次** —— 第一次提交被拒，钩子报
「本次提交新增了批次行 **[730, 732, 734]**，而上一次全绿构建只走到 Batch 255」。
但本批只往台账追加了一行 `| Batch 735 |`，**那行根本不在钩子的匹配范围内**：
`buildrecord.added_batch_numbers` 只认暂存新增行里形如 `+| 730 |` 的**纯数字首格**表格行。
真正的来源是**本 README 的「与前几批的关系」那张表**——首格写成了 `| 730 |`、`| 732 |`、`| 734 |`，
被当成了新登记的批次行。改成台账自身的写法 `| Batch 730 |` 即放行，**没有 `--no-verify`，也没有为一个零改动的 `src/` 去跑构建**。
（`buildrecord.py:145-166` 核「本次提交新增了哪些批次号」；台账行首是 `| Batch 735 |`，两张表长得像、性质不同。）

另记一条**读数抖动**：标记选择状态的 Tab 停靠次数在**另一版探针里读到 30、验收器两轮都是 31**
（`page.tsx:1358` 把 `Tab` 征用成「新建节点」开关，每一步落点会因面板开合而变）
⟹ 判据 C7 只锁特效库那一格（两轮都是 77/27），标记选择那一格只记录不判定。
