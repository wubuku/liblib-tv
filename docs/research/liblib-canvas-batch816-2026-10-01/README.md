> 815 量到 `ImageNode` 七个动作连点三次，三份产物 **x／y／宽高逐像素相同**。
> 815 的「不声称」里明写：★ **三份压在一起之后用户还能不能选中底下那两份，

## 一、★ 为什么不能只点一下就下结论（807 起立的纪律）

「点不中底下那一份」有两种完全不同的成因：

- ① 命中测试天然只命中**最上层**那一份（**Z 序**问题）；
- ② 底下那两份**根本没被选中逻辑排除**，只是**没有别的路径**能把它们选出来。

⟹ 本批把**所有可能的选中路径各走一遍**，逐条记录选区变成什么。

## 二、★ 核心读数：四条选中路径走完，**底下两份从未被选中过一次**

14 条臂（7 动作 × 2 轮）**逐位相同**：

### 为什么第 3 份永远在最上面

Z 序读数（每条臂都一样）：

| 份 | DOM 序号 | `z-index` | 包围盒 |
| --- | --- | --- | --- |
| 第 1 份 | 10 | **0** | 445,268 192×108 |
| 第 2 份 | 11 | **0** | 445,268 192×108 |
| 第 3 份 | 12 | **1000** | 445,268 192×108 |

★ 叠加顺序**不是**「后建的在上」，而是「**选中的那份**在最上」——
第 3 份 `z-index=1000` 是因为它**正被选中**（`addDerivedNode` 末尾有
`selectedNodeIds: [nodeId]`）⟹ 用户每次看到的都是**最后一次点的那份**。

## 三、★ 四条路径**各自**的结局（清单是交付物）

| 路径 | 结局 | 依据 |
| --- | --- | --- |
| 点中心 | **只选中第 3 份**（替换选区） | `page.tsx:1545` `onNodeClick` → `selectNode(node.id)` |
| Cmd／Ctrl + 点中心 | **把第 3 份加进选区**（旧选区保留） | ★ 见第四节 |
| `Cmd+A` | **什么都没选中**（没有全选） | liblib 画布里**没有** `selectAllNodes`（只有 FrameOS 与即梦那两个画布有） |
| pane 上左键拖拽 | **什么都没选中**（也没平移） | `page.tsx:1624` `selectionOnDrag={false}` + `:1629` `selectNodesOnDrag={false}` |
| `Delete` | **只删掉第 3 份** | `page.tsx:1376` 自己处理 Delete／Backspace |
| `Cmd+Z` 撤销 | **三份全带回来** | ★ **唯一**够得着底下两份的路径 |

## 四、★★ 静态读数与实测**相反**的一条

`page.tsx:1545`：

```
if (!event.metaKey && !event.ctrlKey) selectNode(node.id);
```

光读这一句，会以为「**Cmd+点击什么都不选**」。**实测不是**：

```
Cmd 之前选区：["i-1FQ9tErTcC"]
Cmd 之后选区：["i-1FQ9tErTcC", "image-1791272023071"]
```

★ app 自己那次 `selectNode` **确实被跳过了**，**但 React Flow 内部的累加照样发生**
——旧选区里的源图片仍在，最后一份被加了进来。

⟹ ★ **那个静态条件只管住 app 自己那次赋值，管不住框架内部**。

⟹ 于是「Cmd+点击能不能救我选中底下那两份」的答案是**仍然不能**：
它加进来的**还是最上面那一份**。

## 五、★ 探针返工一处（夹具失败伪装成读数）

第一版在**写死**的 `(40,400)` 上做 pane 拖拽，读数是「视口没变、也没多选」。
第一反应是记「框选这条路不存在」—— ★ **不能**：
**那个点可能根本不在画布里**（侧栏／工具条），于是这条臂什么都没发生。

809/810 的老坑：**夹具失败会伪装成读数**。

⟹ 修法：先扫出一个**确实落在 `.react-flow__pane` 上**的点（用
`elementFromPoint` 逐点验证并把 `className` 一并记进 raw）再拖。

修完之后读数不变（`react-flow__pane`、`视口 transform 一字未变`、`没多选`），
但**这次它是个结论，而不是一个夹具事故**。

★ 附带一条读数：pane 上左键拖**也没有平移**（视口 transform 前后逐字相同）。
本批**不判它对不对**——`panOnScroll` 摆在那儿，平移走滚轮**可能是设计**。

★ **全部判据从 raw 的原始字段重算**：原始 `selectedNodeIds`（`选区原文`）、

### 两个「我自己造的假红」

| # | 现象 | 真因 |
| --- | --- | --- |
| 序1 | S3 判红：「五条路径一个不缺」不成立 | ★ 清单其实是「**四条选中路径 + 一条删除动作**」；第一版把「Delete 之前那次点选」也算成一条、于是数目对不上 ⟹ 而它其实就是「再点一次中心」，与路径一**同一条**，不该另算 |
| 序2 | S3「非退化」只是**擦边**通过 | ★ 结局字符串原本只写「选中第 [3] 份」，路径一与路径二**撞成同一串** ⟹ 补上「／ 其他选区 N 个」之后才真正区分得开 |

★ 另有一个**证据字段**的 bug（不参与 `ok`，基线照样全绿）：
`★ 被选中过的永远是最后建的那一份` 读的是 `F_IDS`，而逐条字典里那个键叫
「建了几份」⟹ 恒取到 0 ⟹ 14/14 的真读数被印成 `False`。
★ 教训：**证据字段也是读数**，只有把它也当读数去核才会发现。
