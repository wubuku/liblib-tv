## 发现一：四枚控件被不透明右格埋掉

首跑：

```
### viewport 390x844  total=41
### covered=4  clipped=2
  总时长                    [135, 674.5, 46, 24]   hit <input> 时间轴缩放
  切换时间单位为 s           [182, 674.5, 33, 24]   hit <input> 时间轴缩放
  选中角色、道具或分组后建立轨道  [230, 674.5, 82, 24]  hit <div> 导出视频到画布
  预设运镜                  [312, 672.5, 77, 28]   hit <span> 导出视频到画布
```

前两条的盖子是**缩放滑杆那层透明的原生 range**（`absolute inset-x-0 h-6 w-full opacity-0`，量到 `[155,675,71,24]`，`opacity: 0` 但 `pointer-events: auto` —— 它本来就是拖拽面）。后两条的盖子是不透明的右格 `div[data-director-timeline-strip-right]`（`absolute right-0 top-0 z-30` 244×36 `bg-[#212121]`，实测 `[146,669,244,36]`）。

### 根因不是 z 序，是 CSS 的滚动溢出区

工具条当时是「header 自己 `overflow-x-auto` + `pr-[260px]` 给右格留位」。问题在于：**`padding-right` 属于滚动溢出区** —— 内容一旦溢出 content box，会一直画到 padding box 边缘为止，也就是画进那块预留区。

同一个缺陷在三个宽度上表现完全不同：

| 视口 | 左格窗口 | 内容宽 | 是否溢出 | 表现 |
|---|---|---|---|---|
| 1920 | 1652px | 776px | 否 | 无从察觉 |
| 1024 | 756px | 776px | 是，溢出部分落在视口外 | 只算 clipped，普查不报 |
| 390 | 122px | 776px | 是，654px 全画进预留区 | **压在不透明右格底下** |

1024 那次普查之所以没报，不是因为那里没问题，而是因为溢出部分恰好被视口切掉了，分类器判成 clipped。**同一个洞，只在最窄的一档暴露。**

补充一条实测（`dbg618c`）：把工具条横向滚到末尾，四枚全部恢复命中。所以它们**不是 604/611/615 那种彻底点不着的死控件**，而是「被不透明块盖住、且没有任何提示说后面还有东西」—— 移动端无滚动条，用户几乎不可能知道该往右拖。

### 修法：把滚动宿主下沉一层

裁切线必须落在 content box，滚动容器就得**是** content box 本身。给左格加一层内层 div 承接 `overflow-x-auto`，header 不再滚动：

```jsx
<header className="... pr-[260px]">            {/* 不再 overflow-x-auto */}
  <div data-director-timeline-controls-scroll
       className="flex min-w-0 flex-1 items-center gap-0 overflow-x-auto">
    …左格七项 + 预设运镜 + 轨迹 + 关键帧…
  </div>
</header>
```

390 下四枚从 `covered` 转为 `clipped`（与 1024 一致，滚一下就到），实测 `clientWidth 122 / scrollWidth 776`，裁切线落在 x=130。**桌面一字未动**：1920 下内层 1652 > 内容 776，不产生滚动条；子节点各自的 `ml-[15px]` / `gap-px` 都在内层 flex 里，位置逐像素不变（验收钉住播放 26 / 自动帧 24 / 循环 26 / 新建轨道 82 的宽度与内层起点 x=8）。

## 发现二：一个一直在赌时间的回归（batch 96）

跑回归时 **batch 96 红了**：

```
Locator.click: Timeout 30000ms exceeded
  [data-director-shot-bar] > [data-director-shot-option]
  <span class="text-[15px] font-medium …">角色</span> … intercepts pointer events
```

96 的移动端腿是：打开属性抽屉 → 等它可见 → 断言无横向溢出 → **点镜头条 chip**。用不用 stash 的基线对照（备份到 /tmp 后 `git checkout --`）确认：**撤掉本批改动 96 通过**。但基线上量到的几何与改后**完全一样** —— 抽屉（x 109..390）本来就盖住 chip（x 41.6..218.7，中心 130）。

于是逐时刻采样（`dbg618f.py`，基线与修复各跑一次）：

```
基线：t=  0ms  drawerX=131  hit=span:机位01 · 对峙中   ← chip 可点
      t= 80ms  drawerX=109  hit=span:角色             ← 已被盖住
      t=1200ms drawerX=109  hit=span:角色
```

抽屉带 `transition-transform duration-200`，从 x=131 滑到 109。**96 的那次点击一直只在头 ~50ms 里才点得中**——它不是在验证几何，是在赢一场竞速。本批的工具条改动让渲染多了一个节点，足以让它输掉。

### 修法：让属性抽屉和遮罩、和树抽屉对齐

同一屏里另两样东西早已说明镜头条那一行**不该**被抽屉吃掉：

1. 关闭抽屉的遮罩是 `absolute inset-0` = **88..668**，起点正好在镜头条之下 —— 遮罩的取景已经声明了「这一行保持可用」；
2. 场景树抽屉用的是 `top-[88px] min-[900px]:top-[52px]` —— 窄屏同样从 88 起。

只有属性抽屉例外：它用无条件的 `-top-9`（-36px，把列顶边从 88 提到 52，桌面对齐源站所需），窄屏也跟着提到了 52，于是盖住镜头条。**两个抽屉行为不一致，是遗漏不是设计。**

补一条窄屏覆写即可：

```jsx
"absolute -top-9 bottom-0 right-0 z-30 w-[281px] … duration-200",
"max-[899px]:top-0",        // 包含块本身就起于 88，top-0 即 88
```

实测抽屉由 `[109,52,281,616]` 变为 `[109,88,281,580]`：与遮罩、与树抽屉三者对齐；桌面 `-top-9` 原样保留，614 的列几何（顶 52 / 宽 281 / 下沿止于时间线）一字未动。落定后 chip 中心在 80ms…1200ms 全程命中的都是它自己。

## 迁移两条被推翻的历史合同

- **batch 596** `strip:left-cell-scrolls` 断言 **header 自身** `overflowX ∈ {auto, scroll}`。语义（「左格可横向滚动」）不变，读数换成内层宿主。596 当初「右格必须在 header 之外」的理由（header 的 overflow-y 会裁掉向上弹出的导出面板）**不受影响** —— 右格本来就在 header 之外。
- **batch 36** 窄屏腿断言 `[data-director-timeline-controls]` 的 `scrollWidth > clientWidth`，同一处迁移。

迁移而非删除：两条合同描述的行为都还在，只换了承担它的元素。

## 验收（41 项）

- **390 桌面态（12）**：普查 41 枚、零 covered；那四枚确为 clipped 而非 covered；内层宿主 `overflow-x:auto`、header 恢复 `visible`、`pr-[260px]` 仍在、390 下确实溢出；**沿右格 244px 宽度每 8px 采样 31 个点，命中目标无一个属于左格**（这是本缺陷的直接表述 —— `getBoundingClientRect` 不计裁切，光看盒子看不见，只有命中测试看得见）；把 `时间单位` 滚到窗口中央后用**原始鼠标点击**（无自动滚动）真的把 `s` 翻成 `ms`；点完再普查仍零 covered。
- **导出面板开 / 时间线收起（各 4）**：零 covered、无错误。
- **属性抽屉开（8）**：抽屉顶边 = 88、下沿与遮罩下沿一致、遮罩仍从 88 起；镜头条 chip 与标签**各自命中自己**；抽屉打开状态下真实点击 chip 落地（active shot id 不变、`aria-pressed=true`）。等待 1200ms，量的是**落定后**的版面。
- **1920 桌面（13）**：工具条仍 36px 通栏、右格仍 244×36 贴右缘、预留仍 260px、内层右缘 = 1920−260、**不产生滚动**、源站序四枚宽度与起点未变、**属性列顶边仍 52**、普查仍只有 `帮助` 被盖（617 记录过、源站同样如此）。

### 验收脚本自身修了两处

1. 原本打算「滚到末尾再点」—— 结果 `时间单位` 钮被推出窗口左侧（x 变负），点击落空报红。**这是测试写错不是产品缺陷**：776px 内容塞在 122px 窗口里，滚到末尾看到的是工具条尾部。改成把目标控件滚到窗口中央。
2. 首版 618 的抽屉那条断言沿用了 617 的普查口径，会把「被打开的抽屉盖住」和「全屏遮罩自身中心落在它遮的面板下」一并报成缺陷。查证后（`dbg618e`）这两类都不是缺陷，因此抽屉这条腿**不普查**，改为直接断言「抽屉顶边 = 遮罩顶边 = 88」与「chip 命中自己」—— 正面陈述合同，而不是靠排除项蒙混。
