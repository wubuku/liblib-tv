## 一句话

    div.mx-auto.flex.shrink-0.items-center.gap-2

      ├ (gap-2)                               8
      └ data-director-scene-prompt-bar      225

**这与 645 当年记的 `toolbarWidth + 8 + 225` 逐位相同** —— 645 的 `promptBarWidth` 就是 225，
工具条上带着 `max-w-[calc(100vw-48px)]` 所以 `toolbarWidth = min(711, W−48)`。
本批把这些常数**现场重测**并与 645 的 audit 文件**逐位比对**（不是重打一遍）。

行只有**两个**子元素，`flexShrink` 实测恒为 `0`，`gap` 恒为 `8px`。

## 1. 给 645 补一段它没写的 regime

645 记的 `rowBoxWidth` 是「窄 `W−24` / 桌面 `W−586`」，**桌面族起点 = 944 + 586 = 1530**。

但那行是 **`shrink-0`** —— 它**不会缩**。所以 **W < 1530 时 `W−586` 这条公式不成立**：

| W | 行宽 | `W−586` | 实际发生 |
|---|---|---|---|
| 1280 / 1440 / 1509 / 1510 | **944** | 694 / 854 / 923 / 924 | 行**不缩**，而是**溢出宿主** 250 / 90 / 21 / 20px |
| 1530 及以上 | **944** | 944 / … | 刚好装下 |

**645 的闭式在它适用的范围内是对的，它只是没说外面那一段。**
本批把那一段补上并断言 —— **不完整比错更难受，因为错会自己暴露，不完整不会。**

**700 窄屏把 645 另一条公式的分支也跑到了**：工具条按 `min(711, W−48)` 缩到 **652**，
行变成 **885**（= 652 + 8 + 225）。711 = W − 48 在 **W = 759** 饱和，本批所有宽度都在它之上 ——
所以 645 那条公式的**窄屏分支此前一次都没被跑过**。

## 2. 三级门槛：**推导**出来的，不是我打进去的

同一条行有三个右沿，清出裁剪盒所需的宽度各不相同：

| 谁 | 右沿（行左沿 293 时） | 清出裁剪盒的最小 W |
|---|---|---|
| 按钮**中心** | 1216 | **1510** ← 659 的可达边界 |
| 按钮**右沿** | 1232 | **1530** |
| **行右沿** | 1237 | **1532** |

**第二级 1530 正好等于 645 的桌面族起点（944 + 586）。**
**同一个数，从同一个矩形的第三个点上看出来的** —— 一个批次问的是「余量归零」，
另一个问的是「能不能点到」，第三个问的是「整行装不装得下」，三者在 1530 会师。

**但这一段第一版是错的，而且检查是绿的。**
我硬打了 `{1510, 1526, 1531}` 上去，然后**只断言这三个数是有序的** ——
没拿它们和数据比。数据说：按钮整枚进盒是 **1530** 不是 1526，行整条进盒是 **1532** 不是 1531。
**一条因为前提没被检验而通过的检查**，和一条空集通过的计数是同一类错误。
改成 `first_true(...)` 从扫出来的格里推导，数字错在哪儿也记在案里。

> **拿数字跟读数比，不要拿数字跟另一个数字比。**

## 3. 跨批次：645 与 659 相差恰好 1px

645 的 audit 记的 `发送` 桌面边界是 **1509**，659 的裁剪可达边界是 **1510**。

* **W=1509**：宿主右沿 **1216** = 按钮中心 **1216** → `overflow:auto` 的右沿**排他** → 出界 → 栈内位置 **−1**（不可达）
* **W=1510**：宿主右沿 **1217** > 1216 → 在内 → 栈内位置 **2**（可达）

**两个批次从完全不同的角度落在同一像素的两侧**，而那 1px 就是排他性。
645 的边界值是从它的 audit 文件里**读出来**的，不是重新打一遍。
