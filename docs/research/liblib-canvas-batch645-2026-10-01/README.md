# batch 645 —— 联合性的**余量**有闭式；五个边界从四个实测常数推出来，而 899 是**跳变**不是延续

日期 2026-10-01 · 验收器 `scripts/verify-liblib-batch645.py` · **11 checks / 0 failures**

## 一句话

644 的闭式成立，但它用的是**每格的实测值**，于是「余量自己怎么随宽度走」没人问。
问出来不是平滑衰减，而是**三段 regime + 一处跳变**，
而**联合性在宽度上非单调**（620 有 → 780/898 没有 → 899 又回到 8）。

## 1. 先纠正一条我在 643 里读错的结构事实

643 看到「工具条的 `16:9` 被提示条压住」，我当时记成**谁盖谁**。
645 把祖先链原样 dump 出来，真相是：

```
div.mx-auto.flex.shrink-0.items-center.gap-2      ← 容器宽 = 工具条 + 8 + 225
  ├─ div[data-director-viewport-toolbar]  711 宽（窄族 min(711, W−48)）
  └─ div[data-director-scene-prompt-bar]  225 宽，贴容器**右端**
```

**提示条不是独立的一行，它与视口工具条是同一个 `mx-auto shrink-0` 容器里的两个 flex 兄弟。**
于是「工具条溢出落进提示条」是**同一行里两枚药丸的 x 区间相交**，
不是一行画在另一行上。这与 643 的地面真值结论一致（那些控件**根本没被绘制**），
但给出了**为什么** —— 结构上根本没有上下关系可谈。

实测每格：`sharedRowWidth = toolbarWidth + 8 + 225`，19 个宽度**全中**。

## 2. 四个实测常数（每格与页面核对，不写死）

| 常数 | 窄族（≤898） | 桌面族（≥899） |
|---|---|---|
| 工具条宽 | `min(711, W − 48)` | `711` |
| 行盒宽 | `W − 24` | `W − 586` |

| 提示条药丸 | `225` | `225` |

药丸内 `上传图片` 距药丸左沿 **25**、`发送` **204**；工具条内 `开启九宫格辅助线` 距工具条左沿 **447**。

## 3. 三段 regime

```
cx = rowLeft + 居中项 + [工具条相关项]
居中项 = max(0, (行盒宽 − 容器宽) / 2)
```

| regime | 条件 | 表现 |
|---|---|---|
| **A 未饱和** | 工具条还在长（窄族 `W < 759`） | 药丸贴着行右端，两条边**同速**前进 → 余量**恒定 9** |
| **B 饱和** | 工具条卡在 711 | 余量开始**每像素掉 1** |
| **C 居中** | 行盒装得下容器 944（桌面族 `W ≥ 1530`） | `mx-auto` 把余量分给两侧 → 整行右移 `(行宽−944)/2` |

实测 `上传图片` 的余量轨迹：

```
窄族  339:9   480:9   495:9   620:9   767:1   768:0        ← A 段恒定 9，B 段归零
桌面族  899:431  1152:178  1280:50  1330:0               ← 跳变后单调衰减，C 段右移
```

**注意**：`开启九宫格辅助线`@480 的余量（对行右沿算）是 −9，而它**是**联合的 ——
因为它被裁的是**工具条自己**（右沿 444），不是行（468）。
**本批的闭式是关于 `cx`（位置）的**；联合与否还要接 644 那条
「`cx > 它自己那层裁剪祖先的右沿`」。两条分工不同，本批不混。

## 4. 899 是跳变

```
             行盒宽      上传图片余量    发送余量
   898（窄）    874          −130          +49
   899（桌面）  313          +431         +610
```

族断点上行的左内缩从 12 跳到 293、宽度从 `W−24` 跳到 `W−586` ——
**行窄了约 562，而两枚药丸原地不动**，于是余量不是延续而是**重新开始**。
检查直接断言这个跳变 **≥ 500px**（实测 561 与 561）。

| `上传图片` | **768** | **1330** |
| `发送` | **947** | **1509** |

**网格只夹逼、不插值**，但两个最关键的边界被夹到**逐像素**：
`上传图片` 767 余量 **+1**、768 余量 **0**；1330 余量 **0**、1331 起该控件不再联合。

## 6. 联合性非单调（作为算术断言，不是叙述）

```
339:2  480:2  495:1  620:1  767:1  768:1  780:0  898:0 │ 899:8  1152:4  1280:3
1330:3  1331:2  1440:1  1500:1  1509:1  1510:0  1600:0  1920:0
```

最小值出现在**内部**（780/898），其左右两侧都严格更高。
一条单调衰减律会更容易断言，而且**会是错的** ——
它会在族断点处被自己的数据否掉。

## 7. 我自己写错的三处

1. **`predict_cx` 把药丸宽度多加了一次** —— 药丸贴容器右端，它的**左沿**就是
   `rowLeft + 工具条 + 8`，按钮中心再 +25。第一版写成再加 225，误差整整一个药丸宽。
2. **药丸内偏移我手推 padding 算术** —— 改成实测常数（25 / 204）并断言它们恒定；
   手推那版错了 36px。
3. **「余量恒定」的窗口筛选写错** —— 我按「是否联合」筛，把工具条已饱和的 767/768
   也算进去，于是那四项永远不可能相等。改成按「工具条是否饱和」筛，
   剩下的 339/480/495/620 四项**确实全为 9**。

外加一处是**探针自己的错**：`bothCoveredAndClicked`（桶名拼错）导致联合集恒为空，
而我把键名也写错了，读数全是 `None`。**先量结构再猜机制**，这条又被复习了一遍。
