# batch 761 — 缩放与视口：这块**基本没毛病**，毛病全在滚轮和节点尺寸上

## 起点

760 把 `canvasTool` 两态结清了，顺手在静态侦察里扫到三条还没人碰过的东西：

- `page.tsx:1547` 和 `:1549` **同时**开着 `panOnScroll` 和 `zoomOnScroll`，
  而 `:1551` 是 `panActivationKeyCode={null}` —— 连「按 Space 临时关掉平移」
  这条退路都堵死了。两个开关抢同一个滚轮事件，谁赢只能实测。
- `page.tsx:163/:164` 的 `desktopViewport` / `compactViewport` 两个常量，
  挂在 `:452`、`:677`、`:1148` 三处，配一套「bootstrap / stable 视口归属」机制，
  外加一个 `window.__libtv_viewport_owner_log` 调试钩子
  （这是 748 留下的「调试钩子来源」那条线索的落点）。
- `uiStore.ts:223` 的 `zoomLevel` 初值是**硬编码的 54**。

外加一件从没被问过的事：**节点能不能缩放**。`NodeResizer` 在 LibTV 侧根本不存在
（`resizeNode` 只在 `frameosStore` 里）。

四段探针各跑满两轮：a/b/c/d。原始读数随产物提交在 `raw/`。

## 一、★ 先说没毛病的部分

### 两档视口常量都逐位生效（不是死常量）

| 档 | 请求宽度 | `matchMedia("(max-width: 768px)")` | store viewport | 对应常量 |
|---|---|---|---|---|
| desktop | 1440 | `false` | `{x:-583.8, y:260.8, zoom:0.526}` | `page.tsx:163` **三字段全等** |
| compact | 700 | `true` | `{x:17, y:128, zoom:0.28}` | `page.tsx:164` **三字段全等** |
| midband | 800 | `false` | `{x:-583.8, y:260.8, zoom:0.526}` | 断点按写的 768 生效 |

DOM `.react-flow__viewport` 的 matrix 与 store 也一致。**顺带给 `groupKind`（757）
和 `data-canvas-tool`（760）两个死字段做个对照：这两个视口常量是活的。**

### 缩放菜单 6 格 + 三个快捷键 + 上下限，全部符合合同

| 操作 | 期望 | 实测 zoom | 指示器 |
|---|---|---|---|
| `data-zoom-action="100"` | 1 | **1** | 100 ✅ |
| `data-zoom-action="in"`（放大） | +0.1 | **1.1** | 110 ✅ |
| `data-zoom-action="out"`（缩小） | −0.1 | **1** | 100 ✅ |
| `data-zoom-action="fit"`（适合屏幕） | fitView | **0.375** | 38 ✅ |
| `data-zoom-action="800"` | 8 | **8** | 800 ✅ |
| `data-zoom-action="50"` | 0.5 | **0.5** | 50 ✅ |
| `⌘+` / `⌘-` / `⌘0` | +0.1 / −0.1 / fit | **Δ=+0.1 / −0.1 / fitView** | ✅ |

**每一格的指示器都与真实 zoom 相符**，一次都没错。

上下限也钉死了：连点 26 次「缩小」→ 恰好停在 **0.1**；连点 90 次「放大」→ 恰好停在 **8**，
正是 `minZoom={0.1}` / `maxZoom={8}`。

### 那个硬编码的 54，没露脸

`uiStore.ts:223` 写着 `zoomLevel: 54`，而首屏真实 zoom 是 0.526 = 52.6%。

首屏读数（**任何交互之前**）：`uiStore.zoomLevel = 53`、`trigger 文本 = "53%"`、
`store.zoom = 0.526` —— **三处完全一致**。`onViewportChange` 在挂载时就把 54
纠正成了 `round(0.526×100) = 53`。

**看到硬编码不等于它会露脸**，中间隔着一次首次提交。这条差点被我写成缺陷（见 R44）。

## 二、★ 缺陷一：`zoomOnScroll` 是死代码

`page.tsx:1547/1549` 同时开 `panOnScroll` 与 `zoomOnScroll`，`:1551` 又把
`panActivationKeyCode` 设成 `null`。实测 **13 次滚轮**（4 慢 + 6 几乎连发 + 3 反向）：

- **`Δzoom` 的取值集合 = `{0.0}`，13 次全 0**
- `Δy` 恒为 **±120/次**（= wheelDelta × `panOnScrollSpeed={1}`）

⟹ **滚轮只平移，不缩放。**写 `zoomOnScroll` 的人显然是想让滚轮缩放的。

## 三、★ 缺陷二：滚轮落在节点上**完全无响应**

滚轮落在节点正文上（命中 `IMG.object-cover`，祖先带 `nopan`）：

- `before` 与 `after` **完全相同**，`{x:-583.8, y:260.8, zoom:0.526}` 一个数都没动

⟹ 因为 `zoomOnScroll` 本来就是死的（不会缩放），`nopan` 又把平移也挡了，
**滚轮在节点上是一个完全没有响应的输入**。

## 四、★ 缺陷三：平移收尾时 store 的视口落后画面一个滚轮格

3 次向下滚轮，每格固定 120，期望 `Δy = −360`：

- DOM `.react-flow__viewport`：`Δy = **−360**` ✅
- store `canvas.viewport`：`Δy = **−240**` ❌ 少了一格

而且**不会自行收敛**：

| 读数时点 | store.y | dom.y | 差距 | `owner_log` 条数 |
|---|---|---|---|---|
| t+0ms | 20.8 | −99 | y 差 **119.8** | 6 |
| t+500ms | 20.8 | −99 | 119.8 | 6 |
| t+1500ms | 20.8 | −99 | 119.8 | 6 |
| t+3000ms | 20.8 | −99 | 119.8 | 6 |
| t+5000ms | 20.8 | −99 | 119.8 | 6 |

`owner_log` 的条数**冻结在 6 不再增长** ⟹ 不会再有提交了（不是动画没走完）。

下一次视口变化时会被**一次性抹平**：紧接着又 3 次上滚之后，差距回到 `−0.2`
（也就是我自己的取整噪声）。所以这是**丢了一帧提交**，不是持续漂移。

这条要紧，因为 `canvas.viewport` 是**画布对象上的字段**：落后一格意味着
切到别的画布再切回来，视口会被恢复到差一格的位置。**（后果本身未测，见不声称。）**

## 五、★ 缺陷四：640–850px 整段，缩放菜单的唯一入口消失

`BottomToolbar.tsx:122` 的容器 class 是 `relative sm:max-[850px]:hidden`。
`sm:` 在 Tailwind 里是 **min-width** 变体，所以隐藏区间是 **[640, 850]**：

| 视口宽度 | 缩放按钮 | 盒宽 | 父容器 display |
|---|---|---|---|
| `560px` | **可见** | 36 | `block` |
| `700px` | **隐藏** | 0 | `none` |
| `800px` | **隐藏** | 0 | `none` |
| `900px` | **可见** | 36 | `block` |
| `1440px` | **可见** | 36 | `block` |

`data-viewport-menu-trigger` 是缩放菜单的**唯一**入口（全 `src/` 只此一处），
所以在这一整段里，用户只剩 `⌘+` / `⌘-` / `⌘0` 三个快捷键，
而**没有任何可见的缩放读数**（那个百分比就在同一个被隐藏的容器里）。

## 六、节点根本不能缩放，而且拖边角会得到「移动」

| 量 | 值 |
|---|---|
| `.react-flow__resize-control` 元素数 | **0** |
| class 里带 `resize` 的元素数 | **0** |
| `NodeResizer` / `nodeResize` / `nodesResizable` | 全 `src/` 无（`resizeNode` 只在 `frameosStore`） |

拖一个 350×200 的文本节点的三处：

| 起点 | 命中元素 | 结果 |
|---|---|---|
| 右边缘 | `react-flow__handle-right nodrag nopan source` | **完全无反应**（`nodrag` 把拖动吞了） |
| 下边缘 | `P.whitespace-pre-wrap` | **节点被移动** |
| 右下角 | `DIV.min-h-0 flex-1 overflow-hidden p-3` | **节点被移动** |

store 的 `width`/`height`（350×200）、`measured`、`style` 全程一个数都没变；
DOM 宽高也没变。

⟹ 想缩放的用户在右下角会**把节点挪走**，而在右边缘会得到「点了没反应」。
没有任何提示、没有任何光标变化。

## 七、改宽不重投影，是**显式设计**而不是缺陷

1440 → 700 之后视口纹丝不动（`Δ = {0,0,0}`），没有切成 `compactViewport`。
看起来像个缺陷，但 `window.__libtv_viewport_owner_log` 里有一条：

```json
{"canvasId":"canvas-2","status":"skipped","reason":"breakpoint-flip-delegated","ownership":"stable"}
```

代码自己记下了「断点翻转已委托别处」并主动 `skipped`。**这不是漏做，是记录在案的设计。**
（首屏那两条是 `bootstrap-applied` + `projection-echo`。）

## 八、判据（16 条）

1. `desktopViewport` 逐位生效（1440 档 store 三字段全等常量）。

4. 首屏 `zoomLevel` 是 53 不是硬编码的 54，三处一致 ⟹ **不是缺陷**。
5. 缩放菜单 6 格全部符合合同，每格指示器都与真实 zoom 相符。
6. `⌘+` / `⌘-` / `⌘0` 与菜单是同两个回调。
7. 上下限生效：26 次缩小恰好停 0.1、90 次放大恰好停 8。
8. **缺陷**：`zoomOnScroll` 是死代码，13 次滚轮 `Δzoom` 全 0、`Δy` 恒 ±120/次。
9. **缺陷**：滚轮落在节点上因 `nopan` 完全无响应，`before == after`。
10. **缺陷**：平移收尾 store 视口落后画面 ≈120px，5 秒不收敛、`owner_log` 冻结。
11. 该落后会在下一次视口变化时被一次性抹平 ⟹ 是丢了一帧提交。
12. **缺陷**：640–850px 整段缩放菜单唯一入口被隐藏（700/800 隐藏，560/900/1440 可见）。
13. 节点不可缩放：resize 控件 0 个，`NodeResizer` 只存在于 FrameOS 侧。

15. 拖下边缘与右下角得到的是「移动节点」；store 尺寸 / `measured` / `style` 全程不变。
16. 改宽不重投影，但 owner_log 记着 `breakpoint-flip-delegated / skipped` ⟹ **是设计**。

## 十、待拍板（需改 `src/`，等授权）

1. **滚轮要不要缩放**（缺陷一）：删掉 `panOnScroll` 让 `zoomOnScroll` 生效，
   还是保留「滚轮平移」并把 `zoomOnScroll` 这行死代码删掉（不留误导）？
   两条路的产品后果完全不同 —— 画布类产品滚轮缩放是主流，但平移也有需求。
2. **滚轮在节点上无响应**（缺陷二）：handle 祖先的 `nopan` 是 React Flow 自带的，
   要让滚轮在节点上也能平移，得在 `noPanClassName` / `panOnScroll` 上另想办法。
3. **store 视口丢一帧**（缺陷三）：`onMoveEnd` 收尾时补一次提交，
   还是接受它（毕竟下一次变化会抹平）？
4. **640–850px 的隐藏区间**（缺陷四）：`sm:max-[850px]:hidden` 是有意的吗？
   如果是，隐藏期间是不是至少该留个可点的缩放入口。
5. **节点缩放**（第六节）：要不要给 `NodeResizer`？给了就得处理
   「分组框跟随成员」那个老问题（760 已把范围收窄成只需做子→父方向）。
6. **`panOnScrollSpeed={1}`** 是否就是想要的滚轮手感。
