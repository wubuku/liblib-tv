# batch 659 —— 658 那句「场景提示条点不到」的**原因**：一条 944 宽的行溢出 `overflow: auto` 的宿主，提示条被**裁掉**了；边界钉在 **W = 1510**

## 一句话

658 的遮挡普查记下：整个场景提示条（上传图片 / 输入框 / 发送 / sr-only file）
在 1280 宽的中心点都不可达，但**没有说为什么**。本批去问「为什么」。

**答案是一个闭式，边界落在单个像素上：**

    可达  ⟺  提交按钮的中心点 严格落在 宿主的裁剪盒内

    按钮中心恒在 1216 ；宿主右沿 = W − 293 ；1216 < W − 293  ⟺  W ≥ 1510

**W = 1509 不可达，W = 1510 可达。中间没有可争辩的宽度。**

## 1. 三个假设被数据否掉

| 假设 | 判决 | 怎么否掉的 |
|---|---|---|
| **z 序** | **否** | 底栏声明 `z-200`、检视器 `aside` 声明 `z-30`，按 z 底栏该赢；读数相反。而且按钮 **`submitIndexInStack = -1`** —— 它不是「被压住」，是**根本没画在那里** |
| **pointer-events** | **否** | 底栏 wrapper 计算值就是 `none`。做了一次**页内实验**把它改成 `auto`，栈**一个元素都没动**（改前改后都是 `-1`） |
| **那行装不下底栏** | **否** | 1510 那行仍**超出底栏 8px**，却是**可达**的。判据比「装得下」更松 |

**z-index 写着 200 却输了 —— 这是布局的事实，不是层叠顺序的事实。**
643 当年否掉「z-200 vs z-30 打架」，**否得对**：底栏确实压得过检视器，
而它还是输的那一方，**因为它的内容压根没画到检视器那一列上**。

## 2. 站得住的那一个：**裁剪**

```
div[data-director-bottom-bar]   pointer-events-none absolute inset-x-0 z-200
└ div.pointer-events-auto.flex        ← 裁剪器：overflow: auto，W=1280 时 694 宽
  └ div.mx-auto.flex.shrink-0         ← 那行：944 宽，钉死，装不下就向右溢出
    └ div[data-director-scene-prompt-bar]   pointer-events-auto relative z-10
      └ 上传图片 / 描述想搭建的场景 / 发送 / sr-only file
```

W=1280 时：宿主 **293..987**，那行 **293..1237** —— 溢出 **250px**。
提示条在 **1012..1237**，**整个落在裁剪盒之外**，因此**根本没被绘制**，
`elementsFromPoint` 自然找不到它。

`overflow: auto` 的右沿是**排他**的，而这正是边界能落在单个像素上的原因。

## 3. **我自己把这个答案否掉过一次，又捡回来了**

这是本批最该记的一条。

开工前的探针量的是 `bar.parentElement` —— 那一层**确实是** `overflow: visible`、
`scrollWidth === clientWidth`。于是我写下「裁剪故事死了」。
**裁剪器在下一层。** 我量错了元素，否掉了一个正确的机制。

同一个错误犯了两遍：先是**祖先链里**读到「944 宽的行装在 694 宽的父里」→
直接跳到「overflow 裁掉了」；然后读到父是 944 宽、`visible` →
**把裁剪整个丢掉**。两次都是**一个数字读错就翻转结论**。

> **一个被误读的元素否掉的机制，和一个被误读的元素造出来的机制，代价一样大。**

## 4. 第二个轴是必需的

只扫宽度只能产生**一个**转变点，而一个转变点分不开
「中心在裁剪盒内」与「行整体装得下」。折叠面板能在**不改窗口宽度**的情况下
单独改变结果 —— 因为 `mx-auto` 会重新居中，**动的是中心点，不是行宽**：

| 单元 | 宿主右沿 | **按钮中心** | 超出列 | 可达 |
|---|---|---|---|---|
| W=1280 展开 | 987 | **1216** | 238 | ✗ |
| W=1280 折叠 | 987 | **983** | 5 | ✓ |
| W=1440 展开 | 1147 | **1216** | 78 | ✗ |
| W=1440 折叠 | 1147 | **1055** | −83 | ✓ |
| W=1510 展开 | **1217** | **1216** | 8 | ✓ |
| W=1510 折叠 | 1217 | 1090 | −118 | ✓ |

六个转变点：−118 / −83 / 5 / 8 / 78 / 238。**六个，规则零分歧。**

边界两格的原始读数：

| W | 宿主右沿 | 中心 | 栈内位置 | 栈顶 |
|---|---|---|---|---|
| **1509** | **1216** | 1216 | **−1** | `div[data-director-webgl-canvas]` |
| **1510** | **1217** | 1216 | **2** | `path` / `svg`（按钮自己的图标） |

1509 那格宿主右沿**恰好等于**中心 —— 排他，所以出界。

## 5. 「8px 安全边」是个漂亮的巧合

第一版把这个边界写成「超出视口列 ≤ **8**px」，并且注意到 **626 的 `SAFE_MARGIN` 正好是 8**、
649 记过「菜单无一破 8px 安全边」。

**两种表述在六个转变点上完全等价**（超出 238/78 失败、8/5/−83/−118 成功）。
但那个 8 只是**几个常数凑出来的形状**：944 行宽 + 12px 内缩 + 按钮中心钉在 1216。
**长得像 626 的常量，不等于就是 626 的常量。**

写成断言的是**裁剪**那条（说得清为什么），8px 那条降级为**等价重述**并记在案。

## 6. 它解释了 658 的哪些、没解释哪些

**解释了**：658 在 1280×{720,900,1150} 记下的那 4 枚
（`scene-prompt-file` / `-input` / `-submit` / `-upload`）。
658 说「不知道为什么」，本批说为什么，**并说清在哪些宽度、哪种面板状态下它们会回来**。

**没解释**，本闭式不认领：

* `help` —— 另一个机制：被时间轴轨道行盖住（657/658）
* 720 高度那两枚颜色控件 —— 另一个机制：被 `data-director-export-trigger` 盖住

> **一个不能被关掉的解释不是解释。** 所以这条规则的作用域被写死在上面。

## 7. 不声称

* **不主张**源站同样如此 —— **零源站断言**。
* **不主张**「超出 ≤ 8」是独立于裁剪的第二条规则 —— 它是等价重述。
* **不主张**「中心在裁剪盒内」等于「用户点得到」—— 中心点只是**一次**点击的位置；
  一个部分被裁的控件仍可能从可见部分点到。
* **不主张**这三枚提示条控件以外的东西受这条规则影响。

## 8. 我自己写错的地方

1. **否掉了一个正确的机制**（第 3 节）—— 量错元素，两次相反方向都踩。
2. **把常数凑出的 8 当成了项目里既有的 8** —— 形状相同不等于同一个常量。
3. **闭式第一版预测 1506、实测边界 1510** —— 差 4px，因为我当时以为
   `W ≥ 562 + 944` 就是判据；实际判据是中心点与裁剪盒的关系，
   中间隔着 12px 内缩和按钮自身 16px 的半宽。
4. 一个 `return 1 if v.failures if v.failures else 0`（`ast.parse` 当场抓住）。
5. 文档字符串里两个乱码字。
