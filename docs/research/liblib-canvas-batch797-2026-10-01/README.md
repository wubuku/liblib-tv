# batch 797 —— 网格吸附**开着**时，拖组会把成员**拖下网格**

> 探针 `probes/dbg797a.py` · 诊断 `probes/diag797.py` · 汇编器 `probes/mk797audit.py` · 验收 `scripts/verify-liblib-batch797.py`
> 读数 `raw/vb797a-pre.json` / `raw/vb797a-post.json` · 诊断 `raw/diag797-dragpoint.json` · 断言 `runtime-audit.json` · 验收 `verify-report.json`

## 一句话

796 记下「若将来要做尺寸吸附/对齐，这里需要先归一化」。本批去查「将来」是不是**已经**发生了 —— **已经**：
画布**早已有**网格吸附，但分组的 padding 不是网格的整数倍，于是拖组会把整齐的成员带出网格。改一个常量修好。

## ★ 前提复核：吸附**已经存在**

- `page.tsx` 传 `snapToGrid={snapToGrid}` + `snapGrid={[20, 20]}`
- 状态在 `uiStore`（初值 `false`），UI 入口是底栏那个「网格吸附」按钮

若吸附还不存在，整批立论就塌了 ⟹ 这是 S1。

## ★★ 核心机理：唯一来源是 `GROUP_PADDING = 32`（不是 20 的倍数）

派生量的定义决定了「在不在网格」只取决于 padding：

- 组的位置 = `min(成员绝对) − PADDING`
- 成员的相对偏移 = `成员绝对 − 组位置`

实测（吸附开、两个成员都已落在网格上）：

| 量 | pre | post |
| --- | --- | --- |
| 成员绝对（拖前） | `(300,280)` `(260,-120)` ✓ | `(300,280)` `(260,-120)` ✓ |
| 组位置（拖前） | `(228,-152)` ✗ | `(220,-160)` ✓ |
| 相对偏移 | `(72,432)` `(32,32)` ✗ | `(80,440)` `(40,40)` ✓ |
| **拖组后** 成员绝对 | `(632,272)` `(592,-128)` **✗ 掉出网格** | `(640,280)` `(600,-120)` **✓ 仍在网格** |

★ 拖组时相对偏移**一个字节都没变**（`32,32` 拖前拖后一致），只有组位置被
react-flow 吸附 ⟹ 成员整体平移吸附余数 ⟹ 掉出网格。

## 修法：`GROUP_PADDING` 32 → 40（= 2×20）

只改一个常量。★ 改动**前先推演验证**过：padding=40 时组位置、相对偏移、
拖后成员绝对位置**三组量全部在网格**，且仍严格满足 793 的贴合不变量。
不是试出来的。

## ★★ 一条必须钉死的区分

`dragGroupSnapOn` 那条臂里，成员**拖之前就不在网格**（`(132,273)`）⟹ 拖组只是把它们
整体平移，「结果不在网格」**不能**算缺陷。★ 所以**只有**
`groupDragAfterMembersSnapped`（先把成员摆到网格上）是有效判据。

★ 探针给这条臂加了**前提守卫**：摆平后若成员仍不在网格上，直接报 FAILED 而不是硬跑。
★ 验收器 S6 把「`dragGroupSnapOn` 前提不满足」显式写成一条断言，
免得后人读成「post 也没修好」。

## ★ 探针自己踩的三个坑

1. **「组纹丝不动」分不清「不能拖」与「没点着」**（789 记的「阳性对照必须有」）。
   诊断 `diag797.py` 逐点查 `elementFromPoint`：组的 class 里有 `draggable`、
   28 个采样点里 **20 个**命中组 ⟹ 组**能拖**、扫描也**点得着**。
   真因是 `inset=3` 的左右两点命中的是 **`react-flow__handle`**（20×20 的连线把手）
   ⟹ 改成从 `inset=26` 起扫并**显式跳过 handle**
2. 诊断脚本第一版把 `'l'`/`'r'` 传给 `Math.round` ⟹ `elementFromPoint` 报
   "non-finite"，白跑一轮。★ 教训：先**把四个采样点算成数值**再取点
3. 第一版 `members` 顺序不保证稳定 ⟹ 加 `sort` 按 id 排序

## ★★ 顺带还了一笔债：793 验收器的过时断言

793 的 S1 原本写死 `len(fn_call) == 1`（收口调用点恰好 1 处）。在 793 提交时是对的，
但 794（删除 ×2）与 795（键盘 ×1）**合法**地各加了写点 ⟹ 变成 4 之后那条断言
**永久变红**。★ 验收器红着就不能再信它 ⟹ 本批改成「定义恰好 1 个 + 拖拽那处仍经收口
+ 旧裸写点已消失」；连带 N5 的源码变异也必须从**按子串**改成**按行号**定位
（那个 needle 现在有 4 处，按子串替换会一次改掉四处）。

★ 教训：**「恰好 N 处」这种断言会随后续合法扩展永久失效。**

## ★ 代价与限定（如实记账）

- ★ 吸附**关**时 padding 只是视觉留白，32→40 会让框**宽 8 像素**。40 仍是整齐偶数、
  更贴近 8pt 栅格 ⟹ 这是**取舍**不是零成本
- ★ **未与源站对照**（源站需登录）⟹ 40 是工程判断，不是源站实测值
- ★ 未测**嵌套分组**在吸附下的表现；★ 未测**框的尺寸**是否也该吸附（本批只处理位置）
