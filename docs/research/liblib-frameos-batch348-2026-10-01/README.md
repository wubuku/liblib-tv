# Batch 348（2026-10-01）：「双击空白添加节点」是**半成品接线**——事件接了，菜单没渲染

## 结论一句话

Batch 168 早就把「双击空白处打开『选择节点类型』菜单」的**事件半边**接好了，
但 `paneMenuAt` **从没有任何组件读过**：双击空白处什么都不会出现，而且
**Esc 也关不掉那个状态**。本批补上渲染半边，并让节点落在**双击的那一点**上。

这一批还**修正了 Batch 346 的一个判断错误**。

## 运行时证据（修复前）

探针 `scripts/probe-frameos-batch348-dblclick-addnode.py`：

```
[双击前] paneMenuAt=None                     节点数=7
[双击后] paneMenuAt={'x':140,'y':140}        出现「选择节点类型」字样=False
[二次双击] paneMenuAt={'x':200,'y':180}      ← 状态确实在被写
[Esc 后]   paneMenuAt={'x':200,'y':180}      ← 关不掉
HALF_WIRED: true
```

`page.tsx:188` 的注释就是证据：

> `// 双击空白处打开「选择节点类型」菜单 (Batch 168)`

事件监听完整（`.react-flow__pane` 的 dblclick、跳过节点上的双击、记录坐标），
**只有渲染那半边从来不存在**。

## 🔑 这一批修正了 Batch 346 的判断

Batch 346 我把「双击空白处添加节点」记为**保真度差距**，理由是：

> 承诺只说「添加节点」，没说添加哪一种；工具条的添加节点是带类型选择的菜单，
> 选一个默认类型就是发明产品行为 → 不发明。

**这个推理是错的。** Batch 168 的设计**已经回答了这个问题**——它要的是一个
「选择节点类型」**菜单**，由用户自己选。所以这不是「无法实现」，而是
**「做了一半」**：事件半边在，渲染半边缺。

> **教训**：在把一个功能记为「没有源站证据、无法实现」之前，先查一下
> **是不是已经有半成品实现把答案写好了**。半成品的存在本身就是强证据 ——
> 它说明有人已经想过这件事，而且想清楚了该怎么做。
> 「我不能发明」和「我不能凭空发明」是两回事：前者的答案可能就躺在代码里。

## 修复

**1. 补渲染半边** `FrameosPaneAddNodeMenu`（新组件，挂在 `page.tsx`）：
类型列表**直接复用工具条导出的 `NODE_TYPES`** —— 同一个「有哪些节点类型」的事实
只该有一个出处，不该两处各写一份。

**2. `AddNodeOpts` 增加可选 `position`（画布流坐标）**：
此前 `addNode` 只能放**视口中央**或**随机位置**。用户在哪儿双击，节点就必须
在哪儿出现，否则这个交互没有意义。

**3. Esc 多级退出链补上 `paneMenuAt`**：此前这个状态根本关不掉。

## 写探针时踩的两个坑（都是探针自己的问题，不是应用缺陷）

1. 第一次跑，遮罩点击超时——因为上一步刚在那个坐标加了个节点，第二次双击
   落在**节点**上（双击节点不弹菜单是**正确行为**）。修法：重新找空白点。
2. 验证器里把 Playwright `position={"x":1000,"y":700}` 误写成 `{"height":700}`。

> **验证失败先看失败在哪一步** —— 这条纪律本会话已经用第三次了，每次省的
> 都是「差点去改应用代码」的错误。
