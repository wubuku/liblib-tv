# batch 654 —— 把「打开路径的滚动 offset」做成**可复用闸门**；闸门自己的分类法**被它第一跑推翻**

## 一句话

651 查出 650 的头条读数是 `hover()` 自动滚动的伪影，652 把污染面量成「11 分之 1」，
653 关掉了自己留的那条「不声称」。
但**三批都是「每批各查一次自己那几条路径」** —— 每写一条新打开路径就默认干净，
而 651 已经证明「干净」是需要证据的。

本批交付**闸门本身**（一条不认识任何路径的前置断言），
并用**已知阳性 / 已知阴性**证明它有鉴别力。
然后闸门在第一次运行中**推翻了自己的分类法**：
「有没有滚到末端」不是路径的属性，是**路径 × 窗高**的联合属性，六个窗高里三个到、三个不到。

**9 checks 全绿**。独立重跑 651 的六窗高表，**6/6 逐位复现**。

## 1. 闸门

```python
scroll_gate(page) -> {fired, moved, partial, toEnd, verdict}
```

**它不需要知道是哪条路径。** 它只问一件事：这一格跑完之后，
页面上有没有任何可滚动容器离开了它的自然原点。
有就报出是谁、滚了多少、相对上限多少 —— 因为「滚到 779/804」和「滚到 12/19」
是两个不同的事实（652），而只有前者是探针伪影。

判词三值：`clean` / `partial-scroll` / `scrolled-to-end`。
实现上它**复用 652 的 `SNAP_JS`**，一个新 JS 都没写 ——
**本批的标的不是新仪器，是把仪器变成前置断言。**

## 2. 鉴别力：12 个已知答案

一把只会通过的闸门等于没有闸门。本批用 651/652 亲手量出的答案当标定集。

| | 路径 | 结果 |
|---|---|---|
| **必须响** | `camera-fov-help-tooltip` | 2/2 窗高全响 |
| **必须响** | `camera-preset-panel` | 2/2 窗高全响 |
| **必须静默** | 其余 9 条 | 9 条 × 2 窗高全 `clean` |

**恰好**是 651/652 指认的那两条响，其余九条一条不响。
另外单独断言「阳性必须在**每个**窗高都响」——
一个只在单个视口上采样的闸门会在 1440×900 放行，把 651 整条漏掉。

## 3. 头条：第一跑推翻了自己的分类法

闸门原设计出三个判词，**并打算用它们把 651 的那一族和 652 的那一族分开**
（「651 的是滚到末端，652 的是部分滚动」）。

第一次运行就红在这条上：同一条 `camera-fov-hover@` 路径，
1150 判 `scrolled-to-end`，720 判 `partial-scroll`。

追下去发现**前提从来就不成立**。本批随即按 651 的六个窗高**独立重跑**（不是引用 651 的文件），
并与 651 的 audit **逐格比对**：

| 窗高 | 654 实测 | 651 记录 | 差 | 判词 |
|---|---|---|---|---|
| 560 | 756 / 964 | 756 / 964 | **208** | partial-scroll |
| 640 | 676 / 884 | 676 / 884 | **208** | partial-scroll |
| 720 | 779 / 804 | 779 / 804 | **25** | partial-scroll |
| 800 | 724 / 724 | 724 / 724 | 0 | scrolled-to-end |
| 900 | 624 / 624 | 624 / 624 | 0 | scrolled-to-end |
| 1150 | 374 / 374 | 374 / 374 | 0 | scrolled-to-end |

**6/6 的 `scrollTop` 与 `maxTop` 逐位相同。**

**六个窗高里三个到末端、三个不到。**
一个二元的「到末端了吗」闸门会在 651 六格里的 3 格放行、另外 3 格漏掉 ——
**漏掉的恰好是它本该抓住的那个族**。

补一句更细的：560 和 640 都**恰好差 208**，
说明「差多少」本身也不是连续的 —— 720 突然只剩 25。
这不是噪声，是一个有结构的停止点。

**稳定的判别式仍是 652 那条：偏移量随窗高漂不漂。**
`camera-fov-help-tooltip` 不恒定，`camera-preset-panel` 恒为 12/19 且**从不到末端**。
本批保留它，把否定结果连同 651 的原始表一起钉在案。

> 为什么独立重跑而不是引用：651 的数字**来自一个已被证明会误导的探针**。
> 引用它会把「651 说的」和「本批看到的」混成一件事，而 651 的整个论点就是这两件事必须分开。

## 4. 顺带：分母是个数，而且**我第一版写错了 5.4 倍**

本批把「这个项目有多少条打开路径」普查成一个**活的读数**，
写进 audit 并断言它可复现（新增一个验收器，分母就变，检查就红）。

普查走 **AST**（`ast.Call` 且 `func.attr ∈ {click, hover}`，外加 `dispatch_event('click')`），
**不**走正则。

| 口径 | 数 |
|---|---|
| `verify-liblib-batch*.py` | **352** |
| `.click()` 调用点 | **1400** |
| `.hover()` 调用点 | **32** |
| `dispatch_event('click')` | **5** |
| **打开路径站点总分母** | **1437** |

**为什么必须是 AST**：同一批文件上按文本正则数 `.click(` 得 **1474**，
多出来的 **74** 处是**文档字符串里被引用的代码**。
而本脚本的文档字符串**自己就写着 `.click(`** ——
一份会因为引用了这个数字而改变自己读数的文档，不是仪器。
这与 643 的 `surfaceOf`、649 的导出式竞争集是同一条教训：
**手写的「要测什么」清单是唯一会过期的那个东西。**

**我第一版普查写下的分母是「约 258」。**
查下来 258 根本不是调用点数，是**含 `.click(` 的文件数**（259，减去本脚本自己那一份）。
真实调用点 1400 —— **差 5.4 倍**。
而 258 既不是零也不是荒谬，**它看起来就像一次普查**。
只有用两种方法量两次才看得出。

**这一条被写成断言**（`the-draft-denominator-was-a-file-count-not-a-call-count`）而不是留在叙述里：
分母在被任何人依赖之前就已经错了，而修法不是「以后写得更仔细」，
是**让它变成一个会随项目变化的活读数**。

## 5. 已量 / 分母

15 条路径被闸门量过（11 条 626 导演台浮层 + 4 条 648 抽屉），
分母 1437 —— **比值 0.0104**。

**这是一个棘轮，不是 pass/fail。**
差距被记成一个数，只许变小；给它判 pass/fail 只会得到两种结果之一：
要么空洞（断言一个必然为真的东西），要么不可达（1437 − 15）。
