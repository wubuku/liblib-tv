## 一、这批为什么存在：一条**没有源**的「源站实测」

batch 833 的 README 里写着一条结论：

> 「镜头名沿用源站的命名模式（源站实测『**机位01 · 对峙中景 · 镜头**』）」

本批去源站找这条「实测」的源头，**没找到**：

| 检索范围 | 「对峙中景」出现次数 |
| --- | --- |
| 仓库里全部 46 个**源站** raw（`raw/source-*.json`） | **0** |
| 源站**整页关键词扫描**（`raw/source-837-shotname-page-scan.json`） | **0** |
| 源站画布上真实显示的镜头名 | 「**S83·镜2**」（完全另一套体系） |
| 源站 15 枚机位预设 | 只有「**正面中景**」「**背面中景**」（语义属于**预设**） |

而「机位01 · 对峙中景」这串字是 **batch `3661ccae`**（最早的 r3f 导演台）给 clone **自拟**的，
一路躺在 `src/store/directorStore.ts` 的种子数据里。

### ★ 循环论证的形状（这一批真正的收获）

```
clone 自拟一个名字
  ⟹ 在 clone 界面上看到这串字
  ⟹ 以为那是源站的命名
  ⟹ 写成「源站实测」
  ⟹ 后续批次拿它当【期望值的来源】
  ⟹ 越滚越实
```

**每一环读的都是自己造的东西。** batch 833 那条「源站实测」写得很确定，
连 batch 836 都照着它写进了 raw（「源站的镜头叫『机位01 · 对峙中景 · 镜头』」），
本批才把它查穿。★ **判据设计的教训**：任何「这是源站的 X」这种话，
都必须能在**源站侧**的 raw 里找到**那个字面量**；找不到就只能是 clone 自己的。

## 二、源站实测（本批新做的）

### 2.1 源站镜头名不含机位名

`raw/source-837-shotname-scan.json`：在源站新建机位（机位3、机位4），
逐个查「镜头名里是否含机位名」——**全部为空**；「镜头名 == 机位名 + 『 · 镜头』」为 **false**。

★ 源站场景树里**没有镜头节点**，只有一枚「**确认镜头**」按钮 ⟹
源站的镜头名**不是**「机位名 + 后缀」这种派生式。

### 2.2 源站的镜头名是另一套体系

`raw/source-837-shotname-page-scan.json` 的整页扫描读到的**同族**文字：

- `S83·镜2`（x 127, y 104）—— 画布上真实显示的镜头名
- `确认镜头`（x 430, y 399）—— 场景树里那枚按钮
- `分镜`（x 121, y 675）

⟹ 源站用「**S<数字>·镜<数字>**」体系 ⟹ clone 的「机位名 · 镜头」派生式**仍与源站不一致**。

★ **本批不声称**镜头命名体系已对齐 —— 这条留给后续批次。

### 2.3 语义属于「预设」，不属于「初始机位」

源站的 15 枚机位预设里有「正面中景」「背面中景」，
而源站每个项目的**第一台机位**叫「**机位1**」——纯编号，无语义后缀。
⟹ clone 把「中景」写进**初始机位名**是**层级错置**：那是**预设的语义**。

### 3.1 派生量**自动跟随**（无需另改）

| 派生量 | 派生式（源码位置） | 改名前 | 改名后 |

★ 三条都是**从机位名派生**，所以改一处即全体跟随（实测，store 与 DOM 两侧都读到新值）。

### 3.2 ★★ 顺手消掉了 batch 836 记的「编号体系错位」

batch 836 的 raw 里记过一条：

> 「clone 默认机位名『机位01 · 对峙中景』**不匹配** `^机位\d+$` ⟹ **不算作编号** ⟹
> clone 那台**不占编号** ⟹ 两边『编号 2』指向的机位**在树里的序号不同**」

改名成「机位1」之后，这台默认机位**匹配**编号正则 ⟹ **它占编号 1** ⟹
新建那台叫「**机位2**」⟹ clone 的编号序列与源站（机位1→机位2）**逐字一致**。

★ 这是**推论**，所以本批**实测**了它（`raw/clone-837-runtime.json`）：
默认机位名匹配正则 ✓、新建那台叫「机位2」✓、
台数用**与名字无关**的口径交叉校验为 2 ✓ ⟹ 错位**确实消失**。

★ 注意：`cameraIndex` 用的是 `cameraCount + 1`（**计数**口径），
所以改名**不影响**编号的计算过程，只影响「默认机位算不算编号 1」这个**语义**。
