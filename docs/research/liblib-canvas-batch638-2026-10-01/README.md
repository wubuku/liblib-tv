# Batch 638 —— **审计我自己的量具**：高度的三方真值表，以及属性在哪两格撒谎

## 零源站断言

源站窄屏的时间轴默认高度与收起高度**未取证**。本批只主张 clone 的读数，
**不发明新数**，也**不主张该往哪边修**（沿用 636/637 的处置）。

## 一、为什么要审量具

636 在「高度恰好等于 182」时挖到 store 与 DOM 分歧；637 发现收起态下 store 被完全
忽略。两批都靠 `getBoundingClientRect` 取高度。但高度在代码里有**三个**独立的表述
来源，任何一个撒谎都会污染下游：

| 来源 | 位置 | 它说的是 |
| --- | --- | --- |
| store 的 `timelineHeight` | `directorStore.ts` | 用户意图 |
| 行内样式 / CSS 类 | `DirectorTimeline.tsx:836-845`、`:814` | **实际渲染** |
| `data-director-timeline-height` | `:794` | `collapsed ? 88 : timelineHeight` |

第三个来源是**照抄 store 的**（收起时更糟——硬编码 88，连 store 都不是），
而**实际渲染在两个时刻交给 CSS**。所以它必然在某些格子里与 DOM 不符。

## 二、判据从机制推导，不从记忆誊写

第一版我把「属性说谎的格子」**硬编码**成「收起 + 窄族」，结果红了一格：
`w898/exp/store=182` —— **636 自己挖出来的那格我忘了**。

**这正是我写进台账的那条教训又发生了一次**：钉住用的集合必须来自机制，不能来自
「我记得是哪些」。改写成从规则推导：

```
属性说谎 ⟺ 窄族 且（收起 或 store == 182）
```

——「窄族」是前提（桌面族两处交接都恰好与 store 相等），「收起 / store==182」
是 `:836-845` 那个三元**省略行内样式的两个时刻**。推导式与实测 7 格**完全相等**。

## 三、三方真值表（36 格，3 宽度 × 2 态 × 6 个 store 值）

| 状态 | store | 行内样式 | 窄族（≤898）实际 | 桌面（≥899）实际 | 属性 |
| --- | --- | --- | --- | --- | --- |
| 展开 | **182** | **省略** | **176** | 182 | 182 |
| 展开 | 88 / 124 / 176 / 240 / 420 | 有 | 原样 | 原样 | = store |
| **收起** | **完全忽略** | **省略** | **124** | **88** | **88（硬编码）** |

三条断言把表钉死：

- `every-cell-renders-what-its-regime-predicts` —— 36 格逐格符合其所属regime
- `all-three-height-regimes-are-exercised` —— 三个 regime 都被真实走到
  （否则上表可能只由一条规则满足）
- **`182-is-the-only-store-value-that-goes-to-css`** —— 扫 88/124/176/240/420
  **全部原样渲染**，只有 182 被改写。这把 `:845` 那个三元的「唯一特例」钉成了断言。

**属性说谎的 7 格全在窄族**：`w898/exp/store=182`（说 182、实 176）+
6 个 `w898/col/*`（说 88、实 124）。而
`while-expanded-the-attribute-is-always-just-the-store-value` 确认：**展开态下
属性恒等于 store**，它从不自己编数字——除了收起态那个硬编码的 88。

## 四、审计结论：**629–637 的高度结论是可靠的**

`the-rect-readers-629-to-637-were-reading-the-true-height` —— 36 格
**`getBoundingClientRect` 的高与 `getComputedStyle` 的高逐格相等**，即 rect 没有被
transform / zoom 之类的因素污染。629–637 每一批的高度读数都建立在 rect 上，
所以它们**读的是真高度**。这是本批最该被记下的一条：**我审的是量具，结论是量具可信。**

静态审计（不需浏览器，直接扫 `scripts/`）：全仓只有 **607 / 637 / 638** 读这个属性，
且**每一个用它做断言的脚本都同时读几何**（`unsound: {}`）。637 记录属性但断言全用
rect，607 两个都断言——所以**没有一个脚本被它骗过**。

## 五、607 的合同被**迁移**，并补上它的域

607 的 `collapse:independent-of-resize` 断言合取 `(计算高 == 88 且 属性 == "88")`。
本批在三个宽度上**原样重放**它：

| 宽度 | 计算高 | 属性 | 607 的合取 |
| --- | --- | --- | --- |
| 898 | **124** | 88 | **不成立** ← 607 从未跑过这一格 |
| 899 | 88 | 88 | 成立 |
| 1440 | 88 | 88 | 成立 |

**607 的 viewport 是 1920×1150，只跑过桌面族** —— 所以它那条「收起态 = MIN_H(88)」
的合同**只在桌面族成立，而它从没说**。红灯在这里是**被断言要求的事实**，
不是缺陷：合同保留，域补上。

## 六、判据自己踩的另一个坑：harness 把「当前状态」当成了「是否等于目标」

`ask_collapse` 我写成「点击（若需要）→ 返回重读到的状态」，漏了 `== want`。
于是**每一个本来就正确的状态都被记成「切换失败」**——3 个宽度全红，
看起来像三个坏掉的开关，实际是**一个 harness bug**。

**信号的方向要读对**：三个宽度同时在同一处红，且红的方式是「不需要动作却报失败」，
这形状指向判据而不是被测物。637 里同一个函数是对的（多了 `== want`），
两批的差别就是这一行。
