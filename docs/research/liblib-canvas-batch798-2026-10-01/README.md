## 一句话

797 修的是组**位置**与成员的**相对偏移**（`GROUP_PADDING` 是这两者的来源），并留下一句
「未测框的**尺寸**是否也该吸附」。本批去回答 —— 答案是**不该**，而且这不是「懒得做」，
是**数学上做不到**。

★ 本批是**拍板批次**，`src/` **一行没改**。不是所有批次都要改代码；但「不改」必须被钉住。

## ★★ 证明一：组尺寸的余数由**成员边界**决定，与 padding 无关

组框尺寸 = `(max(成员右) − min(成员左)) + 2 × PADDING`。若成员**位置**都在网格上：

| padding 取值 | 重算出的尺寸余数 |
| --- | --- |
| p798-a `0` | `(18, 10)` |
| p798-b `20` | `(18, 10)` |
| p798-c **`32`（非倍数）** | `(2, 14)` |
| p798-d `40` | `(18, 10)` |
| p798-e `60` | `(18, 10)` |

★ **网格倍数之间余数恒定** ⟹ 换任何网格倍数都救不了。
★ **非倍数（32）算出不同余数**，这反而是更硬的证据：它说明余数**确实**受 padding 影响，
只是在网格倍数上是**阶梯恒定**的。

## ★★ 证明二：前提是「成员尺寸本身就不是网格倍数」

种子成员实测 `618 % 20 = 18`、`350 % 20 = 10`。★ 如果成员尺寸都是倍数，组尺寸也会是 ⟹
结论会反过来。⟹ 这条前提被显式钉成断言（S5 / E），不是默认成立。

## ★ 依据：组**没有** resize 控件 ⟹ 尺寸吸附帮不了任何操作

- 运行时：组的 DOM 上 `.react-flow__resize-control` 数量 = **0**，**选中前后都是 0**
- 源码侧：`src/` 全仓 `grep NodeResizer` = **0**（不只是组组件，是整个 `src/`）

★ 双向互证：只看运行时可能是探针漏看，只看源码可能漏了别的入口。
★ 尺寸吸附只对「**用户能调的尺寸**」有意义。既然组不可调 ⟹ 「容器不吸附、只对象吸附」。

## ★★ 对照：吸附**关**时尺寸**同样**不是倍数

这说明容器尺寸不吸附是**常态**，不是「吸附开着才出现的副作用」。

## 核心读数（同一份探针，pre / post 各 2 轮 × 3 臂，两阶段逐格相同）

| 量 | 值 | 余数 |
| --- | --- | --- |
| 成员尺寸 | `618×350`、`350×200` | `18`、`10` |
| 组**位置** | `(220,-160)` | **0** ✓（797 的成果，本批不许回退） |
| 组**尺寸** | `738×830` | **18 / 10** ✗ |

★ 独立重算（只用 raw 的成员读数 + padding，不读源码公式）：
`max(300+618, 260+350) − min(300,260) + 80 = 738`、
`max(280+350, −120+200) − min(280,−120) + 80 = 830` ⟹ **逐位吻合**。

## ★ 被否决的另两条路

| 路 | 为什么否决 |
| --- | --- |
| ① 改**成员**尺寸 | 那是改**用户对象**的大小，超出「组框」范围 |
| ② 放弃「恰好包住成员」 | **破坏 793 的不变量**（框不再贴合），且会让成员掉出框 |

## ★ 判据踩的坑（两边都改）

它证明余数确实受 padding 影响，只在网格倍数上是阶梯恒定的。
