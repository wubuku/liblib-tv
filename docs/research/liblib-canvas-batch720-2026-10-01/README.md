# batch 720：加模型写历史且当场可撤销；「关台丢内容」只对单独的加模型成立

日期：2026-10-03　验收器：`scripts/verify-liblib-batch720.py`（7 条判据，零 store 写入，不改 `src/`）

## 起点

原计划是普查导演台里所有 `keydown` 判据看不看修饰键（719 测出场景描述 prompt
的四种 Enter 组合全部提交）。普查做完了，但**顺着它撞见的一件事把这一批整个改写了**。

顺着「从模型库加一个模型」走一圈之后发现：**Escape 关台之后，刚加的模型没了。**
于是本批改问一个更基础的问题：**关台到底丢什么？**

## 决定性读数

### 静态普查（`src/components/director/`，10 处 `onKeyDown`）

| 类别 | 处数 | 修饰键 | 键位判据 |
|---|---|---|---|
| 组件级 handler | **8** | **一处都不查** | 全部只比 `Enter` |
| `useDirectorGestureBoundary.ts:92`（hook） | 1 | **查** | — |
| `DirectorDesk.tsx:570`（`window` 全局快捷键） | 1 | **查**（c/v/z/y 要求修饰键） | — |

**8 处组件级 handler 全部修饰键盲，而查修饰键的恰好是两处需要它的地方** ——
这是一套自洽的约定，不是混乱。其中两处把 `Enter` 与空格 `" "` 视为同一个键，
且**两处动作都改变状态**：模型库卡片的 `onAdd(item)` 与 AI 导入上传区的
`imageInputRef.current?.click()`。导演台内**没有 `<form>`**，Enter 的隐式提交不是问题。

### 加模型这一步本身是完整的

| 读数 | 值 |
|---|---|
| `objects` | **5 → 6**（多出「饮料瓶」） |
| `history.past` | **0 → 1** |
| `lastCommandResult` | **null → SET**，`projectChanged: true` |
| 模型库卡片数 | **3 → 0**（一次激活就把列表清空） |
| 台开着时按 `Meta+z` | **`past` 1 → 0、`objects` 6 → 5** ⟹ **当场可撤销** |

**⟹ 这是与 719 那枚 prompt 的正面对照**：同一个底部条区域里，
一个是「纯本地回显、store 一个字段都不动」，一个是「真写历史、真进对象表」。

### 关台丢了什么：三条路线对照

| 路线 | 改动 | 关台后 store | **重开（点节点卡上那枚按钮）** |
|---|---|---|---|
| **A** | **只加模型** | objects 6、**past 0** | **objects 5，饮料瓶没了** |
| **B** | **只改名** | — | **改名还在**，且 **`past` 回到 1** |
| **C** | **先改名、再加模型** | objects 6 | **6 个全在**，改名与饮料瓶都留住 |

- 关台后 **`past` 立刻归 0**，而 store 的 `objects` 仍是 6 ——
  **丢的是「重开时读到什么」，不是「关台那一刻」**
- 路线 A 用裸 `Escape` 就能关台；路线 B/C 需要先关掉可能开着的模型库面板
  （**面板开着时 Escape 只关面板、不关台**），两条路径最终读数同构
- **路线 B 的 `past` 重开后回到 1** ⟹ **关台不丢历史，刷新才丢**（711 测的是刷新）

### 顺带认领的一枚元素

模型库卡片是 `<article role="group" tabIndex={0} aria-label="添加模型 饮料瓶">`：
**可聚焦、可激活（Enter 与空格）、可及名是动作句，但角色是 `group` 而不是 `button`**，
而且样式里有 `focus-visible:ring-1`（说明作者预期它是个键盘焦点目标）。
⟹ 屏幕阅读器会把它读成一个「组」，不会读成可激活控件。

## 与 710 的关系：读数存活，概括要收窄

710 测出「同一节点上关台重开：内容与历史都保留」，并据此**撤回了**
「关台丢内容」这个假设。

**710 的读数全部存活** —— 但它的概括太宽：**改名成立，单独的加模型不成立。**
所以准确的表述是：**「关台丢内容」不是普遍现象，它取决于这次改动是什么。**

## 不声称（本批不解释的）

为什么「先改名、再加模型」两个改动都留住，而「只加模型」会丢？
这三条读数本身**不足以判定**。已知的事实是：

- 台开着时，那一步是完整入账的（`objects` +1、`past` +1、`projectChanged: true`）
- 关台那一刻 store 仍持有那个对象（`objects` 仍是 6）
- **只有重开之后它才消失**

所以问题落在「关台时写进持久化的是什么」这一层，
而「先改名」为什么会改变这件事，**需要读 `closeSession` / `persistence.save`
对不同改动类型的处理才能回答** —— 本批只取证，不解释。

## 方法论收获（可复用）

**① 一批的题目可以在中途被读数改写 —— 前提是顺着动作真的走完一圈。**
原题是「修饰键语义普查」，普查结论（8 处全盲、约定自洽）确实成立；
但**同一批里顺手做的「加一个模型再关台」撞出了别的东西**，
于是整批改问「关台丢什么」。
⟹ **不要因为原题已经做完就收工**；顺路走一圈的动作往往比原题更有信息量。

**② 「丢了」要问清丢在哪一步。**
本批最容易犯的错是：看到关台后 store 里没有那个对象，就说「关台丢了内容」。
实际上**关台那一刻 `objects` 仍是 6**，是**重开之后**才变成 5。
⟹ **「丢失」是一个跨步骤的过程，必须把每一步都读一遍** ——
关台前 / 关台后 / 重开后。少读一步就会把「关台丢的」说成「重开丢的」。

**③ 同样的动作，换一个前置状态，结果可以相反。**
路线 A（只加模型）重开后少一个；路线 C（先改名再��模型）重开后全在。
**同一条关台路径、同一个按钮、同一枚卡片。**
⟹ 报「某操作会丢东西」之前，**至少换一个前置状态再试一次**；
只试一个前置状态就下的结论，就是 710 那种「概括太宽」。

**④ 探针的「换一步」可能比「重试一次」更重要。**
路线 C 里 `Escape` 没能关台（面板开着，Escape 先关面板），
我第一反应是「探针坏了」，实际上是**一条关于交互优先级的读数**。
⟹ 遇到「预期的键不起作用」，先问「是不是被更内层的层吃掉了」，
再考虑是不是探针问题 —— 707 立的「无响应至少三类」在这里又中了一次。

**⑤ 断言消息用元组时只会打印第一个元素。**
`assert cond, (key, ctx)` 的失败信息**只有 `key`**，
我因此把一个 D 路线的失败误判成了 C 路线。改成 `assert cond, ctx` 或
`assert cond, f"{key}: {ctx}"` 才会看到真正的读数。

## 待拍板（不阻塞）

- **单独的「从模型库加一个模型」在关台重开后消失** —— 需要定位
  `closeSession` / `persistence.save` 对这类改动的处理（**本批不声称成因**）
- **模型库卡片 `role="group"`** —— 它可聚焦、有激活语义、可及名是动作句，
  要不要改成 `role="button"`
- **8 处组件级 keydown 全部修饰键盲**，其中两处把空格当作激活键 ——
  要不要只认裸 Enter（与 719 的待拍板项同一条）
- **模型库面板开着时 `Escape` 只关面板不关台** —— 与 707 的「Escape 双重语义」是同一条线
- 715/716 的底部条横向溢出（clone 独有）与其余遗留照旧挂着
