# Batch 687 — 630 那条「只减不增」的自动钳制：往返是有损的，而且损的是用户值

日期：2026-10-01
验收脚本：`scripts/verify-liblib-batch687.py`（**7 项，7/7 通过**）
取证脚本：`/tmp/dbg687a.py`（三条往返腿 + 拖把手 + 重载）、`/tmp/dbg687b.py`（用户偏好那一版）

本批**零源站断言**（无源站授权、未开源站会话）。拖把手是拖**我们自己的 clone** 的控件，
**不碰源站**；`src/` **一字未改**。

## 起点：686 那条读数不是缺陷，是 630 写明的意图

686 读到时间轴高度 store 值「被夹到 88 之后再也不涨回来」，措辞像缺陷。**读源码发现不是** ——
`DirectorTimeline.tsx:686` 的 `fit()` 明确只做减法，注释里写了意图：

> 越界多少上移多少，**不越界一个像素不动**（不越界时根本不调 `setTimelineHeight`）
> —— 默认 182 逐像素不变。

而且 630 连 176 那条边界都记了。所以「粘住」是**有意设计**。

**630 从未覆盖的是往返**：窗口变矮（触发钳制）之后再变高，值回不回来；
以及更尖锐的一版 —— **用户自己拖出来的高度会不会被吃掉**。

## 读数一：自动钳制在 **H < 270** 介入，store 的 MIN 在 **H < 176** —— 差 94px

| 往返 | 触发钳制？ | `timelineHeight` 读数 |
|---|---|---|
| 720 → **300** → 720 | **否**（300 > 270） | 182 → **182** → 182，一点没变 |
| 720 → **200** → 720 | 是 | 182 → **112** → 112 |
| 720 → **150** → 720 | 是，且撞 MIN | 182 → **88** → 88 |

- **270** = 面板顶边被顶到 `88` + 高度 `182` ⟹ 低于它面板才越界 ⟹ **「自动钳制会不会跑」的那条线**。
- **176** = `88 + MIN(88)` ⟹ store 的 MIN 才起作用的那条线。**630 只记了这一条。**

**两条线差 94px，而只量注释里那条，会完全错过「钳制到底跑不跑」的判据。**

## 读数二：往返的损失**恰好等于触发它的那次溢出**

`fit()` 就是 `setTimelineHeight(timelineHeight - overflow)`，所以：

- `720→200`：溢出 `270 − 200 = 70` ⟹ `182 − 70 = **112**` ✓
- `720→150`：溢出 `270 − 150 = 120` ⟹ `182 − 120 = 62` ⟹ **被 store 的 MIN 抬回 88** ✓
  而那一步 **`overflowBy = 26`** —— 独立复核了 630 记的「面板仍会越界」：
  被钳到 88 后面板是 `[88, 176]`，而窗口只有 150。

## 读数三：损失**与 MIN 无关**

`720→200` 那条腿全程读到 **182 / 112 / 112**，一次也没碰到 88，**照样丢掉 70px**。

所以「粘性」不是 MIN 的性质，是「**只减不增**」的性质 ——
**只要窗口曾低于 270，高度就永久降一档，无论那扇窗开了多久。**
把它归因到 MIN 会是一个听起来很顺、但错的解释。

## 读数四：往返不是纯粹的损失，是一次**静默重分配**

| `timelineHeight` | 3D 视口高 | 面板越界 | 面板下方空隙 |
|---|---|---|---|
| 182（默认） | 450 | 0 | 0 |
| 112（往返后） | **520** | **0** | **0** |

省下的 70px **全部给了 3D 画布**（450 → 520），而且**越界 0、空隙 0**。

**这就是它一直没被看见的原因**：一个长得像「画布变大了」的东西，不会被当成缺陷报上来。
损失之所以难发现，是因为它同时改善了另一样东西。

## 读数五：最尖锐的一版 —— **用户自己拖出来的 320，被一次缩窗改成 112**

| 步骤 | `timelineHeight` | 3D 视口高 |
|---|---|---|
| 打开（1280×720） | 182 | 450 |
| **拖把手 +138** | **320**（用户的偏好） | 312 |
| 缩到 1280×200 | **112** | 0 |
| **回到 1280×720** | **112**（不是 320，也不是 182） | 520 |
| 再拖 +70 | 182 | 450 |

**缩窗之后那个值是窗口高的函数（112 = 200 − 88），与用户的 320 无关。**
630 保护的是**默认值**；**没有任何东西保护用户选的值。**

## 完整状态机

| 事件 | `timelineHeight` 变成 |
|---|---|
| 打开 / **重载** | **182**（`DIRECTOR_TIMELINE_DEFAULT_HEIGHT`） |
| 拖把手 | 拖出来的值（88..420） |
| 窗口 resize 且面板会越界（`H < 270`） | **减掉恰好那次溢出**，下限 88 |
| 继续 resize 且仍越界 | 继续减 |
| **窗口变高** | **什么都不做** |
| **重载** | **182** —— 不是被钳后的值，**也不是用户的 320** |

**两条恢复路都毁掉用户偏好**：
手动拖是从**被钳后的值**起步（112 起，不是 320 起）；
重载回到**默认值**（182，也不是 320）。
`timelineHeight` 不进持久化 schema（599 的结论：视图态故意不入 schema），
所以重载永远给默认值。

**⟹ 用户的时间轴高度不是一份耐久偏好，它只是一份缓存**：既活不过一次缩窗，也活不过一次重载。

## 要你拍板的那一条（本批不擅自改 `src/`）

630 的目标「默认 182 逐像素不变」**达成了**；但同一条「只减不增」规则
**让用户值被一次瞬时缩窗静默销毁**。这两条**不能同时满足**：

- **A「变高时自动恢复」** ⟹ 630 想保护的 182 会被自动写回，
  于是「逐像素不变」在用户没拖过的情况下也不成立了；
- **B「永不自动恢复」**（现状）⟹ 用户只能手动拖或重载，**而两条都拿不回自己的值**；
- **C「记住钳制前的值，只在用户没拖过时自动恢复」** ⟹ 保住 630 的目标，
  代价是引入「这个值是用户的还是自动的」这一个状态位。

**这与 628/630 对「最小视口高」的处置是同一条纪律**：窗口能被拖到多矮
「是产品决定，不是能从几何推出的」。本批只把冲突量出来，**不替它选**。
