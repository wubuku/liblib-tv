## 为什么这批改了 `src/`

785–789 连续五批只做静态分析与运行时测量，**一条界面都没建**。目标已更新为
「复刻**用户体验**（可交互原型）」，本批开始真正动界面。

选的第一件事不是新功能，而是一个**已记账的缺陷**：batch 755 记了一条高严重度
读数 —— 画布列表行内菜单（**重命名 / 复制 / 删除**）被祖先容器的 `overflow`
裁掉，三项功能**对多数用户不可达**，且可达性取决于**画布数量**与**行在列表里
的位置**。

★ **为什么不直接照抄 755 的结论**：755 是**旧读数**。改 `src/` 之前必须先确认
缺陷**还在当前代码里** ⟹ 前置探针用**与后置完全相同**的测量代码跑两遍
（`pre` / `post`），差异只能来自 `src/`。

### C790-1：755 记的不可达**在当前代码里仍然成立** —— 4 个格子里 3 个

`重命名 / 复制 / 删除` 三项在 **2 张·首行、2 张·末行、6 张·末行** 三个格子里
**点不到**（命中 ✗、功能 ✗）。菜单越靠下，裁得越多。

### ★ C790-2：真裁剪者**只有 1 个**，我第一批的判断是错的

我原本以为「`position:absolute` 的菜单能逃出 `static` 列表的
`overflow-y-auto`」—— **错的**。规则是：祖先的 `overflow` 只裁**在菜单包含块
链上**的那些。

- `absolute` ⟹ 包含块 = 最靠近的定位祖先 = 行（`:244` `relative`）
  ⟹ 列表 `:238` 是 `static`、**不在**链上，**裁不到它**
  ⟹ 面板 `:173` 是 `absolute`、**在**链上 ⟹ ★ **真裁剪者只有 1 个**
- `fixed` ⟹ 包含块 = **视口** ⟹ 任何祖先都裁不到它 ⟹ **真裁剪者 0 个**

★ 第一批后置读数里「裁下边的 = 2」是**假阳性**（只算了几何、没算包含块），
探针因此改写，**两个阶段都用改写后的判据重跑**。

### C790-3 + C790-4

★ **6 张·首行是天然阳性对照**（755 的 R18）：没有它，「3/4 不可用」与

## 改了什么

只动一个文件 `src/components/CanvasTabDropdown.tsx`：

| 位置 | 改动 |
| --- | --- |
| 行菜单容器 | `absolute right-2 top-full` ⟹ **`fixed`** + 内联 `top`/`left`（打开时从按钮 rect 算出） |
| 空间不够 | `useLayoutEffect` 量到真高度后**翻到按钮上方** |
| 列表滚动 / 窗口缩放 | 菜单**关掉**（`fixed` 不再被列表带着走，不关就会和它的行脱钩） |
| 触发器 | 加 `data-canvas-row-more` / `aria-expanded` / `aria-haspopup` |
| 菜单与四项 | 加 `data-canvas-row-menu` / `data-canvas-row-menu-item` 与 `role="menu"` / `role="menuitem"` |

★ 为什么 `fixed` 可行：**运行时读过整条祖先链**（9 层），**0 个**带
`transform` / `filter` / `backdrop-filter` / `will-change` / `contain` /
`perspective` ⟹ 没有任何祖先会重新成为它的包含块。

★ **没有用 portal**：菜单仍然留在行里（只是定位改成 `fixed`）⟹ 外点关闭那套
`dropdownRef.contains()` 逻辑**一行都不用改**。
