# Batch 637 —— 636 的「store/DOM 分歧」从一个魔数扩到一个**用户能按下的开关**

## 零源站断言

源站时间轴在窄屏的默认高度与收起高度**未取证**。本批只主张 clone 的读数，
**不主张 176/124/88/182 里哪个该是源站的数**，也不发明新数。

## 一、636 打开的那扇门后面是整个收起态

636 发现分歧只发生在「高度**恰好等于** 182」这一个值上，根因是 `DirectorTimeline.tsx:843-845`：

```tsx
timelineCollapsed || timelineHeight === DIRECTOR_TIMELINE_DEFAULT_HEIGHT
  ? undefined                    // 不设行内样式
  : { height: timelineHeight }
```

**同一个三元的另一个分支更彻底**：`timelineCollapsed` 为真时，store 的高度
**不是被钳制、而是被完全忽略**。高度只由 CSS 决定，而收起态的 CSS 高度
（同文件 `:832-836`）是分族的：

| | ≤898 | ≥899 |
| --- | --- | --- |
| 收起态高度（纯 CSS） | **124** | **88** |
| 展开态「交给 CSS」时（仅 store=182） | **176** | **182** |

## 二、结论：store 被忽略，**不是被钳制**

| 宽度族 | store 写入 88 / 124 / 182 / 240 / 420，收起态实测高度 |
| --- | --- |
| **898** | 124 / 124 / 124 / 124 / 124（**5 个值同一个数**） |
| **899** | 88 / 88 / 88 / 88 / 88 |
| **1440** | 88 / 88 / 88 / 88 / 88 |

`every-store-value-renders-the-same-height-while-collapsed` —— 五个跨度 332px 的
store 值，收起后**渲染高度一动不动**。store 在这个状态下**没有发言权**。

## 三、分歧逐格等于 `store − 该族 CSS 默认`，**且无界**

| store 值 | 窄族 gap | 桌面族 gap |
| --- | --- | --- |
| 182（默认） | **58** | **94** |
| 240 | 116 | 152 |
| 420 | 296 | **332** |

636 那条 6px 在默认档是 `182−176`。而**收起态下这个 gap 是 `store − 族默认`**，
store 能写多高，gap 就有多大 —— 实测最大 **332px**。所以 636 挖到的不是
「一个 6px 的小瑕疵」，而是**一个随 store 值线性放大的分歧**，
倍数是 636 的 **9.67 倍**。

**不修**，理由与 636 同源、且更强：

1. **不发明 UX 数字**。124 这个数是 618 把窄屏工具条改成两行后推出来的
   （源码注释：`124 = 36（第一行）+ 36（第二行）+ 52（轨道条）`）—— 它有布局依据。
   182 也有（613 在源站实测钉住）。**该让 store 断点感知、还是让 CSS 回到 182、
   还是承认 store 在收起态无意义**，三条路都说得通，**这是产品决定**。
2. **源站未取证**。不能照想象的源站改。

本批把分歧**钉成逐格闭式**（`divergence == storeHeight − familyCssDefault`），
这样任何处置者拿到的是一条可代入的公式，而不是一句「store 和 UI 对不上」。

## 四、把「收起」这个状态轴与窗高轴交叉

631 扫过状态轴，但它的 `WINDOWS` 是 (w,h) **耦合对**，且量的是**视线轴的**
`viewportPanelsCollapsed`（侧栏）而不是时间轴的 `timelineCollapsed`，也从没钉住
「收起态实际渲染成多高」。本批补上：

- **收起从不埋得更多**（15 个 (宽度, 窗高) 对全部满足）
- **但它确实改变掩埋曲面**：15 对里 6 对变了，且变化很大 ——
  窗高 328 时 `13 → 5`、436 时 `14 → 7`、560 时 `4 → 1`
- **635 的二元律跨过状态轴依然成立**（按族分组后 26 组、ragged 0）
- **窄族在两种状态下都恒为 0**（20 格）
- 636 的 6px 在本批**原样存活**（898 展开 176、gap 6；899/1440 展开 182、gap 0）

## 五、判据自己踩的坑：**把两个不同的 CSS 问题塞进一张表**

第一版我只有一张 `CSS_EXPANDED[collapsed][narrow]` 表，于是：

1. 内层字典**写反了**（写成窄族收起 88、桌面 124），两条高度断言在**正确的数据**上变红；
2. 更深一层的错：我把「**CSS 默认值**」和「**实际渲染值**」当成一回事，于是
   `DEFAULT_STORE − CSS_EXPANDED[False][True]` 算出 `182 − 182 = 0`，
   后面拿它当分母直接 `ZeroDivisionError`。

**这两个是不同的问法**：展开态只有在 store=182 时才交给 CSS（窄族得 176），
其余值走行内高度原样渲染；收起态才永远由 CSS 决定（124/88）。
拆成 `CSS_COLLAPSED` 与 `CSS_AT_DEFAULT` 两张表之后，两条断言一次通过。

另一条同类错：扫了**五个** store 值，我却拿 182 去比每一格的 gap。判据必须
**逐格用该格自己的 store 值**。
