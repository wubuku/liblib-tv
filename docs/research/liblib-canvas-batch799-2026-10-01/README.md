# batch 799 —— 嵌套分组：`fitStoryboardGroupsToChildren` 的**写回坐标系**

> 结论先行：793–798 **六批**造的分组**全都没有父节点**，所以它们全都测不到这一类缺陷。
> 一旦组有父节点，组框写回时用的坐标系就是**错的**——外层位移被**重复计入**，
> 框与成员当场脱节，并在 react-flow 的尺寸反馈里**越跑越远**。
> 修法是一个纯函数内的坐标换算（绝对 → 相对父节点），不新增 API、不动 UI。

## 一、起点：793 注释里的那句话有一半是错的

793 加 `fitStoryboardGroupsToChildren` 时，在边界 2 写下：

> 组的顺序按「先外后内」，每轮都重新从当前列表算绝对位置，
> **这样嵌套时内层拿到的绝对位置已经是对的**。

799 把这句话拆成两半来验：

| 半句 | 结论 | 依据 |
| --- | --- | --- |
| 「内层**读**到的绝对位置是对的」 | **对** | `getAbsoluteNodePosition`（`canvasStore.ts:569`）沿 `parentId` 链逐层求和，一直没问题 |
| 「所以嵌套是对的」 | **错** | 错在**写回**：`nextPosition` 是 kids 的**绝对**包围盒，却被原样写进组的 `position` |

而 `position` 的语义（`:569` 同一处）恰恰是「**相对直接父节点**」。
**单层**组没有父节点 ⟹ 父的绝对位置是 `(0,0)` ⟹ 绝对值与相对值**恰好相等**
⟹ 两种写法**不可区分** ⟹ 793、794、795、796、797、798 六批造的组全都没有父节点。

★ 这不是「799 想到了别人没想到的边角」，而是**任何只造单层组的探针都必然测不到它**。
793 遗留里写着「★ **嵌套分组仍未验**」，799 就是来销这条账的。

## 二、前提复核：UI 今天仍然造不出嵌套

792 记过「嵌套组合没实现」。799 重新核到**实现**（不是接口声明）：

```ts
// canvasStore.ts:3499，groupSelectedNodes 内
const children = currentCanvas.nodes.filter(
  (node) => selectedIds.has(node.id)
    && node.type !== "storyboard-group"
    && !selectedGroupIds.has(node.parentId ?? ""),
);
```

`children` 的过滤器把 `storyboard-group` 排除掉 ⟹ **组不能成为新组的子节点**
⟹ 键盘 `G` 与右键菜单都造不出嵌套。

★ 后果：799 只能**直接往 store 注入**嵌套数据再触发一条会走 fit 的路径。
验收器 S14 把这条**显式钉成断言**——792 那条遗留**今天仍然成立**，
799 **没有**顺带实现「造得出来」。

## 三、真正的隐藏调用者：react-flow 的尺寸反馈

第一版探针的结论是「`setNodes` 不经过 fit」，这**对但不完整**。
`dbg799diag.py` 在注入后的**同一个 tick 内**立刻读，读数是 `width=10, measured=None`
（纯 `setNodes` 同步态）；**30ms 后**已经贴合且 `measured` 也被填上了 ⟹ 期间跑过 fit。

顺着找下去，调用者是 `routeReactFlowChanges`（`canvasStore.ts:3819`）：
`onNodesChange`（`page.tsx:610`）在**每一次** react-flow 变化时都会调它，
而 fit 会改 `style.width/height` ⟹ DOM 重排 ⟹ react-flow **重新测量** ⟹ 又发一次
`dimensions` change ⟹ 又调一次 fit。**这是一条正反馈**。

三条后果，全部实测到：

1. **注入后的首读就已经是「跑到不动点」的状态**，不是单趟。`nestedOrigin` 注入即
   `inner 680x180` / `outer 760x580`，与「先外后内」手算的第二趟结果**逐位吻合**
   （第一趟应是 `outer 280x580`，第二趟才吃到内层的最终尺寸 `760x580`）。
2. **★ 「先外后内 + 每轮重算」单趟是不够的**——外层永远看不到内层的最终尺寸。
   正确性**依赖**上面那条反馈。这条已写进源码注释的边界 3。
3. 嵌套缺陷一旦发作，正反馈把每轮坐标放大 ⟹ 尺寸爆炸，且**速率依赖时序**（见第六节）。

## 四、判据：两条与坐标系语义无关的不变量

`position` 该写绝对还是相对，是**实现细节**。所以判据不猜实现，只判**用户看得见的绝对几何**：

- **不变量 A（793 的核心承诺）**：任何**有父组**的节点，其**绝对**矩形必须被父组的
  **绝对**矩形包含。对**子组**同样成立——内层组也是外层的子节点。
- **不变量 B（贴合）**：任何**有直接子节点**的组，其**绝对**框 =
  直接子节点绝对包围盒 ⊕ `GROUP_PADDING`。

两条都用绝对坐标表述 ⟹ 无论 `position` 存的是绝对还是相对都判得出来 ⟹
「把实现改对」和「把判据写死成某句代码」都躲不过去。

★ `GROUP_PADDING` **没有写死**：汇编器与验收器各自用 16 个候选
（`0/4/8/10/12/16/20/24/28/32/36/40/44/48/56/64`）独立反推，**必须唯一**。
两边都得到 **40**——顺带**独立验证了 797 定下的那个常量**。

## 五、四条臂：外层组在原点 vs 外层组有偏移

只用**键盘方向键**（795 加的、已验过的能力）触发 fit，**不用鼠标拖**。
理由：一旦发散，节点会飞出视口 ⟹ 取到屏幕外坐标、拖动根本没发生 ⟹ 整条臂变成
**空读数**（793 第一版踩过）。键盘 nudge 不依赖节点在视口内。

| 臂 | 数据 | 步数 | 角色 |
| --- | --- | --- | --- |
| 单层 nudge | 组无父节点 | 2 | 阳性对照：单层必须全对 |
| 嵌套·外层在原点 | `outer@(0,0)` | 2 | 阴性对照：`parentAbs==0`，新旧写法**等价** |
| 嵌套·外层有偏移（一次） | `outer@(200,150)` | 1 | 首次分歧定位 |
| 嵌套·外层有偏移（两次） | `outer@(200,150)` | 2 | 分歧累积 |

★ 阴性对照的作用要说准：`nestedOrigin` 全绿**证明不了修复有效**（父绝对位置为 0 时
两种写法输出完全相同），它只证明**探针和判据没坏**。所以汇编器 P2 / 验收器 S2
额外断言该臂的 `g-outer` 相对位置**确实是 `(0,0)`**，把「阴性」钉死；
阴性对照 N4 专门把它挪到 `(200,150)`，S2 必须翻红。

## 六、读数

### 缺陷（pre）

`nestedOffsetOnce` 注入后的**首读**（已经含自动多趟）：

```
g-inner rel(8640,22640) abs(9040,23740) 680x180
g-outer rel(200,550)   abs(200,550)   9360x22860
n-m1 abs(9080,23780)  n-m2 abs(9480,23780)  n-loose abs(240,590)
```

内层被推到九千多像素外，成员在框**外面**——正是 793 要消灭的那个症状
（「store 说它属于这个组，屏幕说它不在框里」）在嵌套下**原样复现**。

诊断探针还读到一条**自相矛盾**的读数：同一时刻
`g-outer` 的 `style.width=1160` 而 `measured.width=960`。
fit 写进去的 style 已经触发了 DOM 重排，react-flow 量到的是**另一个尺寸**——
正是那条正反馈的现场证据。修复后这个矛盾消失（两者都是 760）。

### 修复（post）

同一份探针，同一条注入路径：

```
g-inner rel(40,40) abs(240,190) 680x180
g-outer rel(200,150) abs(200,150) 760x580
n-m1 abs(280,230)   n-m2 abs(680,230)   n-loose abs(240,590)
```

方向键按一次后：`g-inner rel(41,40) abs(241,190) 679x180`——
成员右移 1 像素 ⟹ 内层框跟着左扩 1 像素（变窄 1），**逐位自洽**。

### 独立重算

汇编器与验收器**各自独立**实现了一遍 fit 模拟（相对化 + 先外后内 + 多趟到不动点），
**不 import 任何 `src/` 代码**，只吃 raw 里的 `position/parentId/width/height`：

- 模拟器的输出与 post 实测**逐位相同**（编 14/14、验 15/15）。
- **同一个模拟器**把 `relativize` 关掉，就能解释 pre 的**稳定态**：
  `origin` 臂在第 **2** 趟起命中，而嵌套层数恰好也是 **2** ⟹ 收敛趟数 = 嵌套层数，
  这条是**被反推出来的**，不是写死的。
- 同一模拟器对 pre 的**偏移臂**一趟都命中不了 ⟹ 证明模拟不是橡皮章。

## 七、★ 如实记账：发散的**中间态**不可逐位复刻

同一份 pre 代码、同一个探针，**两次**运行，t=700 的读数不同：

| 运行 | `g-inner` 相对位置 |
| --- | --- |
| 第一次 | `(8840,23190)` |
| 第二次 | `(9040,23740)` |

⟹ 反馈趟数取决于 DOM 测量回调的**时序**，**不是**确定函数。
所以验收器 S11 **只判两件事**，不硬凑逐位吻合：

1. 相对化的模拟对 pre 偏移臂**一趟都不命中**（阴性对照成立）；
2. 旧实现的模拟在第 1–40 趟**每一趟都越界**（**性质**一致）。

★ 「发散速率不稳定」本身不影响结论：稳定态、越界性质、以及修复后的收敛都已被逐位钉住。

## 八、修复

只改 `fitStoryboardGroupsToChildren` 内部，三处 1↔1 行替换 + 一行声明：

```ts
const parentNode = group.parentId ? byId.get(group.parentId) : undefined;
const parentAbs = parentNode ? getAbsoluteNodePosition(parentNode, byId) : { x: 0, y: 0 };
// ...
near(live.position.x + parentAbs.x, nextPosition.x) &&      // no-op 判定
near(live.position.y + parentAbs.y, nextPosition.y) &&
// ...
position: { x: nextPosition.x - parentAbs.x, y: nextPosition.y - parentAbs.y },  // 写回
```

- `nextPosition` **保持绝对语义**不动，只有在**写进组自己**时才减父位置；
  子节点重基（`absolute.x - nextPosition.x`）**一行没改**（验收器 S13 守着）。
- no-op 判定那两处**必须**一起改，否则「已经贴合」会判错、每趟白白重建一遍组与子节点
  （这正是 793 引入 `EPS` 要避免的事）。验收器 N2 专门只打掉这一半。
- 顺带**更正 793 的注释**：原文「这样嵌套时内层拿到的绝对位置已经是对的」被 799 证伪，
  改成「读是对的、写是错的」，并补上边界 3（单趟不足，靠反馈补齐）。

## 十、结果与边界

- 断言 **14 条 / 0 失败**（汇编器）；验收 **15/15**、阴性对照 **6/6**，
  阴性后 `canvasStore.ts` 与四份 raw **字节级复原**（sha256 核对）。
- `npm run typecheck` rc=0；`npm run build` 全绿。
- **未与源站对照**（源站需登录）⟹「嵌套组应当如何表现」是工程判断，不是源站实测值。
- **792 的「嵌套组合没实现」今天仍然成立**：799 只修「已有嵌套数据时几何是否正确」，
  **没有**让 UI 造得出嵌套。这两件事是分开的，别把 799 读成后者也做了。
- ★ **重新评估的条件**：若将来让 `groupSelectedNodes` 允许把组收进新组，
  那么「外层位移被重复计入」会第一次出现在**用户可达**的路径上，
  本批的修复仍适用，但**必须**补一条「从 UI 造出嵌套」的臂——现在的证据全部来自注入。
- 797 记的「其余 **14 处未普查写点」仍未普查；本批的发现说明那一栏**可能还藏着
  同类的坐标系错误**，优先级应当提高。
- 793 遗留的「空组要不要收缩/弱化」（757 待拍板 ②）**仍未碰**：793 边界 1「0 成员的组不动」
  在本批注入的两条臂里都没有空组，未受影响也未验证。
