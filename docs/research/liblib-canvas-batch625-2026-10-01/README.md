# Batch 625 —— 把 624 的教训变成尺子：量遍 rail 里每一个浮层的层叠

日期：2026-10-01 · 零源站断言

624 最值钱的副产物不是修好了 AI 导入模态，而是证明了**一件事**：模态的 `z-[290]` 写得再高也没用，因为它被关在资源栏的 `absolute z-30` 上下文里；而且因为当时那个视口恰好不重叠，普查是绿的。**几何不重叠 ≠ 层叠没被关住。**

这把尺子本批量到 rail 里**每一个**浮层上。

## 零源站断言

`probe616` 复跑：源站仍 1600×1000、导演台被他人关闭。**特别地**：本批不裁定「源站的 rail 菜单在多宽下该不该盖住时间线」—— 那需要源站读数。本批只主张 clone 自己的一件事：**用户看得见的控件必须点得着**。

## 一、量了什么

rail 里五个浮层，各自声明的 z 与它们实际竞争的上下文：

| 浮层 | 代码里写的 z | 最近祖先层叠上下文 | **有效 z** |
| --- | --- | --- | --- |
| `panorama-flyout` | z-40 | `div[data-director-icon-rail]` z-30 | **30** |
| `aspect-flyout` | z-40 | 同上 | **30** |
| `add-character-flyout` | z-40 | 同上 | **30** |
| `geometry-submenu` | z-50 | 同上 | **30** |
| `crowd-dialog` | z-50 | 同上 | **30** |

五个的 z **全部**被关在资源栏的上下文里，有效值都是 30，而时间线是 z-40。也就是说：**只要几何上够得着，它们就一定被时间线盖住。**

每个浮层量两半：

1. **结构半**：最近祖先层叠上下文的 z（z-index 真正参与比较的地方）；
2. **几何半**：把浮层内每个控件按中心点归类，看哪些**落在时间线矩形内**，再对这些控件做命中测试。

两半都必要。结构半说的是「z 被关住了」，几何半说的是「以及它关住了哪一个控件」。只断言结构半是对代码形状的评论；只断言几何半则会在当前视口恰好不重叠时失明 —— 那正是让 624 的 bug 躲过 619 的那个洞。

## 二、探针自己踩的三个坑

按惯例记录，因为**每一个都差点变成假结论**：

1. **命中判据测错了控件**：第一版测的是浮层里「最后一个可见控件」。于是 1280×720 的 aspect-flyout 报出「与时间线重叠」的同时又报「仍在自己上面」—— 这**不能**证明时间线没盖住它，因为那个控件根本不在重叠带里。改成先筛出中心落在时间线矩形内的控件，只测那些。
2. **把 `kind: "submenu"` 的入口当成顶层 rail 入口**：`群众 (3x3)` 与 `几何模型` 并不渲染成 rail 入口，它们是**添加角色 flyout 内部的一行**（`[data-director-character-option=...]`）。按 rail 入口去点，全部超时。
3. **哨兵字符串直接喂给 `locator()`**：第一版用 `"@geometry@"` 这类哨兵，`page.locator()` 收到后报 `Unsupported token`。

## 三、结果：结构半全塌，几何半抓到真实伤亡

**结构半**（五个浮层全被困，无一例外）：

| 浮层 | 写的 z | 最近祖先层叠上下文 | 有效 z |
| --- | --- | --- | --- |
| `panorama-flyout` | z-40 | `div[data-director-icon-rail]` z-30 | **30** |
| `aspect-flyout` | z-40 | 同上 | **30** |
| `add-character-flyout` | z-40 | 同上 | **30** |
| `geometry-submenu` | z-50 | **`div[data-director-character-flyout]` z-40** | **30** |
| `crowd-dialog` | z-50 | `div[data-director-icon-rail]` z-30 | **30** |

`geometry-submenu` 最惨：它**双重嵌套** —— 既在资源栏里，又在添加角色 flyout 里，于是有效 z 是 30 而不是 50。

**几何半**（落在时间线矩形内、被时间线抢走的控件）：

| 视口 | geometry-submenu | aspect-flyout |
| --- | --- | --- |
| 1920×1150 | 0 | 0 |
| 1440×900 | **2** | 0 |
| 1280×720 | **5** | 0 |
| 1920×844 | **3** | 0 |
| 1100×700 | **6** | **1** |

被埋的控件是实打实的活控件：立方体、球体、圆柱体、环状体、圆锥、添加空对象、棱锥、上传文件、9:16。命中的元素是 `总时长`、`绘制轨迹`、`下一关键帧`、`拖动调整时间轴高度`、`角色01 · 陈默` —— 全是时间线自己的东西。

## 四、改法：portal 出去，z 取 160

照 624 对 AI 导入模态的同一手法，把三个顶层 flyout portal 到 `document.body`。**几何模型子菜单随父 flyout 一起出去**（它是嵌套在添加角色 flyout 里的），这一并解决了最坏的那个。`crowd-dialog` 本轮五个视口 0 伤亡，记为候选。

**两个否掉的方案**（都写下来，免得下次重踩）：

- **抬 rail 的 z**：rail 是 48px 宽通栏贴左，抬到 45 之后它会反过来盖住时间线左侧的播放控件（总时长、时间单位那几枚）。拿三个浮层换一排活控件，不做。
- **把 rail 改成 `z-auto`**（让它不创建上下文、让 flyout 的 z-40 直接与时间线的 z-40 比）：那样 rail 与时间线的胜负就交给 DOM 顺序，比一个显式的 z 更脆弱。

z 取 **160** 的理由：高于工作区的 z-100（时间线就在它里面）与场景树右键菜单的 z-120，低于视口底部条 z-200 与 AI 导入模态 z-290。

**定位必须自己算**：portal 之后 CSS 的 `absolute left-[calc(100%+8px)] top-0` 失效了（那个包含块是 rail 里的 `div.relative`）。所以量 anchor 的视口坐标自己注入，并且**订阅 resize 重算** —— 原实现是 CSS 锚定、窗口一变就跟着重排，只量一次的话 resize 会让浮层停在旧位置。

坐标口径用实测校准：`left = anchor.left + anchor.width + 8`、`top = anchor.top`。实测 x=48 与之吻合 —— rail 48 宽居中 32px 按钮，anchor 在 x=8，8+32+8=48。

**几何不变的承诺**：portal 改的只是层叠，位置由同一套坐标重算，所以改动前后五个盒子的 `[x, y, w, h]` 必须逐格相同。这一点写进验收。

## 五、本批最值得记的一课：修复本身又造出了同一个陷阱

第一次实现把 flyout 包在一个 `<div style={{position:"fixed", left, top}}>` 里，**没给 z-index**。结果：

- flyout 的 7 枚按钮在**所有视口**（连 1920×1150 这种毫无重叠的地方）都命中场景树的内容；
- Playwright 拒绝点击「几何模型」「群众 (3x3)」，因为元素被遮挡 → 10 个格子全部超时。

原因不是玄学：**`position: fixed` 会创建层叠上下文**（不只是定位元素才创建）。所以那个 z-auto 的包裹层把 flyout 的 `z-160` 关在了 effective z-auto（0），**落在工作区 z-100 之下** —— 于是在修「子元素 z 被父级上下文关住」的同时，我在上一层制造了同一个 bug。这是这个陷阱的**第四次**出现，也是**第一次由我自己引入**。

| 批次 | 陷阱 | 抬的是 |
| --- | --- | --- |
| 611 | section 的 `backdrop-filter` 造出上下文 | section |
| 621 | 父级 flex item 的 `z-30` | 父级 |
| 624 | 组件被嵌在资源栏内 | portal 出去 |
| **625（修复过程）** | **`position: fixed` 包裹层 z-auto** | **包裹层自己带 z** |

诊断它的关键是**不满足于「z 是 160」这个读数**：160 确实在元素上，但它所在的那个上下文是 z-auto。要问的从来不是「这个元素的 z 是多少」，而是「**它最近的那个创建层叠上下文的祖先，z 是多少**」。

## 六、定位过程里我自己犯的两次错

1. **探针找错了元素**：在全文档搜文本 `9:16`，抓到的是**时间线**里那枚（x=629，而 flyout 只占 x 48..280），于是得出了「命中自己」的假结论，差点让我以为 portal 已经好了。改成只枚举 `[data-director-aspect-flyout]` 内部的控件。
2. **把 `kind: "submenu"` 的入口当成顶层 rail 入口**：`群众 (3x3)` 与 `几何模型` 并不渲染成 rail 入口，它们是**添加角色 flyout 内部的一行**（`[data-director-character-option=...]`）。按 rail 入口去点，全部超时。

两条都属于「**测试自身写错要当信号读**」：第一条的假阳性差点掩盖真缺陷，第二条的假失败差点让我以为改动坏了功能。

## 七、我自己把源文件压成了一行（以及怎么救回来的）

给群众弹窗补 portal 时，我用一段 Python 脚本找闭合括号并回写文件。脚本里用了 `splitlines()` 却**漏了 `keepends=True`**，于是回写时换行全丢 —— 603 行的文件被压成**一行**，`tsc` 随即报 `has no exported member 'DirectorIconRail'`（整个模块解析失败）。

处理方式：

1. 先备份压平后的内容到 `/tmp`；
2. 判断语法是否还成立（`export function` 是否完好、文件尾是否完整）—— 成立就说明只是排版坏了；
3. 项目里**没有 prettier** 可用；
4. 于是 `git checkout --` 回到 HEAD，用 Edit 工具**逐处重做**全部改动，而不是在压平的文本上抢救。

重做时改用 Edit 而不是脚本，正是因为脚本正是肇因。代价是这一轮多花了些时间；收益是最终文件 721 行、行尾完整、`tsc` 0 错、`eslint` 0 error（还顺手补掉一条 hook 依赖告警）。

记这一条是因为它和前面那些「测试写错」性质相同：**工具（这次是改写脚本）出错时，症状往往出现在别处**（表现为 tsc 报一个看似无关的「没有导出成员」），而正确反应是先判断「是排版坏了还是逻辑坏了」，再决定抢救还是重做 —— 而不是对着报错硬改。

## 八、验收

- 五个浮层 × 五个视口**全部能打开**（1920×1150 / 1440×900 / 1280×720 / 1920×844 / 1100×700，刻意含矮视口：时间线固定 182px 贴底，视口越矮它占的比例越大，越容易被够到）。
- **结构**：没有浮层的有效 z 低于它自己写的数。
- **几何**：落在时间线带内的控件全部命中自己。
- **非空断言**：每个浮层确实带控件（否则前两条是空转），并逐格记录「有多少控件落进时间线带」写进 audit。
- **几何不变**：portal 只该改层叠。改动前后五个盒子的 `[x, y, w, h]` 逐格相同（基线取自改动前的实测），位移哪怕一个像素都算失败。

## 不声称

- **源站任何事**，包括源站 rail 菜单的 z 与它们在多宽下是否该盖住时间线。
- **「某浮层在某视口下没有控件落进时间线带」不等于它没问题**。那只说明该视口下没撞上 —— 正是 624 踩过的那个洞，本批把它写进 audit 而不是让它变成通过。
- 本批只查 rail 内的浮层。相机预设面板与轨迹菜单在时间轴里，未查。
- **`crowd-dialog` 的几何未单独量过改动前后**：它的 portal 与三个 flyout 同一套机制、同一 z，但基线表里它的盒子同样取自改动前实测，`the-portal-moved-nothing` 一并覆盖了它（五个浮层都在那张表里）。

回归 12 个相关验收器全绿：624(10，覆盖 rail 浮层态本身) / 623(24) / 622(47) / 621(40) / 620(57) / 619(89) / 618(42) / 617(30) / 613(55) / 611(49) / 590(85) / 96。其中 613(55) 钉的正是资源栏与源站实测的 48 宽、场景树 48/233 几何 —— 也就是说本批**没有动**那套源站实测关系（抬 rail z 的方案被否掉正是为此）。

### 迁移一处历史合同：590 的后代链定位

590 有两处用 `rail.locator("[data-director-character-option='…']")` 靠 **DOM 后代链**从资源栏摸到浮层内的选项。portal 之后该选项不再是 rail 的后代，这条链断了，590 因此超时。

按约定**迁移定位器、不删被测行为**：改成 `page.locator("[data-director-character-option='…']")`。同一个文件上面本来就有一处用的是全局写法，两处原本不一致，迁移后统一。被测行为（点 群众 (3x3) 打开弹窗、点 几何模型 展开子菜单、flyout 保持打开）**一字未改**，改后 590 仍是 85 checks / 0 diagnostics。

> 顺带记一条辨析：同文件里 `rail.locator("[data-director-rail-entry='…']")` **没有**受影响 —— 那些是 rail 自己的按钮，portal 的只是浮层，DOM 祖先关系没变。分不清这两种「rail.locator」就会把没坏的地方也一起改掉。
