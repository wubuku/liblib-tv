# Batch 371 — 把 liblib 的 runner 三件套对齐到 frameos；顺带抓到一个**本线早已修过、那边还留着**的 bug

日期：2026-10-02
范围：`scripts/run-frameos-verifiers.sh`（**工具批，产品代码零改动**）

## 起因

Batch 370 给 liblib runner 加了运行中健康监测，顺手查了 frameos runner，
发现它缺的不止一样：

| 能力 | liblib runner | frameos runner（修前） |
|---|---|---|
| 前置探活（挂了别刷屏） | 有（batch 361） | **无** |
| 运行中健康监测 | 有（batch 370） | **无** |
| 自身指纹核对（运行中被改就 exit 3） | 有（batch 361） | **无** |
| **汇总与清单同源** | 有（修过） | **无 —— 而且是活的 bug** |

动手前先确认前提：此刻无人跑 frameos 验证器，文件也没被任何 session 改动。
（上一批就是因为「别人可能正在用」而只记录不动；这次窗口是干净的。）

## 那个 bug：汇总说 1 个失败，清单列了 2 个

不是读代码看出来的，是**用两个临时探针跑出来的**：
9001 永远失败（代表真回归），9002 首败次过（代表偶发）。修前输出：

```text
RETRY FAIL batch9001
RETRY PASS batch9002          ← 它已经通过了
----
frameos verifiers: 1 passed, 1 failed (after retry)
failed batches: 9001 9002     ← 清单里还留着 9002
```

根因：重试循环只重算 `fail` 计数（`fail=$retried_fail`），
`failed_list` **从头到尾没更新过**。

同样的 bug 在 liblib runner 上**早就修过**，那边的注释写着
「汇总与清单必须同源：清单只放重试后仍红的」——还记着当年踩的是
「汇总说 19 failed，清单却列了 33 个」。这边一直漏着。

**同一类缺陷隔着一份代码复制到另一条线，只修了一份。**
这本身是个提醒：修复不会自己传播。

## 计数规则只有一条

**首轮 +1；重试通过 −1；重试仍败不动。**

我第一版改写时在 `RETRY FAIL` 分支也写了 `fail--`，结果 `fail` 恒为 0，
汇总会说「0 failed」而清单非空——**又造出一个新的「汇总与清单不同源」**。
自己刚修的 bug，换个写法就又犯了一遍。所以这条规则也写进了断言：
**汇总里的数字必须等于清单里的个数**，三个场景都要成立。

## 双向自检，以及它教给我的两件事

`probe_batch371_runner_alignment.py`（16 项）覆盖：前置探活（死端口 exit 2）、
运行中监测（假服务器先 200 后 503）、健康时不告警、以及上面那条汇总/清单一致性。
两个 runner 各验一遍。

### 教训 1：自检红了，先归因再动手

第一版 11/14，红的三条**全是我测试设计错，不是 runner 的问题**：

1. 「全过」场景里我放进了 9002——而 9002 是**设计上首轮就失败**的偶发探针；
2. 健康监测用了一个**秒完的平凡探针** + `FAIL_AFTER=6`，假服务器只被探针打到
   **2 次**，整轮跑完它都还健康着，告警当然不响。

> 自检因为「测试自己写错」而红，对被测代码什么也没说明，却极易被误读成
> 「代码有缺陷」而去改本来正常的逻辑。这一坑与 batch 367 那次
> 「变异被 `ValueError` 抓住」同族：**红的位置要先归因，再动手。**

修法：用**真门禁**（够慢，探针能采到样）+ 阈值压到 1（第 1 个请求给前置探活返
200，之后立刻 503，正好是「开跑前活着、跑起来就挂」）。并加一条
`prober-actually-sampled`——**断言探针真的采到过样**，否则「没告警」只是因为
没机会看。

### 教训 2：翻转阈值不该是可调参数

阈值做成环境变量后，我第一反应就是「调大一点」，而调大就调到了「整轮都没坏过」
的状态，于是看起来像告警失灵。已改成固定值并写明理由：**阈值可调，就会有人
调到「测不出东西」而误以为被测代码有问题。**
