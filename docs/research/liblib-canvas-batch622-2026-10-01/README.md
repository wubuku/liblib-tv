## 一、900–1043px 那一档：候选撤销（不改代码）

`/tmp/dbg622a.py` 在 899/900/960/1024/1043/1100/1280 逐宽度普查，并把控制簇里 14 枚控件**逐枚滚到窗口中央再做命中测试**：

结论很干脆：`reachable_but_blocked=0`、`never_in_window=0` 在**每个宽度**都成立。那一档的「隐藏」是**纯滚动可达** —— 而 ≥900 的单行布局（右格浮在右端 + 左格横向滚动）正是 batch 593/596 的**源站实测**设计。滚动可达是它的正常形态，不是缺陷。

所以把断点提到 1043 **不修复任何东西**，只会拿一份没有源站读数支撑的 clone 侧重排，去替换一套源站实测过的桌面布局。**候选撤销，不是推迟。** 本批把那组读数转写成合同（每档断言 14 枚全部可滚动可达 + 普查零 covered），让「它不是缺陷」以后有人复查时不必重新推一遍。

> 附带一条：`align` 的 `AGREE` 那一栏在这次普查里第一次显出不对（见下），是普查顺带捞出来的，不是本条候选找出来的。

## 二、真缺陷：恰好 899px，场景树与属性列整棵 inert

普查在 vw=899 报出 **22 枚 covered**，而 900 起归零、898 及以下也归零（移动端抽屉本就收在屏外）。只有一个宽度不对。

`/tmp/dbg622b.py` 把两侧判定并排读出来：

```
vw     JS(≤899)  CSS(<899)  一致?   场景树 box                 inert
897      True      True      ✓      [-220, 88, 220, 812]        True   ← 屏外，正确
898      True      True      ✓      [-220, 88, 220, 812]        True   ← 屏外，正确
899      True      False     ✗      [   0, 88, 220, 812]        True   ← 在屏上，却 inert
900     False     False      ✓      （桌面，无 inert 包裹）      —
```

根因是**移动端断点差了一个像素**：

| | 查询 | 移动端成立的宽度 |
| --- | --- | --- |
| JS | `matchMedia("(max-width: 899px)")` | ≤ 899 |
| CSS | Tailwind `max-[899px]` → `@media (width < 899px)` | ≤ 898 |

于是 vw=899 上 JS 认定在手机上、CSS 认定在桌面上。场景树与属性列被**按桌面布局可见地**渲染在 `[0,88]` 与 `[618,52]`，然后因为 `treeMobileInactive` / `inspectorMobileInactive` 派生自那个 JS 标志，两列被整棵加上 `inert` → **全部控件在屏幕上、却一个都点不动**。这正是本项目反复追的那类「看起来能点、其实点不动」的缺陷，而且是 617 普查的 `covered` 分类天生能抓到的。

**改法：把 JS 对齐到 CSS**（`max-width: 898px`），而不是反过来改 CSS。理由是 898/899 这个落点是全代码库 `max-[899px]` 的既有约定，621 已把它记为「记录不修」（改它会一次性移动每一条同类规则）；让 JS 单独对齐是唯一零外溢的选择。改后 ≤898 抽屉依旧正确 inert 且在屏外，≥900 桌面行为**一字未动**，只有 899 这一档从「可见的死控件」变回「正常桌面」。

## 验收（40 项）

- **断点一侧（897/898/899/900/901 各 8 项）**：JS 与 CSS 判定一致；视口分类符合预期；两条**行为不变量**——「在屏上就必须可交互，停在屏外就必须 inert」——对场景树与属性列各自成立（用 `aside[aria-label="场景对象"]` 与 `[data-director-inspector]` 两个**不依赖 inert 属性**的地标）；普查零 covered；逐宽度无页面/控制台错误。
- **撤销候选一侧（900/960/1024/1043/1100/1280 各 2 项）**：14 枚控制簇控件全部可滚动可达；隐藏部分只被裁不被埋。

### 验收脚本自己踩的三个坑（都记在案）

1. **硬编码查询串让测试说谎**：第一版把 `matchMedia('(max-width: 899px)')` 写死在断言里。修复后源码已是 898，测试却还在量一个**源码里已不存在的字面量**，于是在 899 报出一条运行中的 app 早已不存在的分歧（38/40）。改成从源码解析出实际使用的查询串再送进页面求值。
2. **解析时匹配到了注释**：第二版加了正则，却先撞上另一个坑 —— 我在源码注释里写的那句 `matchMedia("(max-width: 899px)")`（解释旧值的那句）被正则先匹配到，于是仍在量注释。加了「先剥注释再解析」。
3. **地标依赖了被测属性**：第三版用 `closest('[inert]')` 找两列，而该属性只在窄屏存在，于是桌面档（900/901）返回 `null`、报「不在屏上」（34/42）。改用与 `inert` 无关的 `aria-label` / `data-*` 地标。

三条都属于「**测试自身写错要当信号读**」：第一、二条的假红差点被误当成修复无效，第三条的假红差点被误当成新缺陷。

## 不声称

- **源站任何事** —— 本批零源站读数。
- **898/899 这个落点本身是对的**。它只是全代码库既有约定，621 记为不修；本批只消除了 JS 与 CSS 对它的**分歧**，没有移动断点。
- **900–1043 那一档被改进了**。它没被碰，而且测据说明那里没有可改进的东西。
- 画布页 `app/page.tsx` 里另有一处 `innerWidth <= 768`（`canvas-2` 的初始视口取值）。它是**初值启发式**、不参与响应式渲染切换，本批**只记录不处理**，未构造用例证明它与 CSS 是否有同类错位。
- **屏外却没 inert 的属性列**。≤898 时场景树抽屉停在 `[-220,...]` 且 inert，属性列停在 `[vw,88,...]`（屏外右侧）却**不** inert。这是本批之前就有的不对称、不是本批引入、也没被本批修掉：屏外元素点不到，普查在该宽度也干净，理论上唯一受影响的表面是**键盘焦点**可能落进一个看不见的面板。验收里因此只断言「**在屏上就不能 inert**」这一个方向（899 真正坏掉的方向），把反向情形记进 `offscreen-not-inert` 字段而不是变成一条代码从未承诺过的通过/失败规则。
