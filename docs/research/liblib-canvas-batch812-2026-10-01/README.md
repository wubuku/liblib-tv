# batch 812 —— 连点两下同一个操作：两个动作**防重**、三个**不防重**、两个塞**空记录**

> 811 在验撤销时顺带发现：7 个派生动作里**有两个带防重守卫**、**五个没有**。
> 809 / 811 都只把它们当作「为什么要设阳性对照」的引用，**它们本身的用户可见
> 行为从来没量过**。用户会真的连点两下，所以本批去量。
>
> **三态，一条臂一种。** 而其中一条有**真实的后果**：首帧芯片连点两下之后，
> **一次 `Cmd+Z` 撤不掉刚建出来的首帧图，要按两次**。

## 一、三层读数：UI 层 / store 层 / 后果层

| 动作 | UI 第二下 | 入口在第一次之后 | store 第二下 | 结局 |
| --- | --- | --- | --- | --- |
| `createFirstFrameReference` | **点得到** | 芯片还在 | 不建 · **历史 +1** | ★ **空记录** |
| `createFirstLastFrameReference` | **点得到** | 芯片还在 | 不建 · **历史 +1** | ★ **空记录** |
| `addDerivedNode`（逐帧拉片） | **点不动** | 拉片节点还在、按钮还在 | **又建了一遍** · 历史 +1 | 完全没拦 |
| `createVideoContinuation` | **点不动** | 芯片还在、工具栏没了 | **又建了一遍** · 历史 +1 | 完全没拦 |
| `createSubtitleErase` | **点不动** | 工具栏没了 | 不建 · **历史不变** | **被守卫拦住** |
| `createAudioSplit` | **点不动** | 工具栏没了 | **又建了一遍** · 历史 +1 | 完全没拦 |
| `completeShotBreakdown` | **点不动（按钮变 `disabled`、文案改成「拉片完成」）** | 按钮仍在但禁用 | 不建 · **历史不变** | **被守卫拦住** |

（两轮逐位相同。）

★ **为什么 UI 层几乎全是「点不动」**：第一次触发之后**选区迁到了新建的节点上**
⟹ 工具栏与芯片属于**原来那个源节点**，自然不在了。
唯一两个例外就是**首帧芯片** —— 它属于源节点且不迁移，所以**点得到**。

★ 这正是 806 那条纪律的回报：**条件渲染的入口会消失或被禁用**。
我第一版把「点不动」当成 `FAILED`，于是 7 条臂里 **5 条**报了
`RuntimeError`／`TimeoutError` ⟹ **前提不满足的臂必须显式作废、不能当成故障**
（802 起立的规矩）。改成「点不动是一种读数」之后，全部 14 条臂都产出了读数。

★ **store 层是必要的补充**：UI 层已经把入口禁掉了，
那两个守卫就**永远观察不到** ⟹ 只能绕开 UI 直接再调一次。
结果正是它们自己的设计：`createSubtitleErase` 的**指纹去重**（`:1970`）
与 `completeShotBreakdown` 的「已有结果就 return」（`:3188`）**都真的拦住了**，
而且**连历史都不动**。

## 二、★ 唯一一条有真实后果的读数：空记录

两个首帧芯片的第二下**不建任何东西**，却**往撤销栈里塞了一条记录**
（`pushHistory` 是无条件调的）。后果：

| 时刻 | 节点 | 边 | 历史 |
| --- | --- | --- | --- |
| 动作前 | 10 | 8 | 0 |
| 第一下（建 1 个 image） | 11 | 9 | 1 |
| 第二下（**什么都没建**） | 11 | 9 | **2** |
| **按一次 `Cmd+Z`** | **11** | 9 | 1 |
| 按第二次 `Cmd+Z` | 10 | 8 | 0 |

⟹ ★ **一次 `Cmd+Z` 撤不掉那个新建的 image 节点**，它只是把那条空记录弹掉了。

★ 这和 811 的「撤销粒度 = 1 个动作 = 1 次 `Cmd+Z`」**不矛盾、但有边界**：
811 量的是**单次**触发，812 量的是**连点两下**。写在一起才是完整说法。

## 三、★ 我自己预设错了方向

S3 我第一版只写了**两种**结局（被拦住 / 完全没拦），并断言「不允许半截状态」。
结果基线直接判红 —— 因为真实发生的是「**没建东西、但历史 +1**」，
而我防的是「**建了东西、但历史没 +1**」。

⟹ ★ **我预设的那半截状态方向反了。** 判据改成**三态并报出是哪一态**，
这比两态更接近事实，也比我原来的断言更诚实。

## 四、验收结果

主检查 **7/7**，阴性对照 **6/6**，raw 的 sha256 未变（对照全是**纯内存**变异）。

| 阴性对照 | 打在哪个字段上 | 翻红 |
| --- | --- | --- |
| N1 | ★ 伪造「第一下压根没发生」 | S1 |
| N2 | ★ 伪造「store 第二下没有确定读数」 | S4b |
| N3 | 伪造「UI 第二下的结局是第三种」 | S4 |
| N4 | ★ 伪造「入口状态**读不到**」 | S2 |
| N5 | ★ 伪造「一次 `Cmd+Z` 就撤掉了」 | S6 |
| N6 | 反向对照：只动 `secs` 这个无关字段 | 无 |

★ **N1 是本批最重要的一条**：在「第一下压根没发生」的情况下，
S3 会**假绿**（没建东西、也没进历史 = 「被守卫拦住」）。

★ **N2 打的正是第一版的处境**：把「点不动」当 `FAILED` 时，store 层读数缺失。

★ **N4 有一个反直觉的点**：它**不能**打「读成 false」—— `false` 仍然是
**有效读数**，而 S2 只要求「读到了」⟹ 第一版我把对照打成「全改成 false」，
结果**打不中**。改成「读不到」才命中。★ 阴性对照本身也要被判据反推一遍。

## 五、探针返工一处（差点让三分之二的臂作废）

| # | 现象 | 真因 |
| --- | --- | --- |
| 序1 | 7 条臂里 5 条报 `RuntimeError`／`TimeoutError`，整批只剩 2 条读数 | ★ 我把「第二次点不动」当成了**故障**。真因是**入口在第一次触发后消失或被禁用** —— 这**就是答案**。第一版 `failed` 分支把它记成 `FAILED`，等于**把读数当成了 bug** |

★ 修法：把第二下的触发包进 `try`，失败**分类成读数**
（`clicked` / `★ 点不动`）而不是异常；再补一层 store 调用，
因为 UI 层的禁用会让守卫**永远观察不到**。

## 六、不声称

- ★ **「防重」与「不防重」本批只报事实，不判对错。** 三个「完全没拦」的动作
  （逐帧拉片／智能续写／音视频分离）**在 UI 上本来就点不到第二下**
  ⟹ store 层那条「又建了一遍」的路径**用户走不到**，除非有别的入口
  （快捷键？右键菜单？批量操作？——**本批没普查**）。
- ★ **只测了完全相同参数的第二次触发。** `createSubtitleErase` 的守卫是
  **指纹**（mode + regions）⟹ **换一个区域再提交**是「不同请求」，
  会正常建新节点；这条**未测**。
- ★ **只测了第二次**。第三次、第四次**未测**。
- ★ **UI 层的「点不动」只归因到「选区迁走了」这一个解释**，
  没有逐条去源码里核对每种情形（`completeShotBreakdown` 那种
  「按钮 disabled + 文案改掉」是**另一个**解释，raw 里能读到文案但本批没做成判据）。
- ★ **反馈普查只覆盖了**芯片 `aria-pressed`、几个 `data-*` 状态文本、
  节点/边数量 ⟹ **没有**覆盖 toast / 全局状态栏 / 无障碍播报。
- ★ **S6 只测了 `createFirstFrameReference` 一条**。
  `createFirstLastFrameReference` 是不是同款**未单独测**（它同样是空记录结局，
  但「两次 `Cmd+Z`」的后果**没量**）。
- ★ **空记录本身要不要修**属**产品决策**（是 `pushHistory` 该跳过 no-op，
  还是 UI 该禁用芯片？）⟹ **不发明**。
- ★ **未与源站对照**（源站需登录）。本批只判 clone 自身的内部一致性。
