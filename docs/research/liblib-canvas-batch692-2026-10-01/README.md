# batch 692 — 「字段有几个读数面」**不能**从「代码在哪几处取了整」推出来

> 起点：691 撞出「同一个字段在四个面上读出四种精度」和一个负零。那是**逐个字段**
> 发现的。本批问：个案还是通例？做法是先把「读数面」做成普查，再拿运行时
> **去反驳这个普查**。
>
> 验收：`scripts/verify-liblib-batch692.py`（5/5）
> 仪器：`scripts/census-directorstore-value-domains.mjs --readout`（本批加的模式）
> 读数：`runtime-audit.json`

## ① 普查：41 处显式取整，精度档 ≥2 的只有 3 个

`src/components/director/**` 全部 `toFixed` / `Math.round` / `Math.floor` / `Math.ceil`：

| 表达式 | 处数 | 精度档 | 位置 |
|---|---|---|---|
| `phoneVcam.pose.yaw` | **4** | `toFixed(2)` / `toFixed(0)` / `Math.round` | `:502 :507 :519 :520` |
| `phoneVcam.pose.pitch` | **3** | `toFixed(2)` / `toFixed(0)` | `:503 :508 :520` |
| `phoneVcam.pose.roll` | **2** | `toFixed(2)` / `toFixed(0)` | `:504 :509` |

**41 处 / 32 个表达式 / 只有 3 个多档。** 读数一致性不是通例，是个案 ——
而那 3 个**全在同一个面板里**。

## ② 但普查有一个结构性盲点，而它自己就能演示

普查只数**带取整调用**的表达式。于是：

- 普查说 `yaw`（4 处 / 3 档）比 `pitch`（3 处 / 2 档）**复杂**
- 运行时**两者完全一样**：各有 **4 个面**、同样的 3 档取整 + **1 档不取整**

那个多出来的面是**位置**：yaw 是 `left: ${50 + (yaw/90)*100}%`（`:552`）、
pitch 是 `top: ${50 - (pitch/60)*100}%`（`:553`）——
**两处都没有任何取整调用，普查看不见它们。**

⟹ **一个字段的显示复杂度，不能从「给它取整的那几行代码」恢复出来。**
普查衡量的是「代码里写了几档」，不是「用户能看到几个不同的数」。

`phoneVcam.pose.roll` 是反证：它只有 2 处，因为它**根本没有位置面** —— roll 不画。

## ③ 一条边框，两轴都错

垫子四边各 1px 边框。实测：border box **314 × 96**，padding box **312 × 94**，
而代码除的是 `rect.width`/`rect.height`（border box）。

| 轴 | 预测 | 42 个样本吻合 | 最大偏差 |
|---|---|---|---|
| x | `1 + off×(312−314)/314` | **42/42**（到 1/64） | **0.984** px |
| y | `1 + off×(94−96)/96` | 同上 | **0.953** px |

⟹ 691 那条 1px 错位**不是孤例，是同一条缺陷被读了两遍**。
仍是**整整一个设备像素**，与 685/690 那些 1/64px 的事差两个数量级。

## ④ `phoneVcam.stability`：普查说单档，运行时三个面

普查里它**只有一处** `Math.round`（`:600` 标签 `稳定度：{Math.round(v)}`）⟹ 单档。
但它有两个**同时可见**的面加一个 store 面：`input[type=range] step=1 value={v}`（**原始值**）。

**A 段（真键盘 ArrowRight，6 步）**：store `[59,60,61,62,63,64]`、
滑杆 `["59".."64"]`、标签 **6/6** 吻合 ⟹ **UI 可达集全是整数，两个可见面彼此一致。**

**B 段（只有 store API 到得了，4 个分数）**：

| 写入 | store | 滑杆显示 |
|---|---|---|
| 57.4 | 57.4 | **57** |
| 12.5 | 12.5 | **13** |
| 0.25 | 0.25 | **0** |
| 99.75 | 99.75 | **100** |

⟹ `step=1` 让浏览器把读数**吸附**到步长格（**就近**，12.5→13 是四舍五入向上）。
**两个可见面仍然一致，是 store 成了唯一带分数的那个** ——
与 yaw 正好相反（yaw 是 store 看着像整数、圆点带分数）。

⟹ **「哪个面是异类」不是字段的固定属性，取决于你读哪个面。**

## 自记

- **普查器第二版栽在同一类错上**：`aria-valuenow={Math.round(x)}` 既是 CallExpression
  又被外层 JsxExpression 再数一遍 ⟹ yaw 报 6 处而 grep 只有 5 处。
  **这次是被 grep 抓住的**：691 刚写下「一个普查如果和上一批的结论一致，那不是它对的
  证据」，所以这次特意拿**另一个独立工具**交叉核对，而不是拿记忆核对。
- **判据问了一个实验没产生的东西**（两次）：
  1. 第一版断言「pitch 文本会变」，而拖动**只沿 x** ⟹ pitch 恒定。改成两轴都扫。
  2. 改完仍 FAIL：y 扫沿用了 x 扫的 **14px 步长**，而垫子只有 96 高，
     指针从 `T+2` 走到 `T+282` —— **跑出控件**，`normalizedY` 被夹到 1，
     于是报出 **187px** 的「错位」，那完全是我自己造成的。
     **步长必须分轴**（x 用 14、y 用 4）。
- **判据又比了一次采样运气**：第三版要求两轴的**最大值**相差 < 1/64，实测差
  0.03125 = 恰好 2/64 —— 因为两轴步长不同、极值样本落在不同 offset 上。
  **比两个采样相关的最大值，比的是运气不是机制**。改成结构形式：
  每个样本各自等于自己那条轴的预测值（42/42 吻合到 1/64）。
- **先写结论再找数，被自己抓到一次**：第 5 条第一版断言「store 是带分数的那个」，
  而键盘扫回来的**全是整数** ⟹ 那个断言**没有被自己的读数支撑**。
  补了 B 段（真 setter 写分数）才把它量出来。
  这正是 687/688 记的那条：**先写结论会让读数看起来已被解释过。**
- 变量名踩了一次：`for v in STAB_API` 把验收器实例 `v` 遮蔽了。
