# Batch 627 —— 普查不再丢弃「视口外控件」，并把这条边界判据立给桌面控件

日期：2026-10-01 · 零源站断言 · **一个界面的字符都没改**

626 抓到两个「末尾活控件挂在视口外」的真缺陷。回头查成因，发现不是判据不够锐利，而是**普查按构造就看不见这类控件**。

## 零源站断言

`probe616`：源站仍 1600×1000、导演台被他人关闭。**本批改的是普查的量法，不是界面** —— 源码改动为零，唯一被修改的文件是 `scripts/verify-liblib-batch617.py` 里那段共享的 `AUDIT_JS`，以及两个验收器。

## 一、那行 `continue`

617 的共享 `AUDIT_JS` 里有这么一句：

```js
if (cx < 0 || cy < 0 || cx > innerWidth || cy > innerHeight) continue;
```

中心点落在视口外的控件被**静默丢弃**：不进 `items`、不记进 `covered`、不记进 `clipped`。所以 626 的两个缺陷不是「被判失败」，而是**从未被枚举**。

第二层后果更隐蔽，也更值得记：**窄屏下普查的分母会自己缩水**。618/621 早就知道窄屏工具条有 776px 内容、放不进 390 的窗口、要横向滚动才见尾部 —— 这本身是对的。但因为窗口外的控件被 `continue` 掉，普查在窄屏量到的「控件数」比桌面**少**。一个「控件变少了」的读数看起来像好事，实际上是量表自己漏了。

## 二、改法：把「丢弃」换成「分类」

```js
const offViewport = cx < 0 || cy < 0 || cx > innerWidth || cy > innerHeight;
const hit = offViewport ? null : document.elementFromPoint(cx, cy);
const own = !!(hit && (hit === el || el.contains(hit) || hit.contains(el)));
const panel = own ? null : covering(el, hit);
const clipped = !own && !panel && isClipped(el);   // 沿用 617 原有的判据
items.push({ ..., own, clipped, offViewport, ... });
```

剩下的判断**完全交给已有的 `isClipped`**，这是本批最省事也最正确的地方：

- 落在某个裁剪祖先之外 → `clipped`，**滚得到，记不失败** —— 正是 621 窄屏工具条那种情况；
- 不在任何裁剪祖先之外 → 真的够不着 → 落进 `covered`，与其他伤亡同等看待。

新增三个桶让分类可读，而不是只留一句「它消失了」：

| 桶 | 含义 |
| --- | --- |
| `offViewportItems` | 所有中心在视口外的控件 |
| `offViewportScrollable` | 其中落在裁剪祖先之外的（滚得到） |
| `offViewportUnreachable` | 其中不落在任何裁剪祖先之外的（**真缺陷**） |

`elementFromPoint` 在视口外必须不调用 —— 越界的坐标会被钳到边缘，问它等于问了一个假问题。

## 四、两个视口不算数，扫 86 个宽度（探针 B）

「零」可能只是那两个宽度恰好都落在有滚动容器的布局里。沿用 623 立的宽度集（每个开关点 ±3 密集 49 个 + 360→1920 每 40px 粗扫 40 个，取并集 86），主扫靠 resize 一个页面，再用 623 同一批 **17 个全新加载**交叉校验：

| 读数 | 值 |
| --- | --- |
| 扫描宽度 | 86 |
| 视口外控件累计 | **4657** |
| 出现「够不着」的宽度 | **0** |
| 全新加载与 resize 不一致 | **0** |
| **`covered` 非零的宽度** | **0**（层叠那半没被动到） |
| **一个视口外控件都没有的宽度** | **0** ← 非空转证据 |

最后一行是本批最该强调的一条：**一条静默的 `continue` 和一个真的干净桌面，读数长得一模一样。** 所以「零缺陷」必须配一条「分支真的跑过」才算数。

## 六、验收的三条合同

`scripts/verify-liblib-batch627.py`，7 checks：

1. **`no-width-has-an-off-viewport-unreachable-control`** —— 86 个宽度上都没有「视口外且够不着」的控件。
2. **`every-width-actually-exercised-the-off-viewport-branch`** —— 每个宽度上视口外控件数都 > 0（非空转）。
3. **`the-new-classification-added-exactly-the-off-viewport-controls`** —— 差分断言：同一页并排跑「旧的 `continue` 版」与「新的分类版」，断言 `新版总数 − 旧版总数 == 新版视口外控件数`。**差值恒等于分类数，就同时证明了两件事**：旧代码确实是瞎的，而新代码没有顺手多收别的控件、也没有漏收。配 `the-legacy-continue-was-blind-at-every-width` 兜住前半个意思。

另加 `no-width-has-a-covered-control`（层叠那半没被这次改动扰动）与 17 个全新加载的一致性。

619 自身也加了两条**逐态**断言，让这条边界判据对桌面控件常设生效：
`no-control-is-off-viewport-and-unreachable` 与 `the-off-viewport-branch-actually-ran`（12 态 × 2 = +24 checks，89 → 113）。

## 七、迁移一处历史合同：618 的 `clipped-count-is-explained`

它红了：`len(r["clipped"]) <= 20`。这个魔数阈值的**本意**是「窄屏没有把一大堆控件藏到滚动区后面」——而 `clipped` 从此装了两类东西：

| 类别 | 390 下数量 | 性质 |
| --- | --- | --- |
| ① 窗口**内**、被自己面板 overflow 滚下去的 | 少量 | 618 原本在数的，少是好 |
| ② 中心**整个在窗口外**、只能横向滚窄屏工具条那 776px 才见得到 | 84 | 627 之前被 `continue` 静默丢弃，从来不进这个计数 |

**把 20 抬到 100 能让这一条变绿，但那等于放弃 618 真正想守的东西。** 所以按原义取数：

```python
in_window_clipped = [b for b in r["clipped"] if not b.get("offViewport")]
v.check("mobile:clipped-count-is-explained", len(in_window_clipped) <= 20, ...)
```

阈值不动、语义不动，新类别单独记进 `detail`。改后 618 **42/42**。

> 这条迁移的通用教训：**一个计数被新加入的类别撑大时，先问「这个阈值本来在数什么」，别先问「阈值该抬到几」。** 抬阈值是最容易做成的那一步，也最容易把一条真合同悄悄废掉。

## 八、本批自己的一处错

627 的验收器里，我把 legacy 版从新版「还原」回去时，只还原了三处、漏了 `items.push` 里那个 `offViewport` 字段 —— legacy 形状里已经没有这个声明了，于是 `ReferenceError: offViewport is not defined`，第一轮在第一个宽度就崩。

值得记的不是这个错本身，而是它的形态：**「还原成旧行为」这个动作本身需要断言**。所以我给还原后的字符串加了一条 `assert`，把「legacy 形状里不该再出现这个标识符」变成硬约束，而不是靠下一轮崩了才发现。这类「为了对照而写的旧版副本」和 626 的标量 `effectiveZ` 是同一类风险：一份看起来合理的副本，实际测量的是别的东西。

## 不声称

- **源站任何事**。本批不改界面，只改量法。
- **窄屏工具条的 776px 内容「放得下」** —— 它们仍然需要横向滚动才见尾部。这里只主张「滚得到」，这正是 `clipped` 的原义。
- **导演台控件在几何边界上从此干净到永远**。只主张在 86 个宽度 × 900 高这一个网格上是干净的；未测的是**高度**方向（626 已证明 `motion-path-menu` 的问题在高度上，所以这条网格并不覆盖它）、以及浮层打开态下的桌面控件（619 的 12 态覆盖了一部分，不是全部宽度）。
- `covered` 为 0 说的是**层叠**那半干净，与本批新增的几何边界那半是两件事；前者是 619–625 一直在守的。
