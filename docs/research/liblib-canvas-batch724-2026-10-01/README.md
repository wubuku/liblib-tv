## 纠正 723：「零控件」应为「零按钮」

723 的判据是 `n.querySelectorAll('button, [role="button"]').length` ——
测的是**按钮**。而 React Flow 的 Handle 是 `<div class="react-flow__handle">`，
**根本没进那个集合**。

**十张卡每张都有 2 个 Handle**（`target` + `source`），共 **20** 个：

| 事实 | 值 |
|---|---|
| 元素标签 | **`div`**（不是 button，没有 `role`，`tabIndex` 也不给） |
| 实测尺寸 | **11×11** |
| 源码声明 | `style={{ width: 20, height: 20 }}`（`ImageNode.tsx:261-262` 等） |
| 可连接性表达方式 | `data-connectable` 属性为 **`null`**；只有 class 里的 `connectable` |
| 默认视口下在屏 | **9 / 20** |

**11 = 20 × 0.526**（`desktopViewport.zoom`）⟹ **Handle 跟着画布一起缩放**，
源码写的 20 是「100% 缩放下的意图尺寸」。

⟹ **723 的读数全部存活，错的是它顺带说的那个概括。**
按本项目的方法论，这属于「读数对、概括宽一步」，
纠正记在本批，不重写历史批次。

## 缩放快捷键没坏 —— 但只在「没有面板开着」的时候

| 前提 | ⌘+ | ⌘0 | ⌘− |
|---|---|---|---|
| **干净状态** | **+10pp** ✓ | 落到 **38%（= fit 值）** ✓ | **−10pp** ✓ |
| **缩放菜单开着** | 不变 ✗ | 不变 ✗ | 不变 ✗ |

源码侧：`page.tsx:1306` 的 `handleKeyDown` 开头有
`if (resolveLibTVBlockingForegroundSurface(uiState)) return;`，
而 `resolveLibTVBlockingForegroundSurface`（`libtvSelectionCommandContext.ts:121`）
把 `isZoomMenuOpen` 列为阻塞面。

⟹ **菜单上印给自己的三个快捷键提示，在菜单打开期间全部不成立**；
Escape 关掉面板后同一个键就可用。

**这一条差点被我自己写成缺陷。** 第一版探针刚点过缩放菜单项就按键，
得出「⌘+/⌘0 坏了、菜单点击却正常」的矛盾结论 ——
甚至一度以为是捕获阶段 `stopImmediatePropagation()` 吞的。
第二版把「有没有面板开着」作为唯一变量做 A/B，
才发现 `zoomBy` 和菜单的 `onZoomBy` 是**同一个函数**（`page.tsx:1630`），
干净状态下三个键全部生效。**那一版读数作废。**

## 方法论

1. **概括比判据宽一步时，要回去看判据到底测了什么** ——
   723 判的是「每张卡几个 button」，说的是「零控件」。
   **判据只覆盖了按钮，凭什么说控件？** 这是与 721 同源的第三档风险：
   判据本身没错，但概括越过了它。
2. **读数不可用时先查操作历史** ——
   「⌘+ 无效」只在我先点开过缩放菜单时成立。**先查自己动过什么，再开单。**
3. **A/B 只变一个变量** —— 第二版把「有没有面板开着」作为唯一变量，
   焦点元素、视口、缩放档位全部固定，才分得清。
4. **失败的手势要看中间态** —— 只看 `edges` 11→11 分不出「被规则拒绝」与
   「手势没被接住」；`connection` 出现而 connecting/valid 恒 0，
   才把范围缩到「连接进行到一半就断了」。
5. **「同一个数字在两层含义不同」是第三次出现了**（721 的 −13、
   723 的 Handle、724 的 20 vs 11）——
   **源码里的字面尺寸是意图值，几何读数是渲染值**，两者差一个缩放因子。
