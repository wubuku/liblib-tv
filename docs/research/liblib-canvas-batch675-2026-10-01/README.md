# batch 675 —— **归因不是靠身份稳住的，是靠口径看不见身份**；而计数随身份走

## 一句话

673 给出名字折叠的人口（28 枚），674 给出换五套身份的折叠量（28/68/10/11/4）。
两批都只给了「人口」。本批问真正要紧的那句：

**672 的 8 族表、673 的碰撞名单，哪些随身份变、哪些不变？**

答案分成两半，而且两半的方向相反：
**归因那一侧「不变」是假象（口径根本不用身份）；计数那一侧真的随身份走。**

## 仪器

`scripts/verify-liblib-batch675.py`，三视口 1280 / 1440 / 1920 × 1150，130 枚控件。

**普查 JS 直接复用 674 的那一份**（`b674.JS`）—— 同一台量具、同一批读数，只换分析口径。
跨批次一致性由第 7 条判据单独验：**两次独立运行的身份计数与吞掉数逐位吻合**
（102/62/120/119/126 与 28/68/10/11/4），所以下面的读数不是某一次运行的偶发。

## 1. 672 的族表逐格复现 —— 但复现的原因不是「稳健」

族表在本次运行里**逐格复现**（下表即 672 §1）：

| 族（blame 的 class 头几段） | 1280 | 1440 | 1920 |
|---|---|---|---|
| `relative.min-h-0.flex-1` | **25** | **25** | **25** |
| `absolute.inset-0` | 19 | 21 | **22** |
| `min-h-0.flex-1.overflow-y-auto.px-2.…` | 12 | 12 | 12 |
| `h-full.min-w-0.flex-1.appearance-none.…` | 9 | 9 | 9 |
| `absolute.bottom-0.left-0.top-[52px].…` | 3 | 3 | 3 |
| `flex.h-9.shrink-0.items-center.…` | 2 | 2 | 2 |
| `flex.min-w-0.items-center.justify-center.px-2` | 2 | 2 | 2 |
| `lucide.lucide-circle-question-mark` | 1 | 1 | 1 |
| **合计控件** | **73** | **75** | **76** |

**但它复现，是因为它属于 V3 口径（见 §2），而 V3 根本不使用身份。**

「族表在四套身份下逐格不变」这句话是**同义反复**，不是稳健性的证据。
本批特意把这条写成一条判据，就是为了不让后人把它当成「归因很稳」。

## 2. 同一句「66 个名字」有三种读法，三张不同的表

| 口径 | 含义 | 控件数 1280/1440/1920 | 随身份变？ |
|---|---|---|---|
| **V1** | 键在三视口都是真阳性 ⟹ 把该键的**所有**控件都算进去 | name **85** · kS **78** · kS2 **73** · kS3 **77** · kS4 **73** | **变** |
| **V2** | 且该枚控件自身在该档也是真阳性 | **73 / 73 / 73**（五套身份全同） | 不变 |
| **V3** | 每档全部真阳性控件（**不用身份**） | **73 / 75 / 76** | 不变（口径看不见身份） |

**670/672 并列写下的两句出自两种不同读法**：
「66 个名字每档都假阳性」是 V2（恒 73），「每档 73–76 格」是 V3。
两句都不算错，但它们**量的是两个不同的集合**，并列写会让人以为它们互相印证。

**只有 V1 随身份移动**（85 / 78 / 73 / 77 / 73），而 V1 恰好是最自然的那句读法：
「这个键在三档都真阳性，所以它代表的控件都应该算进去」。

## 3. 折叠会**凭空造出一个族**

V1 在**按名字**与按 kS / kS3 时各有 **9** 个族，比 V3 多一个：

```
relative.min-h-0.flex-1=25, absolute.inset-0=19, <no-class>=12, …
```

多出来的那个族，12 枚控件的 blame 落在一枚**完全没有 class** 的元素上。
它们在那三个视口里**并不是真阳性** —— 是被名字折叠拖进集合的。

**折叠不只是合并成员，还能造出一个在原集合里不存在的类别。**
（V1 在 kS2 / kS4 下没有这个多余族，因为那两套键不把非真阳性的控件拖进来。）

## 4. 673 的 8 个碰撞名，kS4 **全部**分开

| 名字 | 控件 | kS2 键 | **kS4 键** |
|---|---|---|---|
| `当前帧有关键帧` | 11 | 11 | **11** |
| `<input>` | 10 | **4** | **10** |
| `左右拖动调整 X / Y / Z 轴` | 各 3 | 各 3 | **各 3** |
| `收起属性` | 2 | 2 | **2** |
| `上一关键帧` / `下一关键帧` | 各 2 | 各 2 | **各 2** |

**8 个碰撞名里每一个，kS4 都给出了与控件数一样多的键。**
`<input>` 那一组最能说明问题：kS2 只给 4 个键（10 → 4，因为它同样只取第一个 data 属性），
kS4 给 10 个。

## 5. kS4 自己的残留 ⊂ 名字的折叠集

| 集合 | 折叠控件数 |
|---|---|
| 按名字折叠 | **36** |
| 按 kS2 折叠 | 15 |
| 按 kS4 折叠 | **6** |
| **两者都折叠** | **6** |
| 只有名字折叠（kS4 分得开） | **30** |
| 只有 kS4 折叠 | **0** |

kS4 折叠的那 6 枚是两条轨道各 3 枚导航钮（`上一/当前/下一关键帧`），
判别位是祖先的 `data-director-track-label=director-track-camera-main` /
`…-character-lead-transform`。**它们全部落在名字的 36 枚之内**
（`kS4 \ name = 0`）—— 因为这三个名字本身各自也是重复的名字。

**净账：kS4 分开了名字折叠的 36 枚里的 30 枚，剩下 6 枚两边都折叠。**

## 6. 自记错误两条

- 第一版把 `Counter(...).items()` 迭代出来的 `(name, count)` 元组当列表用，
  `len(grp)` 报 `'int' object has no len()`。**先看清 `sorted(Counter.items())` 给的是元组。**
- 跨批次对照那条判据按 dict 取 674 的 `uniquish`，实际它是**位置数组**；
  改成长度对齐后逐位比对。**引用别人的 audit 前先看它的实际形状。**
