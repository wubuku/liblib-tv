## 613 错在哪

613 做对了结构：把资源栏与场景树按源站放到 52 → 视口底，左列 0..281 整条被这两块占住。然后它给 clone 独有的镜头条让位 `ml-12` —— 48px，**只是资源栏的宽** —— 并断言 `镜头` 标签的 x ≥ 48。

两条断言都成立，也都跟问题无关：**场景树宽 233 且 `z-30`，镜头条 `z-auto`**。于是镜头条的全部内容（自 x=48 起的 `镜头` 标签与每一枚 `机位N` chip）**整条被场景树压在下面**。画得出、尺寸正确、完全点不动。

教训写进代码注释了：**位置不等于层叠**。x 几何断言看不见 z 序问题。所以 613 的验收补了 `shotbar:label-receives-its-own-click` 与 `shotbar:first-shot-chip-receives-its-own-click` 两条命中测试（613 现 55 项），同一个洞不会再开。

## 修法

让位量改成**整条左列 281px**（48 资源栏 + 233 场景树）：`min-[900px]:ml-[281px]`。这也和源站的形状一致 —— 源站在 y 52..88 这条带里 x<281 的部分同样是左列。窄屏 rail 隐藏、场景树是抽屉，故不加边距。

## 普查自身也修了两处判据

**一、必须区分「被盖住」与「被自己的滚动容器裁掉」。** 首版把两者混为一谈，1024px 那条腿报了 14 枚「遮挡」，绝大多数其实只是滚出了属性面板自己的 `overflow-y-auto` 或视口工具条的 `overflow-x-auto`。现在分成 `covered`（真缺陷）与 `clipped`（滚一下就到，记录不失败），并把 clipped 数量也钉一道上限，免得某个面板开始裁掉一半控件却无人察觉。

**二、「最近的裁剪祖先」是错的判据。** 视口工具条的内容行同时套在两个 `overflow-x-auto` 里 —— 工具条自身（711 宽）和包着它的 `w-full`（client 438、scrollWidth 944）。取最近的那个会判成「在范围内 → 被盖住」，而它其实落在更外层那个 438 宽的盒子里、**被裁掉了**。正确规则是：**只要落在任意一个裁剪祖先之外，就算被裁**。

## 仍然被盖住的那一枚，以及为什么保留

`帮助` @`[7.5,1110,32,32]` 压在时间线下面，本批**不改**：

- 源站也压着 —— `probe613f` 在 (23.5,1126) 做 `elementFromPoint` 命中的是时间线左控制簇 `div.z-10.shrink-0.bg-[#1f1f1f]`，裁图同区域纯黑。源站自己最底那枚 rail 项在时间线打开时就是死控件。
- 反向抬高 rail 会把时间线自己的 `播放` / `自动帧` / `循环播放` / `时间` 输入埋掉 —— 拿一枚死控件换四枚活控件。

所以照抄源站并**按名字显式排除**在验收里，而不是假装普查什么都没发现。
