# batch 643 —— 「被裁」与「被盖」本来是两件事，判据却把前者当成后者的否决权

日期 2026-10-01 · 验收器 `scripts/verify-liblib-batch643.py` · **17 checks / 0 failures**

## 一句话

普查里 `clipped`（「它落在**自己**某个裁剪祖先之外」）被当成了「被盖住」的**否决权**，
于是「既滚出自己的行、又被另一个面压住」的控件**四个记账桶一个都不进** ——
这种控件实测 **14 枚**，而判据过去连放它们的地方都没有。

本批同时用地面真值**排除掉**了那个最顺手的嫌疑：它们**不是被谁的 z 值压住的**，
而是**根本没被画在采样点上**。

**本批不主张这 14 枚是缺陷**（它们的滚动盒真的能滚，14/14），也**不主张它们无害**。
它只主张：两件事实被合并了记账，而**两种直觉修法都会错**。

---

## 1. 否决权写在判据的哪四行

`scripts/verify-liblib-batch617.py` 的 `AUDIT_JS`（本批**纯增量**改动）：

```js
const clipped          = !own && !panel && isClipped(el);      // ① 被自己裁掉
const timelineOverlay  = !own && !clipped && !panel && ...    // ②
const viewportSqueeze  = !own && !clipped && !panel && ...    // ③
const unexplained      = failed.filter(!i.clipped && !i.panel // ④
                                        && !i.timelineOverlay
                                        && !i.viewportSqueeze);
```

`!own` 与 `!clipped` 是**两个不同问题**：

| | 问的是什么 | 答案来自 |
|---|---|---|
| `clipped` | 它在**自己**的滚动盒里露不露面 | 受害者自己的滚动容器 |
| 被盖住 | 它中心点上被**谁**画住了 | 那个坐标上碰巧有谁 |

①让 `clipped` 只在「未被面板挡住」时成立，②③④又都用 `!clipped` 当前置。
结果：一个同时满足两件事的控件，被 ① 归进 `clipped`，然后被 ②③④ 全部排除。

**640 看不见它**（它的搜索条件是「中心点通 + 本体被挡」，中心点被挡的按构造就搜不到）；
**642 报出了它**（`发送`@1440），但那是新加的 `roundControls` 列表**顺手**带出来的 ——
两个批次都不在找这个状态。

## 3. 地面真值：它们根本没被画在采样点上

`elementFromPoint` 只返回一个元素，**无法区分**「有东西压在我上面」与「我压根没画在这里」——
而这正是本批要问的那件事。所以改用 `elementsFromPoint`（返回整摞）：

> **14/14 枚联合控件，在自己的采样点上都不在自己的 `elementsFromPoint` 栈里。**

例：@339 的 `16:9`，中心 (319,700)，栈顶六层是
`directorScenePromptBar → div → div → directorWebglCanvas → viewport → main`。

**所以第 2 节那张表右列记的是「那个坐标上碰巧有谁」，不是「谁压住了它」。**
五个邻居不同，是因为溢出尾部落到不同版式区域，不是因为有五种 z 值冲突。

### 顺手排除掉的那个嫌疑

底部带声明 `z-[200]`，属性列只有 `z-30`，而实测属性列拿走了 @899/@1440 的命中 ——
第一反应当然是「z 值打架」。**实测否掉了这个解释**：

* 两者**共享同一个层叠上下文**（工作区根 `[data-director-workspace]`，
  `position: fixed; z-index: 100`），且**各自都创建了自己的层叠上下文**
  （都是 `absolute` + z 非 auto）；
* 所以 `200` 与 `30` **直接可比**，200 本该压过 30；
* 它没有赢，**不是因为层叠**——是因为**那个位置上根本没有底部带的像素可输**。

> 标量 `z-index` 跨子树不可比这条纪律在这里**不适用**：这一处它们同上下文、可比。
> 差点据此写下一个错误的「层叠缺陷」。

## 4. 两条此前从未被测量的事实

| 事实 | 读数 | 意义 |
|---|---|---|
| `covererInClipper`（邻居在不在受害者的滚动盒里） | **14/14 = false** | `clipped` 的读法是「滚一下就回来了」，但这招要求那个坐标上的东西**跟着一起滚**。实测**从不**。 |
| `clipperCanScroll`（那个滚动盒到底能不能滚） | **14/14 = true** | 「滚到」这个补救**是真的**。所以本批**不主张**这 14 枚是缺陷。 |

这两条必须一起说：**补救是真的，但它解释不了「采样点上是谁」。** 合并成一个
`clipped` 布尔，就同时丢掉了「为什么点不到」和「为什么能滚到」两个不同答案。

## 5. 两种直觉修法，都被实测否掉

### 修法 A：删掉 `!clipped`，让它们落进 `viewportSqueeze`

看着最自然。**但它错在看起来很干净**：

* 14 枚里 **12** 枚 `victimInViewport` 为真 → 会被 squeeze 族吸收；
* 另外 **2** 枚（时间轴自己的 `添加关键帧`/`删除关键帧`，不在视口里）→ 会**反向**
  冒成两条新的 `covered` 缺陷。

一个修法**同时朝两个方向出错**，就不是修法。

更糟的是：629 的闭式 `(bottom − vp_top) + band ≥ vh` 对 **14/14 全部成立**。
所以这个改动会被自己的公式判为「自洽」，任何「公式同不同意」的检查都会放行它。
可闭式对这 5 组布局的答案是**同一个** —— 它根本没有分辨力。

> **闭式同意，不构成证据。**

### 修法 B：把联合状态当成新缺陷报出来

同样错：补救是「横向滚一下」，这不是缺陷。
而且报出来就得回答「该不该修」，那是**版式决策**，源站未取证。

**所以本批一个判定都没改。** 只记。

## 6. 我自己写错的四处

这一批我错了四次，四次都是同一条纪律在起作用：**测试自身写错要当信号读**。

1. **联合桶虚胖了 26 倍。** 第一版写 `!own && !panel && isClipped(el)`，跑出 **363 枚**。
   错在 `!own` 对**出屏**控件同样为真 —— 出屏时中心探针被跳过、`hit` 是 `null`，
   根本没有东西在那儿。「只是滚出窗口」被当成了「被盖住」。
   覆盖那一半必须显式要求 `hit !== null`；收紧后 **14 枚**，与独立探针逐格一致。
2. **「每个宽度都必须非空」是错的断言。** 它在 898 与 1920 变红，
   而**红是对的**：那两格的联合桶本来就该空。改为由几何推出的两条：
   * 必要条件 —— 有联合控件的宽度**必有**一行横向溢出（5/5 成立）；
   * 空宽度的理由可读 —— 898 唯一溢出的行（提示条行 944 > 874）溢出尾部落在 **x956**，
     **整段在 898 窗口之外**，那里什么都没画；1920 三行**全都不溢出**。
3. **层叠推导靠错误的原因变绿。** 我写的检查在「两者同一上下文」分支里比的是
   **祖先的 z**（100 vs 100），靠平局裁决碰巧蒙对了实测的赢家，而它 `reading` 里
   写的「不在同一层叠上下文」与数据相反。整条检查已删。
4. **命中栈检查是空转的。** `hs` 是宽度循环里的局部变量，循环结束后只剩**最后一个宽度**
   （1920，联合桶为空）的结果，于是 14 枚全查不到、`victimPresent` 全是 `None`，
   而 `not None` 判成通过。改成存进每个 cell，并额外断言**查表零落空**。

第 3、4 条合起来是最贵的一课：**一条检查变绿和一条检查在测量，是两件事**。
第 4 条尤其眼熟 —— 它和 640 那次「在第二次采样填充字段之前就读它」是同一个形状。
