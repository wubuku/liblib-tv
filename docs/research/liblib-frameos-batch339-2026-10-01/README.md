# Batch 339（2026-10-01）：「断言方向」门禁尝试 —— 否定结论（未上线）

## 结论一句话

尝试给断言门禁加一条 `UNANNOTATED_DIRECTION` 规则，拦截 Batch 208 那类
**方向反了**的断言。**结论：不可行，已放弃，不予保留。** 记录原因以免后人重做。

## 动机（问题本身是真实的）

Batch 208 断言 `nodes_after == nodes_before` 却命名为「刷新后内容保留」，
实际验证的是**内容丢失**。方向反了的断言与恒真断言同样坏：
账本显示「✅ 已覆盖」，实际锁着缺陷。

想法：门禁不判断对错，只**强制作者说明方向** —— 没有注释或自明的检查名就报错。
把「后人无从判断」变成「作者当场讲清楚」。

## 为什么放弃

### 1. 误报规模压倒性

加规则后全仓报出 **129 条**（其中相当一部分是 `page.evaluate` 里
**多行 JS 字符串**被误当 Python 代码扫到，例如
`"(after) => window.__director_store..."`）。

即便过滤掉 JS 字符串，仍有 **83 条**真实 Python 断言命中。

### 2. 真实命中里绝大多数是**对的**

逐条看这 83 条，方向基本都正确，且**检查名已经自明**：

```python
check("node:duplicate-added",  ... == nodes_before + 1)   # 复制后 +1，对
check("undo:node-removed",      ... == nodes_before)      # 撤销后复原，对
check("paste:node-added",       ... == nodes_before + 1)  # 粘贴后 +1，对
check("alt:count-plus-one",     after["count"] == count_before + 1)  # 对
```

`undo` / `redo` / `paste` / `add` / `delete` 这些词**已经把方向说清楚了**。
再加一条「请注释说明方向」的要求，是在为已经自明的地方强加噪声。

### 3. 真正的缺陷（208）靠的不是这条规则

Batch 208 的问题是**检查名与断言互相矛盾**（名说「保留」、断言验「丢失」）。
能抓住它的是**人工交叉核对**（名 vs 断言），不是「有没有注释」。
而自动判断「名与断言是否矛盾」需要理解语义 —— 超出正则能力。

## 决定

**不加这条规则。** 保持 Batch 336 的门禁（只查恒真，那类判定是确定性的）。

理由：门禁的价值在于**零误报**。Batch 336 建立时我就明确「刻意不查 `== []`」，
理由是「误报比漏报更消耗信任」。同一条标准适用于此：
129 条误报的门禁，等于没有门禁 —— 团队会习惯性忽略它。

## 保留的收获

- 「方向反了」这一类**确实存在**（Batch 208 为证），但它需要**语义理解**，
  不是正则能覆盖的；
- 若日后要做，方向应是**交叉核对检查名与断言**（如名含 `persist` 却断言
  `== nodes_before`），而非「有无注释」；
- 本批是一次**有价值的否定结论**：花一轮确认「这条路走不通」，
  比留一条噪声规则在门禁里强。
