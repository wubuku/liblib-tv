## 一、一句话结论

748 的 C1／C3／C4 判的是**绝对快照数字**（并集 446、累计 250、`add-camera` 带出 34 种…）。
**这些数字每加一批 `data-*` 的批次就必红** ⟹ 这不是「期望值过时」那么简单，
而是**判据形式本身有缺陷**：一个**普查快照**被写成了**恒定契约**。

本批**不逐批抄新数字**（那只是把快照过期推迟到下一批）⟹ 改成**关系式判据**：
判**账要平**（不变量），而不判**账是几**。

★ 同时用一条**增量账**判据保留追溯力：断言「748 基线 ⟶ HEAD 净增的属性名**恰好是那 22 个**，
且每一条都能在**它声称的那个批次**的源码里查到」⟹ 既抗漂移，**又不丢「谁加的」**。

★ **748 的行为契约一条没放松**：C2（打开导演台 store 零写入）、C5（快门两跳）、
C6（导出真跑通）、C7（六个区域齐）**原样保留**（本门禁**直接调用 748 的脚本**取读数，
不复制粘贴它的实现 ⟹ 避免「抄一份就漂一份」）。

## 三、★★ C4 那两条红的成因是**产品变好了**，不是退化

这是本批最需要说清的一层 —— **改期望值时如果不说清它，就等于把「产品改进」记成了「数字变了」。**

- **`help` 从 0 新增变成 2 新增**：batch 831 实现了「帮助 → 快捷键」面板
  （`data-director-shortcuts-dialog` / `-overlay` / `-title` / `-row` …）。
  ⟹ 748 当年那句「`scene` 与 `help` 两枚一个 `data-*` 都没新增」**在 831 之后就不再成立**。

- **`add-camera` 从 34 变成 3**：batch 832 **推翻了 batch 537/540 的旧读数** ——
  源站的「添加机位」**不是**直接加一个机位，而是把左侧资源栏切成**一个 15 枚机位预设的面板**
  ⟹ 面板本身只带 `data-director-camera-preset` / `-glyph` 两种属性；
  那 34 种是「直接加机位后弹出的属性面板（FOV／跟随／look-at 全套）」的属性。

⟹ ★ 所以 C4 现在正确的形状是「**零新增的入口恰好是 `scene` 一枚**」，而不是「恰好两枚」。

## 四、本批的门禁（`scripts/verify-liblib-batch835.py`）

### ★ 门禁自己踩过的两个坑（都被它自己抓住）

1. ★ **路径解析错**：门禁第一版把 `ROOT` 写成 `parents[4]`（脚本在 `scripts/` 下，多了一级）
   ⟹ 静态扫描读到**空目录** ⟹ S1 打印「文件数 0」却**判绿**（因为空集也让恒等式成立）
   ⟹ ★ **这是「恒真」的典型形态**：读不到东西的时候，判据不报错。
   ⟹ 修法：**读到空目录／漏文件／读不到 rail 入口／首屏明显没进导演台 ⟹ 直接失败**。

2. ★ **吃外部缓存**：门禁第二版去读 `/tmp/b835-runtime.json` ⟹ 那文件**可以手改**、
   也可能在代码变了之后还留着旧值 ⟹ **拿着过期读数报绿**。
   ⟹ 修法：**门禁自己跑运行时读数**（与 748 同一套口径：整页 `data-*` 集合 ＋ 逐枚点 rail 做差），
   不读任何外部文件。
   ⟹ 阴性对照 **N7** 用**反例实验**证明这条危险：造一个「各项不变量都是 true」的**过期缓存**
   ⟹ 旧写法会**照单全收**地报绿 ⟹ 所以「吃缓存」不是「方便」，是**看不见的失真源**。

3. ★ **副产物污染**：门禁跑 748 时，748 会把产物写进**它自己的批次目录**
   （`batch748-…/runtime-audit.json`）⟹ 修法：**记下原始字节 → 跑完按字节复原**。

### ★★ S2 自己暴露的一个真盲区（由**真实注入自检**抓出来）

`probes/inject835.py` 改产品源码里 `data-director-camera-preset-glyph` 这一枚之后，
**S5 红了**（符合预期）⟹ 但 **S2 没红**。

⟹ 原因：S2 第一版把「当前」**硬编码成 `HEAD_COMMIT`（`8074234d`）** ⟹
**工作区里改了源码，S2 完全察觉不到** ⟹ ★ 这就是「判据比的是历史快照、不是当前事实」的盲区。
⟹ 修法：基线仍取 748 的 commit（那是历史事实），而「当前」取**工作区实际文件**。
⟹ 修完后同一次注入：**S2 红 ＋ S5 红 ＋ S1 仍绿**。

⟹ ★★ **S1 仍绿正是「关系式判据抗漂移」的可见证据**：属性名被改了，恒等式**照样成立**
（它只关心账平不平）⟹ 而「名字对不对」由 S2／S5 负责 ⟹ ★ **两类判据分工明确**，
这正是不变量式判据的价值：**该紧的地方紧，该松的地方松**。

### ★★ 阴性脚本自己也踩过两个坑（都很典型）

1. ★ **注入把脚本写坏了 ⟹ 看起来像「注入有效果」**：
   N3 第一版把 Python 语法写坏 ⟹ 门禁**崩了** ⟹ 解析出来是「全红」⟹
   看着像「注入翻红了很多条」，其实**脚本压根没跑起来**。
2. ★ **替换串没匹配上 ⟹ 注入没生效 ⟹ 期望当然不成立**：
   N6 第一版改的是 748 判据里的**三个数字** ⟹ 而 748 的每条判据有**十几个 `and` 条件**
   （`fileCount==13`／每个文件的 count／`firstPaintCount==200`／`afterRailWalkCount==250`／
   `gains` 字典…）⟹ 只改三处 ⟹ **748 压根没转绿** ⟹ S7 当然还绿。
   ⟹ ★ 教训：**注入要针对「判据整体」，不是「判据里的某个数字」**。

⟹ ★ 修法：**每条注入都先自校验** —— 锚点**唯一**、替换后文本**确实变了**、
**语法可解析**、**读回验证真的落盘** ⟹ **打不上就中止**，绝不当作阴性通过。
⟹ ★ 这就是「**打不上**」与「**打上了但没效果**」必须分开的那一刀。

### ★ 真实注入自检（`probes/inject835.py`）

改**产品源码**里 `data-director-camera-preset-glyph` 这一枚 ⟹ 实测：
**S2 红 ＋ S5 红 ＋ S1 仍绿** ⟹ 按字节复原（sha256 一致）。

⟹ ★★ **S1 仍绿**就是「关系式判据抗漂移」的可见证据（恒等式只关心账平不平）；
