# batch 757 — `storyboard-group` 的视觉契约：查出分组框**与成员之间没有任何跟随关系**

## 起点

753–756 全在做多选与分组的**数据**行为（谁能选中、复制出几个节点、边怎么处理、
组合会不会掏空旧组）。读的都是 `window.__libtv_store.getState()`。

于是留下一个从未被碰过的问题：**这些分组在屏幕上到底长什么样。**
`storyboard-group` 这个组件此前只被读过 store 字段，一次 DOM 都没读过。

先做静态普查，结论就已经很硬：

| 静态事实 | 出处 |
|---|---|
| 组件**只读** `data.title` 与 `data.variant`，**从不读 `children`** | `StoryboardGroupNode.tsx:15-16` |
| 全 `src/` 里 `groupKind` **只出现 1 次**（`canvasStore.ts:3298` 写入），**零个读取点** | grep |
| 全仓库**没有** `useUpdateNodeInternals`、**没有**任何分组边界重算逻辑 | grep |
| 标题在 `-top-8`（框外上方 32px）、`pointer-events-none`、恒为 `text-[#777]` | `StoryboardGroupNode.tsx:28` |
| 选中分支只加 `border-[#09caf5]` + `shadow`，**标题那行没有 selected 条件** | `StoryboardGroupNode.tsx:23` |

「组件不看 children」+「没有重算逻辑」+「标题不随选中变」三条合起来，
指向一个很具体的预测：**把子节点拖出分组，框不会动，也不会缩放。**

本批就去验这个预测。

## 一、核心读数：拖子节点出框，框原地不动

先把画布向左平移（为什么需要平移见第六节 R19），然后抓住 `v-UGQZzZOpbv`
横向拖 501px，把它**完全推出去** 722×460 的分组框：

| 读数 | 值 |
|---|---|
| 分组框 DOM 位置 | (747,161) → **(747,161)**，`groupDomMoved=**false**` |
| 分组框 DOM 尺寸 | 271×173 → **271×173**，`groupDomResized=**false**` |
| 分组 store 位置 | 未变，`groupStoreMoved=**false**` |
| 子节点相对位置 | (62,62) → **(1461,174)**，`childMoved=**true**` |
| 子节点是否还在框内 | **`childFullyInsideGroup=false`** |
| 子节点左边缘距框右边缘 | **277** 屏幕像素（在框外） |
| `parentId` 挂载 | **仍挂着**，`childrenStillLinked=["v-UGQZzZOpbv"]` |

于是出现一种**自相矛盾的状态**：

> **store 说它属于这个组，屏幕说它不在框里。**

框不移动、不缩放，也不提示。撤销是有的（`Cmd+Z` 后子节点回到 (62,62)，
past 归零）—— 缺的不是撤销能力，是**跟随**。

## 二、空组照样画完整框：这就是 756 那次掏空的最终形态

`g-245IDFh8sB` 在种子里 `children=[]`（这不是 756 造成的，种子本来就是空的），
所以不用重跑 756 就能直接观察空组：

| | 空组 `g-245IDFh8sB` | 有子节点组 `g-EFbbHpwq5w` |
|---|---|---|
| `children` | **[]** | `["v-UGQZzZOpbv"]` |
| 框尺寸（未缩放） | **430×452** | 722×460 |
| 标题 | 「分镜图 · 第一集：咖啡馆对峙-图片组」完整显示 | 「视频组 · …」完整显示 |
| handle | **左右各 1 个** | 左右各 1 个 |
| `borderColor` | `1px white/10` | `1px white/10` |

**空组和有子节点的组在渲染上完全同形。** 这直接补上了 756「不声称」里留的
那一格：756 把 `g-EFbbHpwq5w` 的 children 从 1 掏成 0 之后，屏幕上是一个
**原封不动的旧框**（连同原标题「视频组 · 第一集：咖啡馆对峙-视频组」），
用户在界面上**没有任何线索**能看出它已经空了。

更上一层：空组**仍然带左右两个 20×20 的 handle**，也就是说一个 0 成员的分组
**仍然可以当连线端点**。

## 三、`groupKind` 是写而不读的死字段

`groupKind: "selection"` 只在 `canvasStore.ts:3298`（`groupSelectedNodes` 里
新建「组合节点」时）写入，**全 `src/` 没有任何一处读它**。

后果：「组合节点」与种子分组在渲染上**完全同形**，只有 `title` 不同
（「组合节点」vs「分镜图 · …-图片组」）。这个字段本可以承载语义差异
（组合出来的组和素材自带的组应该有不同视觉或不同操作集），但没接上。

顺带查清一个探针读错的地方：两个种子分组的 `-1001` 层叠写在
`style.zIndex` 里（`canvasStore.ts:787/799`），**顶层 `zIndex` 是 null**；
`groupSelectedNodes` 则顶层和 `style` 都写。DOM 上实测 wrapperZ = `-1001`，
两个来源一致。

## 四、视觉细节与一处对比度缺陷

`variant` 驱动外观（`:22`），两组的差别全部实测到：

| | `variant=image` | `variant=video` |
|---|---|---|
| 圆角 | **20px** | **4px** |
| 底色 | `oklab(… / 0.1)`（white/10） | **`rgb(33, 33, 33)`** = #212121 |

**选中时**（两个组一致，且都带「点中后真的进了 selected 态」的阳性对照）：

| 读数 | 未选中 | 选中 |
|---|---|---|
| `borderColor` | `oklab(…/0.1)` | **`rgb(9, 202, 245)`** = #09caf5 |
| `boxShadow` | 无 | **新增** |
| 标题 `color` | `rgb(119, 119, 119)` | **`rgb(119, 119, 119)`（不变）** |

**标题颜色恒定。** 框变青、shadow 出现，标题一动不动 —— 而在 zoom 0.375 下
这个框只有 271×173 屏幕像素，标题是框外上方 11px 的 `rgb(119,119,119)`。

由此算出一处对比度问题（对比度在汇编器里现算，不手抄）：

| 情形 | 对比度 | AA 阈值 4.5 |
|---|---|---|
| 标题压在 #212121 上 | **3.6 : 1** | **不过** |
| 标题压在画布底 #141414 上 | **4.11 : 1** | **不过** |

标题是画在**框外**的（`overflow: visible` + `-top-8`），所以它实际压的
是画布底色；但图片组那段框几乎贴着它，视觉上仍会读成「框上的字」。
**同一段文字的对比度取决于它旁边恰好有没有框** —— 这本身就是缺陷。

另外两格正向读数：

- **框内空白可点中**（`insideGroup=true`）⟹ 「点分组选中它」这条路是通的；
- **标题 `pointer-events: none`**，打标题**自身**中心点落到 `react-flow__pane`
  ⟹ 标题不吃点击。

## 五、平移机制：三路实测（把 753 的静态读法钉成结论）

753 从静态得出「`panOnDrag={[1]}` 是中键」。本批做了三路对照，**带阴性对照**：

| 组 | 操作 | 视口是否平移 | 屏幕位移 |
|---|---|---|---|
| b1 | 左键拖空白，**不**按 Space | **否** | `deltaX=0` |
| b2 | 左键拖空白，**按** Space | 是 | `deltaX=200` |
| b3 | **中键**拖空白，不按 Space | 是 | `deltaX=200` |

`:477` 是 `effectivePan = canvasTool === "pan" || isSpacePressed`，
`:1550` 是 `panOnDrag={effectivePan ? [0, 1] : [1]}`。

关键在于**读懂按钮数组**：`event.button` 是 0=左 / 1=中 / 2=右，
所以 `[0,1]` 是「左键+中键」而不是「排除 0」。这解释了 b1 与 b2 的差别，
也让 753 那条静态结论得到实测确认（**不是推翻，是补齐**）。

还有一格：按住 Space 后拖节点 → `nodeMoved=false`、`pastDelta=0`，
同时画布 class 从 `react-flow bg-[#141414] light` 变成
`react-flow cursor-grab bg-[#141414] light`。
Space 是「临时切到平移模式」，光标变抓手、节点变不可拖，两个反馈都验到了
（`:1554 nodesDraggable={canvasTool === "select" && !effectivePan}`）。

## 七、探针与验收器返工五处（探针四处 + 验收器一处）

| id | 现象 | 教训 |
|---|---|---|
| R19 | 拖动计划算出终点 x=1651 超出 1440 视口，第一版**没有护栏** | **算出「需要越过边界」的坐标时必须先问它在不在视口内**；越界要么拒绝记录，要么改合法路径后重算 |
| R20 | 把「Space + 左键拖 = 平移」当成已知机制写进代码，没验 | **鼠标按钮数组要按 DOM 语义读**：`[0,1]` 是左+中，不是「排除 0」。凭直觉解释会把结论读反 |
| R21 | `groupZ` 读了 `n.data.zIndex`（空路径）⟹ 读到 `null` | **属性路径取不到值时先确认路径对不对**，并在产物里注明这个 null 是路径问题还是真没有 |
| R22 | 用「标题**上方 6px**」证明标题不吃点击 —— 那个点本来就在 pane 上 | **证明「某元素不吃事件」必须打在该元素身上**；打旁边空白只能证明空白是空白 |
| R23 | **验收器自己的洞**：核心结论在产物层没有任何断言 | **阴性对照要专门试「只改结论不改读数」** |

R22 尤其值得记：757a 那格读数「命中 pane」看着像证据，其实**推不出任何结论**，
是 757c 改打标题中心才真的钉住的。

**R23 是本批最值钱的一条**。第一版验收器 53 条检查里，核心读数那一格是
**直接从 `/tmp` 原始 JSON 现取**的，压根不经过产物 —— 于是把判据 13 的结论文本
从「框不移动」改成「框移动了」，**一条检查都没挂**。等于「只改文案不改读数」
可以蒙混过关。补法是把 `before/after` 现算出四格派生布尔写进 `evidence`，
再加三条检查（派生值本身、派生值与读数自洽、文案与派生值一致）。补完后重跑
**8 发注入全部被拦**：改文案 / 伪造 `groupDomResized` / 伪造 `childMoved` /
伪造标题变色 / 伪造对比度 9.0 / 伪造阴性对照 `deltaX=200` /

## 九、不声称

- 只测了 fitView 后 zoom=0.375 **一个缩放档位**，其它 zoom 下的命中与尺寸没测
- 「组合节点」的视觉与种子分组同形，但**没有实际跑一次组合再测它的 DOM**
  （756 测了 store，本批测了 seed 分组的 DOM）
- **分组框本身能不能被拖动**没测（只测了子节点能不能拖出）；
  `canvasTool=pan` / `select` 两态也没分别测
- 标题**换行/超长**没测：两个种子标题长度接近，只取到一种宽度读数
- 未选中态的 border/底色是 `oklab(...)` 形式（Tailwind v4 把 `white/10`
  编译成 oklab），探针的对比度解析只处理 `rgb()`/hex ⟹ 判据 9 只覆盖
  **选中后的青色与画布底色**，未选中底色上的对比度没算出来
- handle 的 20×20 是按 zoom 0.375 换算的结论，没有在第二个 zoom 档位复验
- 拖出用的是**水平**方向；垂直方向、拖到别的分组里、拖出视口后再平移回来都没测
- **没有与源站对照**：源站的分组是否会跟随成员、是否有 resize 行为，未知
- 757b 只测了 pan 三路与 Space 抑制节点拖拽；`canvasTool=pan` 工具按钮态下
  `panOnDrag=[0,1]` 与 `[1]` 两分支没有分别单独验证
