## 二、源站实测：这个「查看角色资产」点开是什么

### 2.1 找到它之前，连踩了三个坑

| 坑 | 现象 | 真因 |
| --- | --- | --- |
| v1 | 面板**明明开着**（截图里那个 1198×758 的大弹窗），可读数器**一根叶子文本都读不到** | ★ **读数器的元素类型覆盖不全** —— 面板里的「性别／年龄段／文化区域／创建新角色」全在 `<button>` 里 ⟹ 只扫 `span/div/p/label` 就会以为「面板没开」 |
| v2 | 怀疑面板在 **iframe** 里 ⟹ 去数 iframe | ★ 主文档里**有**那个按钮（「我的角色库」BUTTON @385,183）⟹ ⟹ **假设被否**，面板就在主文档 |
| v3 | 在「**我的角色库**」页签里找不到那枚浮层 | ★★ **前提不成立** —— 源站那枚浮层**只在「官方角色库」页签**里（826/827 的 raw 记的也是那一页签）⟹ ⟹ 「找不到」≠「不存在」 |

★ 三个坑合起来是一条通用教训：**「读不到」有两种完全不同的成因** ——
「**读数器坏了**」（元素类型/文档不对）与「**东西不在这一页**」（前提不成立）。
⟹ 先问「**我读的那一类东西对不对**」，再问「**它在这一页吗**」。

### 2.2 ★★ 浮层是 `pointer-events-none` ⟹ **必须先悬停**

源站那枚浮层的 class 里写死了 `pointer-events-none`，而 `group-hover` 会把它放开：

| | opacity | pointer-events |
| --- | --- | --- |
| 未悬停 | `0` | `none` |
| 悬停后 | `1` | `auto` |

⟹ ★ **直接点它 ⇒ 事件穿透**到下面的卡片 ⟹ 什么也不会发生；
⟹ ★ 正解是：**先悬停 ⟹ 等样式生效（≥1s）⟹ 再点**。

## 三、clone 的改动

### 3.1 「查看角色资产」不再是死按钮

`src/components/CharacterLibraryPanel.tsx`：那枚浮层从 `<span>` 变成可点击的
`role="button"` ＋ `tabIndex` ＋ `onClick`（**`stopPropagation`** —— 它在卡片
`<button>` 里面，不拦就会连「选中」一起触发）⟹ 点它 ⟹ 打开资产视图。

### 3.2 资产视图（几何全走普通 CSS）

`src/components/character-studio.css` 新增 `.cs-assets-stage` / `.cs-asset-strip` /
`.cs-asset-img` / `.cs-voice-row` / `.cs-voice-btn` 五条规则，
坐标**逐条照抄 §2.3 的源站实测**（相对 `.cs-content`）。

★ 为什么走普通 CSS 而不是 Tailwind 类：**4317 的 Tailwind 扫描是冻结的**，
新增任意值类在 dev 上不生成。

### 3.3 ★★★ Esc 只关资产视图 —— 靠**前台阻塞面**，不是组件本地状态

这是本批最难的一处，前后试错了三版：

1. ✘ 组件本地 `useState` ＋ `window` 监听 ⟹ **面板和资产视图一起消失**；
2. ✘ 组件本地 `useState` ＋ React `onKeyDown` + `stopPropagation()` ⟹ **还是一起消失**；
3. ✘ 容器上的**原生** `addEventListener` + `stopPropagation()` ⟹ **还是一起消失**。

★★ **根因**（查出来了）：
- clone 的面板是被 `app/page.tsx` 的**全局** keydown 监听关掉的
  （`uiState.closeTopForegroundSurface()`）；
- 那个监听挂在 **`window` 的捕获阶段** ⟹ ★ **它比任何元素上的监听都早**
  ⟹ ⟹ **元素级监听永远拦不住它**；
- 而且**焦点不在模态里**时，keydown 的 target 是 `body` ⟹ 模态里的监听**一个都收不到**
  （实测：window 上一个 keydown 都没收到）。

⟹ ★★ **正解**：把资产视图登记成**前台阻塞面** —— clone 本来就有这套机制
（`resolveLibTVBlockingForegroundSurface`），`storyboard-editor` 就是这么做的：

- `src/lib/libtvSelectionCommandContext.ts`：阻塞面表加 `"character-assets"`，
  并在解析里**排在 `activePrimaryPanel` 之前**（它是 primary-panel 的**下一层**）；
- `src/store/uiStore.ts`：加 `characterAssetsId` ＋ `setCharacterAssetsId`，
  并在 `closeTopForegroundSurface` 里加 `case "character-assets"`；
- `src/components/CharacterLibraryPanel.tsx`：状态**改读 store**（组件本地状态那一层看不见）。

⟹ 实测：按 Esc ⟹ **资产视图关了、面板还在** ✔

★ 顺带：换/关面板时顺手清掉 `characterAssetsId` ⟹ 否则它会**残留**成一个
「谁也关不掉、Esc 也只关它」的死状态。

### 3.4 图源

仓库里只有**一张角色**的 4 张详情图（`character-detail-1..4.webp`）⟹
第 1 个角色用这 4 张，**其余角色复用缩略图**（与既有 spec 的约定一致）。

## 五、本批踩到的第三类坑：**我量到的不是服务端现在下发的那个东西**

这一类坑本批撞上了**三种形态**，一层比一层阴 ⟹ 每一层都写在这儿。

### 5.1 第一形态：dev server 的 **CSS 重建是异步的**

现象：CSS 明明已经改成「按钮不再绝对定位」，可读数还是旧的（按钮跑到 @1036,1002）。

排查过程：把**服务端实际下发的 CSS chunk** 抓下来跟**磁盘上的文件**对拍 ⟹
⟹ **服务端那份还带着 `position:absolute; top:367px; left:535px`** ⟹
⟹ 也就是说**我量的是旧 chunk**。

⟹ ★ 根因：**重建是异步的** ⟹ 改完立刻量，量的可能是**上一版**。
⟹ ★★ 正解：**量之前先确认服务端已重建** —— 抓 chunk 下来确认新标记在。

★ 这一条与已入库那条「**读数对不上时先怀疑自己的动作**」同族，
但方向相反：那次是「怀疑动作」，这次是「**怀疑环境**（构建产物没跟上）」。

### 5.2 ★★★ 第二形态：**Turbopack 的持久缓存把陈旧的编译结果原样吐出来**

阴性对照跑到一半，本批撞上了比 5.1 **阴得多**的一种：

- 磁盘上的 `src/components/character-studio.css` **已经是** `left: 139px`（源码里甚至**一处 `100px` 都没有**）；
- 可**服务端下发的 chunk** 还是 `left: 100px` —— 那是**阴性对照注入期**的值；
- ⟹ **重启 dev server 也不行**（新进程照样吐旧的）；
- ⟹ **删掉 chunk 文件也不行**（dev server 认为它还在，直接 404）；
- ⟹ ★★ **只有 `rm -rf .next/dev/cache/turbopack` 才恢复**（那份缓存有 1.8G）。

⟹ ★★★ 真因：**Turbopack 的持久缓存**（`.next/dev/cache/turbopack`）里存着**陈旧**的编译产物，
**磁盘改了它也不会失效** ⟹ ⟹ 光「等一会儿」**不够**、光「重启」**也不够**。

★ 这一条最贵的性质是：它**长得跟「我的改动没落地」一模一样** ⟹
  若不是把服务端 chunk 与磁盘**逐条对拍**，我极可能会把结论写成
  「**我的代码没生效**」⟹ ⟹ 那是**一条假陈述**。

★ 顺带：dev server 自己也给不出线索 ⟹ 日志里**没有任何报错** ⟹
  ⟹ 「**不报错、只给旧的读数**」是这一类失败的标志。

### 5.3 ★★ 正解：门禁加一道**前置检查**

`scripts/verify-liblib-batch839.py` 现在**先**做一件事：
**抓 dev server 正在下发的 CSS chunk，与磁盘上的关键声明对拍**
（`.cs-asset-strip` / `.cs-asset-img` / `.cs-voice-row` / `.cs-voice-btn`
的 `left` / `top` / `width` / `height`）⟹

- 不一致 ⟹ **等**（最多 90 秒，容许异步重建）⟹ 仍不一致 ⟹ **显式失败**
  （退出码 2 ＋ `PREFLIGHT-FAIL` ＋ 提示要清 Turbopack 缓存并重启）⟹
  ⟹ ⟹ **而不是**给出「像真的、其实是假的」红；
- 一致 ⟹ 才进入读数阶段。

★ 解析 CSS 时有**两个坑**，都踩过：
① 只认**精确等于**该选择器的规则体 ⟹ 否则会把分组规则
`.cs-assets-stage .cs-asset-strip, … { pointer-events: auto; }` 的声明算到 `.cs-asset-strip` 头上；
② **先剥注释** ⟹ 否则磁盘上「选择器上面那条注释」会被并进选择器 ⟹
⟹ 精确匹配**永远对不上** ⟹ 第一版就是这么误报成「磁盘上找不到这个选择器」的。

### 5.4 ★★★ 判据自己也要**能被证伪** —— 两处同型教训

⟹ 前置检查是**否定性判据**（「没发现不一致」）⟹ 一个永远返回「一致」的检查器
会把**所有**陈旧读数放过去 ⟹ ⟹ 于是写了
`probes/preflight_selftest839.py`：**三条臂**证明它**能发现**陈旧 chunk ——
A「值不同」（伪造 chunk）／B「选择器缺失」（伪造空 chunk）／
C「真·端到端」（真的改磁盘 ⟹ 在 watcher 追平前抓到瞬时差异）⟹ 三条都过。

⟹ ★★ **同型第二处**：阴性对照 **N7** 第一版**没翻红**
（期望 S7 红，实际 7/7 全绿）⟹ ⟹ 查出来是**判据太松**：
S7 原本只查「README **全文**里有没有出现过 `mock`」⟹ 而 README 里有**三处** `mock` ⟹
N7 只改掉其中一处 ⟹ 判据照样绿 ⟹ ⟹ **负控自己暴露了判据的缺陷**。

⟹ ⟹ 两边都加硬：① 门禁 S7 改成**定位到 §2.4 那一节**（记录「选择角色音色」实测的那一节）
去查 `mock`；② N7 改成**改掉全部** `mock` 标注 ⟹ ⟹ 重跑后 N7 精确只红 S7。

★ 通用形态：**否定性判据要么「定位到具体位置」，要么「清空全部出现处」** ——
**全文弱存在式**（「有没有出现过某个词」）几乎等于**没有牙**。

## 六、回归：一次**受控对照实验**，查出两条门禁的旧账

★ **做法**：一次**受控对照实验** —— 把本批改动的 4 个源文件**按字节备份**、
`git checkout --` 回到 HEAD（839 之前）、**重跑**这两条门禁、记录读数，
再把文件**逐字节复原**（用 SHA-256 对拍确认复原无残留）。

| 门禁 | HEAD 基线（撤掉本批改动） | 带本批改动 | 差 |
| --- | --- | --- | --- |
| `736` | **5/10**（C1／C3／C4／C7／C9 红） | 5/10 → **6/10**（C9 修好后） | 本批**没**打破任何一条 ⟹ 还顺手修好了一条 |

★ 两个结论：
