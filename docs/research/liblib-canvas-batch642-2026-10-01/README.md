# Batch 642 —— 把「圆控件只能取中心点」写进**共享判据**，并因此挖出 640 的第二个盲区

## 零源站断言

本批只主张 clone 的读数与判据的性质，**不主张源站任何事**。

## 一、为什么要动共用文件

631 立过一条纪律：**不为一个批次的提问改所有批次共用的判据**（先看几何能否回答）。
本批是那条纪律的**明确例外**：641 证明晶格探针在 `rounded-full` 控件上落在形状的
**亚像素边界**上（余量 0.01px），于是「圆控件该用中心点」这条规则必须**对所有后来者
可见**，否则每个新批次都要重踩一遍。

改 `verify-liblib-batch617.py` 的 `AUDIT_JS`，**只增不改**：

```
items[].round           半径 ≥ 短边一半
items[].borderRadiusPx  实测计算半径
items[].samplePoint     固定 "centre"
items[].sampleNote      圆控件才有的说明
return.roundControls    圆控件清单
```

`own` / `clipped` / `panel` / `timelineOverlay` / `viewportSqueeze` /
`hitInBottomBar` / `hitInShotBar` **一个都没动**。

## 二、零回归是**机械证明**的

```
verify-liblib-batch639.py  → 15 checks, 0 failures
verify-liblib-batch640.py  → 14 checks, 0 failures
git diff --quiet <两份已落盘 audit>  →  IDENTICAL
```

**一个字节都没变。** 这是「只增不改」的可执行形式——不是声称，是 `git diff` 的结果。

## 三、共享判据立刻挖出 **640 的第二个盲区**

普查找到的圆控件是 **8 枚，不是 6 枚**。多出来的两枚是
**`上传图片` 与 `发送`**（各 32×32，提示条内），而 **`发送` 在 7 个宽度里有 6 个
中心被挡**。

关键在于：**640 搜的是「中心干净 **且** 身体被挡」，结构上永远搜不到中心就被挡的
控件**。那属于另一个类，普查把它归进 `clipped` 桶。**640 的盲区搜索自己有一个
看不见的盲区** —— 而它当时还断言「唯一无法解释的被盖是 632 那一处」，那句话是对的，
只是覆盖面不够。

## 四、`发送` 在 1440 是一个**真缺陷**（clone-only，未修）

| 宽度 | `发送` 中心命中 | 归因 |
| --- | --- | --- |
| 339 / 480 / 620 | **null**（出屏） | 提示条比窗口宽、横向出屏 |
| 898 / 899 / 1024 | **null**（出屏） | 同上 |
| **1440** | **属性列的 `div`** | 盒 `[1200,679,32,32]` 落在属性列矩形 `[1160,157,280,561]`（b=718）**之内** |
| 1920 | 自身 | 干净 |

1440 是**桌面宽度**，那里的 `发送`（一个主动作）**被属性列压住、点不到**。

而普查把它归进 `clipped` 桶（`clipped: True`），**不是**「被盖」——所以它从边界轴上
溜掉了，两条轴都报 0。**「被裁」与「被盖」在现实中并不互斥，普查先判了前者。**

**不修**，理由是纪律而不是懈怠：提示条与右列谁该压过谁，是**版式决定**，
而**源站在这个宽度上的行为未取证**。本批把它**钉成一条带精确边界的候选缺陷**，
和 632 的 170px 居中组同等对待（那一件已经这样挂了十批）。

## 五、判据自己踩的坑：`cs` 撞名

第一次改完，**639 与 640 双双崩在 `AUDIT_JS`**：
`ReferenceError: Cannot access 'cs' before initialization` —— 循环顶部早就有
`const s = cs(el)`（取 zIndex 的辅助函数），我在同一作用域声明
`const cs = getComputedStyle(el)`，把上面每次 `cs(el)` 调用变成了 TDZ。

**在别人的共享脚本里加变量，先把该作用域已绑定的名字读完。** 这条坑与批次内容无关，
但它让「只增不改」在第一次尝试时是**假**的。

## 不声称

- 源站任何事；尤其**不主张源站的提示条与右列谁压过谁**，那是 1440 下 `发送` 的处置依据。
- 提示条在 ≤1024 横向出屏**是不是缺陷**：普查判它「可滚动到」（与 621 的窄屏工具条
  同一模式），所以它不进 `unreachable`。**该模式在本批未被重新评估。**
- `上传图片` 与 `发送` 是**仅有的**两枚非 gizmo 圆控件——**在这 7 个宽度下**。
