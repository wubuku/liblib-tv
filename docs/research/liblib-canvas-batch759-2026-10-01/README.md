# batch 759 — `/project` 页首轮普查：查出一处**高严重度缺陷** + 一条跨批次的连锁

## 起点

755 在验画布下拉时**只预看了一眼** `/project` 就转去画布了。这一页有
**21 个 `data-*` 钩子**，一个都没被系统量过。

静态普查先给出四条预测（全部来自 `src/app/project/page.tsx`）：

| | 预测 | 结果 |
|---|---|---|
| P1 | 回收站写「仅显示最近 30 天内删除的内容」+ 每项「剩余 30 天」，但代码里没有任何时间过滤 | ✅ 成立，且比预测更严重 |
| P2 | 卡片副行日期是 `{today}`，所有卡片同一天 | ✅ 成立 |
| P3 | 侧栏 7 项里 6 个是「本地原型：X 未接入」 | ✅ 成立，连促销/帮助/新建文件夹共 9 个 |
| P4 | `openCanvas` 先 `setActiveCanvas` 再 `window.open("/")`，而 store 无持久化 | ✅ 成立 |

## 一、缺陷：点项目卡，新标签页不是你点的那张

`project/page.tsx:28-31`：

```tsx
const openCanvas = (canvasId: string) => {
  setActiveCanvas(canvasId);
  window.open("/", "_blank");
};
```

实测（点 `canvas-1` 的卡）：

| 读数 | 值 |
|---|---|
| 被点的卡 | `canvas-1`（**0 个节点**），`hitSelf=true` |
| 点之前本标签页 active | `canvas-2` |
| 点之后本标签页 active | **`canvas-1`**（`setActiveCanvas` 确实执行了） |
| 新标签页 URL | `http://localhost:4317/` |
| 新标签页 active | **`canvas-2`** |
| 新标签页节点数 | **10** |
| `showsTarget` | **false** |

被点的画布 0 个节点，新标签页显示 10 个 —— **内容肉眼可辨地不是同一个**。
用户在新标签页里会以为自己点错了。

根因：`activeCanvasId` 只活在内存里，新标签页拿到的是种子 store。

## 二、回收站：30 天是声明，没有任何实现

面板顶上写着「仅显示最近 30 天内删除的内容」，每个条目写着「· 剩余 30 天」。
代码里这两句都是**字面量**，周边 160 字符内没有任何 `Date` / `dayjs` / `diff` / 减法。

用「老化实验」把两者分开（⚠ 这一格是 `store.setState` **程序化造数**，
用来区分「硬编码」与「恰好都是今天」）：

| | `removedAt` | 条目文案 |
|---|---|---|
| 改之前 | `2026-10-04` | 「画布 1 2026-10-04 · 剩余 30 天 恢复」 |
| **改之后** | **`2025-01-15`**（约 20 个月前） | 「画布 1 **2025-01-15** · 剩余 **30 天** 恢复」 |

**日期变了，「剩余 30 天」一字未变**，而且 20 个月前删掉的东西照样列在
「仅显示最近 30 天内删除的内容」面板里。

## 三、★ 默认状态下，回收站永远填不满（跨批次连锁）

759a 看到「回收站为空」。这**不能**直接断言「回收站坏了」——按分层归因分三步测：

| 档 | 行内菜单 4 项 `hitSelf` | 删除项落点 | 确认框 | removed | 回收站 |
|---|---|---|---|---|---|
| **2 张画布（默认）** | **1/4**（只有「在新窗口打开」可点，与 755 一致） | **`IMG`**（画布上节点的缩略图） | 未出现 | **0** | 空 |
| **6 张画布 · 顶行** | **4/4** | `BUTTON` | 出现（取消 50×30 / 确认 48×30） | **1** | **出现该条目** |

第二档是关键：**同一份代码、同一套菜单，在 6 张的顶行 4/4 可点**，删除走通全链，
走到 `/project` 回收站里真的出现了「画布 6 2026-10-04 · 剩余 30 天 恢复」。

⟹ 变量是**列表长度与行位置**，不是功能缺失。**这正是 755 的缺陷**：
行内菜单被祖先 `overflow:hidden` 裁掉（菜单底 351 > 容器底 246）。

合起来是一条完整的链：

> **755 的行内菜单缺陷** ⟹ 默认 2 张画布下删不掉画布 ⟹ **759 的回收站在默认状态下永远为空**

单看任一批都发现不了这条链：755 只看到菜单不可点，759 只看到回收站是空的。

| 读数 | 值 |

## 五、store 的存续分两种：客户端路由保留，整页加载丢失

| 路径 | removed |
|---|---|
| TopNavBar →「全部项目」（`router.push`） | **1**（还在） |
| 新标签页 / 手动输 URL（整页加载） | **0** |

755 记过一句「回收站按钮没观察到，store 无持久化，导航时已空」。
**这批把那句话说窄了**：客户端路由下 store 是保留的、回收站能看到刚删的画布；
只有整页加载/新标签页才清空。（纠正记在本批，历史行不改写。）

顺带查清入口：全仓库 `router.push("/project")` **只有一处** ——
`TopNavBar.tsx:287`（`TopNavBar` 由 `app/page.tsx:1439` 渲染）。

## 六、另外三条

**★ 卡片副行日期对所有卡片都是「今天」**：

| 卡 | 副行日期段 |
|---|---|
| `canvas-1` | `2026-10-04` |
| `canvas-2` | `2026-10-04` |

（两张卡的完整 spans 本来就不同 —— 名字与节点数不同，只有日期段相同。）

副行直接渲染 `{today}`（`page.tsx:25`），**完全没有读 `canvas.createdAt`**，
而运行时两张卡的 `createdAt` 都是 `null`。

⚠ 更正一版更粗的说法：`createdAt` **在 store 的类型里是存在的**
（`createdAt: string;`），只是：① 种子画布从没给它赋值；② 页面根本不读它。
所以修法是「赋值 + 读它」或「去掉副行日期」二选一，**不是新增字段**。

**★ 点「回收站」不会清掉上一条提示**：

| 操作 | 底部状态行 |
|---|---|
| 点「新建文件夹」 | 「本地原型：新建文件夹未接入」 |
| 再点「回收站」（面板确实开了，`aria-expanded` false→true） | **仍是同一句** |

页面底部只有一行 `status` 状态位，而回收站按钮的 `onClick` 只 `setRecycleOpen`，
**不碰 `status`**。于是上一条 stub 提示会一直挂着，和刚发生的操作对不上。

**9 个按钮只弹「本地原型：X 未接入」**：侧栏 7 项里的 6 项（首页 / LibTV Agent /
创作者挑战赛 / Blender 插件 / LibTV Plugin / 百万积分大包上线）+ 积分超市 + 帮助 +
新建文件夹。唯一有真行为的是 active 的「项目」项（`setStatus("")`）。
每一条都带 `hitSelf` 阳性对照。

## 八、返工五处（四处探针 + 一处验收器）

| id | 现象 | 教训 |
|---|---|---|
| R29 | `el.closest === it` —— **无参** `closest()` 只返回元素自己 | 于是点落在 button 的**子元素**（文本/图标）上就判 `hitSelf=false`，读数变成 2 张与 6 张都是 0/4，**与 755 已确认的阳性对照直接矛盾** —— 正是这个矛盾让我回头查探针。**`closest()` 必须带选择器** |
| R30 | 行内菜单压根不在 DOM 里就开始量 | 菜单是 `menuOpenId === canvas.id` 才渲染的，开关是行尾那个 `aria-label="更多操作"` 的按钮（`opacity-0`，靠悬停行显形）。**量条件渲染的元素前先把打开它的交互走一遍**；「找不到元素」的第一嫌疑是「没打开」 |
| R31 | B3 点了「另一张」却拿「目标」去比，结论无效 | 第一版跑出 `showsTarget=False` 时看着像缺陷，其实被点的那张恰好是默认画布。**对照实验里被测对象与比较基准必须是同一个 id** |
| R32 | 把 755 的「导航时已空」当成普遍结论 | 分层归因后发现客户端路由**是保留 store 的**，755 那句话过宽。**「某状态是空的」要分清渲染逻辑坏 / 数据本来没有 / 加载方式丢状态**；收窄上一批的结论要显式写出来 |
| R33 | **验收器自己的洞**：负向对照把 `deleteItem.hitSelf` 伪造成 `true`（谎称默认 2 张下删除项可点）竟然跑出 51/51 全过 | 同一事实在产物里存了**两份**（`items` 列表项 + 单独的 `deleteItem` 对象），检查只读了前者。**负向对照要挑「看起来像重复、实际没人看」的字段去伪造** |

R29 与 R33 值得单说：

- **R29**：「读数与已确认结论冲突」是最可靠的探针缺陷信号，
  比「读数看起来不对」强得多。
- **R33**：负向对照不只验产品，也**验验收器自己**。这次它抓到
  `deleteItem.hitSelf` 这个字段根本没被任何检查读到 —— 也就是说
  产物里两份重复表达同一事实的地方，只有一处被守住。补完断言后
  **5 发注入全部被拦**。

## 十、不声称

- 本批**没有与源站对照**（源站的 `/project` 结构与回收站策略未采样）
- 6 张画布那档是**程序化** `addCanvas` ×4 造出来的，不是用户点「新建画布」4 次；
  真实路径下的时序/焦点行为未测
- 「剩余 30 天」的老化实验用 `store.setState` 改 `removedAt`，是**程序化造数**；
  真实用户能否造出 20 个月前删除的画布，取决于 store 有没有持久化（当前没有）
- 画布页通往 `/project` 的入口只验了 TopNavBar 那一处；
  键盘可达性、面包屑、浏览器前进后退都没测
- 「新建项目」（`addCanvas` + `window.open`）**没有单独验** ——
  它与判据 10 同一条链路，但新标签页里同样看不到新建的画布，这一格未单独取数
- 项目卡没有右键菜单、拖拽排序、重命名入口、删除入口 ——
  **这四格只做了存在性判断，没有逐个找过**
- 没有真的点「恢复」与「恢复所选」验证画布回到列表
- 没有测回收站面板的宽度/滚动/与列表的相对位置在多项目下的表现
- 横幅是硬编码营销文案，没测它与源站的时效一致性
