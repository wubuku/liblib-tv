## 方法论

1. **定性的根因要拆成两笔账分别算** —— 716 说根因是「clone 侧两个决定叠加」，
   但没算各自值多少。**分开算之后结论完全不对称**：
   一处改动余 312 vs 三组削功能。用户能直接选了。
2. **「控件集更大」要落到具体宽度** —— 源码注释里那句自陈没有数字，
   **558 / 711** 才是能拿去拍板的数字。
3. **对账要平，残差要归因** —— 逐组相加比容器窄 14；
   第一版只算了 margin（12）、**差 2 没交代**，补上 border 才归零。
   **残差不为 0 时必须指出是哪一项，不能含糊过去。**
4. **「至少要动几个」要用最大组合验证，不能顺手加一个同类项** ——
   第一版把「模型库」当成比「虚拟相机」宽，算出 264 就说四枚够用，
   实际两者都是 32；正确答案是 **248，差 2px**。
5. **上一批的「常数」要先验证是不是常数** —— 715 记的「内容恒为 944」
   在 700 下变成 885。**跨视口的量先扫一遍再当常数用。**
6. **断点结论不能跨元素套用** —— 717/718 建立的 899 断点在底部条这一层不成立。

## 探针返工五处

1. `parseFloat(cs.paddingLeft) + parseFloat(cs.paddingRight)` 写成字符串相加 ⟹ `TypeError`。
2. **第一版断言 `aspect + grid + crowd + vcam == 232 < need` 是链式比较** ——
   `a == b < c` 解析成 `(a==b) and (b<c)`，于是 `232 == True` ⟹ 误报失败。
   **链式比较在断言里几乎总是错的**（第二次栽在 `== 252 >= need`，同一个坑）。
3. **把「模型库」误当成比「虚拟相机」宽的项**，导致「四枚够用」的结论；
   实际四枚最多 232，差 18。
4. 断言 `contentW == 944 for all vw` **被窄屏的真实读数打掉**（700 下 885）——
   这次是我的错，但暴露了一条 715 没写对的「恒为」。
5. `results.update(got)` 写在判据之前，`check_7` 往 run 里写的 `narrowBoundary`
   不会落进 audit ⟹ 挪到判据之后。
