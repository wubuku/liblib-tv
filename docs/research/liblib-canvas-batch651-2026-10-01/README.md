# batch 651 —— **撤回 650 的头条读数**：那是 Playwright `hover()` 自动滚动的伪影

## 一句话

650 报「`camera-fov-help-tooltip` 在 1280×720 被一条 `z-20` 的 `section.sticky.top-0`
盖住 62/68（91%）」，并写成「只发生在 1280×720 ⇒ 宽度驱动」。
本批去收边界，第一步就撞上矛盾，最后查明：
**那条读数量的不是布局，是 Playwright 为了够到 badge 滚了多少。**
把滚动显式钉成 0、只用指针（不做自动滚动）后，
提示条恒在 `y=1042`、sticky 底沿恒在 `325` —— **六个窗高全部不相交**。

## 1. 矛盾是怎么冒出来的

去收边界时发现窗高 **640 不被盖、680 被盖**，而 670→680 之间
badge 的 y **整条祖先链每一级都同移 123px**：

    span[data-director-camera-fov-help-badge]   y 472 → 349   (−123)
    div[data-director-camera-fov-field]         y 472 → 349   (−123)
    div.space-y-3.border-t                       y 269 → 116   (−123)
    div.space-y-4.px-4.py-3                      y −489 → −642 (−123)   高恒 1185
    div.min-h-0.flex-1.overflow-y-auto           y 157 → 157   (  +0)   高 301 → 341

一个「由高度决定位置」的元素不会这样跳。**倒数第二级就是答案**：
`div.space-y-4.px-4.py-3` 的 **y 是负的、高恒 1185**，而它坐在
`div.min-h-0.flex-1.overflow-y-auto` 里 —— **那个容器被滚动了，滚动量恰好 123**。

滚动是谁发起的？`626.open_overlay` 的 `@fov-hover@` 走 Playwright 的
`locator.hover()`，而 `hover()` 会 **`scrollIntoViewIfNeeded`**
（Playwright 自己的重试日志里就写着 `scrolling into view if needed`）。
**提示条是贴着 badge 定位的** —— badge 一被滚，提示条跟着动。

## 2. 铁证：六个窗高，六个滚动量

| 窗高 | `hover()` 选中的 `scrollTop` | 提示条 y | 被盖面积 |
|---|---|---|---|
| 560 | **756** | 286 | 8112 |
| 640 | **676** | 366 | 0 |
| **720** | **779** | 263 | **12896** |
| 800 | **724** | 318 | 1456 |
| 900 | **624** | 418 | 0 |
| 1150 | **374** | 668 | 0 |

**650 那个 12896 在这里被逐像素复现了** —— 条件是 `scrollTop = 779`，
而 779 是 Playwright 在那一格自己挑的。同一个布局给出六个不同的提示条位置。
**一个随探针变化的量不是页面的属性。**

（顺带：**650 那句「宽度驱动」也是错的** —— 固定 720 高、把宽度从 1024 扫到 1920，
**每一格都被盖**。驱动的从来不是宽度。）

## 3. 正确口径下的读数：钉住 `scrollTop = 0`，只用指针

| 窗高 | scrollTop | badge y | 提示条 y | sticky 底沿 | 相交 |
|---|---|---|---|---|---|
| 560 / 640 / 720 / 800 / 900 / 1150 | **0** | **1118** | **1042** | **325** | **全部否** |

**三个量都与窗高无关。** 提示条恒在 1042，离 sticky 底沿 325 有 **717px**。
被盖格数：**钉住 0 时 0 / 6；用 `hover()` 时 3 / 6。**

## 4. 为什么这类读数**不可能**拿到真值

badge 在检查器滚动容器里的自然 y 恒为 **961**，
而可见带底沿随窗高是 **378 / 458 / 538 / 618 / 718 / 968** ——
**每一个窗高下 badge 都在可见带之外**（968 < 961+16 的临界在 h=1150 才勉强够到边缘，
而实测 `insideBand` 六个窗高全为 `False`）。

所以**任何**要悬停这枚 badge 的读数都必然包含一次滚动。
这既是 650 被骗的原因，也是这个盲区的完整形状。

## 5. 第三种状态：探针**报错**，但读数**就在那儿**

矮窗高下 `hover()` 抛 `TimeoutError`（h = 360 / 400 / 440 / 480 四格全部如此），
但 **`tooltipMountedAnyway = True` 四格全中**：
Playwright 先滚动并派发指针，CSS `:hover` 把提示条打开了，
**随后**稳定性检查失败并重试到超时。

**所以第三态不是「没有数据」，是「探针报错而读数存在」。**
把异常当成「打不开」的验收器，会**丢掉这四格真实存在的数据** —— 那本身又是一种盲。

三态分开记：

1. 滚动钉 0、打开、sticky **够不到** —— 上表六格；
2. 打开、**被够到** —— 只在让探针自己滚动时可达，即 650 的读数；
3. **`hover()` 抛异常而提示条已挂上** —— 四个矮窗高。

## 7. 撤回的范围

**撤回**：650 对 `camera-fov-help-tooltip@1280x720` 的四个具体数值，
以及「宽度驱动」那句归因。

**不撤回**：`section.sticky` 在**某个滚动状态**下能画到提示条之上这件事本身 ——
本批只是**量不到**那个状态，因为到达它必须靠探针滚动。
**一个过度扩张的撤回本身就是另一种错误**，所以范围必须写死。

**不主张**提示条**永远**不被遮住 —— 只主张**在 `scrollTop = 0` 这个状态下、
在 560–1150 这六个窗高上不相交**。用户若先把检查器滚到别处，本批没有量过。

**零源站断言。**

## 8. 我自己写错的两处

1. **第三态猜错了**：我以为矮窗高下是「压根打不开」，
   断言「失败后提示条不存在」—— **红是对的**，四格全都有提示条。
   改成断言「探针报错而提示条已挂上」，并额外要求
   `hoverSucceeded` 全为 `False` 与 `tooltipMountedAnyway` 全为 `True` 同时成立。
2. **第一版的第三态检查根本不可能红**：`isinstance(failed, dict)` 恒为真，
   而六个高度都在 ~480 的地板之上 ⇒ 第三态集合是空的。
   补扫 360/400/440/480 四格让第三态成为**读数**而不是叙述。
