> 期望值来源：`raw/source-836-camera-numbering.json`（★ 源站**八趟**活体实测 ＋ clone 对照实测）

## 一、一句话结论

1. ★★ **源站的「机位N」是 `count+1`** ⟹ **删掉一台再新建会与已有编号重名**
   ⟹ **clone 现有的编号逻辑也是 `count+1`** ⟹ ★★ **两者一致 ⟹ clone 不是缺陷，本批不改编号规则。**
2. ★★ **源站那台默认机位删不掉**（**四条独立实验**排除了所有别的解释）⟹
   **clone 删得掉** ⟹ ★ **这是实质差异 ⟹ 本批给 clone 补上「主机位不可删」。**

★ 这**推翻了 batch 833 遗留项背后的隐含假设**（那个假设是「如果会重名，clone 就该改成 max+1」）——
**源站自己就会重名**，所以「重名」不是 clone 的错。

★ 顺带实测出**两个新事实**：
1. **源站的默认机位「机位1」删不掉**（右键菜单里**有**「删除」项，但点了不生效，机位数不变）；
2. clone 的默认机位名是「**机位01 · 对峙中景**」，而源站那台默认机位叫「**机位1**」
   ⟹ ★ 那串「机位01 · 对峙中景」在源站其实是**镜头名**（源站的镜头叫「机位01 · 对峙中景 · 镜头」），
   **clone 把镜头名当成了机位名** ⟹ 这是**另一处**待处理的差异（影响面较大，另批处理）。

## 二、★ 实验设计：连续编号**分不出** count+1 与 max+1

`count+1`（现有机位数 + 1）与 `max+1`（现有最大编号 + 1）在编号连续时**结果完全相同** ⟹
batch 833 只测了「已有 1 台 → 新建叫『机位2』」⟹ ★ **那一次测不出任何东西**。

⟹ 区分实验必须先**制造一个编号空洞**：

```
造出 机位1 机位2 机位3
删掉 机位2（留下 机位1 机位3 ⟹ 编号 [1,3] 不连续）
再新建一台
  ├─ 叫「机位3」 ⟹ count+1 ⟹ 与已有的「机位3」**重名**
  └─ 叫「机位4」 ⟹ max+1  ⟹ 不重名
```

## 三、★★ v1 探针的两个真缺陷（本批最值得记的一处）

### 缺陷 ①：删除没生效 ⟹ 根本没做出空洞 ⟹ 而判定**照样**给出了结论

v1 日志：`删 机位1：3 → 3 台 ✘ 未减少` ⟹ **删除失败** ⟹ 场景里仍是 1,2,3（连续）⟹
第⑤步的「新建」发生在**没有空洞**的状态下 ⟹ 得出「机位4」。

⟹ ★★ 而 v1 的「⑥判定」输出的是：

```json
{"与已有编号重名": false, "规则": "max+1（不重名）"}
```

⟹ ★★ **这是本批最刺眼的一处**：判据**只问「有没有重名」**，
而**连续编号下「不重名」是必然的** ⟹ 于是它在**一个根本没做出空洞的实验**上，
给出了一个**看起来很确定的错误结论**（"max+1"）。

⟹ ★ 形态：**判据没测到要测的那件事** ⟹ 它**不是恒真**（它真的会红），
但它在**前提不成立**时给出了**伪结论** ⟹ 比恒真更危险，因为恒真至少会立刻暴露。

⟹ **修法（v2）**：把「空洞存在」变成判定的**硬前提** ——
删完后编号集合**必须不连续**，否则直接判「**实验无效**」并**不下结论**。

### 缺陷 ②：删的是「机位1」⟹ 它**删不掉**

v1 删的是编号最小的「机位1」⟹ 失败了。v2 查明：**源站的默认机位受保护**（详见第四节）⟹
主实验改删**编号第二小**的那台（留下「机位1」＋「机位3」⟹ 空洞在 2）⟹ 实验成功。

★ ★ 教训：**实验设计不要假设「什么都能删」** ⟹ 探针失败时先分清「工具没出手」与「产品不让」，
本例正是后者 ⟹ 而它本身就是一个**新事实**。

## 四、★★ 决定性实测（v2 → v8，**每一步都在排除一种替代解释**）

### 4.1 编号规则（v2）

| 步 | 动作 | 实测 |
|---|---|---|
| ① | 基线 | 场景树 = `["机位1"]` |
| ② | 造出三台 | `["机位1","机位2","机位3"]` |
| ③ | 删掉「机位2」 | ✔ 3 → 2 台；剩 `["机位1","机位3"]` ⟹ **编号 [1,3] 不连续 ⟹ 空洞真实存在** |
| ④ | **在空洞态新建** | 新机位叫 **「机位3」** ⟹ ★ **与已有的「机位3」重名** |
| ⑤ | 判定 | **`count+1`（会与已有编号重名）** |

★ **clone 对照实测**（同口径、同样先验证前提）：删后编号 `[2,4]` 不连续 ⟹ 新建得「机位4」
⟹ **与已有的「机位4」重名** ⟹ ★ **clone 也是 `count+1`** ⟹ ★★ **两边一致 ⟹ clone 不用改**。

### 4.2 「默认机位删不掉」—— **四条独立实验**排除了所有别的解释

| 趟 | 要排除的解释 | 实验 | 结果 |
|---|---|---|---|
| **v3** | 「只是因为它是**最后一台**」 | 在**有 3 台**时删「机位1」 | **3 → 3 台，删不掉** ⟹ 排除 |
| **v7** | 「只是因为它是**编号最小**的」 | 先删「机位3」（删得掉）⟹ 剩「机位1」「机位2」⟹ 再删「机位1」 | **仍删不掉** ⟹ 排除 |
| **v6** | 「是**我的计数口径**漏了一台」 | 改用**无正则**读数（把所有含「机位」的叶子文本原样读出）⟹ 两个口径台数**一致** ⟹ 无漏数 | 排除 |
| **v8** | 「只是因为它是**当前激活**的」 | 点「机位3」⟹ ★ **读回右栏确认为「机位3」**（前提钉死）⟹ 再删「机位1」 | **仍删不掉** ⟹ 排除 |

⟹ ★★ **结论**：源站有一条**按身份**的保护规则，**与名字／编号／激活态都无关**。

⟹ ★★ **clone 侧对照**（同口径）：有 3 台时删默认机位 ⟹ **删得掉** ⟹
clone 的删除规划器（`src/lib/directorDeletePlanner.ts`）**只有**一条机位保护：
`survivingCameras.length === 0` ⟹ `DIRECTOR_LAST_CAMERA_REQUIRED` ⟹ **与被删对象是不是默认机位无关**
⟹ ★ **实质差异** ⟹ 本批修。

## 五、★★ 本批的产品改动：clone 补上「主机位不可删」

| 序 | 文件 | 改动 |
|---|---|---|
| 序 1 | `src/lib/directorDeletePlanner.ts` | 导出常量 `DIRECTOR_PRIMARY_CAMERA_ID = "director-camera-main"`；在「最后一台」检查**之后**加一条：删主机位且**还有别的机位** ⟹ 返回 `DIRECTOR_PRIMARY_CAMERA_REQUIRED` |
| 序 2 | `src/lib/directorCommandKernel.ts` | `DirectorCommandReason` 新增 `DIRECTOR_PRIMARY_CAMERA_REQUIRED` |
| 序 3 | `src/lib/directorCommandFeedback.ts` | 该 reason 的文案：「主机位不能删除」 |

★ **为什么放在「最后一台」之后**：只剩一台时理由**仍是** `DIRECTOR_LAST_CAMERA_REQUIRED`
⟹ 新增那条**只**在「还有别的机位、但要删的是主机位」时命中 ⟹ ★ **没有绕开原有那条**（门禁 S6 钉住）。

★ **为什么按 id 而不是按名字**：源站的保护是**按身份**（与名字无关）⟹
且 clone 的默认机位当前显示名是「机位01 · 对峙中景」⟹ ★ **那串字在源站是镜头名**
⟹ 用名字判**两处都对不上** ⟹ **id 是唯一稳定的身份标识**。

★ **已知边界（如实记下）**：导入的第三方项目若**不含**这个 id，就没有这条保护 ⟹
本批**不**引入文档级字段（那要动序列化与旧文档兼容）⟹ 边界写进代码注释与 README。

★ 实测（`probes/clone836c.py`）：
```
① 删主机位：  REJECTED / DIRECTOR_PRIMARY_CAMERA_REQUIRED   3 → 3 台
② 删非主机位：COMMITTED                                      3 → 2 台
③ 只剩一台时删它：REJECTED / DIRECTOR_LAST_CAMERA_REQUIRED
```

## 八、★★★ 本批最刺眼的一处：同一个错误形状**连犯三次**

三次都是**「用一个观测去回答一个关于规则的问题」**，而那个观测**不足以**支撑那个答案：

| 序 | 观测 | 我当时的结论 | 实际缺的 | 修法 |
|---|---|---|---|---|
| 序 1 | v1：删「机位1」后台数没变 | 「造出空洞失败 ⟹ 改删机位2」 | ★ 判定只问「有没有重名」，而**连续编号下「不重名」是必然的** ⟹ 于是在**前提不成立**的实验上输出了「max+1」 | ★ 把「空洞存在」变成**硬前提**，不满足就判「**实验无效**」并**不下结论** |
| 序 2 | v2：只有 1 台时「机位1」删不掉 | 「默认机位受保护」 | ★ **没排除「它恰好是最后一台」** ⟹ 而 clone **也有**这条（`DIRECTOR_LAST_CAMERA_REQUIRED`）⟹ 两条不同的规则分不开 | ★ 补「**有 3 台时**删默认机位」的实验（v3） |
| 序 3 | v1–v4 的删除复验判据 `len(after) == len(cams) - 1` | 「机位1 删不掉」 | ★★ `cams` 是**正则过滤后**的集合，而正则 `/^机位\s*\d+$/` **不匹配「机位01 · 对峙中景」** ⟹ 若场景里真有一台那种名字的机位 ⟹ **计数一直少一台** ⟹ ★ 「删掉了」也会被判成「未减少」 | ★ 改用**无正则**读数做复验（v6） |

⟹ ★★ **这三次的共同根因不是「手滑」，是探针的判据结构有系统性缺陷**：
**观测 → 结论**之间**没有夹一层「排除其他解释」**。

⟹ ★ 修法（可复用到任何探针）：
1. **每个否定性判定写成「二选一」**，显式列出替代解释，再**设计一个能把它们分开的实验**；
2. **把前提做成硬闸**：前提不满足 ⟹ 判「实验无效」⟹ **不下结论**；
3. **复验用的计数口径 ⟹ 必须与被测对象的名字形态无关**（★ 这一条最隐蔽：
   一个只认「标准形态」的计数器，会**系统性地**让「非标准形态的对象」变成不可见，
   于是「删掉了」被读成「没删掉」）。

3. ★★ **「机位1 删不掉」的成因已查到「按身份」这一层，但没查到「源站代码里那条规则」**
   —— v3／v7／v6／v8 四条实验排除了「最后一台」「编号最小者」「我的计数口径」「当前激活机位」

6. ★ **clone 侧对照用的是 store 直接调命令**（`addDirectorCamera` / `deleteDirectorEntity`）
   ⟹ ★ **不声称**「点 UI 与调命令完全等价」—— 但本批只读**编号**这个结果，两条路径共用同一段
   `createDirectorCameraFromSource` ⟹ 编号规则**必然**一致。
