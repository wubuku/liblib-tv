# Batch 623 —— 把普查从三个离散档拉到断点邻域，并补上「零尺寸控件」这个盲区

日期：2026-10-01 · 零源站断言

622 那 22 枚「可见但点不动」的控件只存在于 **899 这一个像素**上。而既有普查一直按 390 / 768 / 1920 抽样 —— 也就是说，**单像素级缺陷按这种抽样必然看不见，而且是构造性地看不见**。本批把普查改成宽度扫描，并顺手在扫描里挖出一个普查原本抓不到的真缺陷。

## 零源站断言

`probe616` 复跑：源站仍 1600×1000、导演台被他人关闭。本批不主张任何保真度。

## 一、扫描：86 个宽度，基础态干净

先从源码里**读出**断点（不硬编码，断点变了扫描会跟着变）：

```
430  480  520  620  680  850  899  900
```

开关点是 430/480/520/620/680/850/900。每个开关点取 ±3 的密集邻域，再加 360→1920 每 40px 的粗扫，去重后 **86 个宽度**（49 密集 + 40 粗扫）。

结果：**零 covered**。同时做了一件防止「快而不准」的事 —— 主体是单页 `set_viewport_size` 循环（比重载快一个量级），但另取 17 个宽度用**全新页面加载**复算，`resize vs fresh` **0 处不一致**，所以这条快路可信。

这条否定结论本身有价值：把「我们只抽查过三个宽度」变成「我们扫过 86 个，基础态干净」。

## 二、扫描挖出来的真缺陷：899 上资源栏塌成零尺寸

密集邻域里，899 的控件数是 **108**，而 898 是 52、900 是 **115**。108 这个数夹在中间，不像任何一档。

逐面板量（`/tmp/dbg623c.py`，修复前）：

| | 898 | **899** | 900 |
| --- | --- | --- | --- |
| 场景树 | `[-220,88,220,812]` | `[0,88,220,812]` | `[48,52,233,848]` |
| 资源栏 rail | `[0,0,0,0]` | **`[0,0,0,0]`** | `[0,52,48,848]` |
| 属性列 | `[898,88,281,636]` | `[618,52,281,666]` | `[619,52,281,666]` |
| 镜头条 | — | `[0,52,899,36]` | `[281,52,619,36]` |
| 普查控件数 | 52 | **108** | 115 |

899 是一套**自相矛盾**的状态：树和属性列按桌面可见、资源栏却按窄屏隐藏成零尺寸、镜头条还从 x=0 横穿整个视口。**资源栏那 7 枚活控件（115−108）就这么消失了。**

### 为什么普查没报

因为**普查有个盲区**：它报的是「被别的东西盖住」（covered）。而一个塌成 `[0,0,0,0]` 的控件**没有被任何东西盖住** —— 它是自己没了。所以 899 的普查报 `covered=0`，干干净净地漏掉了 7 枚消失的控件。这和 620 记过的那个探针顺序问题是同一族：工具的判据决定了它能看见什么、看不见什么。

### 根因：断点差一像素，而差的方式是编译器造成的

```
max-[899px]  →  @media (width < 899px)   →  ≤ 898   （窄屏）
min-[900px]  →  @media (width >= 900px)  →  ≥ 900   （桌面）
```

这一对**看上去互补，其实错开一像素**，于是 899 落进「两条都不生效」的基线缝。写这两条时按 `max-[899]` + `min-[900]` 的自然读法（≤899 / ≥900）显然是想要一个干净的二分，但 Tailwind v4 的严格小于把 899 漏了出来。**缝是编译器语义造成的意外，不是设计决定** —— 这和 622 在 JS 侧踩的是同一个坑，只是这次在 CSS 侧。

### 改法：只动 `min-` 那一侧

算清楚之后要改的其实只有一处方向：

- `max-[899px]` 编译成 `width < 899` = **≤898**，**这已经是窄屏该有的范围**，不用动
- `min-[900px]` 编译成 `width >= 900` = **≥900**，把 899 漏在外面，**要改成 `min-[899px]`**（≥899）

于是窄屏 ≤898 / 桌面 ≥899，**无缝无叠**，也与 622 对齐过的 `matchMedia('(max-width: 898px)')` 完全一致。改动是 `min-[900px]` → `min-[899px]` 共 **16 处、2 个文件**（`DirectorDesk.tsx`、`DirectorIconRail.tsx`）。25 处 `max-[899px]` 一字未动。

> 顺带说明为什么**不能**简单把两侧都挪一格：若把 `max-[899px]` 也改成 `max-[898px]`，窄屏就变成 ≤897，缝只是从 899 **搬到了 898**。这也是为什么必须先算清楚编译结果再动手。

修复后 899：`tree=[48,52,233,848]`、`rail=[0,52,48,848]`、`total=115` —— 与 900 **逐项相同**；≤898 一字未动（树仍在 `[-220,...]`、资源栏仍隐藏、控件数仍 52）。

## 三、补上「零尺寸控件」这个盲区 —— 以及它**没有**抓到资源栏

既然普查看不见「自己没了的控件」，本批给每个宽度加了一条独立检查：扫全部 `button / [role=button|switch|separator] / a[href] / input`，凡宽高为 0 或 `display:none` / `visibility:hidden` 的，逐级向上找 —— 若祖先链里有东西确实被收进屏外或隐藏（真抽屉）就放过，否则报出来。

**但必须如实说清：这条检查没有抓到 899 的资源栏。** 资源栏是 `display:none`（基线类 `hidden` 加上未生效的 `min-[899px]:flex`），而「祖先隐藏」正好落在这条检查的**已解释**分支里，于是它被放过了。真正抓住资源栏的是另一条断言 —— ≥899 时资源栏必须有源站实测的 48 宽。

基线对照（备份 `/tmp` 后 `git checkout --`，不用 stash）回退那 16 处，验收器 22/24，两条红精确指向 899：

```
FAIL vw899:the-resource-rail-has-its-source-width  [0, 0, 0, 0]
FAIL vw899:the-tree-sits-at-the-source-column      [0, 88, 220, 812]
```

那 18 枚中真正贡献判别力的是**几何断言**；零尺寸检查在本轮是个**从未触发的兜底**（86 个宽度全绿）。留着的理由是它守着另一类失败模式（控件塌成 0×0 却没有隐藏祖先），但按 619 立下的规矩「豁免/判据必须被证明确实会触发，否则是死代码」，这里如实标注它**本轮未触发**，而不是把它算进本次的功劳。

## 四、更正 622 的一条自述

622 的 README「不声称」里有一条：≤898 时场景树抽屉 inert 而属性列停在屏外**不** inert，说是本批之前就有的不对称。**那是错的，本批读错了元素。**

`inert` 挂在承载状态的外层 **`aside`** 上，622 读的是内部的 `section[data-director-inspector]`，于是读到 `false`。沿两列逐级列祖先后（`/tmp/dbg623b.py`）坐实真相**完全对称**：

```
vw=390/897/898  tree  aside[场景对象]  box=[-220,88,220,812]  inert=true  aria-hidden=true
                insp  aside[属性]      box=[390/897/898,88,..] inert=true  aria-hidden=true
vw=899/900      两列均在屏上，均无 inert 祖先
```

622 的 README 与台账条目已一并更正，623 的验收器改用 `aside` 地标并断言**对称版**不变量：「某列**在屏上就当且仅当**不 inert」。

### 验收脚本第四次把判据写反（同一个形状，第二次犯）

边界不变量首版写成 `onScreen == inert`，而检查名说的是「inert 当且仅当**在屏外**」—— 正确表达式是 `inert == (not onScreen)`。结果是 897/898/899/900 **八条全红，而每一条的数据都是对的**（898 屏外且 inert、899 在屏且不 inert，恰恰都满足不变量）。

这与 622 那条假不对称是**同一种错误**：把「A 当且仅当非 B」写成「A 等于 B」。两批里同一个形状出现两次，说明它不是手滑而是习惯，所以在此记名：断言的名字和它的表达式必须逐字对读一遍，名字说的是什么就跑什么。

## 不声称

- **源站任何事**。特别地，「899 该归桌面」这个选择**不是源站读数** —— 它来自 622 对齐过的 JS（≤898 为窄屏）加上两条 media query 的算术。本批沿用 622 的决定，不重新裁定。
- **其他断点没被改**。430/480/520/620/680/850 是各组件各自的阈值，它们之间的「基线带」是正常的移动优先默认值，不像 899/900 那样是一对本该互补的规则。它们被扫描了，但没动。
- **扫描是穷尽的**。86 个宽度在边界处密集、区间之间每 40px 一个 —— 若某个缺陷恰好藏在两个粗扫步之间的某个未采样像素上，仍然会漏。本批只把「离散三档」升级成「边界密集」，不是连续覆盖。
- 画布页 `app/page.tsx` 的 `innerWidth <= 768`（初值启发式）仍只记录不处理。
