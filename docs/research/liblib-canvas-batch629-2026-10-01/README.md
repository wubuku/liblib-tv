# Batch 629 —— 又矮又窄的那个交叉网格，并**修正 628 豁免的划线位置**

## 零源站断言

本批**没有一条源站读数**。gizmo、视口工具条、prompt 条的几何全部来自 clone 在
1920×1150 的既往实测，而本批所有碰撞都发生在**从未采样过的矮/窄视口**。源站在这些
视口下会不会撞，**未取证**，本文一个字都不主张。

## 一、扫法

627 扫 86 个宽度 × 高度固定 900；628 扫 75 个高度 × 宽度固定 1440。两批各自留白的
正是「又窄又矮」这一角。

| 维度 | 取值 |
| --- | --- |
| 宽度 | 360, 390, 430, 480, 520, 620, 680, 780, 850, 898, 899（623 断点集的窄侧子集 + 899 边界） |
| 高度 | 360, 400, 480, 560, 640, 720, 800, 900 |

| 交叉校验 | 6 个角各自**全新加载**（resize 主扫之外的独立读数） |

## 二、结论一：几何边界轴在这个角上仍然干净

176 格「视口外且够不着」= **0**；视口外控件累计 **12828** 枚（累计数是"非空转"的
证据：判据确实被大量执行过，而不是因为全在窗口内而从未触发）；**无一格**视口外控件
为 0。627 在 900 高、628 在 1440 宽上得到的干净结论，延伸到了这个角。

## 三、结论二：628 的视口挤压豁免**划错了线**

### 3.1 现象

探针一跑，176 格里有 **26 格**出现无法解释的 `covered`。受害者还是 gizmo 的
`X 正向` / `X 反向` / `Y 反向` / `重置视角`，但盖住它们的**不是** 628 认定的
prompt 条，而是同一个 48px 贴底带里的另外两个兄弟：

```
16:9 · 9:16 · 1:1 · 画幅比例 · 开启九宫格辅助线 · 动画时间轴   ← 视口自己的顶部工具条
角色01 · 陈默可拖动三轴控件…                                   ← 工具条里的对象信息
描述想搭建的场景 / 场景描述已记录（本地草稿）                    ← prompt 条本身
```

780×400 那格最能说明问题：视口才 136 高，`Y 反向` 被**同一个 gizmo 的信息面板**盖住。

**精确原因**：`[data-director-bottom-bar]` 是 `absolute bottom-0 z-[200]`，高恒 48，
里面装着三个兄弟（工具条、prompt 条、工具条那一行）。628 的豁免认的是
`[data-director-scene-prompt-bar]`，即**三个孩子之一**——而 628 那些格子里恰好只出现了
这一个。按「盖住者是谁」划的线，只覆盖了作者当时看见的那一次碰撞。

### 3.2 改成按受害者的退化条件划线

617 的 `AUDIT_JS` 里，628 的 `hitInBottomBar` 从**门**降级为**只记录给读者看**；
门改成 `victimInViewport`——受害者在 3D 视口内。619 的账目恒等式、619 的 `帮助` 断言、
628 的三个断言名与元组下标同步更新（`e[3]` → `e[2]`）。

## 四、本批最重要的产出：**我自己那条断言是错的**

629 第一版的第 7 条断言写的是：

> 这条碰撞只取决于视口高度、与窗口宽高无关，所以 628（1440 宽扫高度）与 629
> （11 个窄侧宽度扫高度）独立得出的视口高度上界必须一致。

**它红了。** 360..898 宽的上界恒为视口高 **148**，唯独 899 宽是 **130**。

定点取证（`/tmp/dbg629c.py`，量边界两侧共 8 格）给出的机制：

- **gizmo 整簇在窗口坐标里恒定不动。** 盒恒 `t=108 b=188`；六个轴按钮与「重置视角」的
  底边在 898 / 899 / 1440 三个宽度、360 / 400 / 480 三个高度上**逐像素相同**
  （`Y 反向 b=183`、`重置视角 b=222.5`）。它既不随视口高度动，也不随宽度动。
- **盖住者全都锚在视口底**，就是那个 48px 的 `[data-director-bottom-bar]`。
- **时间轴高度按断点分族**：≤898 是 **176/124**（展开/收起），≥899 是 **182/88**。

于是碰撞条件恒等于

```
受害者在视口内的底边 + 视口底部带宽(实测 48)  ≥  视口高
```

而 `视口高 = 窗口高 − 88 − 时间轴高`。两族时间轴差 **6px**（展开态），所以同一条物理
边界在窄族落在视口高 136、在桌面族落在 130 —— **差得正好是那 6px**。

**我原来那句断言错在跨布局族比较原始视口高**：两族的「窗口高 → 视口高」换算本来就不同
（窄族收起态是 `h − 212`、展开态 `h − 264`；桌面族两态都是 `h − 270`），拿原始视口高
跨族对齐是在比苹果和橘子。

### 4.1 合同不删，迁移成更强的五条

| 断言 | 强度 |
| --- | --- |
| `every-squeeze-row-satisfies-the-closed-form` | 必要条件，**85 行**逐行验 |
| `every-squeeze-coverer-is-in-the-viewports-bottom-band` | 把 3.1 那条从**肉眼观察**变成**断言** —— 钉住「底部带」而不是它某个孩子，628 那条线无法退回命名兄弟 |
| `the-squeeze-set-is-exactly-what-the-geometry-predicts` | 充分条件，**逐格**比对实测集合与公式预测集合（176 格全等；预测集从 `blocked` 候选重建，**不是从实测集合推的**，所以不循环） |
| `the-observed-bound-equals-the-predicted-bound-per-family` | 每个 (态, 族) 的实测上界 == 公式预测上界，**含「可预测地为零」那一支** |
| `the-raw-viewport-bound-is-reconciled-by-the-timeline-height` | 把 148 vs 130 这个差异**钉死**为两族时间轴高度之差（6 == 6），而不是当噪声放过 |

外加 `the-raw-bound-really-did-differ-across-families`（显式断言"差异确实存在过"，免得日后
被当噪音删掉）与 `the-closed-form-also-holds-on-every-fresh-load`。

四个 (态, 族) 组合的实测 = 预测：

| 态/族 | 时间轴高 | 预测上界 | 实测上界 | 格数 |
| --- | --- | --- | --- | --- |
| expanded/narrow (≤898) | 176 | 136 | **136** | 80 |
| expanded/desktop (≥899) | 182 | 130 | **130** | 8 |
| collapsed/narrow | 124 | 148 | **148** | 80 |
| collapsed/desktop | 88 | 无 | **无** | 8 |

`collapsed/desktop` 一格都不撞**不是数据缺口**：88px 的时间轴让视口在网格最矮的窗口
（360）就已经有 184 高，而公式的最高阈值是 182.5 —— "本轮无一格"正是公式给出的答案。

「豁免的边界从扫描自身推导」这条原则在这里升级成：**豁免的边界要能被几何算出来**。
底部带宽 48 每格实测，公式里当读数用，不当魔数。

## 六、本批探针与判据自己踩的六个坑

1. **先猜「窄屏水平 rail 条变长盖住 gizmo」** —— 实测 360/520/780 下
   `data-director-icon-rail` 是 `display:none`、盒子 0×0，命中者根本不在 rail 内。
2. **再猜「盖住者是底部 prompt 条」** —— 被同一带里的工具条打脸。
3. **把「同一个物理量」当成了「同一个数字」**。视口高在两族里是不同的一次函数
   （窄族收起 `h−212`／展开 `h−264`，桌面族两态都 `h−270`），数值不等却其实指向同一条
   边界 —— 差值 6px 正好是时间轴之差。
   **「读数不一致」的第一反应不该是"其中一份错了"，也可能是"它们量的不是同一个量"。**
4. **`predict` 少写两个条件，红了一大片。** 首版只查垂直包含和矩形相交，于是把
   `1:1`/`9:16`/`上传图片`（工具条 `w-[711px]` 在 360 宽视口里横着溢出，被自己的
   `overflow-x-auto` 裁掉）、`描述想搭建的场景`（prompt 条 `l=731 r=956`，整个在视口外）、
   以及场景树的 `删除当前选择`/`锁定角色01 · 陈默`（与视口**不在同一列**，只是 y 带重合）
   全预测成会被盖住。补上 **DOM 归属**（`victimInViewport`）与**裁剪**（`clipped`）两个
   条件后逐格全等。
   **「够到某个带子」不等于「会被那个带子盖住」—— 归属与裁剪是两道独立的门。**
5. **`recon` 的键从元组改成字符串后，下游循环没跟着改** —— `for s, _ in recon` 会
   `ValueError`，而且是在测完 176 格之后才炸。**改名后必须把所有下游取键处一起读一遍。**
6. **跨断点比较必须先分组。** 898 与 899 是两套布局（`min-[899px]`），把它们放进同一个
   「所有宽度」集合再取 max/min，得到的数没有物理含义。

## 不声称

- 源站任何事。
- 这个角是「最危险」的——只主张它是 627 与 628 都没量到的那一块。
- 闭式公式对源站成立。
- 视口挤压该怎么做。视口被压到 90px 高时 3D 场景本身已不可用，但该怎么处置是产品
  决定，不是能从几何推出来的。本批只把解释结构化并量出边界。
- 底部带宽 48 是常量。
- 公式只刻画**底部带**这一种碰撞。同一视口内若有别的控件互相重叠导致被盖，公式不会
  预测它（`every-squeeze-row-satisfies-the-closed-form` 会抓到），但公式也**不声称**
  那种情况不存在——本轮网格里没有。
