## 3. 那 4 条是什么 —— 真发现，正落在 626 自己声明的空白里

    camera-fov-help-tooltip   box=[1016, 263, 208, 68]   @1280x720
      pointer-events  none      活控件 0      伤亡 0

626 的 README 原文：

> **不主张** `camera-fov-help-tooltip` 的**可点击性**：它是 `pointer-events:none` 的
> hover 提示，浮层内 0 枚活控件，「无控件被挡」对它恒真。
> **这不代表它的可读性或定位被验证过。**

**导出式尺子正是从这句话让出的空白里走进来的**：

| 盖住者 | z | 形态 | 背景 | 交集 |
|---|---|---|---|---|
| `section.sticky.top-0` | **20** | **sticky** | `rgba(33,33,33,0.98)` **不透明** | `[1016,263,208,62]` |
| `div.relative.h-[135px]` | 0 | relative | `rgba(8,8,16,0.95)` 近不透明 | `[1016,263,208,45]` |
| `canvas.absolute.left-0` | 0 | absolute | 透明（栈顶） | `[1017,263,207,46]` |
| `button.absolute.bottom-3` | 0 | absolute | `white/10` | `[1219,271,5,24]` |

**68 高的提示条里有 62 高（91%）被一条 `z-20` 的 sticky section 压住。**
只发生在 **1280×720**；1440×900 与 1920×1150 干净 —— 所以是**宽度驱动**的。

**它不是可点性缺陷**：那枚提示条 `pointer-events:none`、0 枚活控件，伤亡半恒为 0。
**主张只关于「绘制」**：一条 sticky section 盖住了它 91%。
626 的手写六项之所以看不见它，是因为**盖住者不是那六项里的任何一个**。

## 4. 两条新增门槛只减不增（写成断言）

649 的尺子比 626 窄两处：结构半多了 `elementsFromPoint` 交叉校验；
伤亡半多了「≤1px」与「clip/clip-path」门槛。**两处都只会移除，不会新增。**

* `the-derivation-never-invents-a-control-or-a-casualty` ——
  活控件数**从未增长**、伤亡数**从未增长**。若某格增长，那是导出式的 bug，不是新发现。
* `every-casualty-difference-is-648s-sr-only-finding-and-nothing-else` ——
  伤亡差集必须**是 626 的子集**且活控件数不增。本批实测**差集为空**
  （这 11 个浮层里没有 `sr-only` 控件；648 那枚在模型库抽屉里，不在这 11 个里）。

## 5. 626 的两个附加合同在导出式下仍然成立

* **`NO_OP_CASES`**：几何子菜单的钳制在无越界处必须是恒等 ——
  1440×800 与 1440×900 都实测 `[52, 508, 204, 270]`，**逐位未变**。
  一条不该动的钳制若悄悄动了，这条会变红。
* **8px 安全边**：39 格**无一破边**，且在 626 记了数的 **6 格**上与 626 逐格相同。
  626 的 `baseline`（**修前**那一跑，111 checks / 15 failures）里
  `motion-path-menu` 与 `geometry-submenu` 的 `fit-in-viewport` 是红的；
  **626 已经把它们修好了**，本批用一把从没见过它们的尺子确认修好了。
