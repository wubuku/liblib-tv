# batch 690 — 689 的整数性**推广不了**：它是两件事的合取，不是字段的性质

> 起点：689 证明了 `timelineHeight` 的值域是闭的 `ℤ ∩ [88,420]`，并写下限制声明
> 「**不声称**整数性是所有布局字段的通性（本批只量了一个字段）」。
> 本批去销这条声明，**并且证明它销不掉**。
>
> 验收：`scripts/verify-liblib-batch690.py`（7/7）
> 仪器：`scripts/census-directorstore-value-domains.mjs`（本批一并提交）
> 读数：`runtime-audit.json`

## ① 普查：74 条叶路径里只有 1 条是整数值的

689 的判据是「唯一写入点 + 该写入点末尾 `Math.round`」。把它推到全树时，
**判据必须落到写入点，不能落到函数体** —— 一个 setter 同时写 5 个字段、
只给其中一个 `Math.round`，整函数体扫描会把另外 4 个读成「也取整了」。

用 TypeScript 编译器 API 解析（不是正则：store 是嵌套子对象树，
正则分不清 `{a:1}` 里的 `a` 属于哪一层；也不是 Python 的 `ast`，
那是 Python 解析器）：

| 量 | 数 |
|---|---|
| setter 成员 | 21 |
| `set()` 调用点 | **221** |
| 叶路径写入点 | **507** |
| 不同叶路径 | **74** |
| **全写入点都取整** | **1**：`timelineHeight` |
| 部分写入点取整 | 1：`phoneVcam.sampleCount` |
| 无任何写入点取整 | 72 |

三个与布局直接相关的输入全在「不取整」那一类：
`timeline.zoom`（`directorStore.ts:7003-7008`，只 clamp 到 `[0,100]`）、
`timeline.currentTime`（6 个写入点）、`timeline.duration`。

## ② 但真正打掉推广的是下一层

```ts
// DirectorTimeline.tsx:495-498
const timelineWidth = Math.max(640, timeline.duration * (3.36 + 4.978 * timeline.zoom));
```

**两个输入都是整数，乘出来照样是小数。** 14 档**整数** zoom（UI 可达那一档）
里，11 档的指定宽度带小数：

| zoom | store 值 | 指定宽度 | 期望 `8×(3.36+4.978z)` |
|---|---|---|---|
| 18 | 18（整数） | `743.712px` | 743.712 |
| 20 | 20（整数） | `823.36px` | 823.36 |
| 22 | 22（整数） | `903.008px` | 903.008 |
| 24 | 24（整数） | `982.656px` | 982.656 |
| 42 | 42（整数） | `1699.49px` | 1699.488 |

⟹ **685 在宽度轴上量到的那批 1/64px 斜坡，有一条成因与分数 store 值完全无关**：
渲染公式自己的常数 3.36 / 4.978 就不是整数。

**所以 689 的整数性不是字段的性质，是合取**：
「写入者喂整数」**且**「每个消费者都是保整表达式」。
`timelineHeight` 两条都满足（消费者是布局引擎，收到一个裸数字）；
`timeline.zoom` 满足第一条、不满足第二条（消费者要乘一个非整数）。

## ③ 分数真的到达 DOM —— 三层精度都量了

`timeline.zoom` 无任何写入点取整，于是它能装分数。用 4 档分数 zoom 经 store
API 写入（**注意第 4 条：这四档 UI 到不了**）：

| 层 | z=42.5 | z=33.333333333333336 | z=42.123456789 |
|---|---|---|---|
| store double（逐位相同） | 1719.4 | 1354.3466666666668 | 1704.4045431651361 |
| DOM 指定值字符串 | `1719.4px` | `1354.35px` | `1704.4px` |
| 布局实际值 | 1719.390625 | 1354.34375 | 1704.390625 |

store 回读与输入**逐位相同**（独立于公式的第二条证据：setter 没有隐形取整）。

**量化规则是「下整」不是「就近」** —— 18 个样本 **11/11** 精确命中
`floor(px×64)/64`。判决性的一档是 z=24：`982.656×64 = 62909.984`，
下整 62909 → **982.640625**，正是实测值；就近会得 982.65625。
残差恒在 `[0, 1/64)` = `[0, 0.015625px]`，本次实测 `[0.00292, 0.01537]`。

⟹ 这是对 685「1/64px 栅格」那条的**加强**：栅格不是就近量化，是**下整**。
量级小于一个 1/64 格（0.0156px），**不报为缺陷**。

## ④ 分数 zoom 从 UI 到不了（688 的纪律）

zoom 的控件是 `input[type=range]` `min=0 max=100` **无 `step`**
（`DirectorTimeline.tsx:1337-1348`）⟹ HTML 默认步长 1。键盘实测 14 档：
`'0' '1' '2' … '12' '100'`，**全整数、步长恰好 1**。

`zoom` 也不在持久化 schema 里（`directorProjectRuntimeAdapter.ts:277`
打开时重置为 `DIRECTOR_TIMELINE_DEFAULT_ZOOM`）⟹ 分数连存档都带不出去。

**所以第 ③ 条那四档分数是「只有 store API 到得了」的一档。**
但第 ② 条说明：**整数 zoom 也照样出小数** ⟹ 亚像素现象压根不依赖那一档。

## ⑤ 指定值 ≠ 用到值，`min-w-full` 交叉点落在公式预测的整数上

canvas 带 `min-w-full`（`:1861`），所以指定宽度小于滚动容器宽时，
**渲染宽是容器宽**。实测容器宽 958：

| zoom | 指定宽度 | 渲染宽 |
|---|---|---|
| 18…23 | 743.712 … 942.832（各不相同） | **全部 958** |
| 24 | 982.656 | 982.640625 |

交叉点公式 `z* = (958/8 − 3.36)/4.978 = 23.3809`，
最后一个被夹住的整数 zoom 是 23、第一个不被夹的是 24 —— **正好夹住 z\***。
7 个被夹档位的渲染宽**逐个精确等于** `scrollerRectW`。

**只读 `style.width` 会报出「zoom ≤ 23 恒为 640px」这条平台** ——
用户看到的是容器宽。这与 685「`Math.round` 把斜坡伪造成平台」同形，
但成因是 `min-w-full`，方向相反（这里是指定值被**实际值盖住**）。

## ⑥ 标尺宽度律带**时长缩放**，而源站数据分不开

源站只在 `duration=10s` 采样过 4 个点（`:487-493` 注释：zoom 49/64/82/100，
宽度 2473/3220/4116/5012，斜率 49.78 px/zoom、截距 ≈33.6px）。两种读法都能拟合：

- **A（clone 实现的）** `duration × (3.36 + 4.978z)`
- **B（与时长无关）** `33.6 + 49.78z`

两者之比**恰好是 `10/duration`**。本次读数（duration = 8）：

| | 值 |
|---|---|
| 实测渲染宽 @ zoom 49 | **1978.25** |
| 读法 A | 1978.256 |
| 读法 B | 2472.82 |
| 比值 实测 / 预测 | 1.25 / 1.25 |

⟹ **在默认时长下 clone 的标尺是读法 B 的 0.8 倍；时长 20 时是 0.5 倍。**
源码注释自己已把时长外推标为「**推断**」；本批只是把这个未验证的选择
**量化成闭式价码**。

**不声称源站的标尺宽与时长无关** —— 源站可能确实随时长缩放，
**没有任何测量能分开这两种读法**。这是**待取证项**，不是缺陷。

## 自记

- **仪器自己先报错**：`ast.parse` 是 Python 解析器，我拿它解析 8750 行的
  TypeScript（`SyntaxError: invalid decimal literal` @ `directorStore.ts:95`）。
  直接换 TypeScript 编译器 API，不在错误解析器上打补丁。
- **探针整整错位一整轮**：`setTimelineZoom()` 和读 DOM 放在同一个
  `page.evaluate` 里，zustand 写完 React 还没提交 ⟹ **每一行读到的都是上一档
  的宽度**。z=0 那行读到的是默认 zoom 44 的 `1779.14px`。
  **如果不拿公式核对，这批读数看起来完全自洽。**
  686 那条「密集扫描的读数有一部分是路径的函数」这次落在我自己的仪器上；
  修法是写与读分成两次 evaluate，中间等两次 rAF。
- **先问可达性再下结论**（688 的纪律）。第一反应是「zoom 不取整 ⟹ 宽度有
  小数 ⟹ 有亚像素缺陷」；688 之后必须先问「UI 到不到得了」。实测步长是 1 ⟹
  分数 UI 不可达。**结论于是不是「有缺陷」，而是「成因与分数 store 值无关」。**
- **判据错了三次，三次都是读数对、断言错**（689 记过同一条）：
  1. 第 3 条漏了 `min-w-full` 地板，在被夹档位报出 **318px** 的假误差 ——
     而「指定值 ≠ 用到值」正是本批第 ⑤ 条要量的东西，**我的判据把本批自己的
     发现当成了噪声**。
  2. 第 4 条用 Python 的 `round()` 当 `Math.round` 的模型。Python 是**银行家
     舍入**：`round(182.5)=182`、`round(100.5)=100`，JS 给 183/101。
     **跨语言复算时「舍入」不是一个可以随手借用的词。**
  3. 容差从 1/128 放宽到 1/64 之后**反而更严**：因为真正的规则是下整，
     区间从「±半格」收成 `[0, 一格)`。顺带把对照物从 `clientWidth`
     换成 `scrollerRectW` —— **`clientWidth` 按规范取整，量不到亚像素**
     （本次两者恰好都是 958.0，所以这一换在本批**不改变任何读数**，
     是为不把偶然当结构）。
