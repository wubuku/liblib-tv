#### 🔴 「宿主自身是否额外被排除」= **无法验证**（不是「不会」）

要把「空节点被排除」和「宿主自身也被排除」分开，需要一个
**自身有资源、且能打开生成面板**的宿主。**这个组合在产品里造不出来**，两轮读数：

| 节点形态 | 工具条里是什么 | 有 `generation-prompt-editor` 吗 | 能打 `@` 吗 |
|---|---|---|---|
| **空**音频 / 空视频 | **生成面板**（参数行、音色库、`12/24`、生成钮） | ✅ 有 | ✅ 能 |
| **有资源**的音频（上传 wav） | **`165×40`，逐字只有「音频修剪」+ 一个 `下载` 钮** | ❌ **0 个** | ❌ **不能** |

⇒ **「有资源」和「有生成面板」两种状态互斥**：
有资源的节点是**资源节点**（工具条是「音频修剪」，全册此前没记过这一档），
空节点才是**生成节点**。
宿主必须空才能打开生成面板，而空宿主必然被「空节点排除」顺带挡掉 ——
**两种假设预测的读数逐字相同，不可区分**。

📌 写「无法验证」的理由属于本项目三类真阻塞中的**第 ④ 类被排除**：
不是需授权、不是需付费、不是需他人数据，而是**「需自己造素材」但这个素材造不出来**
（造出有资源的节点 ⇒ 它就没有生成面板了）。

🔧 **2026-10-01 批次 51 推翻旧机制假设**：早前推测「媒体节点更大/落点更远把**包围盒撑大**」。

### 🔑 节点自报资源账：`X resource(s): Y ready, Z processing, W failed`（2026-10-02 批次 105 首测，此前全册缺失）

**节点的 `innerText` 里始终带一串资源账**。它是判断「素材走到哪一步了」最省事的判据 ——
比「有没有 `<video>` 元素」更早一步，因为后者的出现还取决于选中态与播放态。

| 节点此刻 | 资源账（逐字） |
|---|---|
| 还没放素材 | `No resources: 0 ready, 0 processing, 0 failed.` |
| 素材处理完 | `1 resource: 1 ready, 0 processing, 0 failed.` |
| 素材收下了、还在处理 | `1 resource: 0 ready, 1 processing, 0 failed.` |
| 素材处理失败 | `2 resources: 1 ready, 0 processing, 1 failed.` ← ⚠️ **批次 112 仍未能造出** |

- 资源账后面跟 `Selected.` 或 `Not selected.`
- 节点类型不同，措辞也不同：时间线节点写
  `时间线: 1 visual track, 0 audio tracks, 0 clips.`
- 🔴 **这是「上传期」的账，播放期失败不会改它**
  （批次 105 实测：注入播放期加载失败后，账本仍是 `1 ready, 0 processing, 0 failed`）。
- 🔴 **账在哪个属性里，因节点类型而异**（批次 112 实测）：
  **视频 / 音频节点在 `innerText` 里；图片节点在 `aria-label` 里。**
  一张「预览不可用」的图片节点 `innerText` 逐字是 `预览不可用 重试 jimeng-b1...truncated`，
  **账不在里面**；它在 aria 上：`1 resource: 1 ready, 0 processing, 0 failed. Selected.`
  ⇒ 读账**两个都要读**（aria 优先，回落 `innerText`）。
- 🔴 **`failed` 这一档至今没能自然造出**（批次 105 两次 mp4、批次 112 四种坏图片全部落空）：
  - **0 字节**与**纯文本改扩展名** ⇒ **连节点都不建**（客户端就拒了）
  - 能建出节点的三种损坏（截断 PNG / IDAT 垃圾 / 伪随机 mp4）⇒ 资源账**要么 `1 ready`、要么永远 `processing`**
  ⇒ 结论按三态记「**无法验证**」：`2 resources: 1 ready, 0 processing, 1 failed.`
  **仍然只是抄写**，请以遇到时的实际读数为准。
- 🆕 **找「媒体渲染失败」最快的判据**（批次 112）：
  扫 **`data-canvas-content-state="media_error"`** ——
  它写的就是「这是一个媒体错误」这层语义，比「某个 testid 在不在」可靠。
  图片节点上它出现在
  `<div data-canvas-content-evidence="element" data-canvas-content-state="media_error"
  elementtiming="canvas-initial-content">预览不可用</div>` 里，
  外层 testid **`image-preview-unavailable`**（`192×192` 铺满整卡）。
- 「处理中」这一档的卡片特征：testid **`video-node-uploading`**、
  aria `<素材名>.mp4: 正在处理上传内容…`、卡片里**只有一个** `Rename <名>` 按钮、
  `<video>` 与 `<img>` **各 0 个**。详见[预览与播放视频节点](10-tasks/media-playback.md#媒体异常)。
- 🔑 **`<类型>-node-uploading` 是一族，不止视频一个**（2026-10-03 批次 109 实测）：
  音频传上去时是 **`audio-node-uploading`**，文字**逐字两段**
  `正在上传音频 0%` → `正在处理上传内容…`；
  图片传上去时是 **`image-node-uploading`**，文字 `正在上传图片 0%`。
  这三个都带 **`role="status"`** ⇒ 它们是**页面里第三个、第四个** `[role=status]`，
  且**在节点内部**（下面这条要注意）。

### 播放取流与上传存储不是同一个 key

（2026-10-03 批次 110 实测）

要复现「资源失效」或做故障注入，**必须知道拦哪条 URL**。而画布上有两个长得像、其实不同的 key：

| 环节 | 出现在 | 逐字样例（同一个 4 秒 WAV） |
|---|---|---|
| **上传存储 key** | 上传 POST 的路径里（`tos-d-ct-lf.snssdk.com/upload/v1/tos-cn-v-148450/<key>`） | `ooHx1IfRMfIKm8GlcVBdIOFE9UxdJqfdDnCfEL` |
| **播放取流 key** | `<audio>` / `<video>` 的 `src` 里 | **`oERcOtFfdQDiV1DIHmFBfRExqfYiGndCM8df8E`** |

🔴 **两者不是同一个值。** 拿上传日志里的 key 去拦播放，会得到
「**拦截报了命中、媒体却完好无损**」的假注入（`readyState 4`、`error null`、`duration 4.032`）——
本轮 b 轮就是这么白跑的。**正确做法：从 `<audio>` / `<video>` 的 `src` 里取 key。**

**取流 URL 的形状**（逐字，注意**没有扩展名**）：

```text
https://v3-dreamina-de.jianying.com/<hash>/6ac00098/video/tos/cn/tos-cn-v-148450/<key>/?a=513695&ch=0&…
```

- 同一素材的请求会在**多个 CDN 节点**之间跳（`v3-dreamina-de` / `v26-dreamina-de`），
  换节点时前一个请求会 `net::ERR_ABORTED` —— **那是正常的，别当成失败**
- 🔑 **服务端会转码**：源文件是 **WAV**，取流 URL 上却带 **`mime_type=audio_mpeg`**
  （时长 `4.032` 与源文件一致）⇒ 播的**不是**你上传的那个字节流
- `<audio>` 元素带 **`preload="none"`**，且**未播时它根本不在节点 DOM 里**
  （`audio: null`）⇒ 要读 `src` 得先点一次播放
- 资源账**不会**因为取流失败而变（批次 105 首测、批次 110 复测，两次独立）

- 🆕 **2026-10-05 批次 158 补：取流路径里有**两个**会变的段，做精确拦截前先看清哪段能当锚点**
  （逐字样例，取自 `Network.requestWillBeSent` 里 `type: Media` 的真实 URL）：

  `https://v26-dreamina-de.jianying.com/9b1cc36e5063d367b58d0863f0884010/6ac28a9b/video/tos/cn/tos-cn-v-148450/owLkIxBVhkxfBZNKIHxPmDfCEaEeIPQJOsOAIG/?a=513695&…`

  | 段 | 逐字取值 | 性质 |
  |---|---|---|
  | 域名 | `v26-dreamina-de.jianying.com` | CDN 节点，**会跳**（本文件上面已记「另一个 CDN 节点」） |
  | **第 1 段** | `9b1cc36e5063d367b58d0863f0884010` | 32 位 hex —— 🔴 **批次 158 拿它当拦截锚点，拦错了**（见下面 159 那条） |
  | 第 2 段 | `6ac28a9b` | 8 位 hex，与本节开头样例里的 `6ac00098` 同类 |
  | tos 桶 | `tos-cn-v-148450` | 固定 |
  | 末段 | `owLkIxBVhkxfBZNKIHxPmDfCEaEeIPQJOsOAIG` | 32 位混合大小写 —— **这个才是「播放取流 key」** |

  ⚠️ 「第 1 段每文件唯一」在本轮**只有 1 个样本**，是**推测**不是实测结论；
  而且**连末段也不是稳定标识** —— 同一次播放的兜底请求里，末段会换成另一个 key。

- 🆕 **2026-10-05 批次 159 补：播放钮也只在选中态渲染**
  （与上面第 4 条互补：那条说 `<audio>` 懒创建，这条说**按钮**也懒渲染）。
  页面重载后节点逐字是 `… 1 resource: 1 ready, 0 processing, 0 failed. Not selected.`，
  此时在节点里 `querySelector('button[aria-label^="Play"]')` 读出 `null`；
  **先点中节点再找**（点中后同一个查询读出落点 `712,433`），不要当成「元素没了」。

- 🔴🔴 **2026-10-05 批次 159 补上最重要的一条：同一个素材有「不止一条」取流 URL。**
  这是拦不中播放的**真正原因**，实测链条（逐条都是量出来的）：

  | 轮次 | 动作 | `Network` 事件 | 界面 |
  |---|---|---|---|
  | 首次播放 | 拦「末段 key #1」 | `requestWillBeSent` 一条 | 正常播 |
  | `a.load()` | 拦中 #1 | `loadingFailed` **`blockedReason: "inspector"`** | **仍正常播** |
  | `a.load()` | 拦中 #1 ＋ #2 | 又一条 `requestWillBeSent`，**第 1 段/第 2 段/末段全变** | 仍正常播 |
  | `a.load()` | 拦中 #1 ＋ #2 | 无新 URL（累计 `blockedReason` **3 次**） | ⭐ **失败态出现** |

  ⇒ 📌 **「换 CDN 节点」这条已有记录不够**：换的**不只是域名**，
  **路径里三段全变**（第 1 段 32 位 hex、第 2 段 8 位 hex、末段 32 位 key）。
  ⇒ **只拦一条 key 是拦不住的** —— 应用会自动兜底到下一条把播放接上，
  于是「拦截明明报了命中，界面却毫无异常」。
  **要复现失败态，必须把兜底链逐条拦干净**
  （循环 `a.load()` → 采新 URL → 加进 `setBlockedURLs`，直到不再出现新 URL）。
  完整配方见
  [预览与播放视频节点 · 怎么自己造出这个状态](10-tasks/media-playback.md#怎么自己造出这个状态供复现)。
