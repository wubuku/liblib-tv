# 账号存储、容量与配额

> 适用角色：所有用户。
> **本页证据等级分两层（Batch 221 补记）**：**十项配额的数值与文案全部取自后端运行策略源码**，逐条比对原文、未改写；而**侧栏那条容量进度条的实际渲染本手册没有取到图**（本机账号为空，运行时看不到真实容量数据）。**下面讲容量条那一节讲的是「代码表明它长这样」，不是「我截过图给你看」。**
> 适用版本：以下默认值取自后端运行策略（取证基线 v1.6.22）。**部署方可以改这些值**，所以你看到的报错数字可能与这里不同——以报错里的数字为准。

## 目标

看懂侧栏那条容量进度条，撞到「已达上限」时知道是哪一条、该删什么。

## 侧栏的容量条

::: warning 这一节没有运行时实证
本机账号为空，运行时读不到真实容量数据，**所以这一节的界面描述全部来自源码**（`canvas-project-sidebar.tsx` 与后端 `DefaultRuntimePolicy()`），**不是截下来的界面**。数值口径可放心用，**像素级外观请以你自己界面上看到的为准**。
:::

左侧栏底部的硬盘图标就是它，显示**已用**与**总量**，点它会跳到产品里的**资产页**（`/assets`，本手册未单独成页；素材的上传见 [上传本地图片、视频、音频](upload-materials.md)）。

| 你看到的 | 含义 |
|---|---|
| **本地已用 X，共 Y** | 本地工作区模式：统计的是**浏览器本地**的素材 |
| **已用 X，共 Y** | 账号模式：统计素材文件**与创作会话附件** |
| **剩余 Z** | 还能放多少 |
| **容量已满** | 已用 ≥ 总量，此时「剩余」不再显示 |
| **正在统计容量** | 首次加载中 |
| **容量暂不可用** + 「重试」 | 统计接口出错，点重试重新拉 |

颜色会随占用率变，阈值是硬编码的：

| 占用率 | 状态 |
|---|---|
| < 70% | 正常 |
| ≥ 70% | 提醒（变黄） |
| ≥ 90% 或已满 | 严重（变红） |

数值显示规则：小于 0.1% 且确实有占用时显示「**<0.1%**」；否则保留一位小数。容量单位按 B / KB / MB / GB 自动换算，**数值 ≥ 10 时不显示小数**（所以你会看到 `1.2 GB`，不会看到 `1.25 GB`）。

## 账号有十项配额

这十条是**服务端强制**的，撞到哪条就报哪条，不是提示而是拒绝：

| 配额 | 默认值 | 撞到时的报错 |
|---|---|---|
| 账号存储总量 | **20 GB** | 文件超过账号存储总量上限 20GB |
| 画布 + 素材结构化数据 | **256 MB** | 账号画布和素材数据已达到 256MB 上限，请先删除不需要的内容 |
| 每日上传总量（UTC 自然日） | **2048 MB** | 每个账号 UTC 自然日上传总量必须小于 2GB |
| 单个上传文件 | **小于 50 MB** | 单个上传文件必须小于 50MB |
| 单个生成文件 / 资源 | **小于 64 MB** | 单个生成文件不能超过 64MB / 单个生成资源超过 64MB |
| 素材数量 | **2000 个** | 账号素材数量已达到 2000 个上限 / 账号素材数量不能超过 2000 个 |
| 画布数量 | **1000 个** | 账号画布数量已达到 1000 个上限 / 账号画布数量不能超过 1000 个 |
| 任务历史条数 | **20000 条** | 账号任务历史已达到 20000 条上限，请联系管理员归档 |
| 任务历史数据（文本） | **1 GB** | 账号任务历史数据已达到 1GB 上限，请联系管理员归档 |
| 上游请求日志 | **100000 条** | 账号上游请求日志已达到 100000 条上限，请联系管理员归档 |

::: warning 这张表是**默认值**，不是写死的上限
这十个数来自服务端的**运行时策略**（`DefaultRuntimePolicy()`），**部署方可以改**——把某个部署的存储上限调到 10GB、或把保留期从 30 天改成 7 天，都是配置层面的事。

**所以**：报错里的数字**以你实际遇到的那条为准**。如果你看到的上限和上表不一样，**不是手册错了，是你这个部署改了策略**——照报错里的数字理解即可。

::: danger 你是**本地部署**的话，上表十个数**一个都不适用**
**本地部署走的不是「改了策略」，而是另一套内置策略**：`runtime_policy.go` 里有两套——`DefaultRuntimePolicy()`（上表这些值）与 `selfUseRuntimePolicy()`，而 `RuntimePolicy()` 的判据就是 `if s.localMode { return selfUseRuntimePolicy() }`。

| 策略项 | 默认部署 | **你的本地部署** |
|---|---|---|
| 同时排队或运行的任务上限 | 5 | **999** |
| 素材归档保留天数 | 30 | **0 —— 永远不会自动清除** |
| 存储 / 任务数据 / 素材数 / 画布数上限 | 20GB / 1GB / 2000 / 1000 | 999GB / 999GB / 999999999 / 999999999 |

**两条会真影响你的**：
1. **归档素材在本地不会被自动彻底清除**——清理任务拿到保留天数 0 就直接返回。**磁盘只增不减，删掉的素材要你自己去清**（见 [素材库（资产页）](asset-library.md)）；
2. **「同时排队或运行的任务最多 5 个」那条报错你在本地基本撞不到**（上限是 999）。

两套取值的完整对照与口径见 [参考：快捷键全表、路由与端点](../20-reference.md)，每次构建都会与上游核对。
:::

::: tip 两种写法、同一条限制
同一个上限，**有时会撞出两种措辞**——不是两套限制，是触发路径不同：

- **素材数量 / 画布数量**：新建时报「已达到 N 个上限」，**替换 / 批量导入**时报「不能超过 N 个」；
- **单个生成文件 / 资源**：同样是 64MB 这条上限，一条写「单个生成**文件**不能超过 64MB」，另一条写「单个生成**资源**超过 64MB」。

**认出它们指的是同一个上限，就不会误以为是两件事。**
:::

::: tip 256MB 那条最容易撞
它统计的是**画布与素材的结构化数据**（节点、连线、提示词等），不是你上传的大文件。上传大图吃的是 20GB 那条，但画布里堆几百个带长提示词的节点会先把 256MB 顶满——**这时删大图没用，得删画布或节点**。
:::

::: tip 1GB 那条数的是**任务的文字**，而且你腾不出来
它统计任务记录里的**提示词、输入参数、报错文案、生成结果**这些文本（以及结果条目的地址与载荷），**不是素材文件**——所以画布删光、素材清空都腾不出这 1GB。**要腾只能删任务历史，而产品没有提供删除任务历史的入口**，所以它的报错措辞直接就是「请联系管理员归档」。

**它涨得比你想的快**：新提交任务时记提示词与输入，**任务完成时还会把生成结果整份记进去**——长视频、长音频这类结果大的任务，一次就能顶掉可观的一截。
:::

## 任务多久算超时

除了配额，还有一组**按操作类型区分的超时**——超过就判定失败：

| 任务类型 | 超时 |
|---|---|
| 音频 | **8 分钟** |
| 文本 | **8 分钟** |
| 图片 | **8 分钟** |
| 故事板 | **20 分钟** |
| 视频 | **60 分钟** |
| 其他（未归类） | **10 分钟** |

**视频那 60 分钟是最容易被误判的一条**：长镜头本来就慢，卡在「运行中」很久不等于出错。**先看状态徽章再决定要不要重发**——重发会重新计费（见 [概念：BeefTV 是怎么工作的](../30-concepts.md) 的「提交不确定」）。

::: tip 超时数字同样可被部署调整
它和上面那十项配额出自同一份运行时策略。**以你实际遇到的为准。**
:::

## 每分钟限流

除了总量配额，还有按分钟的频率限制，超了会告诉你等几秒：

| 操作 | 每分钟上限 |
|---|---|
| 提交生成任务 | 30 |
| 上传资源 | 30 |
| 导入资源 | 30 |
| 写素材 | 120 |
| 写画布 | 120 |

报错形如「**请求次数已达上限，请在 N 秒后重试**」。这是**自愈**的——等 N 秒自动好，不需要改配置。

## 批量并发和账号任务上限不是一回事

::: danger 批量表能选到并发 10，但账号同时只跑得下 5 个
[批量创作表](generate-images.md) 的并发选项是 **1 / 5 / 10**，默认 10。看起来设 10 能一次铺满，但**服务端对每个账号有「同时排队或运行的任务最多 5 个」的硬上限**。

实际行为是：调度器会先算 `账号上限 − 当前排队/运行中的任务数 − 本地已预留的`，再从「等待中」的行里取够这个数去提交。所以：

- 设成 10 不会开 10 个任务，**超出的行会继续停在「等待中」**，前面有任务完成就自动补位；
- 你**不会**看到「最多 5 个」这条报错——批量链路会自己排队，不硬撞上限；
- 但**单张卡片**点「生成」不受这层调度保护：账号已有 5 个在跑时再点，会直接报「**同时排队或运行的任务最多 5 个，请等待已有任务完成**」。

所以批量表里**并发选 5 就够**，选 10 不会更快，只是让更多行提前进入「等待中」。上游频控紧时反而应该调低。
:::

## 两种「回收站」，别混

产品里有两个都叫「回收站」的机制，**完全独立**：

| | 画布库回收站 | 素材归档 |
|---|---|---|
| 装什么 | 你删掉的**画布/项目** | 删掉或被清理的**素材文件** |
| 怎么清 | 你手动「彻底删除」 | **后台自动**，默认 **30 天**后彻底清除 |
| 上限 | 保留**最近 200 条**完整快照 | 按天算，不按条 |

素材归档的 30 天是硬编码默认策略，到期由后台任务走和手动删除**同一条强校验路径**清理（有业务引用的会先被跳过）。所以：**素材删掉后一个月内别指望还能在归档里找回来。**

画布库回收站的 200 条限制、恢复的幂等性、彻底删除的二次确认，见 [撤销重做、版本历史与回收站](undo-history-versions.md)。
