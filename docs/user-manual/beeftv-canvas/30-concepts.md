# 概念：BeefTV 是怎么工作的

> 解释性内容，不包含操作步骤。

## 「工作流」和「生成配置」是同一个节点

手册别处会同时出现这两个名字——菜单里叫「**工作流**」，有些地方叫「**生成配置节点**」。它们是同一个东西。

- 菜单「添加节点 → **工作流**」实际创建的是一个**生成配置节点**（默认尺寸 **480 × 390**），节点标题默认就叫「**生成配置**」；
- 只有当你给它选了 RunningHub 提供方时，标题才变成「**RunningHub 工作流**」。

这个节点不是拿来存内容的，它是**引用的汇合点**：把图片、视频、音频、角色卡、提示词都连到它身上，再由它决定把这些引用**喂给谁**。

### 两种提供方

| 提供方 | 面板上显示 | 说明 |
|---|---|---|
| **RunningHub** | 分成「**AI 应用**」和「**工作流**」两组，各自带条目数 | 走 RunningHub 的应用或工作流；每条后面标着它擅长的能力（图片 / 视频 / 音频） |
| **模型直连** | 出现「视频生成模式」等控件 | 走你自己在渠道里配好的模型 |

::: warning 选了 RunningHub 却提交不了
多半是**插件没启用**——报错文案是「**RunningHub 工作流插件未启用**」。先到插件页把它打开（见 [plugins-management.md](10-tasks/plugins-management.md)），再回来提交。
:::

::: warning 别被标题骗了
看到「生成配置」四个字，容易以为它是个设置面板。实际上它**在画布上、占一个节点位置、能被连线**——它是把「素材」和「执行方」接起来的那一环。
:::

## 双轨视口：为什么画布这么顺滑

画布把「你正在拖动」和「系统已确认」分成两条轨道：拖动时只直接改写屏幕上的图层（每帧），界面状态按更低的频率（64ms 虚拟化刷新、120ms 提交）批量确认。React 界面在你拖动时保持静止，因此大画布也不卡。

## 任务对账：刷新页面为什么不怕丢

生成任务提交后，任务身份写在节点上。刷新页面后系统用任务列表与画布节点**对账**：仍在运行的任务继续跟踪；没有任务身份的「加载中」节点标记为本地中断，不会覆盖已完成的结果。

## 多标签同时编辑：谁赢、什么时候会失败

画布存在浏览器本地，存储键按**账号**划分而不是按标签页——同一个账号开两个标签，改的是同一份数据。

### 保存用的是「三方合并」

每次写入都记着三个版本：**上次读到的**、**我这次要写的**、**盘上已有的**。逐个字段比：

| 情况 | 结果 |
|---|---|
| 我没改这个字段 | 用盘上的 |
| 只有我改了 | 用我的 |
| 两边改成一样的值 | 用我的 |
| 两边改成**不同**的值 | **用盘上的**（先落盘的那个赢），**不提示** |

合并是**逐字段**的。所以两个标签各改画布的不同角落，两边都能留住；只有**改到同一个字段**才会互相顶掉。顶层还有两个特例：`updatedAt` 一律以盘上为准；生成结果的幂等标记取**并集**（谁都不会让已确认的结果丢掉）。

删除不是抹掉，而是留一个「墓碑」记着删除发生在哪一版。如果另一个标签在你离线期间删掉了某个节点，而你这边还拿着它继续改，就会被判成冲突——**不会静默复活**。

### 一个标签改了什么，另一个标签不会知道

画布**没有**任何跨标签实时同步通道（没有广播、没有存储事件监听）。所以另一个标签的改动**不会**推到你眼前：你看到的画面一直是自己那份内存里的内容，直到你下一次保存（编辑停止 **400ms** 后自动落盘）时才顺手并入，或者刷新页面时重读。

::: warning 这是本节最该记住的一句
**别把两个标签当成同一张画布的两块屏幕。** 它们是两个各自独立的编辑器，共享一块存储，中间没有同步。
:::

### 冲突待遇：普通编辑 vs 生成结果写回

| | 普通编辑（移动节点、改文字…） | 生成结果写回 |
|---|---|---|
| 同一字段撞车 | 静默以先落盘的为准 | **直接失败**，不写入 |
| 你看到什么 | **没有任何提示** | 明确的报错文案 |

生成结果写回宁可不写也不写错：撞车时报「画布生成副作用与并发修改冲突」，撞上已删除内容时报「画布生成副作用与已删除内容冲突」。两种情况下画布都会先回到「盘上真实的样子」再把错误抛给你，**不会留下半截结果**。

::: tip 看到「生成失败」要展开详情
这两句报错不在错误分类表里，会落进兜底分类，界面上给出的原因与建议是笼统的「生成失败 / 请查看详情后再决定是否重试」。**真正的原因在节点的错误详情里**——那句「与并发修改冲突」或「与已删除内容冲突」会原样留在那儿（参见下文「排查信息与错误来源分类」）。
:::

### 还有一道服务端关卡

本地合并通过之后，画布会连同它读到的版本号一起存到后端。后端发现版本号不是最新的就拒绝写入（绝不覆盖），报「**云端画布已有更新，已停止覆盖；请保留本地草稿并加载最新版本**」；素材被另一个标签换掉时则是「**画布引用的素材已变化，当前内容未被覆盖，请保留草稿并重新加载**」。

这两条与前面的本地冲突是**不同层**的：本地合并能过，后端仍可能拒。

### 什么时候完全不会报

两种情况界面一声不吭：普通编辑撞车（静默让位），以及本地或后端同步失败（只往浏览器控制台写一行日志，等下一次编辑再重试）。**界面安静不代表两边都写成功了。**

本节讲到 4 条并发冲突文案，第 5 条（浏览器不支持跨标签存储锁）与完整对照表见 [90-troubleshooting.md](90-troubleshooting.md)。

## 三层历史

| 层 | 记录什么 | 特点 |
|---|---|---|
| 用户撤销栈 | 每个节点/连线的改动前后像 | 180ms 合并、上限 50 层 |
| Agent 批次 | 整批操作前的完整快照 | 用户一旦接手编辑即整批失效 |
| 项目版本 | 服务端定期与恢复前快照 | 恢复会生成新版本，可再撤销 |

## 生成落账事务

生成结果写回画布是「两阶段」的：提交时登记意图，持久化时只认已确认的标记；失败按四种情形推导回滚目标——避免「半截结果」污染画布。

## 云端 Agent 的封闭指令集

Agent 不能为所欲为：它只能使用 8 种画布操作（增删节点/连线、选区、视口、发起生成等），每次执行后系统按事实复核（比如「资源真的生成了吗」）；与你本地编辑冲突时宁可中断、保留你的编辑。

## 三层能力分布

BeefTV 把「能力」分在三层，各司其职：

| 层 | 承担什么 | 特点 |
|---|---|---|
| 前端内置插件 | 审美批改、提示词优化、Eagle 接入等界面能力 | 编译期打包，**不执行第三方代码** |
| Go 后端协议引擎 | 生成渠道适配（声明式 JSON 模板） | 上传插件只能走声明式路径 |
| 本地伴随进程 | 深度/线稿/姿态等本机推理 | 精确回环地址 + 挑战签名会话 |

安全姿态：上传的插件永远是纯数据，执行永远在可信引擎内。

## 多选与编组

框选 ≥2 个节点后可**成组**：分组盒自动包住成员（外扩 28px）、标签显示「组 N」、支持切换背景色与三种排列方式；组内节点拖拽时整组跟随，**双击标签可重命名**，也可解组恢复独立。分组让「先摆好布局再连线」的工作流成为可能。

## 画布外观

底部工具条「画布外观」面板集中管理画布级视觉设置（v1.6.14 实测）：

- **主题模式**：浅色 / 深色 / **自定义** 三选一（自定义进入画布主题编辑）；
- **空间网格**：点 / 线 / 空白 三种网格形态；
- **网格吸附**：步进 16px，开关可控（与视图控制条的网格吸附开关联动）；
- **显示连线**：控制节点间连线显隐（与视图控制条的隐藏节点连线开关联动）。

## 两种「版本」，别搞混

产品里有两套彼此独立的版本概念，界面上都带「版本」二字：

| | 节点版本族 | 项目版本记录 |
|---|---|---|
| 记的是什么 | **同一个节点的多次生成结果** | **整张画布在某个时点的快照** |
| 组织方式 | 兄弟节点，共享 `versionOfNodeId`，带 A/B/C 标签，其中一个标 primary | 顶栏「版本记录」侧栏的条目列表 |
| 怎么回退 | 切换 primary 标志，或把下游连线指到别的兄弟节点 | 选一个历史版本恢复（恢复前自动备份，恢复本身也可撤销） |
| 谁在用 | 生成流程 | 兜底：误操作、误删、想要回到某个「当时的画布」 |

关键差异：**改生成结果用前者，改画布布局用后者**。想「换回第一版图」是版本族的事，不是版本记录的事。

## 连线顺序就是引用编号顺序

上游资源自动成为下游生成节点的参考素材时，**连线的先后顺序直接决定「参考 1、参考 2……」的编号**。所以想让某张图当主参考，不需要去设置里改，**把连线接在正确的槽位上**就行。调整顺序只影响编号，不影响其他连线。

这也解释了为什么 @mention 模式会「忽略连线」——一旦你在提示词里点名要哪些参考，系统就以你的名单为准，连线顺序不再参与决定。

## 提交不确定：为什么它宁可不动也不重试

网关超时（如 524）时，客户端看到的只是「没等到回应」，**但服务端可能已经在跑**。此时如果自动重发，就可能为同一件事扣两次费。

BeefTV 的选择是把它归为「**提交不确定**」：

- **不自动重试**，也不自动重发；
- v1.6.15 起更进一步——**丢失提交回执会记为「未确认」而不是静默重发**，从根上堵住重复提交；
- 视频任务提供「**取回结果**」：拿原任务 ID 去上游查并下载结果，复用已有工作、**不产生第二次计费**。

理解了这个概念，你就能判断什么时候该重试、什么时候该先去查结果。

## 排查信息与错误来源分类

生成失败时「复制排查信息」给出的文本里，除了原因与建议，还带**错误来源分类**（v1.6.15 起）：

| 来源 | 含义 | 该找谁 |
|---|---|---|
| `local_validation` | 本地校验就没过，请求没发出去 | 改你的参数/素材 |
| `upstream_http` | 上游返回了 HTTP 错误 | 渠道/服务商 |
| `upstream_response` | 上游返回了业务错误（HTTP 200 但业务失败） | 渠道/服务商 |
| `local_response` | 本地响应大小/格式校验没过 | 素材太大或异常 |
| `local_result` / `client_result` | 结果落账或客户端处理环节失败 | 多半重试可解 |
| `unknown` | 归不了类 | 带上完整排查信息报障 |

分类的意义在于**把「谁的锅」说清楚**：本地校验没过就别去怪渠道，上游业务错误就别反复改自己的提示词。配合排查信息里的请求 ID 与上游代码，排查会快很多。

## 时间线字幕的快照契约

字幕有**两个存放位置**，方向是单向的：

```
视频节点 subtitleEntries  ← 权威（authoritative）
        ↓ 快照
时间线 S 轨字幕片段        ← 只读快照
```

- **改节点的字幕弹窗** → 保存后会同步刷新时间线片段；
- **在时间线上拖动/裁剪/删除片段** → 保存时按视频节点回写 `subtitleEntries`；
- 目标只有一个：**不存在两份互相漂移的字幕**。这也是为什么时间线里的字幕片段可以被自由编排，而不用担心改坏节点上的原始数据。

## 时间线的三种轨道

时间线固定三条轨道：**V 视频 / A 音频 / S 字幕**。画布上的视频与音频节点会自动铺到对应轨道（这叫「素材自动铺轨」），字幕轨道来自视频节点的字幕数据。基准比例是 96 像素/秒，缩放范围 2%–400%。

理解了「自动铺轨」，你就知道为什么刚进时间线就有一堆片段——它们不是 bug，而是画布素材的投影。

## 同一个「复制」，两条路径，一条会备份一条不会

BeefTV 里有三个看起来是一回事的「复制一张画布」，但走的是**两条不同的代码路径**，结果差别很大：

| 你点的 | 走哪条路 | 上传服务器吗 |
|---|---|---|
| 画布库卡片菜单「创建副本」 | `createWorkspaceCanvasProject` → `createLocalCanvasProject` | **会** |
| 画布顶栏菜单「复制画布」 | `importProject`（纯内存写入） | **不会** |
| 只读横幅「复制项目」 | 同上 | **不会** |

差别在最后一步有没有 `await syncLocalCanvasProjectToBackend(id)`。有它的那条会把副本存到服务端；没有的那条只把画布写进浏览器的 IndexedDB，然后**照样弹出「画布副本已创建」**。

这不是「本地优先」的设计取舍，而是**实现漏了一步**——同一个文件里另一处创建画布的函数专门写了注释，说明为什么必须上传：

> Creating a project only in IndexedDB leaves the runtime returning 404 and allows its detached-resource cleanup to delete media that the canvas still uses.

**记住这条的实用价值**：在当前版本，「复制一张画布」**默认是不带备份的**。需要可靠副本时，去画布库里用卡片菜单的「创建副本」。实测细节见 [10-tasks/readonly-canvas.md](10-tasks/readonly-canvas.md)。

**同一个漏步还波及改名**，而改名比复制更容易撞上——它是同一个洞的另一面，见下一节。

## 一张画布有两个名字，改哪个都传不上去

画布的名字在产品里存了**两个字段**，各管一块：

| 字段 | 谁读它 | 谁写它 |
|---|---|---|
| 画布标题 | 画布库卡片、顶栏左侧的大字 | 画布库卡片的行内「重命名」 |
| 画布在顶栏的显示名 | 画布顶栏右侧的画布切换器 | 画布顶栏菜单的「重命名画布」 |

**两者互不同步。** 在画布库改的名，顶栏右侧照旧显示「画布 1」；在顶栏改的名，画布库卡片照旧显示旧名。顶栏那一栏会同时摆着两个名字——**左边是新名、右边是「画布 1」**，一眼就能看出它们各说各话。

更要紧的是第二层：**两处改名都不会立刻上传到服务器**（实测写请求数为 0），而且**后续编辑能不能把名字带上，取决于你改的是哪个字段**：

- 改的是画布标题 → 之后任何一次画布内容保存都会**顺带把它存上去**；
- 改的是顶栏显示名 → 之后**编辑多少次都存不上去**（这个字段后端根本不保存）。

**实用结论：名字要在画布库改，改完顺手在画布里做一次任意编辑。** 详见 [10-tasks/manage-canvases.md](10-tasks/manage-canvases.md)。
