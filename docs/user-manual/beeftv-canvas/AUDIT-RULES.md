> 本文件是**给后续批次（以及换人接手时）用的作业规约**，不是给人读的手册正文。
> 内容全部来自 Batch 93–111 的实战教训，每条都注明了它是在哪一批、因为什么被立为规约。
> 与 [AUDIT.md](AUDIT.md) 的分工：AUDIT 按时间记录「查了什么、发现了什么」，本文件只回答「下次该怎么查」。

## 0. 三条底线

| 底线 | 说明 |
|---|---|
| **付费边界** | 生成类操作按量计费。回走验证只到**付费边界前一步**；不配置 Provider Key；**不触发真实生成**。因此依赖真实生成的证据只能是源码锚定，并在页面与账本里显式标注「待运行时实证」。 |
| **证据形态纪律** | **声明处升版、证据处留痕**——各页「v1.6.14 实测」标注是走查发生版本的真实记录，**禁止改写成新版本**。新版本的内容写在新位置，不覆盖旧证据。 |
| **工作区纪律** | master 分支直改，不建/切 worktree，不用 stash，绝不丢弃他人改动。**提交一律用显式路径**（见 §6），因为并行 session 会预先暂存文件。 |

## 1. 资产风险排序：先查哪一类

Batch 106–107 实测得出的排序，决定一个 batch 的审计对象选择：

> **枚举型（可能被增删）> 数值型（可能被改常量）> 行为规则（最稳）**

| 类型 | 例子 | 为什么易错 | 本手册实例 |
|---|---|---|---|
| 枚举 | 菜单项、端点、快捷键、插件清单、参数档位 | 上游会随版本增删，手册不会自动跟 | Batch 96 端点、97 快捷键、98 菜单、101 插件、105 参数 |
| 数值 | 缩放上限、栈深度、像素比、并发数 | 常量一改，文档静默过期 | Batch 104（缩放 200%→800%）、107（180ms/50 层） |
| 行为规则 | 解析规则、校验条件、降级路径 | 通常有较完整测试覆盖，变动少 | Batch 106 字幕 11 条全对 |

**但「漏写」与「写错」同权重。** 行为规则虽然稳定，**手册却常常整节漏写**（Batch 108：批量连接的整节约束从未写过）。写错会被读者发现，漏写会让读者**以为自己操作错了**——后者更隐蔽。

## 2. 三层可达性判据（审任何 UI 能力都要问）

来源：Batch 98（背板）、99（字幕 / more 组）、102（渲染视图按钮）。

> 审一个界面能力，要连问三句。**「注册表里存在」是最容易骗人的一环。**

1. **注册表里有吗？**（工具/菜单/端点是否在注册文件中出现）
2. **当前上下文会渲染它吗？**（是否被 `applicable` 谓词、模式分支、group 渲染条件过滤掉）
3. **点下去 handler 真的做那件事吗？**（handler 是否其实打开了别的东西）

**只查到第 1 层就下结论会犯两种错**：
- 误判成「只是暂时禁用」而保留错误说法（背板：`Frame` 被 `developingNodeTypes` 禁用，且 handler 根本不创建 Frame）
- 误判成「不存在」而虚构缺陷（Batch 102：`grep 取景|CAM` 零命中，实际手册写的是「导演视角/机位视角 + 方向球」）

## 3. 否定性声明要拆两问验

来源：Batch 108（端点改接）、109（演员身份）。

> 否定性声明是最容易被上游新增功能悄悄推翻的一类，且失效后果特殊——读者会去找一个不存在的功能。

必须分别记录，**第二问最容易被跳过，而它恰恰是读者据以行动的依据**：

1. **结论**对不对？（功能确实不存在吗）
2. **理由**对不对？（为什么不存在）

**「结论对、理由错」是独立的一类缺陷**（Batch 109）：手册写「带动画的普通模型不会被当作演员」，结论对，但真实判别依据是**从哪个入口创建**——用户会照着错误理由去剥模型动画、重新导出，成本高且完全无效。**给错理由比不给更糟。**

## 4. 检索方法必须双向自证

来源：Batch 93（0 命中）、110（命中 1000+ 条）。

> 任何「搜源码验证手册说法」的动作，**必须先用已知样本验证检索方法本身有效**，且**正反两个方向都要验**。

- **假阴性**：0 命中可能只是检索写错了（Batch 93 若不复核会漏修 5 处真实缺陷）
- **假阳性**：命中太多同样致命（Batch 110 第一版扫出 1000+ 条，正则贪婪把版本号 `v1.6.14` 的 `0`、列表序号 `1`、单词尾字母全当快捷键）

**假阳性的代价不比假阴性低**——一个报出 1000 条的闸门，使用者会直接关掉它；**闸门一旦失去可信度就等于没有闸门**，还会连带损失真问题的可信度。

具体做法：构造一个**必然存在**的串（应命中）与一个**必然不存在**的串（不应命中），两个都验证通过，才开始正式审计。

### 4.1 先查手册，再下源码

来源：Batch 119 与 Batch 123 **连续两次**。两次都是从源码入手深挖，查到一半才发现**手册早已写过**：

- Batch 119：查到 Seedance 比例是 7 项，险些把手册的「6 档」改成错的——原文其实已写明「六档之外还有 自适应」。
- Batch 123：计划审视频节点工具条的可达性，挖到一半发现 `generate-video.md` / `local-runtime.md` / `subtitle-highlights.md` **三处都已覆盖**，连「`subtitles` 工具已注册但视频节点从不渲染 primary 组」这种细节都记了。

**代价不只是白干**：Batch 119 那次差点**把已经正确的文档改错**——错误的修正比不修正更糟（§3 否定声明两问同源）。

**做法**：选定一个面之前，**先花五分钟 grep 一遍手册**已经写到哪一步，再决定要不要下源码。

- 手册只提了一句话（提到分组名、没展开内容）→ 下源码补内容，这是正路（Batch 122 图片工具条即是）。
- 手册已经成体系地写了 → **换目标**，别把同一份内容重写一遍。

判断「已成体系」的标准：该面在**两个以上**页面被提到，且有参数表或步骤，而不是只出现在别的页面的顺带一句里。

## 5. 闸门五步法：人工结论 → 机械闸

来源：Batch 94（截图四方对账）、96（端点双向校验）、110（快捷键前缀）、111（解禁条件）。

> 已经人工查清的事实，如果**能机械表达**，就应该固化成构建闸门，而不是留在批次记录里等人重查。

1. 先人工查清事实
2. 判定能否机械表达
3. 能则写成脚本接入 `build-site.sh` 步骤 6
4. **必须做反向验证**——人为制造该类缺陷，确认脚本以非零退出码拦下
5. 在 AUDIT 记录「**本闸不检查什么**」

**第 5 步最容易被忽略，但它是闸门可信度的一部分**：明确说出边界，使用者才知道何时不能依赖它。例：`verify-exclusions.py` 只判「条件是否仍成立」，不判「条件写得对不对」；`verify-endpoints.py` 找不到上游源码时静默跳过。

**闸门判据要能正反自证**（否则只会在某一类错误上疯狂误报）：
- 端点闸：声明现存的须注册 **且** 声明下线的须未注册
- 快捷键闸：漏前缀须报 **且** 有 Alt/Shift 变体的须不报

### 现有九道闸

| 闸 | 脚本 | 抓什么 |
|---|---|---|
| 站内死链 | `build-site.sh` 内联 | 指向 `srcExclude` 文件的链接（`ignoreDeadLinks` 会放过） |
| 截图四方对账 | `scripts/verify-screenshots.py` | 库内 / manifest / 发布页引用 / dist 四侧不一致（孤儿图 = 证据在库但读者看不到） |
| 端点双向校验 | `scripts/verify-endpoints.py` | 手册声明的端点与上游生产路由注册不符 |
| 快捷键前缀 | `scripts/verify-shortcuts.py` | 指向「必须带 Ctrl/Cmd 的键」却写成裸键 |
| 解禁条件 | `scripts/verify-exclusions.py` | excluded 任务的开放条件已与上游现状不符 |
| 标签漂移 | `scripts/verify-label-drift.py` | 同一个 value 跨文件出现不同 label，且未在登记表里定性 |
| 不可达声明 | `scripts/verify-unreachable.py` | 「这个功能没有入口」这类**否定式断言**已过期，或登记表与上游现状不一致 |
| 表格结构 | `scripts/verify-tables.py` | 单元格里的裸竖线（`\|\|`、含 `\|` 的 URL）把表格多切一列——**构建照样成功，只有读的人才看得见** |
| 手册元数据 | `scripts/verify-meta.py` | 「本手册有多少篇/项/张/页」与**现场重数**不一致；真值来自本仓库目录与 yml，**前八道按定义照不到**。它还盯着**这张清单表自己**、**闸门脚本里 `git grep` 正则的引擎兼容性**（Batch 157 方向五）、**内链完整性**（Batch 158 方向六：约定 + 孤儿页）、以及**「报错即失败」不变式**（Batch 159 方向七：闸门不得只打印 ✗ 而退出码仍为 0） |

> **注意标题的数怎么来的**：表里 9 行，但 `scripts/` 下只有 **8 个** `verify-*.py`——
> 因为「站内死链」那道是 **`build-site.sh` 内联**的，没有独立脚本。
> **表行数 = 独立脚本数 + 1。**
>
> **这张表本身由第八道闸盯着**（`verify-meta.py` 的方向三）：标题里的数、表里的行、
> `build-site.sh` 里实际调用的脚本，**三方必须一致**。
>
> **为什么要盯**——这张表**连续漏了三次**：Batch 143 加了第七道却没登记；
> Batch 145 修表时把标题写成「七道闸」而表里 8 行；Batch 146 加第八道又只改了一处。
> 根因是**标题在数脚本数、而表行数还要加上内联那道**——**差 1 每次都刚好逃过肉眼**。
> **三次同向的遗漏足以说明：靠人记不住，交给闸门。** 方向三在上线当天就抓出了第三次。

## 6. 工作区纪律：提交一律用显式路径

来源：Batch 99 实战。

并行 session 会**预先 `git add` 自己的文件**，此时 `git diff --cached` 里混着别人的东西。此时 `git commit`（不带路径）会**代为提交他人未完成的工作**。

```bash
# 新文件要先 add 才能用显式路径提交
git add docs/user-manual/beeftv-canvas/scripts/<新文件>.py
git commit -F /tmp/msg.txt -- <我这次改动的全部路径，逐个列出>
```

- 只暂存 `docs/user-manual/beeftv-canvas/` 路径，**且提交时仍要显式列全路径**（`git add <dir>` 只限制 add，不限制后续 commit）。
- 提交前用 `git diff --cached --name-only | grep -v "^docs/user-manual/beeftv-canvas/"` 确认无越界。
- 他人的暂存状态**保持原样**，不取消、不代提。
- 推送后若 `git log -1` 不是自己的提交，说明期间他人已提交，属正常协作，不需处理。

## 8. 写手册的几条措辞纪律

- **界面原文逐字引用**，并注明来源形态（源码锚定 / 运行时 DOM 实证 / 夹具走查）。
- **不能把「随模型/部署/开关变化」的东西写成固定值**（Batch 105：参数实为能力档案驱动）。枚举型信息**不能只给例子**——例子的危害是隐性的。
- **源码文案与用户可触达形态不一致时，以用户能触达的为准**（Batch 98/108：源码叫「背板」，但用户只能建文件夹）。
- 提示语要写**用户能不能据此行动**：是成功还是警告、带不带原因、原因显示几条（Batch 108）。
- 内部黑话（Gate A/B、批次号、localhost、夹具、回走）不出现在发布页（Batch 87）。
- 真实错误码/技术 token 保留，不做「黑话清理」。

## 9. 同一设置多种叫法：本产品的系统性特征

来源：Batch 116/117/119/120 **连续四次**撞上，立为规约。

产品里多个文件各持一份同义枚举表——同一枚 `value` 在不同界面被叫成不同名字。已确认的四处：

| 批次 | 设置 | 一处叫 | 另一处叫 |
|---|---|---|---|
| 116 | 视频生成模式 | 首帧 / 首尾帧 | 图生视频 |
| 116 | 参考类模式 | 参考生成 | 全模态参考 |
| 116 | 局部修改类 | 局部修改 | 视频局部修改 |
| 116 | 运镜类 | 运镜调整 | 镜头/运镜调整 |
| 116 | 音频生视频类 | 音频生视频 | 参考音频生成视频 |
| 116 | 版本对比 | 版本对比 | 结果版本对比 |
| 117 | 执行策略 `strict-assets` | 严格校验 | 严格阻止 |
| 119 | 视频设置面板 | 三套面板，分组名各不相同 | — |
| 120 | 图片质量组标题 | 质量 | 分辨率 |

比例一族更夸张：同一个 `16:9` 至少三种写法（`16:9` / `16:9 横屏` / `16:9 · 横屏` / `横屏`）。

### 怎么审

1. **审任何枚举时，顺手问一句「这个 value 在别处叫什么」**——尤其当它来自一份跨文件复制的同义表时。
2. **手册正文用「用户能触达的那个名字」**（见 §0 证据纪律最后一条），**不要强行统一成某一套**——那是产品文案决策，不是文档能替它做的。
3. 若另一处叫法会**导致用户困惑**（同一页里两个名字、或用户要找的东西找不到），就在手册里单列一张对照表说明来历，**并点明「是同一个设置」**。

### 已建成机械闸

`scripts/verify-label-drift.py`（第五道闸）维护一份**已知分歧登记表**，两个方向都查：

- 出现**未登记**的新分歧 → 退出码 1（提醒补登记，否则后人会以为已审过）
- 登记的分歧**已消失**（上游收敛）→ 退出码 1（提醒清理登记）

**这张表里一半是「巧合」不是「漂移」**：`auto` 既是画质「自动」、又是脚本节点的「单镜时长自动」、又是「自动拆分」；`5` 既是「5 章」又是「每镜 5 秒」。闸门**只查跨文件分歧**（同文件内的多义不算），其余靠登记表逐条定性。**定性是人的判断，脚本只负责把没定性的摆到台面上。**

闸门不检查的还有两条，已写进脚本 docstring：**哪个名字对不对**（产品文案决策），以及**界面上是否真的两处都出现**（需运行时取证，超出静态闸能力）。

### 第六道闸：否定式断言是最容易悄悄过期的一类

前五道闸守的都是**肯定式断言**——「缩放上限 200%」「端点 `/api/x` 存在」。这类断言一旦过期，手册只是某个数字或某张表对不上，读者自己能发现。

**否定式断言**（「画布库没有导入入口」「审美批改建不出这个节点」「章节路由访问不到」）的失效方式要命得多：上游哪天把那个 `ref.current.click()` 补上，**手册会继续言之凿凿地告诉用户「你找不到」**——而用户已经在界面上看到了那个按钮。**这等于把读者的正确观察说成幻觉。**

`scripts/verify-unreachable.py` 为此维护一份**不可达声明登记表**，三个方向都查：

- 已登记的判据**不再成立** → 退出码 1（上游可能已修复，手册该条断言要回走更新）
- 全量扫描出现**未登记**的新缺陷 → 退出码 1（手册漏写了）
- 登记的扫描键**没被扫到** → 退出码 1（登记已失效或键写错）

两路全量扫描，命中集合都必须与登记**双向一致**：

| 方向 | 扫描对象 | 现状 |
|---|---|---|
| 方向二 | `useState` 解构出的 setter **声明后零调用** | 3 处命中，与登记一致 |
| 方向三（Batch 135 新增） | 全库每个 `searchParams.get("X")` 的 X，**有没有「写出点」** | 7 个零写出，已全部归类（豁免 5 + 缺陷登记 2） |

登记表现有 **12 条断言**，反向验证 **11 例**。断言按「缺陷类型」而非「页面」组织：同一族的缺陷（画布库入口、只读无入口、副本/改名不上传、两个名字）各自独立成条，**一条断言只回答一个可被源码推翻的问题**。

**一条断言该拆多细**：Batch 136 的「两个名字」拆成了映射 / 读 / 写三个子判据，因为只有 (a)(b) 时可能只是两处显示不同源，**必须 (c) 写入字段也分开，才敢说「改一处另一处不跟着变」**。同理「改名不上传」要求同时验证「无同步」「有本地 flush」「对照组带同步」——第三条是防「整体改成不上传的设计」的。

**方向三必须带豁免名单，且只保证「每个零写出参数都被显式归类」，不判断「零写出是否就是缺陷」。** 理由是实测的：`baseUrl` 的生产者是外部启动器、`projectId`/`uuid` 的生产者是**用户粘贴的 LibTV 链接**、`fixture`/`demo` 是演示设施——**「界面上没有按钮」不足以断言「功能不存在」**。逐个查过来源之后，真正属于「功能完整但无入口」的只有只读模式一条，另加 `?stay=1`（源码注释自认是留给浏览器验收脚本的开关）。

**为什么扫描只认「setter 零调用」这一条判据**：本产品实测 setter 侧 3/3 全真，而 ref 侧 9/9 全假、宽口径「函数零引用」更是 1192 条噪声。**判据要选「零调用」而不是「少调用」**——ref 出现两次（声明 + 一处正常使用）本就是常态。

**闸门明确不检查的三件事**（写在 docstring 里）：不覆盖运行时行为（按钮是否真的不渲染）、不覆盖 `pages/projects/` 目录级死代码量级、不覆盖 `verify-exclusions.py` 已登记的解禁条件（两者刻意不重叠）。方向三另有两条不检查：`agent` 与 `fixture` 经人工查证同样无界面入口，但源码注释里出现过 `?agent=` / `?fixture=`，**保守档扫不到，闸门不跟踪它们**——宁可少管两个，也不放宽判据去迁就名单。

#### 扫描判据的第一原则：宁可漏报，不可误报

方向三的判据被自己的双向检查连抓三次，全部是**判据太窄**，每一次都指向同一类错误：

| # | 现象 | 根因 |
|---|---|---|
| 1 | `next.set("status", v)` 被误报成零写出 | 接收者不叫 `searchParams`，只认 `searchParams.set(` |
| 2 | 首页三张能力卡 `to: "/canvas?mode=new&add=video"` 被误报成零写出 | **URL 存在数据对象里再当 prop 传**，源码根本不出现 `to=` / `navigate(` |
| 3 | 优化成单遍扫描后，`tasks/index.tsx:551` 的真实导航写点又被误报 | 先匹配整段引号字面量再找参数，而那个**模板字符串内嵌反引号**，整段匹配失败 |

**误报的代价是在手册里写「界面进不去」的假话，漏报只是闸门变弱。** 所以最终口径分两档：**严格档**（任何位置出现 `?name=` 都算写出点，连注释里提到的也算）用于判定；**宽松档**（要求 `?name=` 落在引号对内）检测力更强，但会被注释与内嵌反引号打穿，**只打印、不参与判定**。

同一条纪律的另一个面：**大小写别名会让参数「一半零写一半有写」**。`baseUrl` 与 `baseurl` 是同一个参数（读取处刻意同时接受两种大小写），我第一版把 `baseurl` 登记成豁免项，被闸门当场抓出。**豁免名单一旦靠「我记得它其实是同一个参数」来维持，就等于给闸门开后门**——宁可让别名一起脱零写出。

#### 写这类闸，反向验证比正向验证重要得多

正向验证只能证明「闸门在当前上游通过」，**证明不了它在该报警时会报警**。做法是造一个「缺陷已修复」的上游 ref 让闸门跑，要求它逐条报失效。三个反复踩到的坑：

1. **必须校验反向验证自己的前提**。合成 ref 失败时，闸门对着坏 ref 报错也会输出「✓ 正确报出失效」——**一个从未真正施加修复的验证等于没做**。判结果前先确认修复特征真的出现在合成 ref 里，找不到就作废本次验证。
2. **别用 `grep -q` 配 `pipefail` 做前提校验**。`grep -q` 命中即退出，上游管道会收到 SIGPIPE 返回 141，**文件越大越容易触发**——本批一条大文件用例就这样被误判成假阴性，连废两轮。
3. **判据要覆盖上游「最可能怎么修」**。本批判据只认 `inputRef.current.click(`，不认可选链 `current?.click(`，而同仓库的惯用写法正是可选链——**闸门漏掉的恰好是上游最可能采用的那种修法**。反向验证的价值正在于此：正向跑通时这个洞不会暴露。
4. **要有一条用例证明「扫描不是复读现有名单」**（Batch 135 用例 9）。注入一个全新的、只有读没有写的参数，闸门必须报「需人工判定」——**报不出来就说明这一路扫描根本没在扫**，只是把当前名单重新念了一遍，那才是最危险的假通过：它会一直绿，且绿得毫无意义。
5. **发现一个洞要顺着查同类**。Batch 135 报出「复制画布不上传」后，顺同一批操作往下查，发现**重命名走的是同一条绕开同步的路**——而重命名比复制更容易被用户撞到。**缺陷的严重性按「多容易被撞到」排，不按「写起来多有意思」排。**
6. **从函数实现推出的「用户该怎么做」必须实测**。Batch 136 我按 `persistLocalEdits` 会 PUT 整个项目对象的实现，在正文里写了「改名后随便编辑一下画布内容，新名就会存到服务器」——**实测推翻**（顶栏改名后确实发 PUT，但后端没变，因为那个字段后端根本不收）。**推错的建议比不给建议更糟**：用户会照着做，然后发现没用，还以为是自己操作错了。
7. **判据不能假设上游两处写法一致**。Batch 137 新断言 `canvas-autosave-watches-content-only` 首轮就自己报失效——源码里外观字段在 snapshot 是简写 `canvasAppearance`（状态变量名）、在 patch 是 `appearance: canvasAppearance`（字段名），**我假设了两处写法一致**。与 Batch 133 的 `current.click()` vs `current?.click()` 同源：**闸门最容易漏掉的，是上游「换一种写法实现的同一个东西」。**
8. **「A 不触发 X」≠「结果不成立」**。这是本会话连续两次踩到的同一形状（Batch 135 把「复制那一刻不上传」写成「副本永远只在本机」；Batch 136 把「内容保存会 PUT 整个项目」写成「改名也存得上去」）。**中间可能隔着另一个触发条件**。凡是要据此写「所以你该怎么做」，必须先回答：「还有没有别的路径会触发 X？」
9. **断言的措辞精度就是手册的措辞上限**。Batch 137 把两条断言的 docstring 从「从不上传」改成「**当次不上传**」——心里想的是后者、字面写的是前者时，手册会替人把话说满。**断言写得比事实更绝对，是把手册推向错误的捷径。**
10. **「声称完整的表」本身要被验证完整**（Batch 138）。Batch 137 我自己写了一张「什么会触发上传」的表进手册，**下一批就得问「还有没有漏的」**，而不是等读者发现。同批还立了两条：
    - **要区分「漏了一步」与「后端没这个概念」**。画布库改名和文件夹归类都「不上传」，但前者能搭内容保存的便车、后者永远不能——差别在后端**有没有那个字段**。判据里必须包含对后端侧的检查，否则手册会给出无效建议。
    - **逐项看，不要整体推断**。「本地工作区不上传」这个概括被**时间线剪辑**推翻（它走 `persistCanvasTimeline` 独立同步）。**一个反例能推翻整类概括。**

> 顺带一条通用纪律：**扫描器报的「死代码」看起来总是那么合理**。本批的宽口径扫描把实际被引用 8 次的 `modelOptionLabel` 报成零引用——**用已知真值校验扫描器，再看它的结论**，否则会照单全收。Batch 135 又补了一条方向：**校验扫描器的不只是「已知真值」，还有「双向一致性」**——登记表与扫描结果必须互为约束，任何一边单独变化都要报错。

11. **只读命中点 = 没读**（Batch 139）。看到「这一行调了服务端接口」就下结论，漏掉它外面那层 `if`——我把素材文件夹判成「走服务端、与画布库正相反」，**方向完全反了**：那两处调用都在 `if (remoteMode)` 里，而 `remoteMode` 依赖的 `workspaceCapabilities().local` 是**写死的字面量 `true`**，恒为 false。**一个调用点不能代表一条链路；下结论前至少要看它的守卫条件。** 这与第 8 条是同一个毛病的镜像：第 8 条是「测了 A 那一瞬间推成永远」，这条是「读了 A 那个点推成整条链路」——**没读完的局部证据比错误的全局结论更危险，因为它看起来是查过的。**
12. **判据自己坏了，和上游修好了，长得一模一样**（Batch 139）。新断言 `asset-sync-gated-off` 连着两轮首轮报失效，两次都是我的正则写错：`\b` 加在以 `)` 结尾的 header 后（`)` 与空格都是非词字符，**词边界永远不成立**）、前缀写死 `export function ` 而上游是 `export async function `。**新断言首轮失效时先怀疑判据，并逐个子判据拆开验证**，别直接去翻上游——那会把「我的 bug」记成「上游变了」。

"**这是 Batch 135「锚点错就作废」规矩的推广，证明它对所有反向验证脚本都成立。**"
52. **写「覆盖度」之前先量：上游有多少、手册覆盖多少，差额逐条归因**（Batch 155）。"

53. **反验注入点要选在判据**显式覆盖**的形态上，否则用例会变成假通过**（Batch 155）。"

55. **修一个判据缺陷，很容易制造另一个**（Batch 155）。"

56. **查汇总处先分清「场景入口」与「全量列表」，别拿覆盖率去修场景入口**（Batch 156）。"

59. **改结构化文件优先用文本替换，不要用「解析—改—序列化」往返**（Batch 157）。"

60. **「有实现、零入口」比「可达但无实现」更极端，是第三种形态**（Batch 157）。"

62. **查一处状态时，只查一层会把「叠加出来的结果」当成「单一原因」**（Batch 157）。

63. **跑着的脚本文件不可编辑**（Batch 157 事故，当场自愈）。

64. **工具失败必须与「干净的否定结果」可区分**（Batch 157，本批头条）。
"`git grep -E` 的模式一旦不合法，它会 **fatal、rc=128、stdout 为空**；"

"否则这个工具的任何一次失败都会被读成「结论成立」。"
65. **`git grep -E` 的三条硬约束**（Batch 157 实测，与 Python `re` 和系统 `grep` 都不同）。
"① `\\s` `\\d` `\\w` `\\b` 是**字面字母**；② 方括号里的 `\\n` 排除的是**字母 n**；"
"③ `{0,N}` 的 N 不能超 255，`{0,n}?` 惰性量词**完全不支持**（整条模式被拒）。"
"**别用系统 `grep -E` 去验证 git 的正则**——我这么干过一次，"
"测出「`\\s` 可用」就下了错误结论，**三个引擎不是一回事**。"
66. **判据自报失效时，先问「是不是我刚改的东西」**（Batch 157）。

67. **注入的形态必须与真实代码一致，否则测的是另一条路**（Batch 157）。
"方向五第一版只取「调用行 + 含 REF 的行」，跳过了单独成行的模式；"

68. **作废的用例必须计数并进汇总，且作废 > 0 即判失败**（Batch 157）。

"**作废的用例既没验到、也没被算失败，是最容易骗过人的一种绿灯。**"
"另：**改判据脚本时，反验脚本的锚点必须同步检查。**"
69. **正则在别的引擎里跑 ≠ 在这个引擎里跑**（Batch 157，同 65 的延伸）。
"`\\x60` 在 git grep 里不报错、但**匹配 0 行**（当成字面 `x60`），"

"这一条比 ①–③ 更阴险：前三条会 fatal，你至少知道出事了；"
"**这一条会安静地给你一个错的答案。**"
70. **判据的触发条件要落在「结构」上，不要落在「关键词」上**（Batch 157 发现五）。
"闸门清单表用「行里没有『脚本』二字」跳表头，本批我给某行补了"
"「**闸门脚本**里 git grep 正则的引擎兼容性」这句说明，**说明文字里的「脚本」"
"让这行数据被当成表头跳过** → 报「标题写 9 道闸、清单表却有 8 行」，"
"**离真实原因十万八千里**（表明明还是 9 行）。"
"**关键词、标题文字、章节名都是给人看的，会被正文改写；结构不会。**"
"正确写法：表头 = 第一条 `|` 行，分隔行 = `|---`，其余是数据行。"
"**本轮「修一个缺陷制造另一个」第五次应验，载体还是判据。**"

74. **写闸门时「打印 ✗」与「计入失败」必须同时写**（Batch 158，方向五、方向六**同一个错误犯了两次**）。

75. **判据要覆盖手册里实际存在的全部语法，否则就是稳定误报**（Batch 158）。

76. **不误伤用例要能「反向测豁免」，而不只是「当前恰好不报」**（Batch 158 用例 20）。
"首页 `README.md` 无入链是**框架约定**（vitepress 视之为 `/`），"
"基线绿**只证明基线绿，不证明是豁免让它绿的**。"

"①检测对真实页面有效 ②豁免真正承重。**否则某天检测整体失效也不会有人知道。**"
77. **同一个错误犯两次，就该改结构而不是加检查**（Batch 159）。
"方向五、方向六**各漏过一次 `fails += 1`**：闸门把问题打印出来了、**退出码却是 0**，"
"而 build-site.sh / 反验 / CI **全都只看退出码**。"
"**加一道「记得检查」的闸挡不住第三次**——正确做法是让 `print(\"✗ …\")` "
"**在结构上无法与计数分开**（统一走 `fail()`，把两个动作焊成一个）。"
"**凡是「写的时候记得 X」导致的错误，只要发生过两次，就该把 X 变成结构而不是纪律。**"
78. **退出码只说明「有东西不对」，不说明「对的是你以为的那个」**（Batch 159）。
"注入测试后 `rc=1`，但**报的不是预期那条**——真因是方向七自己解包错了元组、"

"反验脚本同理：断言「退出码非 0」不够，**必须同时断言报出的文案**。"
79. **转换脚本宁可笨，不要聪明**（Batch 159）。
"批量把 `print(f\"  ✗ msg\")` 改成 `fail(msg)` 时，第一版为了剥掉前缀"

"修法：`fail()` **不自己加标记**（标记留在调用方字符串里），"
"转换于是只是 `print(` → `fail(`，**字符串内容一个字不动**。"
"**任何「顺手清理一下」的转换都要停下来问：这一步必要吗？**"
80. **判据要锚在真正的形态上，而不是「这一行出现过某字符串」**（Batch 159）。
"方向七第一版判「行里有 ✗ 且有 print(」，**误报 5 处**："

"以及一条 `✓` 提示语里顺带出现「✗」字样。"
"正确锚点是「**被打印的字符串以 ✗ 开头**」。**误报会让人开始忽略闸门输出。**"
81. **豁免要钉死，否则会被「为让闸门闭嘴」而改坏正确代码**（Batch 159 用例 22）。
