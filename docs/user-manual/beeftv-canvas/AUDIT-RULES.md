# BeefTV 用户手册 · 审计规约

> 本文件是**给后续批次（以及换人接手时）用的作业规约**，不是给人读的手册正文。
> 内容全部来自 Batch 93–111 的实战教训，每条都注明了它是在哪一批、因为什么被立为规约。
> 与 [AUDIT.md](AUDIT.md) 的分工：AUDIT 按时间记录「查了什么、发现了什么」，本文件只回答「下次该怎么查」。

## 0. 三条底线

| 底线 | 说明 |
|---|---|
| **付费边界** | 生成类操作按量计费。回走验证只到**付费边界前一步**；不配置 Provider Key；**不触发真实生成**。因此依赖真实生成的证据只能是源码锚定，并在页面与账本里显式标注「待运行时实证」。 |
| **证据形态纪律** | **声明处升版、证据处留痕**——各页「v1.6.14 实测」标注是走查发生版本的真实记录，**禁止改写成新版本**。新版本的内容写在新位置，不覆盖旧证据。 |
| **工作区纪律** | master 分支直改，不建/切 worktree，不用 stash，绝不丢弃他人改动。**提交一律用显式路径**（见 §6），因为并行 session 会预先暂存文件。 |

## 1. 资产风险排序：先查哪一类

Batch 106–107 实测得出的排序，决定一个 batch 的审计对象选择：

> **枚举型（可能被增删）> 数值型（可能被改常量）> 行为规则（最稳）**

| 类型 | 例子 | 为什么易错 | 本手册实例 |
|---|---|---|---|
| 枚举 | 菜单项、端点、快捷键、插件清单、参数档位 | 上游会随版本增删，手册不会自动跟 | Batch 96 端点、97 快捷键、98 菜单、101 插件、105 参数 |
| 数值 | 缩放上限、栈深度、像素比、并发数 | 常量一改，文档静默过期 | Batch 104（缩放 200%→800%）、107（180ms/50 层） |
| 行为规则 | 解析规则、校验条件、降级路径 | 通常有较完整测试覆盖，变动少 | Batch 106 字幕 11 条全对 |

**但「漏写」与「写错」同权重。** 行为规则虽然稳定，**手册却常常整节漏写**（Batch 108：批量连接的整节约束从未写过）。写错会被读者发现，漏写会让读者**以为自己操作错了**——后者更隐蔽。

## 2. 三层可达性判据（审任何 UI 能力都要问）

来源：Batch 98（背板）、99（字幕 / more 组）、102（渲染视图按钮）。

> 审一个界面能力，要连问三句。**「注册表里存在」是最容易骗人的一环。**

1. **注册表里有吗？**（工具/菜单/端点是否在注册文件中出现）
2. **当前上下文会渲染它吗？**（是否被 `applicable` 谓词、模式分支、group 渲染条件过滤掉）
3. **点下去 handler 真的做那件事吗？**（handler 是否其实打开了别的东西）

**只查到第 1 层就下结论会犯两种错**：
- 误判成「只是暂时禁用」而保留错误说法（背板：`Frame` 被 `developingNodeTypes` 禁用，且 handler 根本不创建 Frame）
- 误判成「不存在」而虚构缺陷（Batch 102：`grep 取景|CAM` 零命中，实际手册写的是「导演视角/机位视角 + 方向球」）

## 3. 否定性声明要拆两问验

来源：Batch 108（端点改接）、109（演员身份）。

> 否定性声明是最容易被上游新增功能悄悄推翻的一类，且失效后果特殊——读者会去找一个不存在的功能。

必须分别记录，**第二问最容易被跳过，而它恰恰是读者据以行动的依据**：

1. **结论**对不对？（功能确实不存在吗）
2. **理由**对不对？（为什么不存在）

**「结论对、理由错」是独立的一类缺陷**（Batch 109）：手册写「带动画的普通模型不会被当作演员」，结论对，但真实判别依据是**从哪个入口创建**——用户会照着错误理由去剥模型动画、重新导出，成本高且完全无效。**给错理由比不给更糟。**

## 4. 检索方法必须双向自证

来源：Batch 93（0 命中）、110（命中 1000+ 条）。

> 任何「搜源码验证手册说法」的动作，**必须先用已知样本验证检索方法本身有效**，且**正反两个方向都要验**。

- **假阴性**：0 命中可能只是检索写错了（Batch 93 若不复核会漏修 5 处真实缺陷）
- **假阳性**：命中太多同样致命（Batch 110 第一版扫出 1000+ 条，正则贪婪把版本号 `v1.6.14` 的 `0`、列表序号 `1`、单词尾字母全当快捷键）

**假阳性的代价不比假阴性低**——一个报出 1000 条的闸门，使用者会直接关掉它；**闸门一旦失去可信度就等于没有闸门**，还会连带损失真问题的可信度。

具体做法：构造一个**必然存在**的串（应命中）与一个**必然不存在**的串（不应命中），两个都验证通过，才开始正式审计。

### 4.1 先查手册，再下源码

来源：Batch 119 与 Batch 123 **连续两次**。两次都是从源码入手深挖，查到一半才发现**手册早已写过**：

- Batch 119：查到 Seedance 比例是 7 项，险些把手册的「6 档」改成错的——原文其实已写明「六档之外还有 自适应」。
- Batch 123：计划审视频节点工具条的可达性，挖到一半发现 `generate-video.md` / `local-runtime.md` / `subtitle-highlights.md` **三处都已覆盖**，连「`subtitles` 工具已注册但视频节点从不渲染 primary 组」这种细节都记了。

**代价不只是白干**：Batch 119 那次差点**把已经正确的文档改错**——错误的修正比不修正更糟（§3 否定声明两问同源）。

**做法**：选定一个面之前，**先花五分钟 grep 一遍手册**已经写到哪一步，再决定要不要下源码。

- 手册只提了一句话（提到分组名、没展开内容）→ 下源码补内容，这是正路（Batch 122 图片工具条即是）。
- 手册已经成体系地写了 → **换目标**，别把同一份内容重写一遍。

判断「已成体系」的标准：该面在**两个以上**页面被提到，且有参数表或步骤，而不是只出现在别的页面的顺带一句里。

## 5. 闸门五步法：人工结论 → 机械闸

来源：Batch 94（截图四方对账）、96（端点双向校验）、110（快捷键前缀）、111（解禁条件）。

> 已经人工查清的事实，如果**能机械表达**，就应该固化成构建闸门，而不是留在批次记录里等人重查。

1. 先人工查清事实
2. 判定能否机械表达
3. 能则写成脚本接入 `build-site.sh` 步骤 6
4. **必须做反向验证**——人为制造该类缺陷，确认脚本以非零退出码拦下
5. 在 AUDIT 记录「**本闸不检查什么**」

**第 5 步最容易被忽略，但它是闸门可信度的一部分**：明确说出边界，使用者才知道何时不能依赖它。例：`verify-exclusions.py` 只判「条件是否仍成立」，不判「条件写得对不对」；`verify-endpoints.py` 找不到上游源码时静默跳过。

**闸门判据要能正反自证**（否则只会在某一类错误上疯狂误报）：
- 端点闸：声明现存的须注册 **且** 声明下线的须未注册
- 快捷键闸：漏前缀须报 **且** 有 Alt/Shift 变体的须不报

### 闸 → 反验的对应关系（Batch 168 建）

> **为什么要有这张表**：第 4 步要求「必须做反向验证」，可**要求写在那里不等于它在事实上被满足**。
> Batch 168 逐条列了一遍，发现**十道闸里三道一道反验都没有**（闸 1 / 2 / 6），
> 而且**差点全数漏判**——闸 2 的反验文件叫 `selftest-screenshots-literals.py`，
> **那是闸 10 的**，名字相近到扫一眼目录就会以为「已经有了」。
> **所以「有没有反验」必须按这张对应关系判断，不能靠文件名相似度。**

|---|---|---|---|

**两条从这张表里读出来的规矩**：

1. **新增闸门时必须同时新增它那一行的反验**，否则这张表就多一个空格——而**空格看起来像有人管**（Batch 161 的原话）。**这张表本身现已由方向十一守着**（Batch 169）：它当时是**建完就没人管**的，而**建表的人和用表的人都不会因此得到提醒**。
2. **反验的锚点必须锚事实**（纪律 107）。`selftest-meta.sh` 的用例 26 曾把整行表格文本誊抄成锚点，因两次正常编辑而**静默失配两个批次**——**作废的用例既不算通过也不算失败，是最容易骗过人的一种绿灯。**

### 风险类别覆盖度（Batch 161 建）

> **这张表存在的理由**：前面十六批反复出现同一个模式——**某类问题连着好几个批次
> 都没人发现，事后一查是「从来就没有任何东西在管它」**（侧栏漏 20 批、
> 内链无人守、`fails += 1` 漏两次、11 处 skip 静默通过）。
> **九道闸各自都写了自己的「不检查什么」，但从来没有一张表把它们合起来看。**
>
> **表里的每一格都必须落到一个具体依据**（某个闸的脚本头声明 / 某条纪律 /
> 某次实测），**不许写「应该有人管」这种没有依据的话**——
> 那正是侧栏和内链出事时的状态。

**B 类 · 明确不覆盖，且判定为「有意设计」（不是缺口）**

| 风险类别 | 为何不覆盖 |
|---|---|
| 侧栏文字与页面 h1 不一致 | 侧栏用短标题是**有意分工**（Batch 152 量过 14 条差异模式一致） |
| 页面 h1 是否漏掉功能词 | 账本 title 带括号补充、页面 h1 简洁；**Batch 152 全量对账 14 条差异模式完全一致**（其中 12 条无括号补充者完全相同，反过来印证分工是有意的） |
| 索引里「标题（提示）」是否恰当 | 只认形态、不判语义（Batch 153 显式声明） |
| dist 产物内容 | 随构建变化，不该作为真值来源（**闸 9 脚本头显式声明**：不检查 dist 产物） |
| `verify-exclusions.py` 已登记的解禁条件 | 闸 7 刻意不重复管，**两闸不重叠是设计** |

**C 类 · 无人覆盖（真实空白，逐条写明原因）**

## 6. 工作区纪律：提交一律用显式路径

来源：Batch 99 实战。

并行 session 会**预先 `git add` 自己的文件**，此时 `git diff --cached` 里混着别人的东西。此时 `git commit`（不带路径）会**代为提交他人未完成的工作**。

```bash
# 新文件要先 add 才能用显式路径提交
git add docs/user-manual/beeftv-canvas/scripts/<新文件>.py
git commit -F /tmp/msg.txt -- <我这次改动的全部路径，逐个列出>
```

- 只暂存 `docs/user-manual/beeftv-canvas/` 路径，**且提交时仍要显式列全路径**（`git add <dir>` 只限制 add，不限制后续 commit）。
- 提交前用 `git diff --cached --name-only | grep -v "^docs/user-manual/beeftv-canvas/"` 确认无越界。
- 他人的暂存状态**保持原样**，不取消、不代提。
- 推送后若 `git log -1` 不是自己的提交，说明期间他人已提交，属正常协作，不需处理。

## 9. 同一设置多种叫法：本产品的系统性特征

来源：Batch 116/117/119/120 **连续四次**撞上，立为规约。

产品里多个文件各持一份同义枚举表——同一枚 `value` 在不同界面被叫成不同名字。已确认的四处：

| 批次 | 设置 | 一处叫 | 另一处叫 |
|---|---|---|---|
| 116 | 视频生成模式 | 首帧 / 首尾帧 | 图生视频 |
| 116 | 参考类模式 | 参考生成 | 全模态参考 |
| 116 | 局部修改类 | 局部修改 | 视频局部修改 |
| 116 | 运镜类 | 运镜调整 | 镜头/运镜调整 |
| 116 | 音频生视频类 | 音频生视频 | 参考音频生成视频 |
| 116 | 版本对比 | 版本对比 | 结果版本对比 |
| 117 | 执行策略 `strict-assets` | 严格校验 | 严格阻止 |
| 119 | 视频设置面板 | 三套面板，分组名各不相同 | — |
| 120 | 图片质量组标题 | 质量 | 分辨率 |

比例一族更夸张：同一个 `16:9` 至少三种写法（`16:9` / `16:9 横屏` / `16:9 · 横屏` / `横屏`）。

### 怎么审

1. **审任何枚举时，顺手问一句「这个 value 在别处叫什么」**——尤其当它来自一份跨文件复制的同义表时。
2. **手册正文用「用户能触达的那个名字」**（见 §0 证据纪律最后一条），**不要强行统一成某一套**——那是产品文案决策，不是文档能替它做的。
3. 若另一处叫法会**导致用户困惑**（同一页里两个名字、或用户要找的东西找不到），就在手册里单列一张对照表说明来历，**并点明「是同一个设置」**。

### 已建成机械闸

`scripts/verify-label-drift.py`（第五道闸）维护一份**已知分歧登记表**，两个方向都查：

- 出现**未登记**的新分歧 → 退出码 1（提醒补登记，否则后人会以为已审过）
- 登记的分歧**已消失**（上游收敛）→ 退出码 1（提醒清理登记）

**这张表里一半是「巧合」不是「漂移」**：`auto` 既是画质「自动」、又是脚本节点的「单镜时长自动」、又是「自动拆分」；`5` 既是「5 章」又是「每镜 5 秒」。闸门**只查跨文件分歧**（同文件内的多义不算），其余靠登记表逐条定性。**定性是人的判断，脚本只负责把没定性的摆到台面上。**

闸门不检查的还有两条，已写进脚本 docstring：**哪个名字对不对**（产品文案决策），以及**界面上是否真的两处都出现**（需运行时取证，超出静态闸能力）。

### 第六道闸：否定式断言是最容易悄悄过期的一类

前五道闸守的都是**肯定式断言**——「缩放上限 200%」「端点 `/api/x` 存在」。这类断言一旦过期，手册只是某个数字或某张表对不上，读者自己能发现。

**否定式断言**（「画布库没有导入入口」「审美批改建不出这个节点」「章节路由访问不到」）的失效方式要命得多：上游哪天把那个 `ref.current.click()` 补上，**手册会继续言之凿凿地告诉用户「你找不到」**——而用户已经在界面上看到了那个按钮。**这等于把读者的正确观察说成幻觉。**

`scripts/verify-unreachable.py` 为此维护一份**不可达声明登记表**，三个方向都查：

- 已登记的判据**不再成立** → 退出码 1（上游可能已修复，手册该条断言要回走更新）
- 全量扫描出现**未登记**的新缺陷 → 退出码 1（手册漏写了）
- 登记的扫描键**没被扫到** → 退出码 1（登记已失效或键写错）

两路全量扫描，命中集合都必须与登记**双向一致**：

| 方向 | 扫描对象 | 现状 |
|---|---|---|
| 方向二 | `useState` 解构出的 setter **声明后零调用** | 3 处命中，与登记一致 |
| 方向三（Batch 135 新增） | 全库每个 `searchParams.get("X")` 的 X，**有没有「写出点」** | 7 个零写出，已全部归类（豁免 5 + 缺陷登记 2） |

登记表现有 **12 条断言**，反向验证 **11 例**。断言按「缺陷类型」而非「页面」组织：同一族的缺陷（画布库入口、只读无入口、副本/改名不上传、两个名字）各自独立成条，**一条断言只回答一个可被源码推翻的问题**。

**一条断言该拆多细**：Batch 136 的「两个名字」拆成了映射 / 读 / 写三个子判据，因为只有 (a)(b) 时可能只是两处显示不同源，**必须 (c) 写入字段也分开，才敢说「改一处另一处不跟着变」**。同理「改名不上传」要求同时验证「无同步」「有本地 flush」「对照组带同步」——第三条是防「整体改成不上传的设计」的。

**方向三必须带豁免名单，且只保证「每个零写出参数都被显式归类」，不判断「零写出是否就是缺陷」。** 理由是实测的：`baseUrl` 的生产者是外部启动器、`projectId`/`uuid` 的生产者是**用户粘贴的 LibTV 链接**、`fixture`/`demo` 是演示设施——**「界面上没有按钮」不足以断言「功能不存在」**。逐个查过来源之后，真正属于「功能完整但无入口」的只有只读模式一条，另加 `?stay=1`（源码注释自认是留给浏览器验收脚本的开关）。

**为什么扫描只认「setter 零调用」这一条判据**：本产品实测 setter 侧 3/3 全真，而 ref 侧 9/9 全假、宽口径「函数零引用」更是 1192 条噪声。**判据要选「零调用」而不是「少调用」**——ref 出现两次（声明 + 一处正常使用）本就是常态。

**闸门明确不检查的三件事**（写在 docstring 里）：不覆盖运行时行为（按钮是否真的不渲染）、不覆盖 `pages/projects/` 目录级死代码量级、不覆盖 `verify-exclusions.py` 已登记的解禁条件（两者刻意不重叠）。方向三另有两条不检查：`agent` 与 `fixture` 经人工查证同样无界面入口，但源码注释里出现过 `?agent=` / `?fixture=`，**保守档扫不到，闸门不跟踪它们**——宁可少管两个，也不放宽判据去迁就名单。

#### 扫描判据的第一原则：宁可漏报，不可误报

方向三的判据被自己的双向检查连抓三次，全部是**判据太窄**，每一次都指向同一类错误：

| # | 现象 | 根因 |
|---|---|---|
| 1 | `next.set("status", v)` 被误报成零写出 | 接收者不叫 `searchParams`，只认 `searchParams.set(` |
| 2 | 首页三张能力卡 `to: "/canvas?mode=new&add=video"` 被误报成零写出 | **URL 存在数据对象里再当 prop 传**，源码根本不出现 `to=` / `navigate(` |
| 3 | 优化成单遍扫描后，`tasks/index.tsx:551` 的真实导航写点又被误报 | 先匹配整段引号字面量再找参数，而那个**模板字符串内嵌反引号**，整段匹配失败 |

**误报的代价是在手册里写「界面进不去」的假话，漏报只是闸门变弱。** 所以最终口径分两档：**严格档**（任何位置出现 `?name=` 都算写出点，连注释里提到的也算）用于判定；**宽松档**（要求 `?name=` 落在引号对内）检测力更强，但会被注释与内嵌反引号打穿，**只打印、不参与判定**。

同一条纪律的另一个面：**大小写别名会让参数「一半零写一半有写」**。`baseUrl` 与 `baseurl` 是同一个参数（读取处刻意同时接受两种大小写），我第一版把 `baseurl` 登记成豁免项，被闸门当场抓出。**豁免名单一旦靠「我记得它其实是同一个参数」来维持，就等于给闸门开后门**——宁可让别名一起脱零写出。

#### 写这类闸，反向验证比正向验证重要得多

正向验证只能证明「闸门在当前上游通过」，**证明不了它在该报警时会报警**。做法是造一个「缺陷已修复」的上游 ref 让闸门跑，要求它逐条报失效。三个反复踩到的坑：

1. **必须校验反向验证自己的前提**。合成 ref 失败时，闸门对着坏 ref 报错也会输出「✓ 正确报出失效」——**一个从未真正施加修复的验证等于没做**。判结果前先确认修复特征真的出现在合成 ref 里，找不到就作废本次验证。
2. **别用 `grep -q` 配 `pipefail` 做前提校验**。`grep -q` 命中即退出，上游管道会收到 SIGPIPE 返回 141，**文件越大越容易触发**——本批一条大文件用例就这样被误判成假阴性，连废两轮。
3. **判据要覆盖上游「最可能怎么修」**。本批判据只认 `inputRef.current.click(`，不认可选链 `current?.click(`，而同仓库的惯用写法正是可选链——**闸门漏掉的恰好是上游最可能采用的那种修法**。反向验证的价值正在于此：正向跑通时这个洞不会暴露。
4. **要有一条用例证明「扫描不是复读现有名单」**（Batch 135 用例 9）。注入一个全新的、只有读没有写的参数，闸门必须报「需人工判定」——**报不出来就说明这一路扫描根本没在扫**，只是把当前名单重新念了一遍，那才是最危险的假通过：它会一直绿，且绿得毫无意义。
5. **发现一个洞要顺着查同类**。Batch 135 报出「复制画布不上传」后，顺同一批操作往下查，发现**重命名走的是同一条绕开同步的路**——而重命名比复制更容易被用户撞到。**缺陷的严重性按「多容易被撞到」排，不按「写起来多有意思」排。**
6. **从函数实现推出的「用户该怎么做」必须实测**。Batch 136 我按 `persistLocalEdits` 会 PUT 整个项目对象的实现，在正文里写了「改名后随便编辑一下画布内容，新名就会存到服务器」——**实测推翻**（顶栏改名后确实发 PUT，但后端没变，因为那个字段后端根本不收）。**推错的建议比不给建议更糟**：用户会照着做，然后发现没用，还以为是自己操作错了。
7. **判据不能假设上游两处写法一致**。Batch 137 新断言 `canvas-autosave-watches-content-only` 首轮就自己报失效——源码里外观字段在 snapshot 是简写 `canvasAppearance`（状态变量名）、在 patch 是 `appearance: canvasAppearance`（字段名），**我假设了两处写法一致**。与 Batch 133 的 `current.click()` vs `current?.click()` 同源：**闸门最容易漏掉的，是上游「换一种写法实现的同一个东西」。**
8. **「A 不触发 X」≠「结果不成立」**。这是本会话连续两次踩到的同一形状（Batch 135 把「复制那一刻不上传」写成「副本永远只在本机」；Batch 136 把「内容保存会 PUT 整个项目」写成「改名也存得上去」）。**中间可能隔着另一个触发条件**。凡是要据此写「所以你该怎么做」，必须先回答：「还有没有别的路径会触发 X？」
9. **断言的措辞精度就是手册的措辞上限**。Batch 137 把两条断言的 docstring 从「从不上传」改成「**当次不上传**」——心里想的是后者、字面写的是前者时，手册会替人把话说满。**断言写得比事实更绝对，是把手册推向错误的捷径。**
10. **「声称完整的表」本身要被验证完整**（Batch 138）。Batch 137 我自己写了一张「什么会触发上传」的表进手册，**下一批就得问「还有没有漏的」**，而不是等读者发现。同批还立了两条：
    - **要区分「漏了一步」与「后端没这个概念」**。画布库改名和文件夹归类都「不上传」，但前者能搭内容保存的便车、后者永远不能——差别在后端**有没有那个字段**。判据里必须包含对后端侧的检查，否则手册会给出无效建议。
    - **逐项看，不要整体推断**。「本地工作区不上传」这个概括被**时间线剪辑**推翻（它走 `persistCanvasTimeline` 独立同步）。**一个反例能推翻整类概括。**

> 顺带一条通用纪律：**扫描器报的「死代码」看起来总是那么合理**。本批的宽口径扫描把实际被引用 8 次的 `modelOptionLabel` 报成零引用——**用已知真值校验扫描器，再看它的结论**，否则会照单全收。Batch 135 又补了一条方向：**校验扫描器的不只是「已知真值」，还有「双向一致性」**——登记表与扫描结果必须互为约束，任何一边单独变化都要报错。

11. **只读命中点 = 没读**（Batch 139）。看到「这一行调了服务端接口」就下结论，漏掉它外面那层 `if`——我把素材文件夹判成「走服务端、与画布库正相反」，**方向完全反了**：那两处调用都在 `if (remoteMode)` 里，而 `remoteMode` 依赖的 `workspaceCapabilities().local` 是**写死的字面量 `true`**，恒为 false。**一个调用点不能代表一条链路；下结论前至少要看它的守卫条件。** 这与第 8 条是同一个毛病的镜像：第 8 条是「测了 A 那一瞬间推成永远」，这条是「读了 A 那个点推成整条链路」——**没读完的局部证据比错误的全局结论更危险，因为它看起来是查过的。**
12. **判据自己坏了，和上游修好了，长得一模一样**（Batch 139）。新断言 `asset-sync-gated-off` 连着两轮首轮报失效，两次都是我的正则写错：`\b` 加在以 `)` 结尾的 header 后（`)` 与空格都是非词字符，**词边界永远不成立**）、前缀写死 `export function ` 而上游是 `export async function `。**新断言首轮失效时先怀疑判据，并逐个子判据拆开验证**，别直接去翻上游——那会把「我的 bug」记成「上游变了」。

"`git grep -E` 的模式一旦不合法，它会 **fatal、rc=128、stdout 为空**；"

65. **`git grep -E` 的三条硬约束**（Batch 157 实测，与 Python `re` 和系统 `grep` 都不同）。
"① `\\s` `\\d` `\\w` `\\b` 是**字面字母**；② 方括号里的 `\\n` 排除的是**字母 n**；"
"③ `{0,N}` 的 N 不能超 255，`{0,n}?` 惰性量词**完全不支持**（整条模式被拒）。"
"**别用系统 `grep -E` 去验证 git 的正则**——我这么干过一次，"
"测出「`\\s` 可用」就下了错误结论，**三个引擎不是一回事**。"
66. **判据自报失效时，先问「是不是我刚改的东西」**（Batch 157）。

68. **作废的用例必须计数并进汇总，且作废 > 0 即判失败**（Batch 157）。

"另：**改判据脚本时，反验脚本的锚点必须同步检查。**"
69. **正则在别的引擎里跑 ≠ 在这个引擎里跑**（Batch 157，同 65 的延伸）。
"`\\x60` 在 git grep 里不报错、但**匹配 0 行**（当成字面 `x60`），"

"**这一条会安静地给你一个错的答案。**"
70. **判据的触发条件要落在「结构」上，不要落在「关键词」上**（Batch 157 发现五）。
"闸门清单表用「行里没有『脚本』二字」跳表头，本批我给某行补了"

"让这行数据被当成表头跳过** → 报「标题写 9 道闸、清单表却有 8 行」，"
"**离真实原因十万八千里**（表明明还是 9 行）。"
"**关键词、标题文字、章节名都是给人看的，会被正文改写；结构不会。**"
"正确写法：表头 = 第一条 `|` 行，分隔行 = `|---`，其余是数据行。"

74. **写闸门时「打印 ✗」与「计入失败」必须同时写**（Batch 158，方向五、方向六**同一个错误犯了两次**）。

75. **判据要覆盖手册里实际存在的全部语法，否则就是稳定误报**（Batch 158）。

76. **不误伤用例要能「反向测豁免」，而不只是「当前恰好不报」**（Batch 158 用例 20）。
"首页 `README.md` 无入链是**框架约定**（vitepress 视之为 `/`），"

"①检测对真实页面有效 ②豁免真正承重。**否则某天检测整体失效也不会有人知道。**"
77. **同一个错误犯两次，就该改结构而不是加检查**（Batch 159）。
"方向五、方向六**各漏过一次 `fails += 1`**：闸门把问题打印出来了、**退出码却是 0**，"
"而 build-site.sh / 反验 / CI **全都只看退出码**。"

"**在结构上无法与计数分开**（统一走 `fail()`，把两个动作焊成一个）。"
"**凡是「写的时候记得 X」导致的错误，只要发生过两次，就该把 X 变成结构而不是纪律。**"
78. **退出码只说明「有东西不对」，不说明「对的是你以为的那个」**（Batch 159）。
"注入测试后 `rc=1`，但**报的不是预期那条**——真因是方向七自己解包错了元组、"

"反验脚本同理：断言「退出码非 0」不够，**必须同时断言报出的文案**。"
79. **转换脚本宁可笨，不要聪明**（Batch 159）。
"批量把 `print(f\"  ✗ msg\")` 改成 `fail(msg)` 时，第一版为了剥掉前缀"

"修法：`fail()` **不自己加标记**（标记留在调用方字符串里），"
"转换于是只是 `print(` → `fail(`，**字符串内容一个字不动**。"
"**任何「顺手清理一下」的转换都要停下来问：这一步必要吗？**"
80. **判据要锚在真正的形态上，而不是「这一行出现过某字符串」**（Batch 159）。

"正确锚点是「**被打印的字符串以 ✗ 开头**」。**误报会让人开始忽略闸门输出。**"
81. **豁免要钉死，否则会被「为让闸门闭嘴」而改坏正确代码**（Batch 159 用例 22）。
"早退 `return 1` 是**正确写法**（退出码由 return 决定，不经计数器）。"
"方向七若不豁免它，就得把早退改成累加器——"
"**那是为让闸门闭嘴而改坏代码。** 每个豁免都要配一条不误伤用例。"
82. **「查不了」与「查过了没问题」必须返回不同的码**（Batch 160，Batch 157 的反面）。
"普查发现 **6 个闸共 11 处**在数据不可用时打印 `[skip]` 然后 `return 0`，"
"而 build-site.sh **只看退出码**——**上游目录一改名，9 道闸里 5 道空转而绿**，"
"账本里「已逐条核实」的声明被无声跳过。"
"约定 **0 一致 / 1 不一致 / 2 未能核对**；`ALLOW_UNVERIFIED=1` 才放行，"
"**「在无上游的环境构建」必须主动决定，不能是默认行为**。"
"**与 Batch 157 的「工具失败被当成零命中」是同一个病的两面。**"
83. **判据要锚定事实，不要锚定某一种写法**（Batch 160，第三次同型）。
"把闸从 `python3 scripts/verify-x.py` 改成 `run_gate verify-x.py` 后，"
"方向三立刻报「实际调用的闸从 8 暴跌到 2」——**判据认的是写法，不是事实**。"
"前两次同型：`.` 吞 `=`、方向五窗口跳行。**载体还是判据。**"
84. **写了却从未落地的修复，比没有修复更坏**（Batch 160）。
"`selftest-unreachable.sh:53` 早就写着「不能用 grep -q，会 SIGPIPE」，"
"**而代码至今仍是 `grep -qF`**——注释冒充已修，本批才真正改掉。"
"**危害与假通过同级**：它让**正确的闸门输出被当成错误**，"
"不细查就会去「修」一个根本没坏的闸门。"
"**每条纪律落地时要在代码里能 grep 到，否则它只是愿望。**"
85. **`set -o pipefail` 下不能用 `grep -q`**（Batch 160 实测）。
"`grep -q` 命中即退出 → 上游 `printf`/`echo` 收到 SIGPIPE 返回 141 → 整条管道判失败 → "
"**明明打印出了要匹配的那行，用例却判「报错了但不是它」**。"
"用 `grep -F \"$x\" >/dev/null`：它会读完整个输入，不产生 SIGPIPE。"
"**输出变大就会改变触发时机**——所以「一直好好的」不代表这条没在坑里。"
86. **「误指派」比「明知不覆盖」更危险**（Batch 161）。
"`verify-meta.py` 声明「不检查截图内容——那是 `verify-screenshots.py` 的职责」，"
"而**截图闸只做四方对账（存在性与数量），零内容判据**。"
"**明知不覆盖会写进声明，误指派则让人以为已经有人管。**"
"**建覆盖度表时要专门找这一类：某个闸声明里把职责「让给」另一个闸的，逐个核实对方真的在做。**"
87. **闸门清单要配一张「哪些风险有人管」的表，且每格必须有依据**（Batch 161）。
"十六批下来同一模式出现四次（侧栏 20 批、内链、`fails += 1` 两次、11 处 skip），"
"共同形态是**「以为有人管」**——而九个闸各自写了「不检查什么」，却从没合起来看过。"
"表分三类：有闸 / 有意不覆盖 / 无人覆盖。**每格必须引用具体依据**"
"（某个闸的脚本头声明 / 某条纪律 / 某次实测），**不许写「应该有人管」**——"
"那正是出事时的状态：**一个没人追问的空位**。"
88. **A 类认领数必须等于闸门清单行数**（Batch 161 方向九，用例 26）。
"这条保证**表不会悄悄落后于现实**。项目已栽过两次同型："
"Batch 147「加了闸忘了改清单表」、153/154「补了索引忘查侧栏」。"
"**注入形态选「A 类多一行」而不是「少一行」**——少一行现实中不可能发生，"
"多一行正是「加了闸忘了登记」的真实形态。"
89. **统计类命令的输出解析最容易出错且最不容易被察觉**（Batch 161，第三次同型）。
"查四条界面文案时全部「0 命中」，差点写成「手册文案是错的」；"
"实际是 `git grep -c | awk -F: '{t+=$2}'` **解析错了列**"
"（输出是 `ref:path:count`，我取了路径当计数）。另两次：孤儿页误报、`alt` 属性被截断。"
"**凡是「命令返回 0 条」这类结论，先用另一种方式复核一次再写进结论**——"
"尤其当那个结论会指向「手册错了」的时候。"
90. **「不可机械覆盖」这个定性必须量过才能写**（Batch 162）。
"覆盖度表里写「不可机械覆盖」时那只是**推理**。本批去试，发现**可建**——"
"但关键不在「能不能建」，在**分界线被量出来了**："
"不收窄 164 片段 / 60 误报，保守形态 77 / 误报 4 且四条全部可归因。"
"**判据能不能建，取决于收窄后误报降到多少，而不是取决于原方案行不行。**"
91. **「为取证专门记录的字段」和「任意引号里的文本」是两回事**（Batch 162）。
"Batch 150 判「界面文案逐字对账」不可建，是因为抽的是正文里**任意**「」短串；"
"而 `manifest` 的 `visible_text` **语义就是「这张图上看到的字」**——"
"**数据的用途本身确定，判据才能落在形态上。**"
"**同一个「比对界面文案」的念头，对象选错了就完全不可建。**"
92. **闸门要检查「免检登记表有没有过期」**（Batch 162）。
"片段被删掉、豁免却还留着 → 报错。**否则免检表只增不减，几年后就是一张没人敢碰的清单。**"
93. **反验的锚点不只会被「改判据脚本」弄失配，改被测文件也会**（Batch 162 补上 Batch 157 的漏）。
"闸门数 9→10、标题改掉之后，用例 6 的 `replace('### 现有九道闸', …)` **静默空转**。"
"**危险在于它不报错**：失败信息说「闸门没报错」，会把人引向完全错误的方向，"
"真实原因却是「测试自己没注入成功」。"
"通用修法：`eval` 前后做快照，**内容没变即判作废**——不必把每条内联注入都改成带 assert 的脚本。"
94. **注入点必须在判据真的读的那一处，且归属要先查清不能猜**（Batch 162，第四次同型）。
"前三次：Batch 155 用例 27、Batch 157 方向五负向测试、本批用例 1（只替换了值字符串，"
"而它在文件更早位置就出现过）。本批还多一个：**用 `[\s\S]*?` 跨文件定位记录，"
"把四条豁免全归到了第一条记录**，于是用例 4 删错了记录。"
"**闸门通过而用例失败时，先怀疑注入，再怀疑闸门。**"
95. **否定式断言要追问：判据看的是不是产生这个事实的那一处**（Batch 163，**本批最重要的一条**）。
"旧判据问的是「写死清单里有没有它」，断言说的是「**画布上**建不出这个节点」——"
"**问的和答的不是同一件事**：写死清单那份文件确实不含它，可入口由插件注册表动态生成，根本不经过那份文件。"
"**判据为真、断言为假**，两者各自都没错，合起来推出一个假结论。"
"新增否定式断言时，除了问「怎么证明它为假」，还要问「**我读的那一处，真的会产生这个事实吗**」。"
96. **有判据的错误比没判据的错误更难发现**（Batch 163）。
"闸 7 恰恰是为「否定式断言会悄悄过期」而建的，它自己那条判据却结构上看不见动态入口——"
"于是错误拿到了机械背书，越活越久，还显得「这里有人管」。"
"**一道看起来严谨的错判据，会把一次人工疏漏升级成制度性错误。**"
"配套做法：否定式断言的反验必须**成对**（能抓 + 不误伤），"
"且「不误伤」那条要选一个**旧判据会报错**的形态——那才是对旧判据的反证。"
97. **「该建一道闸」第三次靠测量而不是推理决定**（Batch 163）。
"本批想加一条「判据至少读 2 个文件」，理由是：声称「某处没有」的判据若只读一个文件，就无法支撑全局断言。"
"实测：**33 个判据里 15 个只读 ≤1 个文件**（其中大部分是正当的——它们断言的范围本来就是单个组件，"
"例如「画布库没有排序控件」确实只看那一个文件）。**照规则一刀切会误伤过半。**"
"真正的分界是**断言的范围与证据的范围是否一致**，而这无法从代码形态可靠推出。"
"**结论：不建，如实记进 C 类，并把测量数字一起记下**——这样下一个人不必重新量一遍。"
98. **闸门的覆盖面本身要被核对，「没人管」不能靠人记得**（Batch 164）。
"闸 5 的名字是「excluded 页解禁条件核对闸」——**读者理所当然会以为每一条 excluded 都被盯着**。"
"实测 6 条 excluded 里 `art-critique` **零次被提及**：它是 Batch 132 才加进账本的，"
"加的人没同步这里，**而没有任何机制会提醒**。于是它的排除理由整个是错的，躺了三十个批次才被发现。"
"**这不是「漏看」，是「以为有人管」——与 Batch 161 覆盖度表抓到的那次同型，只是换到了任务层。**"
"修法不是「记得同步」：账本每条 excluded 必须在 `COVERED`（有判据）或 `EXEMPT`（有免检理由）里，"
"**两者都没有即失败**；反过来登记了却已非 excluded 的也失败——**免检表必须会自己过期**。"
99. **结论里出现的数字必须能被推导，不能写死**（Batch 164，与规则 93 同一根问题的另一面）。
"闸 5 结尾长期写着「**4 条**可机械判定的条件全部仍成立」，而账本早已涨到 6 条 excluded。"
"**那句「全部核对过」在数字对不上的情况下依然是绿的、依然是让人放心的**——这比没有这句更坏。"
"修法：把条件清单写成 `MECHANICAL_CONDITIONS` 元组，结论里的数量由 `len()` 推导，"
"**并加一条自检数 `# —— 条件 N：` 判据块数与清单条目数是否一致**——"
"**写死的数字是规则 93「纪律写在文档里却不在代码里」的孪生兄弟：文档里那句「4 条」同样是死的。**"
100. **判据不要用「誊抄副本」，直接读被核对的那份文件本身**（Batch 165，规则 95 的第二例）。
"闸 3 名为「端点双向校验」，实际把手册声明**誊抄成脚本里的两张硬编码表**（16 条），"
"而**从不读 `20-reference.md`**。实测手册三张表共声明 **28 条**，**12 条从未被看守**——"
"其中「已下线」表里的跨产品导入那对，手册用删除线断言已下线，**闸门却完全不知道它们存在**；"
"上游哪天把它们注册回来，闸门一声不吭。"
"**誊抄副本一定会漂移，而没有任何机制会告诉你它漂了**——这不是疏忽，是结构性的。"
"修法不是「记得同步」（规则 98 刚否掉这条路），而是**让被核对的文件成为唯一真值**，闸门运行时解析它。"
101. **判据自己有「会不会退化」的风险，退化必须表现为失败而不是通过**（Batch 165）。
"把判据从硬编码表换成解析正文之后，引入了一类**以前不可能发生的失败**：表格改版、标题改名、分隔符换了，"
"解析器就会**静悄悄地什么也没抽到**，而「0 条不一致」会被当成「全部通过」。"
"这正是 Batch 157「工具失败被当成零命中」在**判据自己身上**的重演。"
"三处显式 `return 2`（沿用规则 98 与 Batch 160 的三段退出码）：找不到源码 / 找不到手册 / **任一张表解析出 0 条** / 锚点缺失。"
"**「什么都没查到」和「查过了没问题」必须返回不同的码**——这条每换一个判据就要重新问一遍。"
102. **反验的注入要断言「破坏真的造成了」而不只是「锚点在」**（Batch 165 栽了一次）。
"用例 3 想制造锚点失配，却把 `### 已下线端点` 改成 `### 已下线端点（反验注入…）`——"
"**改完的文本仍然包含原锚点**，子串判断照样命中，闸门正常通过，用例判「本应报错却通过了」。"
"正确做法是断言**改完之后锚点真的不见了**。"
"**`assert 原文里有 X` 只证明「改之前在」，不证明「改之后不在」——而后者才是注入的目的。**"
103. **判据的输入范围必须由它自己声明，不能由 cwd 决定**（Batch 166）。
"闸 4 用 `glob.glob('**/*.md')`——相对当前工作目录。实测两种结局："
"**在干净空目录里运行，扫到 0 个文件、0 个问题，输出「快捷键前缀核对通过……手册写法均已带前缀」，rc=0**；"
"在 `/tmp` 里运行，glob 命中已消失的临时目录，`open()` 抛 `FileNotFoundError` **崩栈**，"
"rc=1——而 1 在三段约定里是「不一致」，**信号也是错的**。"
"修法：`__file__` 自定位 + 读不到就跳过（不崩）+ **扫到的文件数低于下限即 `return 2`**。"
"**判据答的是「我查的那些东西有没有问题」，前提是「我确实查到了东西」——后者也要有人守。**"
104. **抑制规则和匹配规则一样会过期，收窄时先量误报**（Batch 166）。
"闸 4 原判据是「同一行里若已出现 Ctrl/Cmd，本行所有表达式一律合规」——"
"**这条抑制过宽到能掩盖真实缺陷**：`Ctrl/Cmd+Z / Shift+Z / Y` 里，"
"前半段的前缀把后半段**真正漏了前缀**的 `Shift+Z` 一起免掉，"
"而上游 `use-canvas-keyboard.ts` 明写 `isModifierShortcut && key === \"z\"`，**裸按 Shift+Z 什么都不会发生**。"
"收窄为「相邻豁免」（只认紧挨着上一表达式的那段分隔文本里带 Ctrl/Cmd）后，"
"**全库 41 个文件命中 1 处、误报 0**，那 1 处正是手工核对确认的真缺陷。"
"**抑制规则与匹配规则互为镜像：过宽的抑制和过窄的匹配一样，都让闸门显得全绿而缺陷还在。**"
105. **一次性人工普查发现的东西，要尽快变成机器常驻的守卫**（Batch 167）。
"Batch 166 是**人工**普查十道闸才发现闸 4 依赖 cwd、会在「一个文件都没读到」时判定通过。"
"人工普查的性质决定它只发生一次——**下一个人不会重做一遍，而新闸还会照旧引入同样的毛病**。"
"于是本批把这条从纪律变成闸 9 的**方向十**：用 AST 扫全部闸脚本，"
"凡用**裸相对路径**定位被核对文件的（`glob.glob(\"**/*.md\")` 或 `os.path.join(裸相对目录常量, …)`）一律报错。"
"**它同时把纪律 101「换一个判据就重新问一遍它会不会静悄悄什么都查不到」变成常驻检查**——"
"而方向十本身只判形态，不替代那次行为实测（从空目录跑一遍、退出码必须一致）。"
106. **每道闸都必须有反向验证，而「有反验文件」与「它在验这道闸」是两件事**（Batch 168）。
"§4 早就写着「必须做反向验证」，实测十道闸里**三道一道都没有**：闸 1、闸 2、闸 6。"
"普查时差点滑过去的原因很具体：**闸 2 的反验文件叫 `selftest-screenshots-literals.py`——"
"它是闸 10 的**，名字相近到足以让人以为已经覆盖。"
"**所以反验覆盖要按「闸 → 反验脚本」的对应关系逐条列出来，不靠文件名相似度判断。**"
"三道零反验的根因也各不相同，且都不是疏忽：闸 1 **内联在 `build-site.sh` 的 heredoc 里**——"
"内联形态根本没有可注入的判据文件，**零反验是形态决定的**；闸 6 **ref 写死 `origin/main`**——"
"注入测试要先建临时 ref，而脚本压根不认环境变量，**连注入的前提都不具备**；闸 2 只是没人写。"
"补法是按根因各修各的：抽出为独立脚本 / ref 改为 `BEEFTV_REF` 可覆盖 / 直接补用例。"
"**顺带把 `INLINE_GATE_SLACK` 从 1 改成 0**——内联闸从此不能再加，"
"因为**内联形态既无法反验，又会把工具失败当成通过**（本批在闸 1 里当场验到了后者）。"
107. **反验的锚点必须锚「事实」，不能锚「某一份文件此刻长什么样」**（Batch 168，规则 100 的第三例，代价最大的一次）。
"`selftest-meta.sh` 报出**一条作废**，指向用例 26——**方向九的核心用例**，"
"专门用来保证「覆盖度表不会悄悄落后于现实」。"
"根因是它的锚点誊抄了 A 类闸 9 行的**整行文本**（`…（8 个方向） | 闸 9 `verify-meta.py`（9 个方向） |`），"
"而 **Batch 162 把它改成 9 个方向、Batch 167 又改成 10 个**——**两次正常编辑，两次静默失配**。"
"**这里的严重性全在「作废」的形态上**：失配的用例**既不算通过也不算失败**，"
"整轮照报「失败 0」，而它失效的那两个批次里，**其他 31 条全绿**。"
"换句话说：**一次真正的守卫失效，在账面上长得和一片正常没有任何区别。**"
"修法：锚点从「誊抄某行文本」改成「**按结构定位**」——"
"找 `**A 类 …` 小节标题 → 取其下连续表格行 → 追加。**表的措辞怎么改都不失配，而真把表删了仍会 assert 失败。**"
"**作废的用例不算通过也不等于被抓住，它是最容易骗过人的一种绿灯**——"
"所以作废数必须出现在汇总里、并且让整体判失败（Batch 157 已定，本批是这条纪律第二次派上用场）。"
108. **登记类判据必须双向：「该有的没登记」和「登记了不存在的」是两个方向**（Batch 169）。
"Batch 168 建的「闸 → 反验对应关系」表建完就**没人管**——而**建表的人和用表的人都不会因此得到提醒**。"
"方向十一把它变成常驻守卫，四条不变式里有**三条是双向的**：漏认领的驱动要报、"
"认领了不存在的反验要报、闸编号集合要与实际闸门数完全相同（**多一个少一个都报**）。"
"反验也成对：用例 **33**（删一行 → 漏认领）与用例 **34**（改成不存在的文件名）互为反面。"
"**只做其中一半，那张表可以既不漏行、又整张都在认领不存在的文件，看上去完全自洽——而它一文不值。**"
"**所以判据里凡出现「集合比对」，先问一句：反过来的那条路走不走得通？** 单边判据的绿灯不说明任何事。"
109. **分类判据要锚「谁引用了谁」这类可观测事实，不要锚命名约定**（Batch 169）。
"本批要把 `scripts/` 下 68 个 `selftest-*` 分成「**10 个入口 + 58 个注入夹具**」，"
"最自然的写法是按**文件名里有没有 `-fix-`**——可那是**约定不是事实**："
"谁取名不照约定，判据就静悄悄失效（纪律 101 的形态，只是这次发生在文件名上）。"
"改用事实判定：**剥掉注释与文档字符串后，没有任何其它 `selftest-*` 引用它的那个，就是入口。**"
"**先按约定写一遍、再用事实写一遍，两者的差就是判据的脆弱处**——本批实测差得很远："
"纯文本匹配只认出 **8 个**（`selftest-meta.sh` 出现在另一份脚本的**注释**里，"
"是方向十「注释会骗过文本判据」的原地重演），用 AST 剥掉注释与文档字符串后**正好 10 个**，"
"且 58 个夹具**全部**被正确识别为夹具。"
"**如实说明边界**：shell 侧剥注释是行级近似（`#` 之后一律截断，字符串里含 `#` 时会多剥一点），"
"实测不影响结果；**若将来出现「只在一行 shell 注释里被引用」的夹具，它会被误判成入口**，"
"而本闸会报一条**可修的错**——**这是可接受的失败方向：误报会逼人修，而漏报不会说话。**"
110. **注释不是界面入口——判据扫「代码里出现的写法」时，注释必须先剥掉**（Batch 170）。
"闸 7 的 URL 写出点扫描原先是「`?X=` 出现在**任何位置**就算有界面入口，连注释里提到的也算」——"
"判据选这一档的理由写着「宁可漏报、闸门变弱，也不误报」。"
"**可把注释当写出点只会让闸门变弱**（多认一个不存在的生产者 → 少报一个真缺口），"
"**它换不来任何安全**。后果具体：`fixture`（读 14 次）与 `agent` 在源码注释里各有一句 "
"`?fixture=` / `?agent=`，于是两者永远脱零写、**闸门从不跟踪它们**，"
"而脚本里还专门写了一段坦白「这两个我不管」——**判据缺陷的自供，却没人当成待办**。"
"改成引号感知的剥注释（**不碰字符串里的 `//`，如 `\"https://…\"`**）后，两者归位、进入看守。"
"**跨行块注释刻意不跟踪，因为做不到**：写出点扫描吃的是 `git grep -h` 的拼接文本，"
"**`-h` 丢掉文件名**，没有文件边界就无法维护注释状态。"
"**这一条不是理论风险**：本批第一版探针正是在这里翻车——某处字符串里的 `/*` 让状态机误进块注释模式，"
"**后面几万行被整段清空**，于是它报告 `tab` 参数「代码内零写出点」，"
"而 `assets/index.tsx` 里明明有两个按钮在 `navigate(\"/assets?tab=history\")`。"
"**那个错误结论差一点就写进手册。**"
"**所以两条规矩**：**跨行状态一律不做**（做不到就明说，别装作做了）；"
"**判据与探针都要带自检**——本批那道「剥注释前后行数必须相等」当场抓到一个 off-by-one"
"（`git grep` 输出带尾随换行），**没有它，这个 bug 会让闸门在某天静悄悄失效**。"
111. **声明处的数要么可复现、要么明写「无法复现」，不许留着一个复现不出来的数**（Batch 170）。
"手册写「全库扫描下来，共有 **10** 个查询参数只有读取、没有任何写入点」。"
"实测两种口径分别是 **7**（把注释当代码）与 **9**（只看代码）——**10 复现不出来**。"
"查历史想定位它是哪个版本留下的，**仓是浅克隆、取不到**——按纪律只能说「无法定位」，"
"**不能编一个听起来合理的原因**。"
"**这种数比没有更坏**：它长得像结论，读者据此判断「有多少东西进不去」，"
"**却没有任何机制会告诉它过期**（闸 3 核的是端点数、闸 9 核的是元数据数，**都不核它**）。"
"改法两条：给这个数一个**定义**（什么算「读」、什么算「写」、**注释算不算**），"
"再让**出这个数的判据自己**在每次构建时现场重数、手册对不上就构建失败。"
"**定义与数一起被守着**，否则下一次改口径时没人知道该改哪一边。"
"**为什么交给同一个判据而不是另一个闸**：放到别的闸去比，就得让它再跑一遍扫描，"
"或者去读某个「上次的结果」——**那正是誊抄副本**（规则 100）。"
112. **用「会变的量」当论据之前，先想清楚谁来看着它**（Batch 171，纪律 111 的续集）。
"手册里那两句「**第二大门户**（源码 2023 行，仅次于画布工作区）」与"
"「**源码量第三大的界面页**（渠道设置 738 行 + RunningHub 设置 357 行）」——"
"**行数在这里不是数据，是论据**：它被用来证明「这个页面重要、值得写一章」。"
"实测 `create-workspace.md` 那句**两处都过期了**：2023 → **2790**（差 767 行），"
"而「仅次于画布工作区」也已被 `projects`（5192 行）超过，**它其实已落到第三**。"
"另外 4 个行数（tasks 1221 / skills 1133 / 渠道 738 / RunningHub 357）**分毫不差**——"
"**这恰恰是最坏的情形：一组数里大部分是对的，于是没人去查不对的那几个。**"
"**根因不是粗心，是这类论据天然无人看守**：行数没有定义、没有出处、没有判据，"
"**它长得像一句客观描述**，读者会拿它当结论。"
"修法两条，缺一不可："
"  ① **把论据从散文里抽出来**，落进 `20-reference.md` 的「上游源码行数快照」表，"
"**并写明口径**（目录＝其下 `.ts`/`.tsx` 行数之和、文件＝自身、对照 `origin/main`）；"
"  ② **立闸 11 现场重数**，对不上就构建失败——**上游一改这里就会红**，"
"那时该做的是**更新快照表或删掉那句话里的论据**，**不是放宽判据**（放宽等于把这次发现再埋一次）。"
"**顺带把结论改弱**：那句现在写「**体量第三大**」而不是「第二大门户」——"
"因为**上游把一个 3000 行的文件拆成三个 1000 行的，数会变而页面并没有变小**，"
"**行数只能当量级参考，不能当重要性结论**。这条边界也写进了脚本 docstring 与表头说明。"
113. **同一个量有两套取值时，手册必须两套都写——只写一套等于对多数读者说错**（Batch 172）。
"顺着纪律 112 普查「用会变的量当论据」的句子，量到 60 处候选。"
"版本号那一类**是干净的**（手册主体写 v1.6.16，与 `origin/main` 的 `VERSION` 一致，旧版本号都在变更说明里）；"
"「数上游实体」那一类**覆盖很薄**——「最多 5 个」「同时排队或运行」「200 条」「8 种」"
"「11 个白名单」「每批 30」**全部无人看守**。顺着其中最被反复引用的一条回源，撞出本批最大的发现。"
"**①`backend/internal/platform/runtime_policy.go` 里有两套策略**，而切换判据只有一行："
"`RuntimePolicy()` 里 `if s.localMode { return selfUseRuntimePolicy() }`，"
"且 `NewLocal(...)` 正是以 `localMode=true` 构造的——"
"**也就是说本手册的读者绝大多数走的是 `selfUseRuntimePolicy()`，不是 `DefaultRuntimePolicy()`。**"
"**②两处对本地用户说错了，且都会真影响行为**："
"  · 「同时排队或运行的任务最多 **5** 个」——本地是 `maxRuntimeConcurrency` = **999**"
"    （那句报错是用 `fmt.Sprintf(…, policy.Task.ActiveTaskLimit)` 渲染的，**5 只是默认那套的值**），"
"    所以本地根本撞不到；"
"  · 「素材归档默认 **30 天**后自动彻底清除」——本地 `RecycleBinRetentionDays = 0`，"
"    而清理 worker `if retentionDays <= 0 { return }`，**于是归档素材永远不会被自动清**，磁盘只增不减。"
"**③手册原有的框架把这件事框歪了**：`storage-quota.md` 写的是"
"「不是手册错了，是你这个部署改了策略」——**本地模式不是「改了策略」，而是另一套内置策略**，"
"而且它是本手册读者的**主要场景**，不是边缘配置。"
"**④修法**：正文 5 处补上部署模式条件（`generate-images.md` 2 处、`storage-quota.md` 的新 danger 块、"
"`undo-history-versions.md` 1 处、`90-troubleshooting.md` 1 处——**排障页那条最有用："
"看到这句报错就说明你连的不是本地部署**）；另立**闸 12** 现场核**两套取值**。"
"**⑤闸 12 的反验刻意把「只改本地那一列」单列成两条用例**（另加一条「本地列被抄成与默认列相同」）："
"**如果它只核默认那一列，本地模式那一半就等于没看守，而那恰恰是本手册读者的主要场景。**"
"**一个判据要核两件事时，反验必须能证明「两件都核了」，而不是只证明「其中一件核了」。**"
114. **条件句必须写清「读者站在哪一边」，否则它等于没说**（Batch 173，纪律 113 的续集）。
"手册多处写「这一整块由 `xxxEnabled` 特性开关控制，**开关关掉时会怎样**」——"
"**却从不说默认是哪一边**。实测 7 个开关里 **6 个默认开**，唯一默认关的只有 `FrontendModelsEnabled`。"
"更要紧的是：**它们一个都改不了**——服务端只注册了 `GET /features`，"
"写入方法 `UpdateFeatureAvailability` 在 handler/cmd 层**零调用**（闸 7 早已守着这一点）。"
"于是「（需开启 `pluginCenterEnabled` 特性）」这种措辞会让人**去找一个根本不存在的开关**。"
"**条件句本身没错，错的是它把判断的责任推给了读者**，而读者没有那份源码。"
"修法是**把「你属于哪一边」写进正文**，并且**明确说「你也改不动它」**——"
"这样「关掉会怎样」才真的是纯条件句，而不是一个待办事项。"
"另立**闸 13** 把 7 个默认值登记成表、现场核对。"
"**布尔判据有个特有的隐蔽失效**：「解析不出来」若被当成 `false`，**就永远不会报错**。"
"本批还真的栽了一次——我自己写的表把唯一默认关的那格写成 `**false**`（带 markdown 强调），"
"闸门当场报「表解析不了 = 整轮未能核对」。**机器可读的格子就该是机器精确的值**，"
"强调要放到别的列去；**这条被钉成反验用例 3**，免得下次又被判据逼着改表。"
115. **「不报错、只是不渲染」的损坏，判据得专门为它写一条**（Batch 174）。
"闸 8 盯的是「表格单元格里多切出一列」，可它**完全看不见另一类损坏**："
"GFM 要求**表头与分隔行紧挨着**，一旦中间被空行或引用块隔开，"
"**整块会被当成普通段落原样显示——不报错、不截断，表格就是消失了**。"
"原判据只比「同一块内各行的列数」，而畸形表在它眼里是「一个 1 行的块」，列数自然一致。"
"**实测量出来非常干净**：全库 143 个 `|` 块里，「单行且不是分隔行」的**只有 2 个，"
"而两个都是真损坏**——一处是 `20-reference.md` 的 `/dev/folders` 那一行被空行隔在路由表之外"
"（**读者看到的是一行悬空的表格文字**），另一处是**本批自己写坏的**："
"给小节加说明时把引用块插到了表头与 `|---|` 之间。"
"**所以判据写成「块只有一行且那行不是分隔行即报」**——零误报，且两类真损坏都命中。"
"**这一类的教训比判据本身更值钱**：它不产生任何错误信号，"
"构建照样成功、闸门照样全绿，**只有读的人才看得见，而读者不会去核对渲染结果**。"
116. **「上游走了」和「手册错了」不能共用同一个红灯**（Batch 175）。
    "此前 8 道读源码的闸各自把 ref 写死成**浮动的 `origin/main`**，而正文声明「适用 v1.6.16」。"
    "上游从 v1.6.16 走到 v1.6.22（**27 个提交、223 个文件有差异**）之后两边静悄悄地分家："
    "实测 2 道闸结论不一致——`web/src/pages/canvas` 行数 17009→17122，"
    "以及「选择镜头模板」文案（`canvas-director-template-modal.tsx` 在 v1.6.22 **已被整个删除**，"
    "`createDirectorShot` 改成硬编码 `\"empty\"`、`DIRECTOR_TEMPLATES` 变成零引用）。"
    "**而这 2 条在 v1.6.16 上都是绿的**——手册没写错，是上游走了。"
    "**危险不在于红灯本身，而在于红灯只有一种修法**：人会去改正文，"
    "把照 v1.6.16 写的内容改成 v1.6.22 的样子，**手册从此不对应任何真实版本**。"
    "两件事的修法**正好相反**——前者该升版并重做增量对账，后者才是改正文。"
    "修法是**把取证基线收敛成唯一真值**（`20-reference.md` 的「取证基线」小节声明版本+提交），"
    "闸门按它取对象；**同时禁止任何闸门再写死浮动 ref**——"
    "因为**声明对了而脚本没读它，等于没声明**。"
    "闸 14 方向四只看**会被执行的代码**（剥注释与 docstring），"
    "否则闸门脚本里那些「这里以前是 origin/main」的历史说明会让它永远红，"
    "**而一条永远红的判据等于没有判据**。"
117. **刚写完的判据自己就可能有两个洞，只有反验能当场发现**（Batch 175，闸 14 上线首跑）。
    "闸 14 的剥注释函数连续犯两个错，两个都被反验用例 5/6 当场抓住："
    "①**把字符串字面量当 docstring 剥掉**——`REF = \"origin/main\"` 里的字面量被当成说明文字清空，"
    "**判据把自己的论据一起删了**，于是对真实的浮动 ref 完全无感（用例 5 漏报）；"
    "②**照搬闸 7 处理 TypeScript 的那套，只认 `//` 与 `/* */`，漏了 Python 的 `#`**——"
    "而本仓全是 Python，于是「只是注释里提到 origin/main」被误判成违规（用例 6 误伤）。"
    "修法①要分清 docstring 与字面量（**只有行首开头的三引号串才是 docstring**），"
    "修法②在补 `#` 分支的同时发现第三个更隐蔽的问题："
    "**边解析边丢弃的扫描器，产出坐标必须跟着产出缓冲走**——"
    "docstring 区间原先记的是 `src` 的下标，而 `out` 因丢弃注释早已错位，"
    "回填时删错了位置，把真正的字面量保住了、把别处删了。**判据看起来在工作，其实没有。**"
    "**教训**：判据写完先跑反验，**别先跑真实数据**——真实数据全绿时，"
    "一个「什么都能通过」的判据和一个正确的判据看起来一模一样。"

119. **豁免表是最容易变成免死金牌的地方，而它的检查最容易放错位置**（Batch 176，闸 15 反验用例 2）。
    "判据本来有一条规矩：每条豁免都要复核它点名的上游句子是否还在。"
    "**可它被写在了「手册没覆盖」分支里**——于是给一条**手册本来就写了**的文案"
    "加一个理由失配的豁免时，判据会先命中「已覆盖」而 continue，"
    "**失配检查一次都不会跑**。而那恰恰是豁免表最可能被滥用的形态："
    "「手册已经写了，我再豁免一下没关系吧」。"
    "修法是**把豁免复核提到循环之外、对整张表无条件执行**。"
    "**更一般的教训：任何「附加检查」都要问一句——它在什么条件下不会运行？**"
    "**挂在主流程分支里的检查，等于在那个分支上不存在。**"
    "另外「手册多写而上游没有的」**刻意不报**：那是内容准确性问题，不是漏写；"
    "**一个闸只管一件事，写清它不管什么，比多抓几条更有用**。"
