# 发布 TDCanvas 用户手册站点（一键脚本 + 手动命令）

把本目录的 Markdown 手册构建为**纯静态网站**，`dist` 目录整体拷贝到任意
Web 服务器（nginx / 对象存储静态托管 / GitHub Pages）即可发布，
无需任何服务器端程序。

## 一键构建（推荐）

```bash
cd docs/user-manual/tdcanvas-canvas
./build-site.sh
```

| 步骤 | 内容 | 说明 |
|---|---|---|
| 1/6 | 环境检查 | node ≥ 18、npm 可用、站点配置与首页内容存在 |
| 2/6 | 依赖安装 | `node_modules/vitepress` 缺失时自动 `npm install`（已装则跳过并打印 vitepress 版本） |
| 3/6 | 内容清单 + **门禁** | 先统计 Markdown 页数与截图数（`find` 排除 AUDIT/PROGRESS/TEST_MEDIA_ASSETS/SOURCE_OBSERVATIONS，注意**未排除 PUBLISH.md 自己**，故此数比实际发布页数多 1），数量异常直接报错；随后依次跑**二十四道门禁 + 一道门禁自检**，见下文「构建时的门禁」 |
| 4/6 | 清理旧产物 | 删除 `.vitepress/dist` 与 `.vitepress/cache`，保证产物干净 |
| 5/6 | 构建 | `npx vitepress build`（client + server 双端打包、页面渲染） |
| 6/6 | 产物校验 | 校验 dist 页面数、截图数（与源截图逐一比对）、总体积、是否有未改写的 `.md` 残留链接、**侧边栏完整性**（每个已发布页面都必须出现在 `config.mjs` 侧边栏中，否则报 warn） |

**可选参数**：`./build-site.sh --preview` —— 构建完成后自动启动本地预览服务
`http://localhost:4173`（Ctrl+C 结束）。

## ⚠️ 发布前注意

`screenshots/` 中的部分截图含**测试素材**（AI 生成的人物图/视频帧）。对外公开发布前，
请确认这些素材可公开，或将 `dist` 中的对应图片替换/脱敏。

## 本地预览

```bash
./build-site.sh --preview                                # 方式一：脚本内置
python3 -m http.server 4173 -d .vitepress/dist           # 方式二：任意静态服务器指向 dist
```

> **不要用 `file://` 直接打开 `dist/index.html`**：产物里的资源路径是绝对路径
> （`/assets/...`），在 `file://` 下会指向文件系统根目录，样式与脚本全部加载
> 失败。必须走 HTTP。
>
> **`python3 -m http.server` 不提供站点的 404 页**：VitePress 生成的
> `dist/404.html`（带侧边栏与导航）只会被「把 404 映射到它」的主机送出
> （GitHub Pages、Netlify 原生如此；nginx 需显式配置
> `error_page 404 /404.html;`）。简易服务器对未知路径只返回自己的裸报错，
> 读者落上去没有任何出口——**这是本地预览的已知限制，不是构建缺陷**，
> 但部署时务必确认目标主机配好了 404 映射。

## 发布到任意 Web 服务器

```bash
rsync -av --delete .vitepress/dist/ user@server:/var/www/html/manual/
```

- 站点为纯静态、资源哈希文件名、完全自包含（离线可用），可放 nginx、
  对象存储静态托管、GitHub Pages 等任意环境。
- 部署在**子路径**（如 `https://host/manual/`）时，先修改 `.vitepress/config.mjs`
  的 `base: '/'` 为 `base: '/manual/'`，再重新执行 `./build-site.sh`。

## 站点包含什么

- 侧边栏四组导航 + 右侧「本页目录」+ **中文全文搜索**（`⌘K`，本地索引，无外部服务）。
- 站点只输出面向用户的页面（README 为首页）；`config.mjs` 的 `srcExclude` 排除了 5 个文件：`AUDIT.md`、`PROGRESS.md`、`TEST_MEDIA_ASSETS.md`、`SOURCE_OBSERVATIONS.md`、**`PUBLISH.md`（本文件）**，都不会发布。另 `task-inventory.yml` 是 YAML 不是 Markdown，**本就不进 VitePress**，并非靠 `srcExclude` 排除——两种机制不要混为一谈。
- 站点结构与标题、侧边栏、搜索文案均在 `.vitepress/config.mjs` 配置
  （含 `rewrites: README.md → 站点首页`）。

## 内容更新流程

### ★ 第一条判据：失败要「响」，静默的缺陷不会自己浮上来（M148 归总）

**本项目最贵的缺陷不是报错的那类，而是「本该失败、却安静地通过」的那类。**

M148 把散落各处的同类案例归总成一条。**它们形态不同，根因完全相同：
失败时返回「无异常」而不是「有异常」**，于是没有任何信号逼你去查。

| 案例 | 形态 | 后果 |
|---|---|---|
| **门禁假通过**（M41 / M140） | 锚点门禁两次判「有效」，而那个 id 根本不存在 | 坏链接被当成**已验证的结论**写进手册 |
| **未跟踪文件被静默跳过**（M33–M40） | `git commit -- <pathspec>` 只提交**已跟踪**路径的工作区内容 | **连续八个批次的新增文件从未入库**，已发布站点整批渲染成坏图 |
| **键匹配静默跳过**（M147） | 映射表用中文弯引号、正文用 ASCII 直引号，那一条不匹配 | 脚本打印 15 个标题、**看着正常，实际漏了一条** |
| **只替换第一处**（M133 段内记的同族案例） | `sed` / `replace(..., 1)` / 非贪婪正则**只改第一处** | 其余几处仍是错的，**而输出显示「已改」**——同一段的注入函数只替换了第一处「实测」，理直气壮地报错 |
| **选择器按旧知识写**（M75） | antd 版本不同，类名不同，查询返回 **0 个** | 而「0 个」正是本项目最常用的否定判据，**分不清是元素不存在还是选择器写错了** |

**通用对策（三条，不是「下次小心」）**：

1. **把静默变成响的**——写完/改完**回读确认**，不假定「命令执行了就等于生效」。
   本项目的老话叫「替换后必须回读」，M147 又验证了一次。
2. **零匹配必须报错**——断言「预期命中的全部命中」，有任何一条没中就**拒绝写盘**、
   退出码非 0。**「没找到」绝不能等同于「不用找了」。**
3. **阴性读数先怀疑判据**——读到 0 / 空 / 全部有效时，先问「我的量具有没有问题」，
   再问「产品是不是这样」。M75 那次连踩三 wrong 才靠 dump DOM 定位到类名，
   **而 0 个的结果长得和「确实没有」一模一样**。

> **为什么这条排在所有流程之前**：上面每一个案例，**当时都是绿的**——
> 构建通过、门禁全绿、脚本输出正常。**绿色的检查只能证明「它检查的那些东西没问题」，
> 不能证明「它该检查的东西都检查了」。**

### ★ 判据出错时，先定位「错在哪一步」（M156 归类）

本项目有 **58 个批次**栽在「自己的判据有问题」上——**这是最大的一类错误**。

★ **但它们不是同一个根因。** M156 原本想把散落的案例归总成一条纪律，
**写到一半自己否掉了**：把 60 个案例硬塞进一个根因，会让人以为
「归总了就不用分别处理」——**而这正是本手册反复反对的做法**。

**真实的结构是四种错，差别在于「错在哪一步」**：

| 错在哪一步 | 形态 | 本项目最常见的样子 | 大约次数 |
|---|---|---|---|
| **① 建映射时** | 用表层特征代替语义 | 把**注释里的文件名**当成代码依赖（M151）；把**词频多少**当成批次性质（M155，M137 被判反） | 约 18 |
| **② 定范围时** | 我列的集合当成全部 | 用 **4 个临时关键词**宣布「零命中」（M140，M152 才发现该问「覆盖全了吗」）；只扫正文却以为账本也在内（M153） | 约 19 |
| **③ 读结果时** | 字面相等当成语义相等 | 映射表写中文弯引号、正文用 ASCII 直引号，那一条**静默跳过**（M147） | 约 13 |
| **④ 下结论时** | **0 / 空 当成「没有问题」** | 门禁判「全部有效」而那个 id 根本不存在（M41/M140）；选择器写错返回 0 个当成「元素不存在」（M75） | **约 60** |

**④ 远多于其余三类**——本项目最贵的错误是「**读到否定结果，就当成了肯定结论**」。

> ⚠️ **这张表自己的读法边界（别学它犯错）**：「大约次数」是**按特征关键词计数**得来的
> （如「假通过」「零命中」各出现多少次），**不是穷举**。
> **它本身就属于第二类错误——我列的关键词集合不等于全集**，
> M151 刚为此栽过（把注释里的文件名当依赖）。
> 所以**「④ 最多」这个相对结论可信（量级差得远），绝对数字只是量级参考**。
> 拿它当线索去查可以，**当统计结论引用不行**。

> **用法**：读数不对劲时，**按这张表从 ① 查到 ④**，别一上来就怀疑产品。
> 每一类的对策不同：① 换成可靠特征或人工核实；② 先问「范围覆盖全了吗」；
> ③ 比较前先归一化（M147 的三条对策）；④ **零匹配必须报错**，
> 缺 PyYAML 这类环境跳过可以留，**但措辞必须是「未执行」而不是「通过」**。

1. 修改对应 md，或替换 `screenshots/` 下同名截图（文件名与 manifest 中的 task_id 保持稳定）；
2. 运行 `./build-site.sh`，确认 6 步全绿（第 6 步的截图数比对会自动发现漏图/坏链）；
3. 新增或改名页面时：同步 `.vitepress/config.mjs` 的 `sidebar`、`task-inventory.yml` 的 `manual_pages`，并运行审计脚本；
4. 重新发布 dist（rsync 整体覆盖即可，页面为哈希文件名，无缓存残留问题）。

### ★ 写锚点链接的两条纪律（M139 / M140 实测）

**纪律一：锚点不要按标题字面手写。** 要么**从产物 HTML 里把真实 `id` 抄出来**
（`grep -o 'id="[^"]*"' .vitepress/dist/<页>.html`），要么指向一个确定存在的标题。
M139 修一处悬空锚点时栽了：标题是「悬浮工具条：每个节点类型都不一样」，
**全角冒号「：」会被 VitePress 的 slugify 折成连字符**，真实 id 是
`悬浮工具条-每个节点类型都不一样`——按字面手写少了那个连字符。
**全角标点分两类**：有兼容分解的（`：，；（）？！…` 等，NFKD 后变 ASCII 标点）
**会折成连字符**；没有兼容分解的（`。「」、《》、—·`）**原样留在 id 里**。
两种都实测过，别凭印象——`：` 折、`。` 不折、`「」` 不折。中文里最常踩的是 `：` 与 `（）`。
**（M140 自己就在这里栽了一次**：初稿凭印象写「中文标点只有『、。「」』例外」，
实测发现漏了 `《》—·`，还把 `。` 误排除在外。**凭印象写标点表 = 手写锚点的同一个错误**，
都必须用 `slugify()` 实跑。）

**纪律二：门禁的「假通过」比「报错」更危险，要防的是前者。** M140 实测：
`check-anchors.py` 曾把 bash 代码块里的 `# 注释` 当成真标题（不识别代码围栏），
于是指向那行的链接被判「有效」、exit=0 放行，**而产物里根本没有那个 id**。
**报错会逼你去查，假通过会让你把一个坏链接当成已验证的结论写进手册。**
所以每改一次判据，先问「它现在会不会假通过」，并用阳性对照实测，**不要只看退出码**。
自查办法：临时往正文塞一条**故意指向不存在标题**的链接，确认门禁会红。

> **为什么这条纪律要单列**：`PUBLISH.md` 自身被 `srcExclude` 排除、不进产物，
> 所以**源码层假通过时，只有产物侧的 `check-render.py` 能兜住**——
> 但被排除的页面永远到不了产物侧，**两层都漏**。根因只能在源码层修，不能指望下游兜。

### ★ 批量改文档：键匹配失败是静默的（M147 实测）

**用脚本批量改正文时，「没匹配上」不会报错、不会少打行数、读起来一切正常。**

M145 写了个脚本给 15 条排障条目补「相关任务页」出口。脚本跑完打印了 15 个标题，
**看着完全正常——实际漏了一条**：映射表里那条写的是中文弯引号 `“视频”`，
而正文标题用的是 **ASCII 直引号 `0x22`**（`上传的"视频"节点黑屏无法播放`），
字符串不相等，那一条被静默跳过。**直到 M147 回头逐条清点才发现。**

- **为什么危险**：批量改动的产物是「少改了几条」，而少改的那几条**看上去是对的**
  （文件能读、能构建、门禁全绿）。**没有报错、没有告警、没有任何异常信号。**
- **对策（三条一起用）**：
  1. **匹配前先归一化**——把 `“ ” 「 」 ‘ ’ — –` 统一成 ASCII，把连续空白压成一个空格再比；
  2. **断言映射表全部命中**——跑完检查「映射表里没有一条是零匹配的」，
     **有就拒绝写盘、退出码非 0**；
  3. **改完逐项验归属与计数**——新增内容挂在了正确的标题下吗？条目数对吗？
     （M145 的 2 处错位就是靠这个抓出来的，已固化成 `check-section-ownership.py`）

> **这与 M145 那条纪律是同一件事的两面**：那里是「位置错了门禁照样全绿」，
> 这里是「**根本没想到要改它、而工具也不告诉你**」。**两者都是「静默」**——
> 而静默的缺陷不会自己浮上来，**只能靠主动清点**。

## 手册验收（审计）流程

- 机械审计：`python3 .agents/skills/web-studio-user-manual/scripts/audit_manual.py docs/user-manual/tdcanvas-canvas --phase gate-a`（内容完成后）与 `--phase final`（发布前；要求任务全部 `verified` 或 `excluded`）。校验点：截图↔manifest 双向一致、sha256 一致、本地链接可达、标题层级、占位文本、core/flagship 任务必须有登记截图。
- 内容审计：按 `AUDIT.md` 记录的 Gate B 方法在真实浏览器逐任务回走（标签逐字核对、提交类动作止于按钮态验证），结论与修复记录进 `AUDIT.md`。
- 手册内容的事实源：真实运行界面。UI 标签变化后以浏览器 DOM 为准修正文档，不以记忆或旧文档为准。

### 构建时的门禁：二十四道 + 一道自检

`./build-site.sh` 步骤 3 会依次跑**二十四道门禁、再跑门禁自检**，然后才进入构建；步骤 6 回填统计并校验产物死链。**这些门禁源于实测暴露的真实缺陷，不是形式检查**：

| 门禁 | 拦什么 | 由来 |
|---|---|---|
| `check-anchors.py` | 交叉引用锚点落空。**两次都是「假通过」而非报错**——报错会逼你去查，假通过会让你把坏链接当成已验证的结论 | M31 实测 4 处锚点全空；M41 查出 `slugify` 复刻**漏了 NFKD**，236 个标题里错判 29 个。**M140 查出第二次假通过**：`collect_ids` 逐行匹配标题、**不识别代码围栏**，把 bash 代码块里的 `# 注释` 当成真标题收进 id 集合，手册现存 4 处这样的"假标题"。实测阳性对照：按脚本算法算出的 slug 写进链接后，本门禁报「全部有效」exit=0 **放行**，而产物里那行是 `<span>` 着色代码、**没有这个 id** |
| `check-structure.py` | 孤儿任务页、索引/侧边栏漏条、**孤儿截图** | M42 实测孤儿页可无声混入产物；M89 实测孤儿图在七道门禁下全部通过 |
| `check-ratings.py` | 任务评级在账本/索引/首页三处不一致 | M58 实测账本与下游漂移 |

### ★ 改自检用例前必读：注入有效性判据（M193 新立）

`selftest-gates.py` 里每条用例都做同一件事：**故意制造一处故障，断言对应门禁以正确的理由拦下它**。
这套东西有个自指的软肋——**它自己坏了的时候，看起来和正常一模一样**。

M193 实测的经过：把不可逆按钮白名单从四项扩到六项之后，两条用例仍在按**旧的四项字面量**
做 `text.replace(...)`。锚点早没了，`replace` 成了**空操作**：

- 一条属「期望门禁拦下」：门禁放行，自检报「**门禁漏网**」——**把人引去改一道根本没坏的闸**；
- 一条属「期望门禁放过」：门禁放行，自检报「**通过**」——**它被架空了，却和正常一模一样**。

所以自检现在在跑门禁**之前**先算一次手册树的内容摘要，注入没改动任何文件时
**根本不跑门禁**，单独报「**注入无效**」。这两种失败的处置完全相反，必须分开。

> **两条纪律**（都来自这次的实际经过，不是推演）：
> **一、注入的锚点要从被测系统现算，不要手写字面量。** 现算的锚点追不上真实状态就会静默失效；
> **二、一条「无论怎么改都会通过」的对照，不是对照。** 我一度造了个所谓阳性对照去改一段
> 判据根本不看散文，结果自然通过——**什么都没证明**。造完对照要先问：判据真的看得见这一处吗？

追加请改用：

把要追加的行**先写进一个临时文件**（用 `write` 工具或编辑器落盘，**不要用 heredoc**，见下），再重定向进去：

```bash

python3 scripts/append-audit.py AUDIT.md < /tmp/audit-rows.txt
```

⚠️ **不要用 `<<'EOF'` heredoc 传中文**（本段此前正是那么写的，M142 已订正）。这是本项目**已确证的写入事故源**：heredoc 会把**末行的中文截断**，写进去的是「对的」变成残缺——M130 用它写 commit message 时亲历过，同一手法的文件用 `write` 工具落盘则完好无损。**判据是写入路径，不是内容**：同一批内容，走 `write` 的完好，走 heredoc 的中招。**中文一律先用 `write` 工具落盘成文件，再从文件重定向进来。**

它做三件事：逐行**自动补齐**收尾竖线并打印提示；校验「追加的表格行必须接在旧表格行后面」，**否则拒绝写入**（不造孤立块）；写盘前复用 `check-tables.py` 的判据整体复查，**不通过就回滚、文件保持原样**。

### ★ 第八条：绝对坐标与像素数分三类（M160 新增）

前七条治的是「读数不可信」。第八条治的是**「读数可信，但它不是常量」**——两者症状完全不同：前七条里你拿到的是错的数，第八条里你拿到的是**当时对的、换个环境就废的**数。**M107（画布缩放）、M159（窗口宽度）各栽一次，M160 是第三次**，所以这次把它写成一条常设判据。

| 类 | 判据 | 能不能写进正文 |
|---|---|---|
| **设计常量** | 源码写死、换视口换缩放**逐位不变** | 可以写，但要连**测试环境**一起写（如「100% 缩放下 240×160」） |
| **相对关系** | 两个都在动的对象之间的距离 | **只写关系，不写数字**（「一常驻一跟节点」） |
| **一次性读数** | 坐标或距离**依赖当时的位置/窗口/缩放** | **不能单独写**；必须标注环境，或直接删掉 |

**分这一类不能靠感觉，要靠第二次读数**——`scripts/probe-absolute-coords.js`（M160 建立）在**两个视口**下量同一批元素，输出逐项 `delta`，**只测一个视口得不出「会不会动」**：单一读数永远看起来稳定。

三条已经付出代价的教训：

1. **源码引用必须落到具体组件，且确认是同一个东西**（M160 查实 R30）。上一轮把画布顶栏记成 56px，源码引用写的是 `h-14`——**那个类名确实存在，但在 `app-top-nav.tsx`，是「工作区」层顶栏**；画布页的是 `canvas-top-bar.tsx` 的 `h-16` = 64px。`git log` 确认 `h-16` 从首提交起没改过，**所以不是版本漂移，是当初就取错了证据**。**「源码里找得到」不等于「就是这个东西的」。**
2. **订正一个数时，要连它的推导链一起验**（M160 查实 R32）。排障页「预防：留出 50px」是从顶栏高度推出来的，顶栏高度错了，**这个数就跟着错，而且错得很整**——50 → 168，差三倍多。**只验结论那个数，会把一个错的数改成另一个错的数。**
3. **量元素位置要先确认量的是哪个元素**（M160）。手册记的「剪刀在 `x=32`」——**按钮本身是 `x=24`，32 是它里面 16px 图标的左边缘**（24 + (32−16)/2）。差的不是 8px，是**量错了对象**。

### 表格行的格子数必须与表头一致（M184）

渲染器**会丢弃表格行里超出表头列数的那些格子，连同里面的内容一起丢**——
源文件里每一行都还在，坏掉的只是产物，而其余门禁一律报 ok。

**最常见的成因是「把两行拼成了一行」**：相邻两行各以竖线结尾又以竖线开头，
中间就成了两个相连的竖线，渲染出三个空格子。M183 就这么在 `AUDIT.md` 里造出一行 21 格、
而表头只有 4 列的记录。

`check-tables.py` 现在的口径分三档：

| 情况 | 判断 | 处理 |
|---|---|---|
| 行格子数 **多于** 表头，**发布页** | 内容会被丢弃，读者看得见 | **一律报错**，指名「第 N 行 M 格、表头 K 列」 |
| 行格子数 **多于** 表头，**内部账本** | 读者看不到（`srcExclude` 排除），且 `AUDIT.md` 早有 M65 在册的历史欠账 | **按基线卡住**：不增长就只点名记账，**增长即报错** |
| 行格子数 **少于** 表头 | CommonMark 里合法（缺格渲染成空），不丢内容 | **不报错**，只统计并打印 |

**基线刻意用计数而不是行号**：这四份内部文件天天在追加，行号会漂，计数不会。
有人顺手修掉一处，计数下降是好事；门禁只在**增长**时报错。
行内反斜杠转义过的竖线（`\|`）不算分隔符，本检查不会误报。

**追加表格行一律走 `scripts/append-audit.py`**——这不是建议是必经步骤。
M65 到 M71 连续四批因为手写漏掉收尾竖线把大表劈开；M183 又因为绕过它把四行拼成一行。

### 订正要分「结论」和「描述」两类（M183）

`check-retractions.py` 里的每一条订正都必须带一个 `kind` 字段，取值只有两个：

| kind | 判据 | 举例 |
|---|---|---|
| `conclusion` | **照着原说法做，会不会做错事**——会：找错入口、以为能做不能做、以为状态会自己恢复、归因归错 | 「有一个可点的『移除插件』按钮」（R34） |
| `wording` | **不会**——结论与行动都不受影响，受影响的只是数字、措辞、标签 | 「命中区 43×43」（R23）、「不在注册表里，剩下的只有一个类型名和一句文案」（R39） |

### 界面元素可发现性探针（M129 建立）

```bash
source ~/.nvm/nvm.sh
node scripts/probe-discoverability.js [画布URL]
# 默认不碰共享 profile；要用共享的显式指定：
TD_PROBE_PROFILE=/tmp/m93-profile node scripts/probe-discoverability.js
```

回答一个问题：**手册里写的某个按钮名，读者在界面上能不能找到？** 它对左侧 Dock 与节点工具条逐个读**四样东西**——`aria-label`、`title`、按钮里的可见文字、悬停浮层——并给每行一个「认得出吗」。

**它的存在理由不是省事，是止损**：M125–M128 连续四批都在这上面栽过跟头，而且**每次栽的方式不同**，所以脚本把判据连同「为什么」一起写进了文件头（M129 立 4 条，M132 补到 7 条）：

1. **DOM 里有文字 ≠ 读者看得见**。Agent 面板 7 个按钮里确实有「对话」「历史」这些文字节点，但尺寸全是 **0×0**——`opacity: 1`、`visibility: visible`、祖先链一切正常，**却占不了任何地方**。只判 `textContent` 会得出完全相反的结论。脚本一律读 `getBoundingClientRect()`。
2. **原生 `title` 提示用 JS 读不到**（浏览器渲染，不是 DOM 元素）。判「有没有提示」= `title` 非空 **OR** 自定义浮层非空。
3. **读持久化数据必须写死 key 且先 parse**。`getAllKeys()[0]` 取到的是 `asset_store`；**`canvas_store` 的值是 JSON 字符串**，不 parse 就全是 `undefined`。**这三个坑的共同点是失败时返回「空」而不是报错**——空读数长得像「产品没这个功能」。脚本在这三处一律**显式抛错**。
4. **「元素存在且有几何」≠「用户看得见」**。已知**四种**「不」：`opacity:0`（M117）、`0×0`（M127）、`visibility:hidden`，以及 **M229 新增的「落在视口外」**——**前三种都会在 `getBoundingClientRect()` 或计算样式上留痕，第四种不会**：Agent 面板收起时 `aside` 的 rect 是 `(1280, 0, 440, 900)`，宽高都是正的、`opacity:1`、`visibility:visible`，**只有一条线索是 `left` 恰好等于视口宽度**，而 `scrollWidth == clientWidth`（没有横向滚动条）意味着它够不着。★ **所以凡是报「整页有几个 X」，必须同时报「落在视口内有几个」**；只报前者的读数正常得没人会怀疑它。详见 `SOURCE_OBSERVATIONS.md` F39，配套探针 `scripts/probe-viewport-buttons.js`。
5. **★ 悬停提示不能按 class 名找**（M132 第 63 次否证，代价最大的一条）。同一个左侧区域里**并存两种浮层实现**：Dock 用自研浮层（类名 `pointer-events-none absolute left-[calc(100%+8px)]`，**不含 tooltip / tip 任何字样**），视图控制与顶栏用 antd 的 `div.ant-tooltip`。**按类名找只抓得到后者**——曾据此把 Dock 全部按钮误读成「悬停无任何提示」，而截图上浮层明明写着「清空画布」。**正确判据是「悬停前后全页可见文本取差集」**，不依赖任何类名。
6. **★ 自己造的数据会被自己过滤掉**（M132）。判「有没有提示」时写了 `新文本.filter(t => t !== aria)`，把「浮层文字与 `aria-label` 相同」这个**最常见的合法情况**整个删光，8 个有浮层的按钮全被判成「无提示」。**过滤证据前先问：这条证据是不是恰恰因为「与已知值相同」才有意义？**
7. **★ 阳性对照要证明「指针真的落在目标上」，而且别把自己的对照截断**（M132 第一版）。`:hover` 链在 `length > 8` 时 `break`，而链正好 8 层，**按钮永远落在截断线之外**。且**判「指针命中」要用几何（链末端元素的 `getBoundingClientRect()`），不能用 aria**——首版拿 aria 名字匹配，把 3 个**无 aria** 的按钮全误报成「没悬停到」。**「我的判据有洞」和「产品有问题」要分开查，前者更常见。**

**它自己也被同一条判据咬过一次**（M129 第一版）：表格里把「有没有提示」写成 `Boolean(r.title || r.悬停浮层 || '(无)')`，那个占位符 `'(无)'` 是**非空字符串、truthy**，于是每行都判「能」——**而末行的汇总却正确列出了 9 个认不出的**，两行自相矛盾。**这与 M125–M128 反复栽的「把『没有』编码成 truthy 哨兵」是同一类错**，故已修并在代码里留了注释。

**它同样不是门禁**：只出读数，判定仍要人来读。M129 首轮跑出来的结果与 M125–M128 的手工读数**逐项吻合**（当时记的是「Dock 认不出 9 个、工具条 13 个全有字且悬停浮层与 `aria-label` 逐字相同」），构成阳性对照。

> ⚠️ **但那个「Dock 认不出 9 个」后来被 M132 整组否证了。** 根因就是上面第 5 条——**量具的毛病，不是产品的毛病**。M132 重写探针后首轮输出与手工读数再次逐项吻合，**这次吻合的是「Dock 8 个按钮悬停提示一个都不缺」**。**同一个脚本、同一份手册，先后「吻合」过两个互相矛盾的结论**——这说明**吻合本身不能证明对错，判据才是**。

### 节点缩放手柄可见性探针（M228 建立）

```bash
source ~/.nvm/nvm.sh
node scripts/probe-resize-handles.js [http://localhost:3000] [/tmp/m228-handles-profile]
```

回答一个手册写错了、**而机器一眼就能验**的问题：**节点四角的缩放手柄，读者到底看不看得见。**

`edit-nodes.md` 原写「选中节点，四角出现圆形缩放手柄」。实测**四角没有任何可见像素**——
源码 `canvas-node.tsx:1091` 的 `ResizeHandle` 是 `absolute z-50 size-7` 加负偏移，
**没有背景、没有边框、没有阴影**，连 `border-radius` 都是 `0px`。**它只是一块透明的命中区。**

它量四件事，每一件都对应一条可数断言：

1. **手柄的 DOM 事实**——数量、盒模型、以及 `background` / `border` / `box-shadow` /
   `border-radius` 四个计算样式。**「DOM 里数得出 4 个」与「读者看得见 4 个」是两件事**，
   而手册说的恰恰是后者。
2. **框边圆点作为阳性对照**——源码 `ConnectionHandleDot` 内层是 `size-3 rounded-full border-2`，
   **带 2px 描边**。**它读不出亮斑，整个像素判据就是坏的，不是产品的问题。**
3. **截图像素读数**——手柄四角窗口 vs 边框中点对照窗口，各报最大亮度与亮像素数。
4. **缩放六档**（`input[type=range]` 5..500 逐档设值）下的命中区屏幕尺寸，
   实测正好 `28 × 缩放%`。

⚠️ **它用一次性 profile，且只建不删**（建一张新画布 + 一个文本节点），
所以不需要还原，也不会碰到共享 profile 的数据。

⚠️ **三条坑写在探针文件头，这里点两条**：

- **`page.evaluate` 的代码跑在页面上下文里，拿不到 Node 侧的模块作用域。**
  第一版在里面直接调 `round()`，报 `ReferenceError: round is not defined`。
- **读数恒定不变，先怀疑事件没送到。** 第二版把鼠标放在画布正中滚滚轮，
  **5 次读数全是 100%**——**那 5 次滚轮落在节点正中被节点吃掉了，不是产品不能缩放**
  （零结果先怀疑判据）。改用缩放滑杆才拿到真读数；
  而滑杆是 **React 受控输入，直接 `el.value = 25` 不会触发 `onChange`**，
  必须走 `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set`
  再派发 `input` / `change`。

★ **本批订正**：**R80 / R81**（正文两处把手柄说成可见的圆形手柄）、
**R82**（清单里一条假否定声明——声称画面里没有的生成面板就在图上）、
**R83 / R84 / R85 / R86**（清单四处）。
★ **一条读数只证明一件事**：**「框上有 4 个 28px 命中区」只证明命中区存在，
「四角零可见像素 + 端口圆点有 2px 描边」才是不可见的证据，两条都要报。**

### 视口内元素计数探针（M229 建立）

```bash
source ~/.nvm/nvm.sh
node scripts/probe-viewport-buttons.js [http://localhost:3000] [/tmp/m229-viewport-profile]
```

回答的是纪律表第 4 条升级后的那个问题：**一条路由上，用户真的点得到的按钮有几个。**

它把三条路由各量两遍（**默认态**与**点开 Agent 面板之后**），**两个读数一起报**：

- `predicate-visible`——**老判据**：`getBoundingClientRect()` 有宽高，且
  `visibility` / `display` / `opacity` 都没把它藏起来；
- `in-viewport`——**新判据**：逐个比 rect 与 `window.innerWidth`。

★ **差值本身就是结论**：实测收起态下两者相差 **11**——那 11 个按钮
**不是「隐藏」，是「在视口外」**（`aside` 的 rect 是 `(1280,0,440,900)`，
而视口宽 1280，`scrollWidth == clientWidth` 所以也够不着）。

⚠️ **三条坑写在探针文件头，这里点最反直觉的一条**：**别按标签名取元素。**
第一版用 `document.querySelector('aside')` 取 Agent 面板，
在 `/config` 页报出 `[150,207,260,140]`——**那是配置页自己的 `<aside>`（左栏 260px 宽）**。
**一把报错的尺子会把人教错**，所以现在按「里面有没有它自己的开关」认。

⚠️ **收尾把面板收回初始态，代码写在 `finally` 里**（M224 F31 立的规矩）。
它只用一次性 profile、不点任何删除类按钮、不改任何画布数据。

★ **本批订正**：**R87**（「整页 17 个可见按钮」是有状态的数）、
**R88**（清单把别的状态的读数记在这张图上）、**R89**（M57 那次订正漏了 `step` 字段）。
## 运维常见问题

| 症状 | 原因与处理 |
|---|---|
| `npm install` 慢或失败 | 可换镜像：`npm install --registry=https://registry.npmmirror.com`；依赖装好后构建不再访问网络 |
| 发布后子路径 404 / 资源 404 | 未改 `base`：`config.mjs` 设 `base: '/子路径/'` 后重新构建 |
| dist 截图数与源不一致 | 某截图未被任何 md 引用会被丢弃；脚本第 6 步会 warn，补正文引用即可 |
| 站点搜不到新内容 | 搜索索引在构建时生成，确认已重新 `build`；索引只含 `srcExclude` 之外的页面 |
| 4173 端口被占用 | `python3 -m http.server <其他端口> -d .vitepress/dist` 换端口预览 |
