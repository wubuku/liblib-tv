## 4. 节点体系

- 类型：文本/图片/视频/音频/组/ComfyUI 工作流（双击空白菜单逐字）；Config/Aitudou 为遗留未注册类型。[运行时+静态]

  - **2026-10-02 M119 升级为运行时实证，并订正这条自身的两处措辞 + 补上一条会误导读者的例外**。
    - **措辞订正一：「缩放限制」实为「节点尺寸限制」**——同一条里并列的「缩放」容易被读成**画布**缩放，而画布缩放范围是 5%–500%（M108 已实测），两者不是一回事。
    - **措辞订正二：220×160–1600×1200 只适用于「手动拖手柄」**，**上传时算出来的尺寸可以突破**（见下）。
    - **两个数字都精确坐实（k=1 已先证）**：k=1 的依据是两条独立读数——新节点 DOM 尺寸 `520×300` 恰等于 `NODE_DEFAULT_SIZE` 的文本常量、下限实测 `220×160` 恰等于 `CANVAS_NODE_RESIZE_LIMITS` 的世界常量。往右下猛拖 → **精确停在 220×160**（两次独立测得）；把节点左上角挪到视口上方、用**右下角手柄**往右下猛拖 → **精确停在 1600×1200**。
    - ★ **尺寸不走网格吸附、位置走**：下限 220 不是 16 的倍数（`CANVAS_GRID_STEP=16`），实测**就是 220 而不是 224**——而节点位置确实吸附（M108）。所以「网格吸附」只管位置。
    - **文本节点不锁比例**（与手册第 122 行一致）：只横拖即可把宽高比从 1.516 改成 1.649。
    - ★ **上传路径会破坏原图比例，且下限优先于比例**（`project.tsx:165-172` 的 `fitMaterialPreviewSize`，调用点 `:1566` 传 `fitMaterialPreviewSize(w, h, 640, 640, 220, 160)`）。实测上传 **2000×100（20:1）** 的图 → 节点 **640×160（4:1）**。手算与实测逐字一致：
      ```
      fit(2000,100,640,640) → scale=0.32 → 640×32
      grow  = max(1, 220/640, 160/32)        = 5     → 3200×160
      shrink= min(1, 640/3200, 640/160)      = 0.2   → 640×32
      return { width: max(220, 640)=640, height: max(160, 32)=**160** }   ← 比例在这一步被破坏
      ```
      即：**先等比缩放、再整体放大到满足下限、最后一道 `Math.max(minHeight, …)` 只兜高度不兜宽度**，于是任何足够扁的图上传后都会变成 640×160。
    - ★ **视频上传用的是另一组下限**：`:1586` 调的是 `fitMaterialPreviewSize(w, h, VIDEO_NODE_MAX_WIDTH, VIDEO_NODE_MAX_HEIGHT, **320, 180**)`——**视频节点的最小尺寸是 320×180，图片是 220×160**，而**手动拖手柄时两者又都回到 220×160**（`components/canvas/canvas-node.tsx:263` 的 `clampCanvasNodeResize`）。这解释了「视频节点天然比图片节点大」。
    - **源码另一处未触发的边界（如实记为静态）**：`lib/canvas/canvas-node-size.ts:27-28` 的 `minRatioWidth = min(maxRatioWidth, max(220, 160×ratio))`——比例极扁（ratio < 220/1200 ≈ 0.183）且**锁比例**时，`minRatioWidth` 会取到 `1200×ratio` 而**小于 minWidth 220**，此时锁比例下的宽度下限反而更低。本批**未实测**（需先在工具条自定义面板勾出「锁比例」，且需构造该比例的节点）。
  - **M119 的取证教训**：① 前两版先后用错两种读法——一版怀疑画布缩放 k ≠ 1（实际 k=1，证据是新节点 DOM 尺寸与默认常量逐字相同），一版改用信息面板反而读不到；**最终以「DOM 尺寸 == 源码常量」这条交叉验证定案**。② 第三版用 top-left 手柄往左上放大，放大后节点左上角被拖出视口、手柄随之够不到，于是第 3 段「尺寸不再变化」**是拖拽没生效、不是 clamp 生效**——差点把「够不到」写成「到上限了」。**改用右下角手柄（左上角固定）、并故意把节点左上角放到视口之外**（画布无限，节点可以部分在视口外），才拿到干净的 1600×1200。**教训：「操作没做成」和「结果就是那样」必须区分开，而判据要能区分它们。**

### 10.1 antd v6 的判据备忘（M81 实测，踩坑三次才攒出来）

本应用锁的是 **antd `^6.4.2`**。**不要照抄旧版 antd 的类名**——以下是实测结论，每一条都曾造成"实测没查到"的假阴性：

| 想找什么 | ❌ 常见写法（此处取不到） | ✅ 本应用实际可用 |

| 下拉弹层选项 | — | `.ant-select-item-option`（注意用 `ant-select-content` 点开，别用旧类名） |

## 11. i18n 文案的三种状态（M85/M86 确立的取证纪律）

**「i18n 里有这个键」≠「界面上有这个词」。** M71 曾把 `canvas.aitudou.status.*` 的八个中文状态名当成「界面原文」写进状态表并据此"订正"过手册，M85 证明这八个词**一个都不在界面上**——它们整组零引用。所以引用 i18n 文案时，**必须先判引用关系，再判字面**：

| 状态 | 判据 | 能不能写进「界面原文」 |
|---|---|---|
| ① 活键 | 存在 `t("该键")` 调用点，且该调用点确实会渲染 | **可以**，但要标注是否已实测 |
| ② 条件渲染 | 有调用点，但只在特定状态出现（如 `canvas.node.generating` 只在跑任务时） | **可以，但必须写明触发条件**，并说明未实测 |
| ③ 死文案 | **全仓零引用** | **绝对不可以** |

**一条命令的判据**（排除 locales 自身与测试）：

```
grep -rn "<键名片段>" web/src --include="*.tsx" --include="*.ts" \
  | grep -v "i18n/locales" | grep -v "\.test\." | grep "t("
```

### 11.2 写普查脚本时踩的三个判据坑（都是"探针没打中"）

- **单行内联对象**：`status: { idle: "待配置", queued: "已排队", … },` 这种写法，若按"以 `{` 开头就是多行块"处理，**整棵子树一个键都进不了清单**。第一版就是这么漏的——**连 M85 刚查出的那八个死键，在普查脚本里都"不存在"**。修法：判断内联对象前**先 `rstrip(",")`**，行尾那个逗号会让 `endswith("}")` 判否。
- **动态前缀的尾点**：`t(\`agent.composer.effort.${effort}\`)` 抽出的前缀**自带尾点**。若按"前缀后必须紧跟 `.`"做边界判断，**永远不成立**，动态引用数恒为 0，于是 467 个 `agent` 键被误判成死文案。修法：抽出来就 `rstrip(".")`。
- **三元表达式里的键（影响面最大的一处）**：`t(!connected ? "agent.skillManager.connectToView" : skills.length ? "…noMatch" : "…none")`——**参数不是字符串字面量，是条件表达式**。只匹配 `t("字面量")` 的判据会把它整条漏掉，`agent.skillManager.connectToView` 因此被判成死文案，**而它在 `agent-skills-view.tsx:352` 明明被引用**。修法：从 `t(` 起做**括号配平扫描**，把该调用范围内的**所有字符串字面量**收进来。**这一处若不发现，后果比 M85 更严重**——M85 是"把死的写成活的"，这一处会让人**把一条真实存在的界面文案当成死文案删掉**。

**教训**：判据写完必须**带自检探针**跑一遍——本脚本开头就断言"八个 M85 死键必须出现在清单里"，第一次跑直接打出 `0/8`，当场暴露了第一个坑。**但自检只能覆盖你写进去的那一条**，第三个坑是**换一个用法**（拿它去查 `use-agent.md`）才暴露的。**没有自检的普查脚本，"跑完了"和"查对了"是两件事；而自检探针本身也需要"换个用法再验一次"。**

### 11.3 这条路走不通的方向（别重复）

**"死文案的中文值出现在手册里"不能当门禁。** 把 407 条死键的中文值拿去撞手册正文，命中 102 条——但绝大多数是**假阳性**：「参数」「提示词」「模型」「上传」「删除」「查看」这类常用词本来就在手册里大量出现，且**往往有活键同名**。命中率看着高、可用信息为零。

**可行的做法是把范围收窄到"手册显式声称取自某个 i18n 键"的地方**——按这个口径复查，手册里的 i18n 引用**只有一条是正向断言**（就是 M71 那条，已订正），其余全是**否定式断言**（"这几条文案零引用"），逐条验下来**全部成立**。

## 12. 「源文件正常、产物坏了」缺陷家族（M84 / M90 / M91 / M92）

**这一族已经出现四次，每次都是同一个形态**：markdown 源文件读起来完全正常——
`**` 成对、表格列数对、锚点写法像样——**但渲染之后内容变了或没了**。而当时的
**全部源码层门禁都报 ok**。所以本手册把"打开产物看一眼"变成了**常设门禁**
（`check-render.py`），并把下面这张表当作排查新写法时的检查清单。

| # | 触发写法 | 产物里变成 | 只能在哪判 | 门禁 |
|---|---|---|---|---|
| 1 | 表格单元格里写**未转义的竖线**（哪怕在行内代码段里） | 该行被撑成多格，**多出的格连同内容一起消失** | 源码（列数仍对）+ 产物（列数不一致） | `check-tables` + `check-render` |
| 2 | 加粗定界符**紧邻标点**且另一侧是实义字 | 字面量 `**`，加粗失效 | 源码（flanking 规则） | `check-emphasis` |
| 3 | **同页锚点**少写 slugify 生成的连字符 | 链接点不动 | 源码 | `check-anchors` |
| 4 | 正文里裸写 `{{ }}` | **整段消失**（代码段里成空 `<code>`，正文里少一句） | 只能源侧 | `check-emphasis` |
| 5 | 行内代码段里想用「反斜杠 + 反引号」显示反引号 | 代码段**提前截断**，后半截漏成正文 | 只能产物侧 | `check-render` |

### 三条必须记住的结论

- **源码层判据有形态上限**。第 1 条的判据数列数，而故障恰恰是"列数对但内容丢"；
  第 5 条的判据数反引号奇偶，而嵌套反引号**总数是偶数**——**判据形态上就抓不到**。
  这类只能从产物侧判。**"我加了判据"不等于"这类故障被覆盖了"**。
- **行内代码段内部不处理反斜杠转义**。CommonMark 的反斜杠转义只在代码段**外面**
  生效；想在代码段里显示反引号，要用双反引号包裹或另选符号。
  **注意这条同样约束本手册自己**——`SOURCE_OBSERVATIONS` 与 `PROGRESS` 里描述这些
  写法时，只能用文字说明、不能把危险序列原样写进表格单元格里（`check-tables.py`
  会把表格里真实的反引号奇偶算进去）。
- **表格单元格里的写法与正文不同**。单元格两侧总有空格，flanking 的 2b 豁免自动
  成立，所以第 2 条**在表格里永远不会中招**，在散文里才会。写判据时若按"首尾是
  标点就错"来判，会得到 146 条假阳性（M90 第一版的教训）。

### 排查新写法时的顺序

1. 先想"这个写法在源码层能看出问题吗"——看不出就**必须**进产物侧判据；
2. 判据写完**做阳性对照**：造一个只含该故障的最小产物，确认抓得住；
3. 再扫真实产物，**把"扫描器有效"和"产物干净"分成两句话说**——没做过第 2 步的
   "0 命中"不能当"没问题"的证据。

- **节点悬浮工具条的按钮有「三套字符串」，其中两套对不上（2026-10-02 M125 运行时实证）**。
  `canvas-node-hover-toolbar.tsx:369-384` 的 `ToolbarAction` 把三者分得很清：
  **`title` → Tooltip 浮层**、**`aria-label` → 无障碍标签（实测与 title 逐字相同）**、
  **`label` → 按钮内可见文字**（仅当 `hasText = showLabel && Boolean(label)` 时渲染）。
  **「存资产」按钮的 `title` 是 `common.addToAssets`（加入我的资产），`label` 才是 `canvas.nodeToolbar.saveAsset`（存资产）**——不是巧合，是逐个按钮分别写的。图片节点 13 个按钮逐个实测：**11 个的悬停提示与按钮上印的字不同**，只有「编辑」和「替换图片」相同。**手册此前列的按钮名是 `label`（读者确实看得见），这点是对的**；此前没写的是悬停那一层。[运行时+静态]
  - **「显示文字」开关实测**：往 `localStorage` 写 `{"showLabels": false}` 刷新后，**按钮数恒为 13 不变**（`ids` 未设时走 `defaultImageQuickToolIds`），**但工具条从 1285 缩到 574**（按钮 86 → 44）；删掉 key 复测回到 1285，无残留。**顺带证明 M121 的「13 vs 14」判据是干净的**——那个差异只由 `ids` 造成，与 `showLabels` 无关。[运行时]
  - **探针纪律（新）**：本 profile 下**纯悬停弹不出工具条**，必须**先点选节点**才出现（试过中心、左上内、下缘内三个悬停点，均无）。用 `data-canvas-node-hover-toolbar` 与 `data-canvas-node-toolbar-action` 定位比按坐标找稳。[运行时]
  - **纯图标状态下有几组图标极易混淆**：切图 / 替换图片（都是叠放方框）、裁剪 / 查看大图（剪刀 / 斜箭头放大镜）——**这正是「悬停提示在任何显示设置下都在」这句话的实际价值**。[运行时]

- **左侧 Dock 的按钮：可见文字 0、悬停提示只有 6/15（2026-10-02 M126 运行时实证）**。逐个实测 16 个按钮（x < 300、宽 ≤ 80 的可见 `button`/`[role=button]`）：**`aria-label` 全部存在，但按钮内 span 文本全为空串，`title` 属性只有 1 个**（顶栏 Codex 面板的「Codex 未连接」）。**整条 Dock 上能看见的文字只有两处**：「＋」按钮上方的「新建」小徽标（蓝底白字）、缩放滑杆旁的百分比读数（实测 `91%`）。[运行时]
  - **悬停浮层只有 6 个有**：主页、打开小地图、隐藏连线、网格吸附、重置视图、快捷键。**其余 9 个（打开画布菜单、添加节点、搜索节点、资产、提示词库、历史、上传资产、画布外观、清空画布）悬停也没有任何提示**——界面上**任何地方都不会显示它们叫什么**。这 9 个只能靠位置顺序认（主列自上而下：＋ / 放大镜 / 文件夹 / 星形 / 时钟 / 上传箭头 / 调色板 /（选中时）垃圾桶 / 剪刀）。[运行时]
  - ★★ **「清空画布」与节点工具条的「裁剪」是同一个图标 class**：实测两者 `svg` 的 class 均为 `lucide lucide-scissors size-4`，**逐字相同**，且**选中图片节点时二者同屏出现**（一个在左侧竖排、一个在节点上方横条）。区分只能靠位置与颜色（Dock 那个是红色且点击后有确认弹窗）。[运行时]

  - **「＋ 新建」是三套字符串不一致的第三例**：按钮上方的可见徽标写**「新建」**，而 `aria-label` 是**「添加节点」**——与 M124 的历史版本按钮、M125 的存资产按钮同属一类。手册正文写「＋ 新建」按可见徽标是对的，**但读屏软件念的是「添加节点」**。[运行时+静态]

- **Agent 面板那排按钮的文字同样是 0×0 的隐形文字（2026-10-02 M127 运行时实证）**。面板打开后（实测容器宽 **441**，与手册的 440px 吻合）逐个读按钮：7 个图标按钮里**确实存在**「未连接」「对话」「历史」「技能」「日志」「新对话」这些文字节点，但 `getBoundingClientRect()` **全部返回 0×0**——`opacity: 1`、`visibility: visible`、祖先链全正常，**却占不了任何地方，读者一个都看不见**。唯一例外是面板里那个 78×32 的「**连接**」主行动按钮（文字 28×22，真可见）。[运行时]
  - ★ **这推翻了本批自己的第一版读数**：只按「按钮里有 span 文本」判，会得出「Agent 面板 6/7 有可见文字」这个**完全相反**的结论。**DOM 里有文字 ≠ 读者看得见**——M117 记录过 `opacity: 0` 的同族坑，这次是 `0×0`，更隐蔽（连计算样式都一切正常）。**判据必须读 `getBoundingClientRect()`，不能只判文本存在。** [运行时]
  - **两处字符串对不上**：① 「面板收起」按钮的 `aria-label` 是「**收起 Agent 面板**」，而悬停浮层是「**收起对话**」；② 「连接设置」在未连接时有**三种说法**——`aria-label`「连接设置，当前未连接」、隐形文字节点「未连接」、悬停浮层「连接设置 · 未连接」。[运行时]
  - ★ **真正有区分度的不是「有没有文字」，而是「悬停提示的覆盖率」**：节点工具条 **13/13**、Agent 面板 **7/7**、左侧 Dock **仅 6/16**。**三处主导航按钮全是纯图标（这一点一致），但 Dock 是唯一连悬停都读不出名字的区域**——所以 M126 的结论不但没被推翻，反而被这条对照收窄到了正确的范围：**问题不在「图标没有字」，而在「Dock 有 9 个按钮连提示都没有」。** [运行时]
  - **判据修正之二（与上一条并列，务必一起记）**：**原生 `title` 提示读不到**——它由浏览器渲染、不是 DOM 元素，`[role=tooltip]` 查不到，只能判属性是否存在。**本批第一版把「配置」「快捷键」这类有 `title` 的按钮误归进「悬停无任何提示」**。正确判据是 **`title` 非空 OR 自定义浮层非空**。（M126 的 Dock 结论不受影响：那 16 个按钮的 `title` 实测确为 null。）
