# 回走审计与中文质量

## 1. 审查透镜

回到真实产品逐项检查：

1. **任务成功**：新人是否能不求助完成目标？
2. **入口可发现**：手册起点是否与用户实际看到的一致？
3. **步骤原子性**：每个编号是否只有一个主要动作？
4. **前置条件**：角色、数据、状态和费用条件是否明确？
5. **反馈闭环**：用户如何知道操作成功、进行中或失败？
6. **错误恢复**：高影响失败是否有安全的下一步？
7. **最小信息量**：how-to 是否被无关概念和页面介绍淹没？
8. **独立可读**：通过搜索进入单页时是否仍能执行？
9. **术语一致**：文档是否逐字使用当前 UI 和产品术语？
10. **证据新鲜度**：步骤、截图、locator 和网络行为是否来自同一目标版本？

## 2. 严重性

- **Blocker**：步骤无法完成、会造成错误副作用、权限/费用风险，或截图与目标不符。
- **Major**：缺关键步骤/前置条件/成功判据，普通用户很可能卡住。
- **Minor**：措辞、裁剪、重复、弱提示等不阻塞完成的问题。

交付前必须清零 Blocker/Major。Minor 修复或由用户明确接受。

## 3. 防幻觉规则

- “点击 **X**”中的 X 必须逐字出现在 DOM 或可访问名称中。
- 字段是否必填来自 label、验证行为或接口契约，不凭星号样式猜测。
- 快捷键必须实际按下并观察结果；未验证就不写。
- 不从按钮名字推断后台行为；用请求/响应和最终状态确认。
- 没有运行证据的内容标为“待验证”，不得混入正式步骤。
- 代码中的未上线 route、feature flag 后分支和测试专用入口不自动写进用户手册。
- 不把一次偶发加载失败写成稳定产品规则；先复测并记录环境。

## 4. 中文成稿规则

- 使用简体中文和全角中文标点。
- 中文与英文/数字之间按项目既有文档风格保留可读空格，如“打开 Web Studio”“等待 10 秒”。
- UI 标签用粗体并保持原文，例如“点击 **开始生成**”，不要自行改成同义词。
- 固定使用同一术语：项目、剧本、场次、分镜格、素材、生成任务等不得混用近义词。
- 标题以用户目标命名：“创建第一个项目”，不写“项目页面介绍”。
- 每个步骤先写动作，再写结果。避免“然后”“接下来”堆叠。
- 提示只放隐藏价值；警告只放真实风险；不要把普通说明全部做成提示框。
- 排障以用户可见症状命名，并给出明确的恢复动作和升级信息。

## 5. `AUDIT.md`

至少记录：

```markdown
# 用户手册回走审计

## 审计基线
- URL / commit：
- 角色：
- viewport / locale：
- 审计时间：

## 结果
| 任务 | 结果 | 级别 | 证据 | 修复 |
|---|---|---|---|---|

## 未覆盖与已接受限制
- ...
```

不要写空泛的“已全部检查”。逐任务记录实际回走结果和剩余限制。
