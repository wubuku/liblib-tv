# LibTV + FrameOS 用户手册

为当前项目的 LibTV 普通画布、`/frameos/*` 画布或其中一个指定子域生成任务导向、证据可追溯、可增量维护的中文用户手册。页面覆盖只是手段；核心目标是让目标用户独立完成高频、重要和高风险操作。最常见输入是用户已登录的 `https://www.frameos.cn/#/canvas/...` 源站画布；没有用户明确授权时，不扩展到登录、账户、计费、删除或生成费用。

将当前 `SKILL.md` 所在目录记为 `<skill-dir>`。所有 `references/` 和 `scripts/` 均从该目录解析；不要假设 Skill 固定安装在 `.agents/`、`.claude/` 或某个绝对路径。

## 0. 权限边界

- Skill 被创建、安装或提及时，不自动启动应用、操作浏览器、截图或写手册。只有用户明确要求创建、更新或审查用户手册时才执行。
- 不修改生产业务代码、测试代码、数据库迁移或 `.env` / `.env.*`。需要配置时只使用当前命令的临时环境变量。
- 不使用生产数据、真实用户隐私数据或共享环境做可变操作。不得触发真实视频/图片生成等高成本 Provider 调用。
- 删除、发布、充值、权限变更、不可逆写入及外部通知始终先取得用户单独许可；截图任务不构成此类许可。
- 保护现有工作区修改。开始前检查父仓及子模块状态，不使用 `stash`、`reset --hard`、`checkout --` 或 `clean`。
- 截图只用于说明，不是功能正确性的证据。每个操作步骤必须先通过 DOM、ARIA 状态、网络请求/响应或安全的只读数据证据验证。

执行前读取仓库根 `AGENTS.md`、`docs/QUALITY.md`、`docs/DEVELOPMENT.md`、`docs/CANVAS_NAVIGATION.md` 及与本次手册范围直接相关的产品文档。FrameOS 任务先读 `docs/research/frameos/README.md`、`BEHAVIORS.md` 和 `PAGE_TOPOLOGY.md`；LibTV 任务先读对应 `docs/research/` 证据。

## 1. 建立计划，但先只做快速扫描

复杂手册任务使用 plan，并只保留一个进行中步骤。第一阶段限于低成本、低副作用的快速扫描：

1. 检查当前分支、工作区状态、可用启动方式、固定 dev 端口 `4317` 和浏览器工具。
2. 扫描当前项目的 `/`、`/frameos/*` 路由、导航、store、主要页面组件、Mock handlers、已有 Playwright 用例和产品文档。
3. 如果用户已提供正在运行的 URL 或浏览器标签页，可只读查看应用壳、一级导航和角色身份；不要进入深层流程或提交表单。
4. 从页面入口而非仅从 URL 枚举候选用户任务。一个任务应表达用户目标，例如“在 FrameOS 画布中创建文本节点并连接”，而不是“打开节点菜单”。
5. 标记证据来源和置信度。代码、测试数量和导航位置只能提供候选优先级，不能代替真实用户频率。

快速扫描阶段不创建 `docs/user-manual/`、不拍摄正式截图、不编写正文。

## 2. 强制执行“高频 / 重要任务确认门”

Agent 不得自行最终决定什么是高频或重要。快速扫描后，先向用户提交精简候选表：

| 候选任务 | 目标角色 | 扫描证据 | 推测频率 | 业务影响/失败代价 | 建议篇幅 | 待确认问题 |
|---|---|---|---|---|---|---|

判断维度：

- **频率**：核心日常 / 常用 / 偶发 / 罕见；
- **影响**：关键 / 高 / 中 / 低；
- **角色**：普通创作者 / 管理员 / 外部协作者等；
- **失败代价**：费用、数据丢失、发布错误、权限风险、长时间等待或无法恢复；
- **文档厚度**：旗舰流程 / 完整 how-to / 简明 how-to / 仅参考。

证据优先级：

1. 用户确认、产品数据、客服/培训反馈；
2. 已批准的产品规划与用户旅程；
3. 真实 UI、导航层级、入口显著性；
4. 路由、代码和测试覆盖；
5. Agent 推断。

向用户明确询问：

- 哪些任务是用户每天或每周必做的？
- 哪些任务做错后代价最高，即使低频也必须重点说明？
- 本手册覆盖哪些角色、权限和设备？
- 有哪些功能不应写入、仍在灰度或即将改版？
- 采用 quick / standard / thorough / exhaustive 哪个深度？

**停止条件**：用户确认候选清单，或明确授权 Agent 按提案自行定级。未通过确认门，不进入正式浏览器探索、截图和成稿。

详细评分、清单结构和文档目录见 [任务优先级与内容结构](references/priority-and-structure.md)。

## 3. 冻结运行环境和安全数据

确认范围后再建立手册工作目录和进度账本。默认输出根为 `docs/user-manual/frameos-canvas/`（FrameOS 专项）或 `docs/user-manual/libtv-canvas/`（LibTV 专项），除非用户指定其他位置。

1. 优先使用用户指定的浏览器/标签页；否则使用当前运行时提供的真实浏览器控制工具；最后才使用项目现有 Playwright。
2. 面向本项目时优先复用用户已登录的源站 URL；需要本地 clone 验证时才启动固定端口 `4317` 的 dev server。若需要自行启动：
   - 主工作区 `main` 可按项目规则使用 `api-server/dev.sh`；
   - 特性 worktree 不得使用 dev profile 或共享 dev 数据库；
   - Mock 前端使用命令级 `VITE_USE_MOCK=true`，不得写 `.env.local`。
3. 使用可复现的种子/演示数据。真实感不等于真实客户数据；必须去除姓名、手机号、Token、密钥、内部 URL 和商业敏感内容。
4. 固定 viewport、locale、时区、主题、缩放、字体和 reduced-motion。默认桌面为 `1280x720`；只有确认覆盖移动端时再增加固定移动视口。
5. 记录登录方式和角色。复用浏览器会话时，不读取或输出 cookie/token；Playwright 优先使用用户批准的 `storageState`。
6. 创建：
   - `task-inventory.yml`：已确认任务、优先级、角色、证据和覆盖状态；
   - `PROGRESS.md`：页面、流程、截图、回走状态和恢复入口；
   - `screenshots/manifest.yml`：每张截图的任务、步骤、路由、视口、定位证据、时间和哈希。
   - `AUDIT.md`：先建立审计基线和空结果表；Gate B 逐任务补充真实回走结论。

浏览器与截图细则见 [真实浏览器与确定性截图](references/browser-and-screenshots.md)。

## 4. 按任务探索真实产品

按确认后的优先级逐个任务完成，不按路由平均用力：

1. 从用户可见入口开始，按正常路径进入目标流程。
2. 记录前置条件、角色、入口、每一步操作、成功标志、取消路径和可恢复错误。
3. UI 标签逐字取自 DOM；优先用 role/name/label 定位。禁止凭记忆补按钮名、字段、快捷键或系统行为。
4. 对关键状态同时验证：
   - DOM 可见性、可操作性和 ARIA 状态；
   - 相关网络请求、状态码和响应形状；
   - 必要时的安全只读后台/数据库证据。
5. 发现 UI 与代码/旧文档冲突时，以当前被测版本的真实运行行为为准，并在审计记录中标注版本和差异。
6. 需要产生数据才能继续时，只操作专用测试数据；在成本或副作用边界前停止并向用户确认。
7. 遇到真实缺陷，不把缺陷伪装成正常步骤。记录为 Blocker/Major/Minor，并询问是绕行记录还是先修产品。

## 5. 截图必须服务于动作

- 先完成 DOM/网络验证，再拍截图；等待数据、字体和布局稳定，最终图不得含 skeleton、无关 toast 或调试工具。
- 概览图保留必要上下文；步骤图聚焦操作区域，避免把整个桌面当作说明图。
- 对“点击/选择/填写”的关键步骤，在实时 DOM 中基于目标元素 bounding box 注入高对比边框和步骤编号，再截图；截图后移除 overlay。
- 每个正式截图都写入 manifest，正文使用描述性 alt。不得使用“A 在左上角”之类文字替代目标标注。
- 同一任务避免为每个细微点击堆图。只在入口、关键决策、重要表单、结果确认和高风险恢复步骤截图。
- 不对截图做改变产品含义的后期编辑；只允许裁剪、遮蔽敏感信息和不改变目标位置的压缩。

可复用 `scripts/highlight-target.js` 注入和移除目标高亮。

## 6. 采用任务导向的中文结构

默认使用以下结构，不按页面清单写成截图目录：

```text
docs/user-manual/
├── README.md
├── 00-quickstart.md
├── 10-tasks/
├── 20-reference.md
├── 30-concepts.md
├── 90-troubleshooting.md
├── task-inventory.yml
├── PROGRESS.md
├── AUDIT.md
└── screenshots/
    └── manifest.yml
```

- **Quickstart / Tutorial**：最短成功路径，只承诺一个可完成结果。
- **How-to**：一页解决一个用户目标；高频/高影响任务步骤、截图、前置条件和恢复路径更完整。
- **Reference**：字段、状态、权限、设置、限制和快捷键，保持简洁准确。
- **Explanation**：解释概念和流程原因，不塞进操作步骤。
- **Troubleshooting**：来自真实探索的症状 → 原因 → 修复 → 仍失败时如何求助。

每个 how-to 至少包含：适用角色、目标、前置条件、入口、原子步骤、成功判据、取消/恢复、相关任务。正文使用产品中的真实中文标签；不要自行翻译或创造术语。FrameOS 与 LibTV 术语、store、路由和截图证据不得互换。

## 7. 两道交付闸门

### Gate A：覆盖率和机械完整性

- 每个“核心日常”任务有完整步骤和关键截图。
- 每个“关键/高影响”任务有前置条件、风险提示、成功判据和恢复路径。
- 每个 UI 标签与当前 DOM 文本一致；每个快捷键已实际执行验证。
- 每个截图文件存在、有描述性 alt、在 manifest 中登记且没有泄露敏感信息。
- 页面链接、标题层级、任务索引和术语一致。
- 运行：

```bash
python3 "<skill-dir>/scripts/audit_manual.py" docs/user-manual/frameos-canvas --phase gate-a
```

### Gate B：真实浏览器回走

依据手册而不是作者记忆，从头重走每条旗舰流程和完整 how-to：

1. 在干净或可复现状态打开文档指定入口；
2. 逐字核对标签和每个原子步骤；
3. 验证预期请求/响应及最终可见状态；
4. 核对截图是否仍对应当前 UI；
5. 将发现记入 `AUDIT.md`，按 Blocker / Major / Minor 分级；
6. 修正文档后重走受影响流程，直到无 Blocker/Major。

回走完成后运行最终机械审计；此时任务状态只能是 `verified` 或带原因的 `excluded`：

```bash
python3 "<skill-dir>/scripts/audit_manual.py" docs/user-manual/frameos-canvas --phase final
```

审查透镜、严重性和中文成稿规范见 [回走审计与中文质量](references/review-and-zh-cn.md)。

## 8. 完成标准

只有同时满足以下条件才报告完成：

- 用户确认的任务范围全部在 inventory 中闭环；
- 高频和高影响任务获得明显高于低频功能的篇幅与验证密度；
- Gate A 通过；
- Gate B 无 Blocker/Major，Minor 已修复或明确接受；
- 最终机械审计通过；
- `PROGRESS.md`、manifest 和 `AUDIT.md` 支持下一位 Agent 增量更新；
- 最终报告列出目标版本/URL、角色、深度、覆盖率、未覆盖项和已知限制。

除非用户另行要求，不因生成手册而修改产品代码、提交 Git、合并或 push。
